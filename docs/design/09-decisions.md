## D1 预定版本的变基规则

**背景**：实体有一个将在 T2 生效的版本 V（完整快照）。之后写入一个生效时间为 T1（T1 < T2）的修改。
若不处理，到了 T2，V 会把这次修改的字段恢复成旧值。

**决策**
1. 写入生效时间为 T 的新版本时，找出该实体所有**生效时间 > T 且尚未被覆盖**的版本，按生效时间升序逐个处理。
   这既包括将来的预定版本，也包括追溯更正时位于 T 与当前之间、已经生效的版本。
2. 每个待处理版本 V 的修改字段集合 F(V) 取自它的 `op_process_item.changed_fields`。
   - 本次修改的字段与 F(V) **无交集**：插入 V 的变基副本 = "新的前一状态 ⊕ V 在 F(V) 上的值"，生效时间与 V 相同，
     `version_no` 更大（相同生效时间下胜出），`action = REBASE`。下一个待处理版本以这个副本作为前一状态。
   - **有交集**：拒绝本次写入（409），错误中列出冲突的版本（生效时间、所属操作）。调用方必须先取消或修改该预定。
3. **墓碑版本**（删除）不参与字段冲突判断：它的变基副本仍然是墓碑，不会因为前面的修改而复活。
4. 变基副本与本次写入属于同一个操作（同一个 `process_seq_id`），同样写入 `op_process_item`。

**理由**：自动保留两边互不相干的修改；真正冲突时交给人判断，不做隐式覆盖。

**放弃的方案**：①不处理（会静默丢失修改）；②有冲突时"后写入者胜"（会静默改变已经确认的预定）；
③限制每个实体只能有一个预定版本（过于严格，价格、费率常有多个排期）。

## D2 撤销操作的冲突检测

**决策**
1. 撤销是一个**新的操作**，`reverts_seq_id` 指向被撤销的操作 P。
2. 冲突判断以**字段**为粒度：对 P 写入的每个实体，若 P 之后（按 `process_seq_id` 顺序）有其他操作修改过 P 所修改的任一字段，
   则拒绝整个撤销（409），列出阻塞的后续操作。调用方可以先撤销这些后续操作（按从新到旧的顺序），再撤销 P。
3. 恢复方式：
   - P 的 `UPDATE`：插入新版本，把 P 修改的字段恢复为 `base_version_no` 时的值（其他字段保持当前值）；
   - P 的 `INSERT`：插入墓碑版本；此时 P 之后对该实体的**任何**修改都视为冲突；
   - P 的 `DELETE`：插入恢复版本，内容为墓碑之前的状态；
   - P 产生的 `REBASE` 版本：与 P 的主版本一起按上述规则恢复。
   - 恢复版本的生效时间与被撤销版本的生效时间相同；若因此需要变基，按 D1 处理（冲突同样拒绝）。
4. P 若有子操作，按相反顺序一并撤销，全部在一个事务内完成；任一冲突则整体拒绝。
5. 撤销一个撤销操作（即"重做"）按同样规则处理，允许。
6. 撤销需要专用权限并必须填写原因。

**理由**：字段粒度的判断既能允许"后续只改了无关字段"的常见情况，又不会覆盖别人的后续修改。

## D3 数据视图范围在取得当前版本之后过滤

**决策**：对时态实体，所有查询（实体查询、计数、SQL 模板中的 `{{Entity}}`）一律先在内层用
`DISTINCT ON` 取得 `asOf` / `knownAt` 条件下的版本，**再在外层**依次应用：墓碑排除 → 数据视图范围 → 查询条件。

**理由**：若范围条件放在内层，一个已经被移出范围的实体会"退回"显示它还在范围内时的旧版本，造成越权或脏读。

**附带要求**：平台生成的 SQL 中，范围条件出现在内层视为缺陷；阶段 4 的测试必须覆盖"移出范围后不可见"。

## D4 操作表本身也只追加

**决策**
1. `op_process`、`op_process_item`、`op_process_result`、`entity_registry` 均只追加，同样受 D5 的触发器保护。
2. 不存在"状态"列的更新：撤销、重做都是新的操作记录。
3. 流程输出需要保存（用于幂等重放）时，写入单独的 `op_process_result` 表，在流程结束时、同一事务内插入：

```sql
CREATE TABLE op_process_result (
    process_seq_id  bigint PRIMARY KEY REFERENCES op_process,
    output          jsonb  NOT NULL          -- 敏感字段遮蔽
);
```

   （`op_process` 在流程开始时插入，那时还没有输出；为了不更新它，输出放在独立的表里。）
4. 带 `Idempotency-Key` 的重复请求：在 `op_process` 中按 `(actor_id, idempotency_key)` 找到原操作，返回其 `op_process_result.output`，不重复执行。

**理由**：操作记录是审计与追溯的依据，它自己不能被改写。

## D5 数据库触发器拒绝时态表的修改和删除

**决策**
1. 提供通用触发器函数 `jabiz_reject_mutation()`；每张时态表和 D4 中的操作类表都创建：
   - 行级 `BEFORE UPDATE OR DELETE` 触发器；
   - 语句级 `BEFORE TRUNCATE` 触发器。
   触发器抛出带固定错误码的异常，平台将其转为 500 并记录为严重错误（这意味着代码中有缺陷）。
2. 唯一的例外是**受控清除流程**（个人信息删除、归档）：该流程在事务内执行 `SET LOCAL jabiz.maintenance_mode = 'purge'`，
   触发器仅在该会话变量为 `purge` 且当前数据库角色属于维护角色时放行；每次清除必须写入清除记录（本身也是一次操作）。
3. 启动自检检查每张时态表上两个触发器都存在。
4. 普通业务数据库账号不授予维护角色。

**理由**：应用层的约定可能被绕过（手写 SQL、运维脚本、将来的新代码）；数据库层兜底，保证"只追加"真正成立。

## D6 时态实体的唯一性用咨询锁加检查实现

**决策**：对声明了 `eb.unique(name, fields...)` 的时态实体，写入时：
1. 在事务内执行 `pg_advisory_xact_lock(key)`，`key` 为 `(实体类型, 约束名, 规范化后的字段值)` 的 64 位哈希。
2. **取锁之后**再查询（必须是取锁后的新语句，才能看到前一个持锁者已提交的数据）：
   是否存在**当前生效版本或尚未生效的预定版本**使用了相同的值（排除实体自身、排除墓碑）。
3. 存在则返回违规 `UNIQUE_VIOLATION`（400，随其他违规一起累积返回）。

**说明**
- 哈希冲突只会导致不相干的写入多等一会儿，不会影响正确性（第 2 步仍然按真实值查询）。
- 把预定版本也纳入检查，是为了防止"某个名字已经预定给别人，现在又被另一个实体占用"，导致到期时出现重复。
- 规范化规则（大小写、首尾空格等）由约束声明决定，默认原样比较。

**放弃的方案**：①在历史表上建唯一索引（历史版本会互相冲突）；②只靠当前快照投影表的唯一索引（MVP 不引入投影表，且无法覆盖预定版本）。

## D7 SQL 模板中的列表参数统一使用 `= ANY(:name)`

**决策**
1. 列表参数在模板中一律写成 `列 = ANY(:name)`（取反用 `列 <> ALL(:name)`），头部声明 `list: true`。
2. 平台按参数的语义类型把列表转换为对应的数组（如 `String[]`、`UUID[]`、`BigDecimal[]`、`Instant[]`）后绑定。
3. 禁止 `IN (:name)` 写法；`platformCheck` 发现后报错。
4. 空列表：`= ANY` 空数组结果为假，`<> ALL` 空数组结果为真，语义符合预期，平台不做特殊处理。

**理由**：一个参数对应一个占位符，渲染后的 SQL 形状固定，可以用 JDBC 预编译做静态校验；也避免列表过长时生成超长 SQL。

## D9 时态模型的实现细则

**背景**：阶段 4 实现时需要确定 D1、D2、D5 没有写明的细节。本条只补充，不取代任何已有决策。
阶段 4 计划确认了第 1、2、4、6–10 条及第 3、5 条的前半；标注【待确认】的内容是实现中发现问题后新增的，需在 PR 评审中确认。

**决策**
1. **版本号与并发**：新版本的 `version_no` = 该实体已有的最大 `version_no + 1`（存在预定版本时 `n + 1` 可能已被占用）。
   调用方提交的 `version` 是"本次生效时间点上生效的版本"的 `version_no`（读取时用同一 `asOf` 即可得到）；
   不一致时 409。并发写入同一实体时都会插入同一个"最大值 + 1"，由 `UNIQUE(entity_id, version_no)` 拦下，409。
2. **`op_process_item.action` 与 `changed_fields`**：
   - 新增 `CANCEL`（取消预定，04 §4.1）：内容为被取消版本之前的状态（没有之前的状态时为墓碑），`base_version_no` 为被取消的版本，
     `changed_fields` 记录被取消版本的字段（撤销取消时据此恢复）。
   - `INSERT`、`DELETE` 的 `changed_fields` 为全部可修改字段（主键和系统字段除外）。
   - `REBASE` 副本的 `changed_fields` 为变基时实际带过去的字段。
3. **变基时一个生效时间点带过去的字段**（D1 第 2 条中的 F(V)）：同一生效时间的版本彼此叠加（更正、变基副本），
   取它们 `changed_fields` 的并集（遇到 `CANCEL` 重新开始）【待确认：属性测试发现，只看胜出版本的 `changed_fields`
   会丢失同一时间点更早版本的修改】，再只保留在该时间点的值与该时间点之前的值**确实不同**的字段【待确认：否则已被撤销的修改
   会继续造成变基冲突，使"先撤销后续操作再撤销 P"无法完成】。
4. **删除与变基**：删除（写墓碑）之后若还有非墓碑版本（例如预定修改），按冲突拒绝（409）；之后的墓碑照常复制为墓碑。
5. **撤销的冲突判断**（补充 D2 第 2 条）：后续操作的 `REBASE` 条目不算修改；后续操作若之后已被撤销，它与撤销它的操作一起抵消，
   不再阻塞（即 D2 所说"先按从新到旧撤销后续操作，再撤销 P"可以成立）【待确认：实现中新增】；撤销的撤销（重做）使被撤销的操作重新计入。
   撤销按实体的默认数据视图定位存储，不施加数据视图范围，要求实体与操作表位于同一存储。
6. **权限码**（默认拒绝，403 `PERMISSION_DENIED`）：`temporal.backdate`（追溯更正）、`temporal.revert`（撤销、重做）、
   `operation.read`（操作详情）。
7. **按时间点读取**：`allowTimeTravel(false)` 同时禁止 `asOf`、`knownAt` 与历史接口（400 `TIME_TRAVEL_NOT_ALLOWED`）。
   历史接口只在实体最新状态（含墓碑）位于数据视图范围内时返回，否则 404。
8. **受控清除**（补充 D5）：维护角色固定名为 `jabiz_maintenance`，由运维创建（迁移脚本不建角色）；触发器拒绝时抛出 SQLSTATE `JZ001`，
   平台转为 `AppendOnlyViolationException`（500，记录 error 日志）。时态表用 `SELECT jabiz_protect_append_only('<表>')` 安装两个触发器。
9. **操作的产生**（阶段 6 之前）：数据视图 `commit` 及现有通用增删改流程只在本批包含时态实体时写 `op_process`；
   已有操作（Reactor Context 中的 `Operation`）时加入该操作（此时不能再给出不同的 `reason`：操作记录不可更新）。
   `op_time` 取 `Clock` 并截断到微秒（与数据库精度一致）。通用流程沿用自己的 `processSeqId` 与流程名，同一流程的多次提交加入同一操作。
   自行开始操作的 `commit` 把输出摘要（实体类型、主键、版本号，不含字段值）写入 `op_process_result`；
   完整输出与遮蔽随阶段 6、7 接入。
10. **数据库字典**：时态表为 `sys_dict_item_version`（平台实体 `SysDictItem`，允许预定，唯一约束 `(dictUrn, itemCode)`）；
    `sys_dict_item` 改为当前项的只读视图，`INSERT` 经 `jabiz_dict_put(...)` 写入**基础数据**（生效时间与记录时间都为 1970-01-01，
    不读取数据库时钟；用于迁移种子），
    已有更晚版本的项拒绝经 SQL 修改。`labels` 使用扩展语义类型 `jabiz.labels`（jsonb）。缓存到下一个预定版本生效时自动过期。

11. **存储与引用**：时态实体不能使用 `physicalTableOverride`（版本、操作条目与撤销都指向实体自己的表，启动时检查）。
    指向时态实体的引用字段以 UUID 保存与比较（写入与查询时转换）。删除前的"仍被引用"检查同时查看引用方的当前版本与预定版本。

**理由**：这些都是 D1–D6 在真实数据上成立所必需的细节；写明以便后续阶段（流程引擎、账本、前端）遵守同一语义。

## D10 SQL 模板中的每个实体都经数据视图渲染

**背景**：阶段 4 之前，模板执行时只给"调用方传入的那个数据视图"的目标实体附加范围，模板中的其他实体渲染为裸表
（时态实体只包装当前版本）。手写 SQL 因此可以通过第二个实体绕过其默认视图的范围与逻辑删除。

**决策**
1. 模板中的每个 `{{Entity}}` 都按一个数据视图渲染：头部 `datasets: {实体: 视图 id}` 指定的视图，未指定的实体用其**默认视图**。
   渲染内容与实体查询相同：范围、逻辑删除排除；时态实体先取当前版本，再在外层依次排除墓碑、施加范围（D3）。
2. 视图必须存在且以该实体为目标；同一模板涉及的视图必须位于同一存储（主库与读库都相同），在启动时检查。
   有读库时模板走读库。行数上限取各视图 `maxQueryBatchSize` 的最小值（**已由 D32 限定为只限浏览的一页**），超时取各视图与 `timeoutMs` 的最小值；
   `timeoutMs` 必须短于各视图的超时。
3. 范围值取自调用方的 `RequestContext`，取不到即拒绝（403 `SCOPE_UNAVAILABLE`），与数据视图 API 相同。
4. `SqlDictionary` 的 `datasetId` 表示其目标实体经该视图读取（相当于 `datasets` 中的一项）；它以系统身份在平台内部执行，
   不经模板 API，不需要声明权限。

**理由**："所有读写都经过数据视图"（03 第 1 节）对手写 SQL 同样成立；否则验收"手写模板无法读到范围外的数据"只对一个实体成立。

**放弃的方案**：只对调用方指定的视图加范围（现状；其他实体会越权）；要求每个模板为全部实体显式指定视图（冗长，且默认视图已经表达了通用访问方式）。

## D11 流程引擎的实现细则

**背景**：阶段 6 实现流程引擎时需要确定 06 与 D4 没有写明的细节。本条只补充，不取代任何已有决策；
D9 第 9 条原本就只描述"阶段 6 之前"的操作产生方式，数据视图 `commit` 的行为不变。

**决策**
1. **每次流程执行都是一个操作**：不论是否涉及时态实体，流程开始时（在它的事务内）写入 `op_process`；子流程同样写一行，
   `parent_seq_id` 指向父流程，`op_time` 相同。输出（JSON）**只在带 `Idempotency-Key` 时**写入 `op_process_result`，即 D4 所说"需要保存（用于幂等重放）时"：
   该表只追加、无法清除，不为重放以外的目的保存可能含字段值的输出。阶段 7 起输出中的秘密为 `null`，`input_summary` 记录遮蔽后的输入【D12】。
2. **权限在调用入口检查**：流程 API 要求调用方具备流程声明的全部权限（403 `PERMISSION_DENIED`；未声明时只有 `dev` 下放行）。
   `ProcessExecutor` 与传输方式无关，不检查权限（定时任务、场景回放以显式的 `RequestContext` 调用它）；子流程不另行检查。
   流程中的 `RunTemplate` 不检查模板自身的权限，数据视图范围照常施加（D10）。
3. **`AFTER_COMMIT` 步骤**：在根流程的事务提交之后按声明顺序执行（子流程的这类步骤推迟到根流程提交后）；
   它们独立于响应运行（保留请求的 Reactor Context），响应不等待，调用方断开也不会取消它们；失败不影响已提交的数据与响应。按步骤的 `RetryPolicy`（默认 3 次，200 ms 起指数退避）在进程内重试，每次尝试追加一行到只追加的
   `op_process_after_commit`（受 D5 触发器保护），用尽后记 error 日志。**不做持久化重试**：需要可靠投递时使用 `PublishEvent`（阶段 9 的 Outbox）。
   `AFTER_COMMIT` 步骤登记的变更不会被提交：记为失败且不重试（重试只会重复外部副作用）。
4. **幂等**：`Idempotency-Key` 须匹配 `[A-Za-z0-9._:-]{1,128}`（否则 400 `INVALID_IDEMPOTENCY_KEY`）。执行前按 `(actor_id, idempotency_key)`
   查找并重放；并发的重复请求在插入 `op_process` 时被唯一约束阻塞，第一个事务提交后得到唯一约束冲突，平台随即重放第一个结果，
   第一个事务回滚时则正常执行——因此同一键只执行一次。同一键用于另一个流程名时 409 `IDEMPOTENCY_KEY_REUSED`。
   重放返回原操作的 `processSeqId`，响应头 `Idempotency-Replayed: true`。
5. **一个流程一个存储**：流程事务开在操作表所在的存储（`jabiz.storage.default-pool-ref`）上；变更经由其他存储的数据视图提交时报错，
   不会悄悄变成第二个事务。变更只能经由以该实体为目标的数据视图提交（缺省为实体的默认视图）。
6. **违规**：所有 `IN_TX` 步骤执行完后若 `violations()` 非空，422 返回全部违规且不提交；某个步骤（例如子流程）抛出 422 时，与此前已累积的违规合并返回。
   `SaveChanges` 在已有违规时拒绝提交。

**理由**：流程是"一次操作"的单位（06 §1），审计与撤销需要每次执行都有记录；输出只在重放需要时保存，避免在不可清除的表里留下未遮蔽的字段值；权限放在入口使执行器可被非 Web 调用方复用；
进程内重试足以覆盖短暂故障，可靠投递留给 Outbox，避免为持久化上下文另建一套机制。

**放弃的方案**：在执行器中检查权限（定时任务与场景回放需要伪造权限）；`AFTER_COMMIT` 失败时让响应失败（数据已提交，会误导调用方重试）；
把重试状态写成可更新的表（违反 D4 的只追加原则）。

## D12 安全：认证、会话、授权与遮蔽

**背景**：阶段 7 接入认证与授权（ROADMAP 阶段 7），需要确定会话方案、RBAC 的载体、登录失败计数的实现和遮蔽范围。
本条补充 D11 第 1 条（`input_summary` 与输出的遮蔽"阶段 7 接入"），并调整 06 §10 中"计算步骤校验密码哈希"的写法（改为阻塞步骤，理由见第 4 条），不取代其他决策。

**决策**
1. **会话用 JWT，不用 Redis 会话**：短期访问令牌（HS256，默认 15 分钟，携带操作人、租户、角色、权限，不存储）+ 刷新令牌
   （随机不透明串，库中只存 SHA-256，默认 8 小时，**每次刷新轮换，只能用一次**；重复使用即吊销整个令牌族）。
   理由：CLAUDE.md 规定 MVP 不引入 Redis；无状态便于多实例。代价：禁用、撤权在下一次刷新时生效（最长为访问令牌有效期）。
   签名密钥来自环境变量 `JABIZ_JWT_SECRET`（至少 32 字节），缺失即启动失败（`dev` 除外）。刷新令牌相关的三张表只插入并受 D5 触发器保护；
   刷新时消费、检查用户、签发下一个令牌在一个事务中；改密码吊销该用户的全部令牌族。
2. **Spring Security 只判断"是谁"**：`/api/**`（登录、刷新、登出除外）必须已认证，否则 401；"能做什么"仍由各入口按元数据声明的权限检查（D11 第 2 条），403。
   例外：通用实体流程写入的实体由输入决定，因此它们在流程内检查该实体默认视图的写权限（任何入口都一样）；其他流程的执行器仍不检查权限。
   撤销（D2）同样是写入：除 `temporal.revert` 外还需要所涉实体默认视图的写权限，且不写回敏感字段的旧值（否则撤销改密码即可恢复旧密码）。
   `RequestContext` 在认证之后由认证结果构造；开发用请求头只在 `dev` 配置下作为另一种认证方式存在，且有访问令牌时不看它们。
3. **RBAC 与菜单用平台自身的时态实体**：`SecUser`、`SecRole`、`SecRolePermission`、`SecUserRole`（可预定）、`SecMenu`、`SecLoginRecord`，
   各有默认数据视图与权限码，经数据视图与流程维护。有效权限 = 当前生效且启用的角色所授予权限的并集；`*` 表示全部权限。菜单项必须声明权限。
4. **登录 = 流程 `SPONSOR_SIGN_IN`**：平台 I/O 步骤加载用户与最新登录记录，**阻塞步骤**比对 BCrypt（CPU 密集且生成盐会读随机源，不能占用事件循环），
   计算步骤检查角色，计算步骤登记登录记录。被拒绝的登录流程正常结束（否则失败计数随回滚消失），登录接口对一切拒绝统一返回 401 `LOGIN_FAILED`。
   用户不存在时也比对假哈希，响应时间不泄露用户名。
5. **锁定**：每条登录记录携带其后生效的 `attemptNo`、`failureCount`、`lockedUntil`；连续 5 次密码错误锁定 15 分钟（可配置），锁定期间一律拒绝且不延长，
   到期后重新计数，成功或管理员解锁（`SEC_USER_UNLOCK`）清零。`(userId, attemptNo)` 声明为唯一约束（D6），并发尝试中基于同一条记录的后来者失败，
   使记录的尝试始终连续，并发猜密码无法绕过计数。
6. **敏感数据**：字段级 `sensitive()`（读接口不返回，数据视图 API 与通用实体流程拒绝写入，列表视图与 SQL 模板不得引用）；流程 record 组件级 `@Sensitive`；
   按属性名遮蔽（敏感字段名、`@Sensitive` 组件名、配置的名称片段）。`op_process.input_summary` 记录遮蔽后的流程输入（`***`，上限 16 KB），
   数据视图 `commit` 只记字段名；`op_process_result.output` 与流程 API 响应中的秘密为 `null`。
7. **首个管理员**由环境变量配置，库中没有用户时于启动时创建（角色 `ADMIN`，权限 `*`）。

**理由**：默认拒绝贯穿始终（无令牌、无权限、无密钥都拒绝）；权限、菜单、登录记录与其他业务数据一样有历史、可追溯；
一切写入仍然只追加（时态表、令牌表），不为安全另开一套例外。

**放弃的方案**：Redis 会话（MVP 不引入 Redis）；在访问令牌中只放用户 ID、每次请求查权限（每个请求一次数据库往返，且仍需缓存失效机制）；
失败登录时让流程失败并另写日志计数（计数不在数据库事务里，多实例不一致）；把失败计数放在用户实体上（每次失败都产生用户的新版本，历史被噪音淹没）。

## D13 业务参数与场景回放的实现细则

**背景**：阶段 8 实现业务参数（04 §9）与场景回放（07 §3）时需要确定两处没有写明的细节：参数值的类型由谁声明、如何在所有写入途径上校验；
回放如何调用流程、如何隔离、快照中哪些值需要规范化。本条只补充，不取代任何已有决策。

**决策**
1. **参数的类型存在行里**：`sys_param_version.value_kind` 用 SQL 模板头 `kind:` 的写法，插入后不可变；值存规范文本。
   只支持规范类型为文本、小数、布尔、时刻的语义类型（`text` `numeric` `monetary` `bool` `temporal`，以及列出允许值的 `code`）。
2. **新增实体级校验 `eb.check(code, EntityCheck)`**（02 §4.1）：在插入与更新的完整候选状态上同步评估，所有写入途径都经过它，违规与其他业务规则一起累积（422）。
   参数"值符合类型"即用它实现，因此数据视图 API 也不能写入不合类型的值。
3. **业务代码读参数只经平台步骤 `LoadParams`**，以业务发生时间为 `asOf`；`ParamService` 返回 `Mono`，只供平台代码使用。
4. **场景回放直接调用 `ProcessExecutor`**（D11 第 2 条），以场景的操作人作为显式 `RequestContext`；输入转换与失败的状态码、违规与流程 API 一致（`ProcessInputs`、`ProblemStatuses`）。
5. **每次回放一个新 schema 与新应用上下文**；主键在回放中由确定性的 UUIDv7 生成器产生。快照中 UUID 与 `processSeqId` 规范化为序号占位，
   **来自可控时钟的时间保留**（它们是确定的，且生效时间等正是要审查的业务行为）——这调整了 07 §3.3 原来"时间戳也规范化"的写法。
6. **缺少快照**：本地首次运行时写入并通过；`CI` 环境下失败（快照必须随变更提交、经过审查）。

**理由**：参数与其他业务数据一样有历史、可预定、可审计，类型错误在写入时就被拒绝，而不是在某个月末的计算中才暴露；
回放与定时任务走同一个执行器，结果与 API 一致；每次从空库开始才能保证"连续运行结果一致"。

**放弃的方案**：①参数类型在代码中声明（管理员无法在运行时新增参数，且与 04 §9 的表结构不一致）；②只在参数流程中校验值（数据视图 API 可绕过）；
③场景回放经 HTTP 调用（违反 D11 第 2 条，且权限需要伪造）；④多次回放共用一个库（唯一约束冲突、快照混入其他回放的数据）。

## D14 账本、Outbox、审计、定时任务的实现细则

**背景**：阶段 9（ROADMAP）要实现复式记账、实体变更事件（Outbox）、审计视图与多实例安全的定时任务。需要确定：
账本的"借贷平衡"跨多个实例（一笔交易的多条分录），不能由单个实体的校验保证；Spring Modulith 是否可用；消费端幂等的做法；
定时任务的声明方式与"只执行一次"的保证。本条只补充，不取代任何已有决策。

**决策**
1. **账本是平台时态实体，交易与分录只经账本流程写入**。新增数据视图策略 `processOnlyWrites()`（03 §2.6）：数据视图 API 的 `commit`
   与通用实体流程拒绝写入（422 `PROCESS_ONLY_DATASET`），`ChangeSet` 可写；以这类视图为默认视图的实体的操作不能撤销（422 `REVERT_NOT_ALLOWED`，
   补充 D2：账本的更正只能是冲正交易）。借贷平衡在写入前由 `LEDGER_POST` 校验，数据库的延迟约束触发器在提交时再检查一次（SQLSTATE `JZ002`）。
   账本单一币种，由配置决定（`Monetary` 在字段上声明币种）。
2. **自行实现 Outbox**：Spring Modulith 的事件发布注册表不支持 R2DBC（只有 JPA、JDBC、MongoDB、Neo4j，且依赖响应式事务下不触发的
   `@TransactionalEventListener`）。事件在发布它的事务中写入 `sys_outbox_event`；投递状态由只追加的消费记录与失败记录推导，不更新任何行（与 D4 同一原则）。
3. **消费者只调用流程；消费标记与消费效果同一事务**：投递时，消费者流程的事务在记录操作之后、第一个步骤之前插入
   `sys_event_consumption(consumer, event_id)`（主键）。失败即随之回滚并按退避重试（至少一次）；并发或重复的投递在主键上等待后失败，
   不产生效果（只处理一次）。为此 `ExecutionOptions` 增加平台内部的 `beforeSteps`（事务内前置工作），不对业务开放。
4. **实体变更事件按实体声明**（`eb.publishChanges()`），所有写入途径都产生，载荷只含字段名不含值；预定版本到期不另发事件。
5. **定时任务是声明**：`JobDefinition`（cron + 流程 + 由计划时刻构造输入），由平台用 Spring 的 `TaskScheduler`（与 `@Scheduled` 同一机制，
   时钟为注入的 `Clock`）注册，不在业务 Bean 上写 `@Scheduled` 方法——任务因此可以启动检查、列出、在场景回放中显式调用
   （这调整了 ROADMAP 阶段 9 要求 5 的字面写法"`@Scheduled` + ShedLock"，经阶段 9 计划确认）。
6. **同一计划时刻只执行一次**：ShedLock（R2DBC 提供者）的集群锁挡住同时运行；流程以幂等键 `job:<名称>:<计划时刻>` 执行（D4/D11），
   锁过期或时钟不一致时第二次执行只重放结果。执行记录写入只追加的 `sys_job_run`。锁的时间是基础设施时间（真实时钟），
   计划时刻与业务时间来自 `Clock`；`jabiz_shedlock` 表由 ShedLock 原地更新，是基础设施表，不受 D5 保护。
7. **审计视图只读操作表**（`audit.read`），只返回名称、标识与版本，不返回字段值；按实体查询覆盖时态实体（普通实体的写入没有操作条目）。

**理由**：借贷平衡、至少一次投递、只执行一次，都落在数据库约束与事务上，而不是靠进程内的约定；一切业务效果仍然只经流程产生、留有操作记录；
新增的表继续只追加。

**放弃的方案**：①用实体级校验保证借贷平衡（它只看一个实例）；②允许数据视图 API 写分录再在提交时检查（错误只能在数据库层以 500 暴露，且绕过科目检查）；
③Outbox 行上加"已投递"状态列并更新（违反只追加）；④消费端用幂等键表 + 另一个事务（消费效果与标记不原子，崩溃时重复处理）；
⑤在业务 Bean 上写 `@Scheduled` + `@SchedulerLock`（任务不可见于元数据、不能在回放中调用，且业务代码直接接触调度）。

## D15 前端：规则一致性、元数据目录、令牌存放、OpenAPI

**背景**：阶段 10（ROADMAP）要让"新增实体与数据视图后不写前端代码即得到列表页和表单页"，并让"同一非法输入，前端提示与后端 `ruleCode` 一致"。
现状有三处缺口：`FieldBuilder.rule(code, kind, params, predicate)` 的导出描述与服务端判断分开写，可能漂移，且 `kind` 不限于前端认识的集合；
前端无从得知有哪些数据视图与流程；流程输入是 Java record，前端拿不到结构。本条只补充 02 §3，不取代任何已有决策。

**决策**
1. **可导出规则是有限集合**：`RANGE` `SCALE` `LENGTH` `PATTERN` `NOT_FUTURE` `REQUIRED`（core `RuleKinds`）；导出其他种类在构建实体时失败
   （需要其他判断时用仅服务端规则）。推荐用 core `Rules` 工厂声明，同一组参数同时产生 `RuleSpec` 与服务端谓词。
   `PATTERN` 只允许 Java 与 JavaScript 读法相同的正则（构建期检查）。
2. **一致性由共享用例证明**：`spec/validation-cases.json` 同时被 core 测试与前端测试执行；core 测试还断言其中的字段元数据就是服务端的导出。
   前端校验逐步复刻服务端的校验路径（转换 → 必填 → 语义类型约束 → 导出规则），只覆盖不需要服务端状态的检查；服务端始终是最终裁决。
3. **元数据目录**：`GET /api/meta/datasets`、`GET /api/meta/processes` 只列出调用方可用的项（默认拒绝，与入口检查同一判断），
   目录只决定导航，不代替各入口的权限检查。流程可标记 `internal()`：只经专用入口或由平台执行，不进目录，权限不变。
   实体导出增加按请求语言的标签与错误文案模板（资源键 `entity.<实体>[.<字段>]`，缺失时回退为名字）。
4. **令牌存放**：访问令牌只在内存；刷新令牌在 `sessionStorage`（关闭标签页即结束；配合 D12 的"刷新即轮换、重用即吊销"）。
   不用 Cookie（D12 已关闭 CSRF 且无会话）。前端不解码令牌，操作人与权限取自 `/api/auth/me`。
5. **OpenAPI**：springdoc（WebFlux，无 UI），文档在 `/api/meta/openapi`（需要认证），启动时生成；仓库保存快照 `frontend/openapi/openapi.json`，
   由后端测试比对、前端据此生成 TS 类型与请求函数（`openapi-typescript` + `openapi-fetch`），CI 检查两者都是最新的。

**理由**：一致性落在"同一份参数、同一份用例"上，而不是两边各写一遍再靠人对照；目录按权限过滤让界面默认只显示能用的东西，同时不削弱服务端检查；
刷新令牌放在 `sessionStorage` 在"刷新页面不掉线"与"暴露面最小"之间取中（XSS 能读内存中的令牌也能读 `sessionStorage`，但令牌短期、轮换且可吊销）。

**放弃的方案**：①在前端手写每个实体的校验（与"不写前端代码"矛盾，且必然漂移）；②把服务端规则编译成 JS（规则是任意 Java 谓词，不可行）；
③刷新令牌放 `localStorage`（跨标签页、长期留存）或 HttpOnly Cookie（需要 CSRF 防护与会话语义，违反 D12 的无状态设计）；
④OpenAPI 公开访问（泄露全部接口结构，违反默认拒绝）；⑤构建时启动后端生成 OpenAPI（前端构建依赖数据库与后端）。

## D16 示范业务、可观测性、一条命令启动与压测

**背景**：阶段 11（ROADMAP）要用平台实现示范业务（订单、库存）、加入指标 / 链路 / 结构化日志与本地观测环境、Docker Compose 一条命令启动、
压测报告。需要确定：库存如何防超卖；遥测何时外发、带哪些标签；一条命令启动时密钥从哪里来；压测用什么工具。本条只补充，不取代任何已有决策。

**决策**
1. **库存与订单只经流程写入**：`StockLevel`、`SalesOrder`、`SalesOrderLine` 的默认视图为 `processOnlyWrites()`（D14 第 1 条的机制）；
   每次库存变化都是库存行在其版本上的更新（D9 第 1 条），并发的下单读到同一版本时只有一个提交成功，另一个 409（或读到新版本后 422 库存不足），
   因此不会超卖；实体级校验 `STOCK_LEVEL_INVALID`（`0 ≤ reserved ≤ onHand`）在所有写入途径上再兜一次底。订单的更正是取消（`ORDER_CANCEL`），
   这些实体的操作不能撤销（D14）。价格变更用时态实体的预定生效（`PRODUCT_REPRICE`），下单按操作时间取价，不需要定时任务。
2. **遥测默认不外发**：OTLP 指标默认关闭，链路与日志只在配置了端点时导出；只推送 OTLP，不开放 `/actuator/prometheus` 等匿名端点。
3. **观测标签只有名字**：平台观测（13 §2）的低基数标签只取流程、版本、数据视图、实体、模板、消费者、任务名与结果，不含主键、操作人、字段值；
   R2DBC span 不记录绑定值。与 10 §6 的遮蔽原则一致。
4. **一条命令启动时的密钥**：compose 的应用容器在未提供 `JABIZ_JWT_SECRET` 与首个管理员密码时于首次启动生成随机值，保存在专用卷中并只打印一次管理员密码；
   仓库中不出现任何密钥（数据库只有本机演示账号）。这只用于本地演示，部署时仍由环境变量注入（D12 第 1、7 条不变）。
5. **压测工具自带**：`:app:loadTest`（`JavaExec`，JDK `HttpClient` + 虚拟线程 + HdrHistogram），经与前端相同的 HTTP API 执行，不引入 k6 / Gatling；
   不进入 `check`。报告写明硬件、数据量与并发，只作相对参考。

**理由**：超卖问题落在数据库的版本唯一约束上，而不是进程内的锁；遥测不应在未经配置时离开进程，也不应成为个人信息的旁路；
"一条命令"与"密钥不入库"可以同时成立；压测工具与业务代码同一语言、同一仓库，任何人都能在没有额外工具的机器上复现。

**放弃的方案**：①库存用 `SELECT … FOR UPDATE` 悲观锁（平台没有这个抽象，且与只追加的版本模型重复）；②开放 Prometheus 抓取端点（匿名暴露指标，违反默认拒绝）；
③在 compose 文件中写固定的签名密钥与管理员密码（密钥入库）；④要求使用者先手工生成 `.env`（不是一条命令）；⑤k6 / Gatling（多一套工具链，且脚本与 Java 类型脱节）。

## D17 公开只读访问

**背景**：要在平台上做面向匿名访客的网站（第一个是应用 culture），而 D12 第 2 条规定 `/api/**` 必须已认证。
需要确定：匿名能读什么、经什么接口读、如何保证未发布的数据与白名单外的字段不会泄露。本条补充 D12 第 2 条（增加一个例外路径），不取代任何决策。

**决策**
1. **公开只读、只经公开模板**：匿名访问只有 `GET/HEAD /api/public/queries/{id}` 与 `GET/HEAD /api/public/files/{id}[/{variant}]`；
   不提供匿名的通用数据视图查询与任何写入。公开模板以头部 `access: public` 声明，代替 `permissions`。
2. **行与列都在数据视图上约束**：公开模板只能读**公开数据视图**（`publicRead(...)`：只读、不可时间旅行、不是默认视图、只允许固定值范围、字段白名单、不含敏感字段）；
   渲染时对公开视图做列投影，模板即使直接写物理列名也读不到白名单以外的列。没有范围的公开视图必须显式声明 `allRows()`。
3. **文件的公开性由引用推导**：文件当且仅当被某个公开视图中可见的行、以白名单中的文件字段引用时才可匿名获取；不设"公开"标记。
   判定可缓存（默认 60 s），业务可在下线时使之失效。
4. **匿名上下文**：公开路径不看 `Authorization` 头，以 `anonymous` 执行；不写操作记录（读取不是操作）。
5. **缓存与限流**：`Cache-Control: public` + `ETag`；按客户端地址的进程内限流（有界），多实例时为近似值。
6. **默认关闭**：`jabiz.public.enabled=false` 时公开路径一律 404；公开视图与模板的检查照常执行。非公开或未知的模板返回 404 而不是 403。
7. **前端契约**：公开模板目录以快照入库，公开前端据此生成类型；OpenAPI 仍需认证（D15 第 5 条不变）。

**实现细则（阶段 13c 计划确认）**
8. 已认证用户也可经 `/api/queries/{id}` 执行公开模板，不需要任何权限（内容本来公开；供后台预览）。
9. 公开模板目录快照默认为 `frontend/openapi/public-queries.json`（`jabizApp.publicQueriesSnapshot`，应用分支指向自己的目录）。
10. 行数上限：公开视图的 `maxQueryBatchSize` 不得超过 `jabiz.public.max-limit`（启动检查），接口也按它截断 `limit`；
    超时按 `min(模板 timeoutMs, 视图超时, jabiz.public.max-timeout)` 执行，模板 `timeoutMs` 超过上限即启动失败。

**理由**：公开的每一行、每一列、每一个查询都能在元数据中找到并在启动时检查，默认拒绝依然成立；范围与投影落在数据视图上，
模板作者的疏忽（忘了 WHERE、写了物理列名）不会造成泄露；文件公开与否跟随数据，没有两处状态需要同步。

**放弃的方案**：①匿名的通用数据视图查询（筛选组合难以审查，行数与字段不受模板声明约束）；②定时导出静态 JSON / 静态页面（更新有延迟，且需要另一套发布与存储机制）；
③在文件上维护"公开"标记（发布、下线、改引用时都要同步，遗漏即泄露或断图）；④公开 OpenAPI（D15 已否决）。

## D18 文件存储

**背景**：应用需要上传图片、PDF、音频。平台没有文件能力；文件常含个人信息（照片中的面孔与 GPS、声音），且必须能按删除权真正删除，
这与时态表"只追加"（D4、D5）的精神冲突。本条补充 D4、D5 的适用范围（它们不适用于文件内容），不取代。

**决策**
1. **`SysFile` 是可删除的普通平台实体**，对象存放在 `FileStore`（第一版为本地目录，S3 兼容存储以后按同一接口加入）。
   上传、删除都是流程操作（有 `op_process` 记录，`input_summary` 不含文件名与内容）；被删除的是内容，审计记录保留。
2. **类型由内容判定**：按魔数判定，只接受策略允许的类型；永不接受 SVG、HTML 等可执行内容；PDF 以附件与 `sandbox` 提供。
3. **图片一律重新编码**：去掉全部元数据（含 GPS）、按方向转正、生成宽度变体；不保留原始字节。解码前检查像素数。
4. **文件策略是声明**（`FilePolicy`：允许的类型、大小、图片处理、上传与读取权限），字段以 `jabiz.file` 引用文件并在写入时检查策略相符。
5. **一致性靠顺序与清扫**：先写对象后插入行，先删行后删对象；孤儿由定时任务清扫（只调用流程，D14）。
6. 图片处理在 `boundedElastic`（虚拟线程）上执行，存储 I/O 非阻塞；`FileStore` 返回 `Mono`/`Flux`，只供平台内部使用。
7. **实现细则（阶段 13b 计划确认）**：引用文件的列不加外键（历史版本可指向已删除的文件）；存储键只由 `fileId` 推导（年月取其 UUIDv7 时间戳），孤儿对象的年龄同样取
   `fileId`（UUIDv7，来自注入的 `Clock`）的时间戳；存储根目录无默认值，注册了策略而未配置即启动失败；`jabiz.file` 的转换在 core
   （`FileKindSupport`），导出中的策略细节由 runtime 补全；业务流程删除文件前先 `SaveChanges.now` 再调用 `FILE_DELETE`；
   引用判定只看数据库中的当前与预定值，不经数据视图范围（14 §2、§4、§6）。

**理由**：删除权要求真正删除；把"谁在何时上传或删除了哪个文件"留在只追加的操作表中，审计不因删除而缺失；
按内容判定类型与重新编码，是防止同源脚本执行与泄露位置信息最直接的办法。

**放弃的方案**：①文件存为 `bytea`（库体积与备份膨胀，且无法流式处理大文件）；②只存外部 URL（依赖第三方、无法保证删除与去元数据）；
③时态的文件表（删除权无法满足）；④信任客户端的 `Content-Type`（可伪装）；⑤保留原图（元数据与 GPS 留存）。

## D19 平台与应用分开：分支、模块、公开前端

**背景**：在平台上开始做具体项目（culture）。平台中的能力应当可被以后的项目复用，项目专有的内容不应混入平台。
另外，CLAUDE.md 第 2 节规定前端用 Ant Design，这适合后台，但不适合面向公众、以视觉为主的网站。本条调整 CLAUDE.md 第 2 节"前端"一行的适用范围（只约束通用后台），不取代任何决策。

**决策**
1. **两类长期分支**：`platform`（承接 `phase-11-baseline`，只含平台与示范应用）与应用分支（`culture` 等，= `platform` + 应用专有目录）。
   合并方向只有 `platform` → 应用；平台需要的改动先在平台工作分支上完成并合入 `platform`。应用分支不修改平台目录，
   由 `.jabiz-app-paths` 与 `tools/check-app-paths.sh` 在 CI 中检查。
2. **一个仓库多个可部署应用**：`backend/` 下的模块自动包含；约定插件 `jabiz.boot-app` 生成可部署 jar（含一个或多个 SPA）；
   每个应用自己的 compose 与 CI 工作流放在应用目录中。
3. **多个 SPA**：按前缀回退与按前缀配置内容安全策略；通用后台可挂在子路径（`/admin/`）。
4. **公开前端不用 Ant Design**：工具链与后台相同，视觉自行设计，数据只来自公开接口；无障碍（WCAG 2.2 AA）与移动端是验收项。
   通用后台仍按 CLAUDE.md 第 2 节与 D15。

**理由**：平台与应用的边界落在目录与合并方向上，由 CI 检查，而不是靠约定；平台能力必须带自己的测试与示范，因此能被下一个应用直接使用；
一个仓库便于应用立即获得平台的修复。

**放弃的方案**：①所有项目在同一分支（项目细节渗入平台）；②应用放在另一个仓库、平台发布为制品（需要制品仓库与版本管理，当前阶段成本过高；以后可以演进到这一步）；
③双向合并（应用内容会回流到平台）；④公开网站也用 Ant Design（体积与视觉都不合适）。

## D20 内容编辑能力：多语言文本、显示字段、实体上的操作、只经流程写入的字段

**背景**：阶段 13d（ROADMAP）要让以内容为主的业务只写声明就得到可用的后台（16）。实现时发现 16 的初稿有几处需要定下来：
①共享校验用例在 core 中执行，而 core 没有任何依赖（不能解析 JSON），多语言文本的语义却写成"由 runtime 提供"；②`Custom` 类型没有报告语义约束的途径；
③设计引用的配置 `jabiz.i18n.locales` 并不存在；④撤销可能绕过只经流程写入的字段；⑤插入时由谁、在哪条路径上给这类字段填值；⑥对没有显示字段的实体调用 `lookup` 如何回答。
本条补充 D14（字段级的只经流程写入）与 D15（新的语义约束进入共享用例），不取代任何决策。

**决策**
1. **多语言文本的语义在 core**：`com.jabiz.entity.i18n` 的 `I18nText`（声明，经 `f.apply(...)` 设置字段类型）与抽象基类 `I18nTextSupport`
   （规范化、校验、运算符、导出）；runtime 的 `I18nTextKindSupport` 继承它，只补上 jsonb 文本的解析并经 `ServiceLoader` 注册。core 的共享用例测试注册一个测试子类。
2. **`CustomKindSupport.validate`**：SPI 增加默认方法（默认无约束），返回 `KindViolation(code, params)`；`EntityValidator` 在转换成功之后调用，
   与其他语义类型约束一样只报第一个。已有实现（`jabiz.labels`、ext-geo）不受影响。
3. **内容语言即平台支持的语言**（core 常量，当前 `zh`、`ja`、`en`，与消息资源同一集合）；不新增 `jabiz.i18n.locales`。
   默认语言仍是 `jabiz.i18n.default-locale`。以后需要内容语言多于界面语言时，再新增决策。
4. **`f.processOnly()` 的写入规则与敏感字段相同、但照常可读**：数据视图 API 与通用实体流程写入它 → 400 `PROCESS_ONLY_FIELD`；
   撤销改过它的操作 → 422 `PROCESS_ONLY_FIELD`；流程的 `ChangeSet` 可以写。
5. **插入时由平台统一填值**：任何途径的插入中缺省该字段时，状态字段取初始状态、范围字段取范围值，否则为空；只在存储写入的插入路径上实现一处。
   必填的 `processOnly` 字段必须是状态字段或（每个可直接写入的视图的）范围字段，启动检查一次性报告。
6. **显示字段与查找**：`eb.display(field)`（`Text` 或 `jabiz.i18n-text`，非敏感）；`lookup`（≤20）/ `labels`（≤200）只读、需要视图读权限、经视图范围（D3），
   关键字转义后绑定；没有声明 `display` 时 400 `DISPLAY_NOT_DECLARED`（默认拒绝，而不是退化为按主键匹配）。
7. **实体上的操作是显示提示**：`actsOn(entity, input[, when])` 只决定按钮出现在哪里、预填哪个输入；`when` 不是权限或规则，服务端照常裁决。启动检查实体、输入组件的类型与 `when` 的字段。
8. **Markdown 只在前端渲染且不允许原始 HTML**（`react-markdown`，不启用 `rehype-raw`，`skipHtml`）；服务端只存文本。

**理由**：语义放在 core，前后端一致性仍由同一份共享用例在最底层证明，runtime 只做它本来就做的 JSON 解析；SPI 的默认方法让新约束成为通用能力，
而不是在 `EntityValidator` 中特判某个 `kindId`；语言集合只有一个来源，避免内容语言与界面语言漂移；撤销与插入的规则补齐后，"只经流程写入"没有旁路；
`lookup` 对未声明的实体明确拒绝，符合默认拒绝。

**放弃的方案**：①多语言文本整体放在 runtime、在 runtime 另写共享用例测试（一致性证明分散在两处，且 core 的 `EntityValidator` 无从报告其约束）；
②在 `EntityValidator` 中按 `kindId` 特判（扩展类型无法复用）；③新增 `jabiz.i18n.locales`（两个语言集合可能不一致）；
④允许撤销恢复 `processOnly` 字段（可以绕过状态机）；⑤没有 `display` 时按主键文本匹配（行为隐含，且主键不是给人看的标签）；⑥服务端渲染 Markdown（多一处 HTML 注入面）。

## D21 平台版本线

**背景**：平台与两个应用（culture、finance）同时演进。平台阶段 14 会带来应用必须适配的改动（例如后台前端的结构），
而 culture 不需要这些改动，也不应被迫适配；只有一条 `platform` 分支时，应用无法停留在某个平台版本上，也看不出自己基于哪个平台版本。
本条补充 D19 第 1 条（两类长期分支），其余各条不变。

**决策**
1. **版本线**：平台的每个不兼容版本是一条长期分支 `<主>.<次>/platform`（如 `1.0/platform`、`1.1/platform`）；应用在每条它所用的线上有
   `<主>.<次>/<应用>`（如 `1.0/culture`、`1.1/finance`）。工作分支带线的前缀：平台 `<线>/phase-<N><x>-<名>`，应用 `<线>/<应用>-<N>-<名>`，
   PR 合回同一条线。不建名为 `<主>.<次>` 的分支（它会与 `<主>.<次>/…` 冲突）。
2. **何时开新线**：只有**不兼容**的改动（应用不改代码或构建就不能继续工作：接口、决策、构建方式、必须适配的行为变化）才开新线，
   新线从上一条线的平台分支拉出。兼容的新增与修复留在当前线。
3. **线的标识**：平台根目录的 `.jabiz-platform-line` 写线号（`1.0`）。它是平台文件，应用只经合并获得、不能修改，
   因此应用分支上的这个文件就是它所基于的线；`tools/check-app-paths.sh` 据此以 `origin/<线>/platform` 为基准，
   并要求以线命名的分支（`1.1/…`）与文件一致（漏了合并新线的平台、或开新线时忘了改文件，都会失败）。
4. **发布点**：平台的发布以标签 `platform-v<主>.<次>.<修订>` 标记（打在对应线的平台分支上）；分支会前进，标签不动。
5. **合并方向**：线内仍只有平台 → 应用（D19）。修复做在**最旧的受影响线**上，再依次向前合并到更新的线（`1.0/platform` → `1.1/platform`），
   各线再合并到自己的应用分支。只合并，不变基、不拣选。
6. **应用升级**：`<新线>/<应用>` 从 `<旧线>/<应用>` 拉出，再合并 `<新线>/platform` 并适配；不从新线的平台分支拉出后复制应用目录（会丢失应用的历史）。
   升级后应用只在新线上开发，旧线上的应用分支冻结（只接受该线平台修复的合并）。
7. **迁移**：不是最新的线**不增加**任何迁移（平台 `db/jabiz` 与应用 `db/migration`）：同一个版本号在两条线上会指向不同的脚本。
   需要改表结构的修复只做在最新的线上，由应用升级获得。
8. **过渡**：原有的 `platform`、`culture`、`finance` 分支即 1.0 线（`1.0/platform`、`1.0/culture`、`1.0/finance` 由它们建立），之后不再使用；
   没有 `.jabiz-platform-line` 的分支仍以 `origin/platform` 为基准检查。

**理由**：线号在分支名上，谁基于哪个平台一目了然；线号又在平台文件中，应用"基于哪条线"由合并决定、由 CI 检查，而不是靠约定；
只为不兼容的改动开新线，线的数量与向前合并的成本都受控。

**放弃的方案**：①只有一条 `platform` 分支、应用只合并到某个标签（应用可以停留，但旧版本的修复没有地方做，需要时再临时开维护分支，规则不清楚）；
②每次平台发布都开新线（线与应用分支成倍增加，向前合并成本高）；③从分支名推导线（CI 与拉取请求中 HEAD 是游离的，分支名不可靠，且无法表达"已合并"）；
④旧线上的修复用拣选（同一修复在各线上是不同的提交，合并时反复冲突，且违反 D19）；⑤各线按号段编排迁移（数据库升级到新线后旧线的迁移乱序，需要打开 Flyway 的 out-of-order）。

## D22 应用自有后台页面与界面语言子集

**背景**：财务等应用有元数据无法表达的专业工作流（多行分录的录入网格、银行对账、结账工作区、报表与钻取），需要自己的后台页面；
而通用后台 `frontend/` 是平台目录，应用分支不能改（D19）。另外财务只面向美式英语用户，却要为每条文案写中、日、英三种。
本条补充 D15（前端）、D19 第 4 条（"不用 Ant Design"只约束公开前端）与 D20 第 3 条（内容语言即平台语言），不取代任何决策。

**决策**
1. **构建时扩展**：应用的后台页面写在应用目录中的一个"扩展"里（入口 `src/index.tsx`，默认导出 `defineExtension({routes, menu, messages, home})`），
   构建通用后台时以 `JABIZ_ADMIN_EXTENSION` 编入（`jabizApp { spa("/", "../../frontend", extension = "…") }`）。平台前端仍是唯一的 SPA 工程：
   一套依赖、一个 lockfile、一份 React 与 antd；平台前端的修复随合并到达应用。未指定扩展时产物与之前相同。
2. **只经 `@jabiz/admin`**：扩展只能引用 `frontend/src/lib/index.ts` 导出的内容（API 客户端、`runQuery`、`runProcess`、登录状态与 `can`、元数据 hooks、
   通用组件、格式化）与平台前端已有的第三方依赖；深层引用由扩展的 lint 规则拒绝。这份导出是约定：破坏它的改动是不兼容改动（按 D21 开新线）。
   扩展不能自带依赖；需要新的通用依赖时先加到平台。
3. **安全不变**：扩展页面只调用现有的 `/api/**`，权限、范围、校验都由服务端按元数据判断；菜单项的 `permission` 只决定是否显示（与 12 §6 相同）。
   扩展不存令牌、不访问后端以外的地址。
4. **页面的边界**：主数据与一般的增删改查仍用元数据生成的页面；扩展只做生成页面无法表达的工作流。扩展的文案在 i18next 命名空间 `app` 中，
   不会覆盖平台的文案。
5. **启动即失败**：扩展的路由不能占用平台路径（`/`、`/login`、`/data…`、`/processes…`），必须是绝对路径且不重复，菜单项要有键与标签；
   违规在应用启动时一次性报告。扩展的类型检查是构建的一部分（`pnpm build`），类型错误使 jar 构建失败。
6. **检查**：`pnpm ext:typecheck | ext:lint | ext:test | ext:check`（`JABIZ_ADMIN_EXTENSION=<目录>`）用平台前端的工具与配置检查扩展；
   扩展的 `tsconfig.json` 继承 `frontend/tsconfig.extension.json`。
7. **界面语言子集与区域**（阶段 14a-2）：应用可只用平台语言中的一部分（`jabizApp { languages(…) }`，前后端取自同一处：jar 中的 `META-INF/jabiz-app.properties` 与前端构建变量），
   并可声明显示区域（`region = "en-US"`，12 §10）；
   文案完整性检查只要求所选语言，界面只提供所选语言。多语言**内容**的语言不变（仍是平台语言，字段声明自己的必填语言），因此不会出现 D20 担心的两套语言集合。

**理由**：一个工程、一套依赖，不会出现两份 React 或两个 antd 的样式与上下文；应用的页面与生成页面共用同一个外框、会话与组件；
约定面集中在一个文件里，平台可以放心地改动其余部分。

**放弃的方案**：①平台前端发布为 npm 包、应用自建完整 SPA（依赖与类型重复，两个 lockfile 要同步版本）；②应用复制一份前端（平台修复无法到达）；
③运行时加载远程模块（Module Federation 等：部署与内容安全策略都更复杂，而应用与平台本来就一起构建）；④允许扩展自带依赖（需要第二个包管理工程，回到方案①的问题）；
⑤语言子集同时改变内容语言（重新引入 D20 否决的两套语言集合）。

## D23 编号、审批、职责分离、任务与通知

**背景**：业务应用（首先是 finance）需要无缺号的单据号、按规则审批（准备人不能审批自己、批准绑定内容、规则有版本）、职责分离、待办与邮件通知。
这些都是通用能力：换一个与财务无关的应用（采购、人事）也需要。本条补充 D11（流程）与 D12（安全），不取代任何决策。按阶段 14b-1、14b-2、14b-3 实施。

**决策**
1. **编号（14b-1）**：序列是代码声明的 Bean `NumberSequence`（名称、格式 `JE-{n:4}` / `SO-{scope}-{n:6}`、是否按范围计数、起始值）。
   只有流程步骤 `AssignNumber` 取号：在流程事务内对 `sys_number_counter` 的一行做一次"插入或加一并返回"，行锁持有到事务结束——
   回滚即归还号码，同一范围的并发取号排队，因此号码无缺、无重复。每个发出的号码写入只追加的 `sys_number_assignment`
   （平台实体 `NumberAssignment`，只读视图，权限 `numbering.read`），连同取号的操作。计数表是基础设施表，可更新，不受 D5 保护。
   `AssignNumber.when(条件, …)`：不需要号码时不取（取了的号码都会保留）。取号应放在可能拒绝流程的检查之后。
2. **审批（14b-2）**：审批对象由代码声明（可用于条件的事实）；规则、审批人限额是时态实体，只经流程改变，修改由提出人以外的人发布
   （受控变更 `SysControlChange`：`CONTROL_CHANGE_PROPOSE` / `CONTROL_CHANGE_PUBLISH`，职责分离规则同样）；
   步骤 `RequireApproval` 按业务时间评估规则并记录所用规则版本与事实；批准绑定内容哈希，内容变化即失效；审批人不能是准备人；最后一层批准后以事件继续原流程。
   影响预览用每个单据最近一次评估记录的事实（实施时细化：代替计划中的"历史事实模板"，见 18 §3.6）。
3. **职责分离（14b-2）**：互斥权限对是时态实体；在用户角色与角色权限的全部写入途径上预防，流程入口运行时兜底；`*` 运行时不拦，但总列入冲突报告。
4. **任务与通知（14b-3）**：待办是时态实体（指派给用户或权限），审批请求自动建待办并逐层传递；新待办的事件经 Outbox 由通知流程消费，
   通知记录只追加、提交后发送并重试（`spring-boot-starter-mail`，缺省关闭）；用户增加可选邮箱。

**理由**：号码在业务事务内取、随事务回滚，是在 PostgreSQL 上做到无缺号最简单可靠的方式（序列对象会跳号）；号码记录只追加，便于审计与完整性核对；
审批与职责分离做成平台能力，每个应用不必各写一套、也不会各有漏洞。

**放弃的方案**：①数据库序列（回滚与崩溃都会跳号）；②先取号、失败时"作废号码"（号码表出现空洞，审计需要解释）；③在应用中自己维护计数实体
（乐观锁冲突时整个过账重试，且各应用各写一遍）；④把审批规则放进业务参数（参数只能存单个值）。

## D24 账本增强：科目层级、分析维度、来源单据、按当时所知的余额、多币种

**背景**：财务应用（及任何记账的应用）需要汇总科目、按部门等维度分析、从账本行钻取到单据、重现"当时所知"的余额，以及外币分录。
这些都扩展平台账本（D14），而不是由应用另建总账。本条补充 D14，不取代任何决策。按阶段 14c-1、14c-2 实施。

**决策**
1. **科目层级**：科目有上级科目与"汇总科目"标记（空 = 可过账，兼容旧数据）；汇总科目不能过账，层级不能成环，已有分录的科目不能变为汇总科目；
   余额模板把汇总科目算作其全部下级之和。层级修改与过账以同一把 advisory lock（独占 / 共享）串行。
2. **分析维度**：分录有固定的 4 个维度列；应用以 `LedgerDimension` Bean 声明使用哪几个、名称与取值来源（字典或实体字段），过账时校验取值。
   固定列换来简单的索引与汇总；需要更多维度时再开新决策。
3. **来源单据与行备注**：来源（实体 + 主键）记在交易上，过账时校验其存在；每行可有备注。冲正照原样复制。
4. **按当时所知**：账本只追加，交易的记录时间即"当时所知"的依据；余额模板接受区间（`from`）与 `knownAt`。过账日期仍为 `bookingTime`（时间点），应用按自己的时区把日期换算为时间点。
5. **多币种（14c-2）**：分录记交易币种、交易币种金额、汇率与本位币金额；本位币金额 = 交易金额 × 汇率按账本小数位四舍五入（严格一致），
   尾差由调用方另加本位币行；每个交易币种各自借贷平衡，本位币合计借贷平衡；旧数据为空即本位币。

**理由**：这些是任何复式账本的通用需要；做在平台上，账本仍只有一个写入口（`LEDGER_POST` / `LEDGER_REVERSE`），数据库兜底与只追加照旧。

**放弃的方案**：①应用在自己的实体里记维度与来源（报表要跨两套数据拼接）；②维度用键值表（汇总需要行转列，索引困难）；
③来源记在每一行（一张单据的各行来源相同，重复存储）；④新增日期型的过账日期列（现有的 `bookingTime` 已能表达，改动面大）。

## D25 报表：时点运行、导出、签发存档与重现

**背景**：应用需要"按某日生效、按某日所知"运行报表并在以后原样重现（财务的 RP-009、RP-020），需要 CSV / Excel / PDF 导出，
后台需要运行报表的页面。平台已有 SQL 模板（05）与只追加的时态数据（04），但模板总按"现在"读取，也没有导出与存档。
这些都是通用能力：任何有报表的应用都需要。本条补充 D10（模板经数据视图渲染）与 D13（场景回放），不取代任何决策。按阶段 14d-1、14d-2、14d-3 实施。

**决策**
1. **报表即模板**：报表是头部声明了 `report` 的 SQL 模板；不另建报表定义。标题与列名在消息资源 `query.<id>`、`query.<id>.<列>`。
2. **时点（14d-1）**：模板运行时的时点只有一个来源：头部 `timeSlice` 映射的参数，或请求字段 `asOf` / `knownAt`，或缺省（现在、不限记录时间）。
   时点作用于模板中所有时态实体；给出时点要求这些实体的视图允许时间旅行；公开模板不接受时点。
   账本交易的生效时间即记录时间，账本模板只把 `knownAt` 映射为时点（19 §2.2）。
3. **模板版本（14d-1）**：模板文件全文（DSL 定义为规范描述）的 SHA-256；存档记录版本与全文。
4. **导出（14d-2）**：CSV、XLSX（fastexcel，数值单元格）、PDF（Apache PDFBox，自己排版表格；输出确定）；行数有上限，超过即拒绝，不截断。
   公司名为配置 `jabiz.reports.company`；区域随应用构建写入。中文、日文字体由应用配置。
5. **存档（14d-3）**：签发把参数、时点、模板版本与全文、页眉、结果行与内容哈希写入只追加的表（数据库中以 text 存规范 JSON——jsonb 会改写原样；受 D5 的触发器保护）；
   重现由存档的行生成文件（不重新查询），核对则按存档的时点重新执行并比较哈希；取代关系另表只追加。

**理由**：只追加的时态数据本身就能按记录时点重算，但主数据若按"现在"读取，名称与层级会漂移，所以时点必须作用于模板中的全部时态实体；
存档保存结果本身，重现不依赖模板是否读取了非时态数据、也不受模板以后修改的影响，核对再证明数据未被改写。

**放弃的方案**：①另建报表定义语言（与模板重复，且财务的版式需求属于应用）；②只保存参数、重现时重新查询（模板或非时态数据变化后无法重现）；
③存档结果放在文件存储（`sys_file` 可删除，保护较弱）；④Apache POI（体积大）与 OpenPDF（LGPL/MPL 许可）；⑤导出超过上限时截断（得到看似完整的错误报表）。

## D26 导入：导入专用文件类型、导入定义、按行保存点、去重、映射

**背景**：财务需要导入主数据、期初余额、日记账、银行对账单、工资与汇率（DI-001/002/004、GL-019、BK-003、FX-002、PC-002）：
全部行校验通过才写入，一行出错整份文件拒收并逐行报告；同一文件或同一外部引用不重复入账；列与值要能映射。
平台的文件只允许图片、PDF 与音频（D18、14 §3），也没有批量写入的通用方式。这些是通用能力，按阶段 14e-1、14e-2 实施。
本条补充 D11（流程）与 D18（文件），并调整 14 §3 "永不允许 XML"一句的适用范围，不取代任何决策。

**决策**
1. **导入专用文件类型**：`MediaTypes` 增加 `TEXT`（CSV、定宽等行格式，内容上不可区分，按导入定义选择解析器）、`XLSX`（ZIP 中有工作簿与无宏的内容类型、没有 VBA）、
   `XML`（XML 声明或首个元素，不是 HTML/SVG，不含 `<script`）。这三种类型只能出现在只允许这三种类型的策略中，原样保存（不重新编码），
   下载一律 `attachment` 加 `CSP: sandbox`，公开接口永远不提供（即使公开行引用了它们）。
2. **解析在 core，纯 Java**：CSV（RFC 4180）、定宽、XLSX（平台自己的读取器：JDK 的 ZIP 与 StAX，每个部件按实际字节计数限制解压大小）、XML（按路径取值）；
   XML 与 XLSX 的部件一律禁止 DTD 与实体引用（防 XXE、实体膨胀）。超过行数、列数、单元格长度、解压大小即拒收整个文件，不截断。
   其他格式（BAI2、camt.053、OFX）由应用实现 `ImportParser`。
3. **导入定义**（`ImportDefinition` Bean）：文件策略与版式、字段（语义类型决定读取与校验）、每行或每组交给哪个流程与如何构造输入、外部引用与重复处理（跳过或报错）、
   整个文件的检查、控制合计、权限（导入权限；映射权限缺省同导入权限）、时区与日期格式、行数上限。
4. **执行**：平台流程 `IMPORT_RUN` 在一个事务中依次把每个单元（行或组）作为子流程执行，每个单元前设保存点；单元失败回滚到保存点并记录其全部违规，后续单元照常执行，
   并看得到前面成功单元的写入。**预览**是 `IMPORT_RUN` 的试运行（`ExecutionOptions.dryRun`：流程完成后整个事务回滚，不执行提交后步骤）；
   **提交**（14e-2）在有任何问题时整体回滚并另行记录被拒的导入。子流程不检查权限，因此导入入口与 `IMPORT_RUN` 本身都要求导入权限、行流程的权限与文件策略的读取权限。
5. **去重（14e-2）**：同一导入同一文件（SHA-256）只能成功提交一次（事务级咨询锁加部分唯一索引，409）；外部引用唯一，与数据同一事务写入。
   被拒的提交回滚到包住全部单元的保存点，只留下导入记录；被撤销的工作所登记的提交后步骤一并丢弃。
6. **映射**：列到字段、字段常量、CSV/XLSX 版式的调整（分隔符、表头、跳过行数、字符集、工作表、表头行）；可按名称保存为时态平台实体 `SysImportMapping`（只经内部流程写入）。
   值的映射（如工资供应商代码到科目）属于业务数据，由行流程查询。

**理由**：导入的正确性就是业务流程的正确性，所以每行交给手工录入所用的同一个流程（审批、编号、校验都一致），平台只负责读取、转换、事务与报告；
按行保存点让一次运行既能报告全部问题，又与提交时看到的数据完全一致（后面的行能看到前面的行）；读取器自己实现，是为了完全掌握解压与 XML 的安全设置。

**放弃的方案**：①暂存表（staging）加两阶段：多一套表与清理，且校验与提交看到的数据不同；②每行单独事务预校验：后面的行看不到前面的行，预览与提交结论可能不同；
③用第三方读取 XLSX（fastexcel-reader、POI）：依赖的 XML 与 ZIP 安全设置不在平台控制之下；④按扩展名区分 CSV 与纯文本：扩展名不可信；⑤导入时截断超限的文件。

## D27 审计记录、防篡改封存、保留期与法律保全、开放格式导出

**背景**：财务要求完整的审计轨迹（CT-010：前后值、操作人、时间、对象、原因、审批人，只追加）、可发现篡改（CT-011）、
保留期与法律保全（CT-020：会计年度结束后 7 年，保全期间不得删除）与不依赖本系统可读的归档（CT-021）。
平台的操作记录只有名称与标识（11 §3），普通表原地修改，只追加由触发器保护而数据库管理员可以绕过，也没有保留与导出。
这些是通用能力，按阶段 14f-1、14f-2、14f-3 实施（21）。本条补充 D4、D5、D14、D18，不取代任何决策。

**决策**
1. **审计记录**：每次实体写入（普通与时态）在同一事务内写一行只追加的 `sys_audit_record`：操作、实体与主键、动作、版本、
   变化字段的前后值、操作人、时间、原因。写入点是 `DatasetEntityManager` 与 `VersionAppender`，所有写入路径都经过它们；业务代码不自己写审计。
2. **遮蔽**：敏感字段的前后值只存 `***`，审计不保存可恢复的原值；"改过"照样记录。
3. **审批人**：审批请求与决定本身是实体写入，其审计行按单据关联查询（`withApprovals`，审批对象以 `entity(…)` 声明其单据的实体类型），不另存一份。
4. **防篡改（14f-2）**：只追加表逐行摘要，定期封存为 HMAC 哈希链（密钥 `JABIZ_INTEGRITY_KEY`，非 dev 缺少即启动失败），
   校验报告被改、缺失的行，被改的块与条目，断链，以及只追加保护被关掉的表；最新块哈希可取出在系统外留存。
   按"有没有条目"找未封存的行，因而晚提交的行不会漏掉，不需要宽限期。封存证明的是封存之后未改、未删；
   两次封存之间在应用之外插入的行无法与正常的新行区分（查操作记录与审计记录）。
5. **保留与保全（14f-3）**：`RetentionPolicy` Bean 声明保留期；保留期内或受法律保全（`SysLegalHold`，只经 `LEGAL_HOLD_PLACE` / `RELEASE`）时，
   逻辑删除、物理删除与文件删除一律拒绝（拦截在删除路径中，业务代码不自己检查；文件清理跳过并报告）。保留期可自会计年度末起算（`jabiz.fiscal-year-end`）。
   到期后的物理删除与匿名化不在本条范围（与 D5 冲突，需另立决策）；到期报告 `GET /api/retention` 列出范围。
6. **开放格式导出（14f-3）**：`POST /api/exports/data` 以流返回 ZIP，内含 CSV（经数据视图读取，权限与数据范围照常，敏感字段不导出）、`schema.json`、
   `manifest.json`（哈希、行数、封存块哈希）与已签发报表的 PDF；导出本身记操作（`DATA_EXPORT`）。

**理由**：写入点只有两处，在那里记录就不会漏掉任何路径，且与数据同一事务，不会出现"数据改了、审计没写"；审计行本身只追加并被封存，
所以普通表虽可原地修改，每次修改都留下不可改的证据；只存遮蔽值使审计本身不成为泄露敏感数据的途径。

**放弃的方案**：①数据库触发器记录前后值：拿不到操作人、原因与字段的语义（敏感、小数位），且写入与应用的遮蔽规则无关；
②从操作记录的输入摘要推导：输入不等于写入的结果；③加密保存敏感原值、授权可看：增加密钥管理且扩大泄露面；④只封存账本：审计、存档、导入同样需要证据。

## D28 安全增强：二次验证、按操作要求二次验证、闲置锁定、OIDC 单点登录、按权限显示明文、数据期限、访问审查

**背景**：财务要求付款放行、供应商银行信息变更与系统管理必须二次验证，支持单点登录，会话闲置后锁定（SC-001）；
审计师只能看某一会计年度的数据（SC-002）；定期的用户访问审查与签核（SC-003）；税号、银行账号按权限显示且每次显示明文都留记录（SC-004）。
D12 的会话只有密码一个因素，没有单点登录与闲置限制；敏感字段要么完全不可读（`sensitive()`），要么完全可读。
这些是通用能力，按阶段 14g-1（二次验证、按操作要求二次验证、闲置锁定）、14g-2（OIDC）、14g-3（明文显示、数据期限、访问审查）实施（10 §9–§13）。
本条补充 D12 与 D17，不取代任何决策。

**决策**
1. **二次验证只用 TOTP 与恢复码**（RFC 6238：SHA-1、6 位、30 秒，前后各容许 1 步；时间只来自注入的 `Clock`）。不做短信、邮件验证码（NIST 800-63B 的受限方式），
   WebAuthn 以后再议。绑定信息是平台的时态实体 `SecUserMfa`（只经流程写入）；TOTP 密钥以 AES-256-GCM 加密存放（附加数据为用户主键，不能挪给别的用户），
   密钥只来自环境变量 `JABIZ_MFA_KEY`（Base64，≥ 32 字节），非 dev 缺少即启动失败；恢复码 10 个、一次性，只存 SHA-256。
2. **登录仍是流程并留登录记录**（D12 第 4 条）：已绑定的用户密码正确后，`SPONSOR_SIGN_IN` 的结果是 `MFA_REQUIRED`，接口返回 5 分钟有效的挑战令牌
   （与访问令牌同一密钥、不同类型，不能当访问令牌用）；第二步是流程 `SPONSOR_MFA_VERIFY`，同样写登录记录。码错误（`MFA_FAILED`）与密码错误计入同一个失败计数与锁定；
   已接受的最后一个时间步随登录记录传下去，同一个码不能用两次；同一用户之后的任何一次密码登录都使旧挑战失效。
3. **角色可要求二次验证**（`SecRole.requireMfa`）：持有这类角色而未绑定的用户，登录结果是 `MFA_ENROLLMENT_REQUIRED`，挑战令牌只能用于绑定；绑定后重新登录。
   未经二次验证的会话不能在刷新时取得这类角色（刷新被拒，需重新登录）。
4. **按操作要求二次验证**：流程 `requiresMfa(…)`、数据视图 `writeRequiresMfa(…)`；在入口（流程 API、数据视图提交、实体 API、导入、撤销）检查访问令牌的
   `mfa_at` 不早于 `jabiz.security.mfa.step-up-max-age`（默认 10 分钟）之前，否则 403 `MFA_REQUIRED`；前端弹出输入框，`POST /api/auth/step-up` 换取新的访问令牌后重试。
   与权限一样只在入口检查（D11 第 2 条）：子流程、场景回放、系统身份不检查。平台的管理操作（安全实体的写入、`SEC_*` 流程、受控变更的发布、法律保全）
   声明为"管理"级别，由 `jabiz.security.mfa.administration`（默认 `true`）控制，只有不对外开放管理的部署才可关闭。
5. **闲置锁定**：刷新只在所用刷新令牌签发后的"访问令牌有效期 + `jabiz.security.session.idle-timeout`（默认 15 分钟）"以内有效，否则 401，需要重新登录；
   访问令牌有效期不得长于闲置时长（启动检查）。前端按键盘与指针活动计时，到时吊销会话并回到登录页。
6. **OIDC 单点登录（14g-2）**：授权码 + PKCE + nonce；平台自己校验 ID 令牌（只接受 RS256 / ES256，JWKS 缓存）后签发自己的令牌，会话仍按 D12；
   不用 Spring 的 oauth2-client（它依赖服务端会话）。外部账号只能由管理员关联到已有用户（`SecUserIdentity`），**不自动开户**；
   身份提供方以 `amr` 声明的二次验证可按配置视同平台的二次验证。不做 SAML。关联用数据视图维护的时态实体 `SecUserIdentity`（管理级二次验证），
   PKCE verifier 存在服务端的只追加表中（不用 Cookie，D12）；只用单点登录的用户可以没有密码（14g-2）。
7. **按权限显示明文（14g-3）**：`f.masked(权限, 样式)` 的字段在读接口、历史、审计中一律是遮蔽值；持有该权限者逐值请求明文，每次写只追加的显示记录；
   SQL 模板与导出对无权限者在 SQL 中投影为遮蔽值，对有权限者每次运行留一条记录；无权限者不能按其筛选、排序，也不能写入它；遮蔽字段不得公开（D17）。
   实施细节（10 §13.1）：遮蔽在 `{{Entity}}` 的子查询中完成，模板的条件与外层筛选同样只见遮蔽值；`REPORT_ISSUE` 签发的报表一律遮蔽
   （存档给别人阅读与校验，校验须得到相同的行）；导入报告与 `input_summary` 中同名属性同样遮蔽。
8. **数据期限（14g-3）**：角色分配可带 `dataFrom` / `dataTo`，进入令牌与 `RequestContext`；数据视图以 `withinDataPeriod(字段)` 声明按期限过滤读取、拒绝期限外的写入。
   期限为空表示"不受期限限制"（有一个不限期的角色分配即如此），这与 `fromContext` 取不到值即拒绝不同，须明确声明才生效。
   实施细节（10 §13.2）：多个限期分配取外包；也可经引用字段按被引用实体的不可变时态字段限定（账本分录按交易的过账时间），此时受限者不能看历史、不能更新；
   审计与操作记录的查询按记录时间截取在期限内。
9. **访问审查（14g-3）**：当前访问权限是一个报表模板，按期末时点以 `REPORT_ISSUE` 签发（D25，不另存报表）；期间内的变更取自审计记录（D27）；
   签核流程只保存对二者的引用与哈希、审查人与意见，同时附上职责分离冲突报告（18 §4）。

**理由**：沿用 D12 的全部结构（登录是流程、令牌无状态、表只追加、默认拒绝），只增加一个因素与几个检查点；二次验证的状态放在登录记录里传递，
不需要新的计数表；在入口检查二次验证与权限检查同位，业务代码不必自己判断。

**放弃的方案**：①短信 / 邮件验证码（易被拦截，且需要外部通道）；②把 TOTP 密钥明文或哈希存放（哈希无法验证，明文泄露即失效）；
③用受限的访问令牌完成强制绑定（令牌多一种形态，每个入口都要区分）；④服务端会话记录最后活动时间（违反 D12 的无状态）；
⑤首次单点登录自动开户（外部身份提供方即可决定谁能进入系统）；⑥有权限者在列表中直接看到明文（每次列表读取都要留记录，或者不留记录）。

## D29 时态数据的规模：不可变字段下推、只写一次的实体、按索引的唯一性检查

**背景**：finance F1c 的压测（`1.1/finance` 的 `docs/finance/perf.md`）在约 200 万个账本分录版本上发现：D3 的当前版本子查询对整表做 `DISTINCT ON`，
科目查询要 3.9 秒、试算表 28 秒；D6 的唯一性检查同样先取整表的当前版本，每次过账约 1 秒。所查的往往是不可变字段（分录所属交易、科目、单据号），
账本交易与分录又只写一次，按版本读本来就足够。这是所有大时态表共有的问题，在平台解决（阶段 14i）。本条补充 D3 与 D6，不取代它们。

**决策**
1. **不可变字段的条件下推到子查询**：查询条件中只涉及不可变字段（主键、`immutable(true)` 的非系统字段）的合取项，同时写进当前版本子查询的内层
   （`Or` 只有每一支都只涉及不可变字段时才下推；`KeyAfter` 分页条件下推），外层照旧全部保留。不可变字段在一个实例的所有版本上取值相同
   （墓碑、撤销、变基都复制基础状态，所有写入路径都拒绝修改不可变字段），所以内层过滤只减少参与 `DISTINCT ON` 的行，不改变结果（把已有的可变字段改为不可变时，须先确认历史中每个实例只有一个值）。
   **数据视图范围不下推**（D3 的理由不变：范围字段可变，下推会让移出范围的实体退回旧版本）。显示字段的批量查询按主键下推。
2. **只写一次的时态实体**：`eb.temporal(t -> t.writeOnce())` 声明每个实例只有一个版本：只能插入，更新、删除、取消预定、撤销一律 422 `WRITE_ONCE`
   （保留期删除走同一删除路径，同样拒绝；更正以冲正等新实例表达）。读取不用 `DISTINCT ON`，直接按时间点过滤版本行。
   表上必须有**只含实体主键的唯一索引**（启动检查 `METAMODEL`，缺少即错误），它由数据库保证"只有一个版本"。平台账本的交易与分录即如此声明。
3. **唯一性检查与"之后仍被引用"检查从索引取候选**：先在约束字段（或引用字段）上找出用过这些值的实例（任一版本），再只对这些实例取当前版本与预定版本判断；
   结果与 D6 相同（排除自身与墓碑、包括预定版本），读的行数与用过该值的实例数成正比，而不是与表的大小成正比。
4. **支撑索引只告警**：唯一约束的字段（作为集合）不是任何索引的前导列时，启动检查报**警告**而不是错误（功能正确，只是慢）；平台与示范迁移补齐了这些索引。
5. **不做当前快照投影表**（04 §5.3 的设想）：投影表需要在每次写入时维护、在预定版本到期时切换，代价与出错面都大；1–3 已使按实例与按不可变字段的读取与表大小无关。
   按可变字段跨大量实例的汇总（如试算表）由应用维护自己的汇总（如按月的科目余额），不由平台通用地解决。

**放弃的方案**：①所有条件都下推（可变字段下推会返回旧版本的值，D3 已否定）；②时态表上直接建业务唯一索引（历史版本冲突，D6 已否定）；
③只写一次的实体改为非时态表（失去 `op_process` 关联、时间点读取与历史接口，账本还需要按当时所知的余额，D24）；④缺少支撑索引即启动失败（已部署的应用会因为性能问题无法启动）。

## D30 单据：代码声明的版式、存档 PDF 原样字节、经通知通道发送

**背景**：finance 的发票（FIN-AR-005：可打印、可邮寄的 PDF，保留每份发出单据的不可变副本，重印与发出的相同；FIN-AR-001：重印显示发票日的地址），
以及以后的付款通知、1099 收件人副本、对账单，都需要"单据"：多个区块（发出方与收件方、单号与日期、明细、按辖区的税、合计、汇款说明），
发出后原样保存并能发给外部收件人。报表（D25）是一张表，存档的是结果行、重印时重新排版；邮件（D23）只发纯文本给系统用户。
这些是通用能力（订单确认书、运费月结单同样需要），在平台实现（阶段 14j）。本条补充 D23、D25，不取代任何决策。

**决策**
1. **版式在代码中声明，数据来自普通 SQL 模板**：`DocumentLayout` Bean 由区块组成（`party`、`facts`、`table`、`totals`、`text`、`note`），
   每块显示一个模板的列；沿用模板的权限、版本、数据范围与时点。不另造模板语言，不做 HTML 转 PDF。启动检查 `DOCUMENTS`。
2. **新流程 `DOCUMENT_ISSUE` 与自己的存档表 `sys_document_run`**，而不是扩展 `REPORT_ISSUE` / `sys_report_run`（后者是"一个模板 + 一张表"，
   硬塞多块单据会让报表的列表、导出与核对都要分支）。共用 14d-3 的规范化与内容哈希、时点固定、数据范围比较。
   （finance 路线图 F3 第 1 条写的"经 `REPORT_ISSUE` 签发存档"据此改为 `DOCUMENT_ISSUE`。）
3. **存档 PDF 原样字节**（`bytea`，只追加，D5 触发器保护，14f-2 封存自动覆盖）：重印与附件一律取存档字节，从不重新排版——
   平台升级（字体、排版）不影响已签发的单据。同时存档各模板的结果与内容哈希，用于按数据核对（`identical` / `differs`，
   版式或模板版本变化时 `layout_changed` / `template_changed`）；存档字节另以 SHA-256 核对（`copyIntact`）。
4. **全部模板按同一时点读取**：调用方给出的时点，未给出的部分固定在签发时刻；单据日期等业务时点由调用的业务流程换算后给出。
   模板不得声明 `timeSlice`，单行区块的模板必须恰好返回一行（否则 422，不保存）。
5. **纸张**：`A4` / `LETTER`，缺省按应用区域（美国、加拿大、墨西哥、菲律宾为 Letter）。
6. **发送（14j-2）沿用 14b-3 的通知机制**：同一发送器 `NotificationSender`（增加带附件的消息），附件为存档字节，每个收件人一封，提交后发送、尝试只追加、失败重试；
   收件人缺省来自数据（版式声明的地址列，签发时随单据存档），发给其他地址需要单独授予的 `document.send.any`。
   （实施时细化：投递记在单据自己的只追加表 `sys_document_delivery` / `_attempt`，而不是计划中的 `sys_notification`——后者是受审计的平台实体，
   主键为文本、只指向待办，不能以外键指向不是实体的单据存档；22 §5.2。）

**理由**：版式是应用的事（财务的发票、订单确认书各不相同），数据与权限已有模板这一套机制，版式只需说"哪一块显示哪个模板的哪些列"；
"与发出的相同"只有保存字节才能在平台升级后仍然成立，数据另存则保留了按数据核对的能力；发送与待办邮件共用一条带重试与记录的通道。

**放弃的方案**：①扩展 `REPORT_ISSUE`（见第 2 条）；②只存数据、重印时重新排版（排版代码一变就不再"相同"）；③PDF 存在文件存储（`sys_file` 可删除，保护较弱，D25 已否定）；
④HTML / Word 模板引擎（体积大、输出不确定、又一种模板语言）；⑤单据各区块用一个模板的不同行类型拼成（模板难写、类型检查失效）。

## D31 纳税人号码的遮蔽样式与生成文件的存档

**背景**：finance 的应付（F4）要保存供应商的纳税人号码（TIN：EIN 或 SSN/ITIN），只让部分人看明文，并要生成交给银行与税务机关的文件
（NACHA 付款文件、正向支付文件、1099 申报文件）。现有遮蔽样式 `LAST4` 显示 `****6789`，不符合 TIN 的习惯写法，也不区分 EIN 与 SSN；
生成的文件既不是上传的文件（`sys_file` 可删除，D18），也不是单据（D30 只存 PDF），而它们恰恰是付款与申报的证据，必须原样保存并能证明未被改动。
两者都是通用能力（任何美国应用的供应商、员工都有 TIN；任何对接银行的应用都生成文件），在平台实现（阶段 14k）。本条补充 D18、D28 第 7 条，不取代任何决策。

**决策**
1. **`MaskStyle.TAX_ID`**：EIN 形式 `NN-NNNNNNN` → `**-***` + 末 4 位；SSN / ITIN 形式（9 位数字，可带连字符）→ `***-**-` + 末 4 位；其他一律 `****`。
   Java 与 SQL 形式逐值相同（集成测试比对），遮蔽形式被识别为遮蔽值、不能作为输入写回。
2. **生成文件存档 `sys_generated_file`（只追加）与子流程 `FILE_ARCHIVE`**：原样字节 + SHA-256 + 读取所需的权限 + 可选对象；只允许文本类媒体类型与受限的文件名、
   有大小上限。`FILE_ARCHIVE` 的权限不授予任何角色，只作为业务流程的子流程运行——生成文件的权限就是业务流程的权限。
3. **读取 `GET /api/generated-files/{id}`**：需要 `file.generated.read` 与保存时声明的全部权限，否则 404；以哈希核对后返回；每次下载记入
   `sys_reveal_record`（`kind = FILE`），因为这类文件含明文账号，下载等同显示明文。

**理由**：TIN 的显示习惯在报表、单据与后台中处处一致才不会让人困惑，放在平台的样式中一处定义；生成文件与单据的存档要求相同（原样字节、哈希、只追加、封存），
但没有版式，放进 `sys_document_run` 会让单据的核对、重印、发送都要分支，所以单独一张小表；下载记入显示记录，让"谁拿到过付款文件"可以审查。

**放弃的方案**：①生成文件存进 `sys_file`（可删除，D18 的删除与清扫语义与证据要求相反）；②作为单据存档（D30 的核对按模板数据，生成文件没有模板）；
③由应用自建存档表（每个应用重复只追加、封存、权限与下载记录）；④`TAX_ID` 由应用以 `ALL` 代替（看不到末 4 位，核对供应商时不可用）。

## D32 `maxQueryBatchSize` 只限浏览的一页；不浏览的读取取全部结果，超过上限即拒绝

**背景**：D10 第 2 条规定模板的"行数上限取各视图 `maxQueryBatchSize` 的最小值"。这对浏览（模板 API、数据视图 API 的一页）是对的，
但流程中的 `RunTemplate`、`QueryEntities` 与 SQL 字典也按这个上限取数，结果被**静默截断**：finance F11c 压测时 600 个科目的试算表在关账检查中只读到前 500 行，
应付账龄与控制科目对不上（"Payables aging 1250.00 against control 0.00"）。导出（D25）与签发的报表早已用 `all` 不受这一上限，流程中的读取却没有。
截断而不报错，比任何错误都危险：账对不上时看不出原因，甚至在数据少的环境中永远不会被测出。本条取代 D10 第 2 条中关于行数上限的一句。

**决策**
1. 数据视图的 `maxQueryBatchSize` 只限**浏览的一页**（模板 API、数据视图 API 的 `limit`），照旧取请求值与各视图上限的最小值。
2. **不浏览的读取取全部结果**：流程中的 `RunTemplate` 读模板的全部行；`QueryEntities` 返回查询自己的 `limit` 那么多行（不再按数据视图的一页截断）；
   SQL 字典读全部条目。它们共用上限 `jabiz.process.max-read-rows`（缺省 100,000），超过即 422 `PROCESS_READ_TOO_LARGE`（参数 `source`、`limit`，三种语言）——
   **拒绝，绝不取一部分**。拒绝看的是实际读到的行数而不是请求的 `limit`：`limit` 大于上限的查询只读到上限多一行，真有那么多行才拒绝
   （平台流程按输入或固定上限请求数千行，如登录读取二次验证记录，不能因调低上限而失败）。查询自己的 `limit` 之外的行不读，需要看到全部的流程请求比预期更多的行。
   平台内部按输入取数的读取（业务参数、账本维度值、待办关闭、职责分离规则）同样不按一页截断。导出与签发保持各自的上限（`jabiz.reports.export.max-rows` 等），同样拒绝不截断。
3. 上限必须在 1 与 `Integer.MAX_VALUE - 1` 之间，否则启动失败。超时、范围、遮蔽、排序与浏览完全相同，只有行数上限不同。

**理由**：一页是给人看的，大小由界面与服务器负担决定；流程、字典要的是"全部"，按页截断让结果取决于数据量，正确性不能取决于数据量。
有上限是为了防止失控的查询拖垮服务器，越过它应该让人知道并缩小范围（参数、条件），而不是悄悄少算。

**放弃的方案**：①把各视图的 `maxQueryBatchSize` 调大（浏览的一页随之变大，且下一个更大的数据集仍会被截断）；②流程中分页循环读取（每个调用方各写一遍，
页之间数据可能变化，且仍需要一个总上限）；③截断时只记警告（结果仍然是错的）。

## D33 Webhook：配置中的订阅、每个订阅一个 Outbox 消费者、HMAC 签名、目标主机白名单

**背景**：finance 的 FIN-DI-007 要把"发票已过账"等事件通知其他系统，并在失败时重试。平台已有事务性 Outbox（D14）与以流程消费的订阅，
但没有出站调用；业务扩展点不能做 I/O（第 3 节分层纪律），出站请求又是 SSRF 与泄密的常见入口。

**决策**
1. 订阅写在配置中（`jabiz.webhooks.subscriptions`），密钥只来自环境变量，不作为可经接口写入的数据：与平台其他密钥同样管理，
   也不需要加密存储与改密钥的流程。增减订阅即改配置并重启。
2. 每个订阅是一个独立的 Outbox 消费者 `jabiz.webhook.<name>`，执行平台的内部流程 `WEBHOOK_DELIVER`：投递、只处理一次、失败记录与退避重试
   全部沿用 D14，各订阅互不影响；至少一次投递，接收方按事件 ID 去重。该流程只在平台的投递中执行，输入只有订阅名与事件 ID，事件从 Outbox 读取：
   任何调用者都不能让平台签发别的内容。每个消费者的一轮在第一次失败处结束（补充 D14），一个不可达的接收方不拖住其他消费者。
3. 请求以 HMAC-SHA256 签名（时间戳 + 正文），算法在 core 的 `WebhookSignature`，接收方可同样验证。
4. 只发往白名单主机（缺省为空）；https，http 只限本机；不跟随重定向；有超时。启动检查报告配置的全部问题。
5. 出站调用只由平台的这一步骤进行，不对业务开放；业务只决定发布哪些事件（`PublishEvent`）。秘密在发布时已去掉；遮蔽字段（D28 第 7 条）的值
   由发布者负责不放入有订阅的事件。

## D34 后台前端改用 shadcn/ui；应用前端共用平台的前端包

**背景**：通用后台用 Ant Design 5 + ProComponents（CLAUDE.md 第 2 节、12），外观不符合要求，且深色模式、与应用自有前端统一外观都要额外工作。
QuizBuks 有三个前端（答题人 PWA、商家后台、管理员后台），要求同一套外观与深色模式；前两个是应用自己的 SPA（与 D19 第 4 条的公开前端同样的工程形态），
但需要登录、令牌刷新、二次验证、调用流程与模板——这些平台前端已有，却只经 `@jabiz/admin` 提供给后台扩展（D22）。
D22 第 2 条的导出中含 ProComponents 的类型（菜单项），换组件库必然破坏它，因此是不兼容改动，放在线 1.2（D21 第 2 条）。
曾考虑 Radix Themes（草案初稿），确认时改为 shadcn/ui：面向消费者的 PWA 对外观要求高，而 Radix Themes 的外观可调范围有限、缺少数据表格与组合框。

**决策**
1. **组件**：shadcn/ui——以 Radix Primitives 为行为层、Tailwind CSS v4 为样式层的组件源码（配套 `class-variance-authority`、`tailwind-merge`、`clsx`），
   图标 `lucide-react`。配套库与其做法一致并固定为：表格 TanStack Table、表单状态 react-hook-form（字段规则仍只来自元数据与 `spec/validation-cases.json`，
   不引入第二套校验库）、日期选择 react-day-picker、图表 Recharts、提示 sonner、命令面板与组合框 cmdk；`dayjs`、TanStack Query、React Router、i18next 不变。
   移除 `antd`、`@ant-design/pro-components`、`@ant-design/icons`、`@ant-design/v5-patch-for-react-19`。
2. **组件源码只有一份**：shadcn 的组件经其 CLI 生成到平台的 `@jabiz/ui` 中，由平台维护（含无障碍与多语言的修改）；应用与扩展**不自行生成或复制** shadcn 组件，
   需要新组件时先加到平台（同 D22 第 2 条"需要新的通用依赖时先加到平台"）。上游更新由平台按需合入。
3. **外观**：主题是 `@jabiz/ui` 的 CSS 变量（shadcn 的语义 token：`--background`、`--foreground`、`--primary` …），深色以 `.dark` 类切换；
   亮、暗、跟随系统三种外观，用户可切换（存于浏览器）。应用可在自己的样式表中覆盖 token（品牌色），不改组件源码；样式只用 Tailwind 的工具类与 token，
   不写死色值。axe 自动检查对亮、暗两种外观都执行，任何违规即失败（12 §11 的做法不变）。
4. **两个共用包**（平台前端目录中，源码形式，不发布到 npm）：
   - `@jabiz/client`：无界面的部分——登录（带登录入口，D36）、令牌刷新、闲置锁定、step-up、OpenAPI 类型的 API 客户端、`runProcess` / `runQuery`、
     i18n 初始化、金额 / 日期 / 数字格式化（金额的显示单位可由应用设定，如 "Kudos"）、`UserName`。
   - `@jabiz/ui`：shadcn 组件与平台的组合组件（数据表格、元数据驱动的表单字段、金额与日期输入、确认对话框、外观切换、页面外壳的积木）、主题样式表。
   `@jabiz/admin`（D22）继续是后台扩展的唯一入口，改为在这两个包之上导出；导出内容随本条变化（不兼容，线 1.2）。
5. **应用自有 SPA**（如 `quizbuks-web/app`）：自己的 `package.json` 与 lockfile（同 D19 第 4 条的公开前端），以路径依赖（`link:`）引用上述两个包，
   样式表引入 `@jabiz/ui` 的主题并把该包加入 Tailwind 的扫描源；`react`、`react-dom`、`tailwindcss`、`@tanstack/react-query`、`i18next` 及 `@jabiz/ui` 的运行时依赖
   的版本必须与平台前端相同，由平台提供的检查脚本（`pnpm app:check`）验证，不一致即失败（避免两份 React 或样式不一致）。
   应用 SPA 只调用 `/api/**`，权限仍只由服务端判断（D22 第 3 条同样适用）。公开前端（D19 第 4 条）可以用 `@jabiz/ui`，也可以完全自行设计。
6. **迁移**：阶段 15a–15d 进行；迁移期间平台分支上 antd 与 shadcn 可以共存，15d 删除 antd，线 1.2 的第一个发布标签之前必须完成。
   示范应用的扩展（`backend/app/admin-extension`）随 15c 迁移。
7. 同步修改：CLAUDE.md 第 2 节"前端"一行；12（随阶段 15 改写）；D22 第 1 条的"一份 React 与 antd"读作"一份 React 与 `@jabiz/ui`"。

**理由**：shadcn/ui 的组件是自己的源码，外观可以完全按产品要求调整，又有 Radix 的可访问行为；它的配套做法（TanStack Table、react-hook-form、react-day-picker、Recharts）
正是平台需要的无头组合，平台继续以元数据驱动表格与表单而不被组件库的数据模型约束；组件源码只放在平台一处，修复随合并到达所有应用。

**放弃的方案**：①继续用 Ant Design 只换主题（外观与体积的问题仍在）；②Radix Themes（外观可调范围有限，缺少数据表格、组合框等组件）；
③MUI、Mantine（又一套重量级组件库与样式方案）；④各应用自行生成 shadcn 组件（各自分叉，平台修复无法到达）；
⑤平台前端发布为 npm 包（D22 放弃方案①的理由仍然成立）。

## D35 事务邮件

**背景**：平台的邮件只用于待办通知与单据发送（18 §5.4、22 §5，CLAUDE.md 第 4 节）。自助注册需要验证邮件、找回密码需要重置邮件，
应用需要"欢迎""转账结果"等通知。这些是通用能力；若各应用自己发信，会重复处理重试、多语言、退订与一次性令牌的泄露问题。
本条扩展 CLAUDE.md 第 4 节"邮件只经待办的通知与单据的发送"一句，补充 D14、D23，不取代其他决策。

**决策**
1. **邮件模板**是 `MailTemplate` Bean：名称、参数名、类别（`TRANSACTIONAL` 不可退订：验证、重置、安全通知；`NOTIFICATION` 可退订）。
   标题与正文写在消息资源 `mail.<名>.subject` / `mail.<名>.body`（应用所选的每种语言；正文为 Markdown，平台渲染为纯文本与 HTML 两部分，参数一律转义，不允许原始 HTML）。
   启动检查：消息齐全、正文中的参数与声明一致。
2. **发送是流程中的平台步骤** `SendMail.of(模板, 收件人, 参数)`：在流程事务内写只追加的 `sys_mail_message`（模板、收件人、语言、遮蔽后的参数）
   并经 Outbox 发布 `jabiz.mail.queued`；平台消费者 `jabiz.mail` 渲染并经 `NotificationSender` 发送，每次尝试写 `sys_notification_attempt`。
   投递、重试与只处理一次沿用 D14（持久的退避重试，不同于 `AFTER_COMMIT` 的进程内重试）。流程回滚即不发信。
3. **一次性令牌在发送时才生成**：模板参数可声明为 `MailParam.oneTimeToken(用途, 有效期)`；消费者发送前生成随机令牌、只存其 SHA-256 与用途、有效期、收件人，
   原文只出现在邮件中，不进数据库、日志与操作摘要。重试发送会生成新令牌并使同一消息的旧令牌失效。验证邮箱与找回密码（D36）用它。
4. **语言**：收件人的语言取用户设置（`SecUser.locale`，新增，缺省为平台缺省语言），流程也可显式给出。
5. **收件偏好**：`NOTIFICATION` 类别按用户与模板可退订（平台时态实体 `SecUserMailPreference`）；邮件附带签名的退订链接（无需登录）；
   `TRANSACTIONAL` 不能退订。
6. `jabiz.mail.enabled` 缺省仍关闭：关闭时消息照常记录、状态为 `SKIPPED`，测试与场景回放据此断言内容；开启而缺少邮件服务器或发件人，启动检查 `MAIL` 报错（同 18 §5.4）。
7. 不做：群发营销、短信、移动推送、模板设计器、打开 / 点击追踪。

**理由**：沿用待办通知已有的发送器与尝试记录，只把"写消息"变成通用步骤并改走 Outbox 以获得持久重试；令牌原文从不落库，读库的人无法激活他人账号；
模板走消息资源，与界面文案同样有三语检查。

**放弃的方案**：①应用在 `AFTER_COMMIT` 中自己发信（进程内重试，重启即丢；各应用重复实现）；②在流程事务内生成令牌并把含令牌的正文存库（读库即可冒用）；
③模板放在数据库中经后台编辑（需要版本、审批与预览，超出当前需要）。

## D36 登录入口、自助注册、邮箱验证、找回密码

**背景**：平台只有管理员开户（10、D12 第 7 条、D28 第 6 条），功能清单明确"不做自助注册"。QuizBuks 的答题人与商家自行注册、验证邮箱后使用，
且答题人 App、商家后台、管理员后台**分开登录**：同一邮箱既是答题人又是商家时，在 App 中不应取得商家权限。
本条取代 10 与功能清单中的"不做自助注册"，补充 D12（会话）与 D28（二次验证、单点登录），不取代其他决策。

**决策**
1. **登录入口**（`jabiz.security.entries.<名>`）：接受的角色、是否允许自助注册、注册时授予的角色、是否要求已验证的邮箱才能登录。
   `POST /api/auth/login`（以及刷新、单点登录、注册）带 `entry`；访问令牌带 `entry` 声明，且**只含该入口所接受角色的权限**；刷新保持入口不变。
   用户没有该入口接受的角色时与密码错误一样返回 401 `LOGIN_FAILED`（不泄露账号存在），并写登录记录。
   未配置入口时只有缺省入口 `admin`，接受全部角色——与现在的行为相同。
2. **自助注册** `POST /api/auth/register`（匿名，按 IP 与邮箱限流）= 流程 `SPONSOR_SIGN_UP`：邮箱未被使用则建用户（状态"待验证"）、授予入口的注册角色、
   发送验证邮件（D35）；邮箱已被使用则不建用户，改发"你已有账号"的邮件（入口的注册角色在用户点击该邮件中的链接、证明拥有邮箱后才追加，即需求中的身份合并）。
   两种情况的响应相同（202），不泄露邮箱是否已注册。密码规则沿用平台（最短长度，BCrypt 在阻塞步骤中计算）。
3. **邮箱验证**：一次性令牌（D35 第 3 条，缺省 24 小时）；`POST /api/auth/verify-email`，可重发（限流）。`SecUser.email` 在非空时唯一（不区分大小写），
   `SecUser.emailVerifiedAt` 只由验证流程写入。访问令牌带 `email_verified`；流程与数据视图可声明 `requiresVerifiedEmail()`，与权限、二次验证同在入口检查（403 `EMAIL_NOT_VERIFIED`）。
   入口可设为"未验证不能登录"。
4. **按邮箱登录**：登录标识可以是用户名或已验证的邮箱。
5. **找回密码** `POST /api/auth/password-reset/request | confirm`：同一令牌机制（缺省 1 小时）；成功后吊销该用户全部令牌族（同 D12 第 1 条的改密码），写登录记录；
   请求的响应不泄露邮箱是否存在。
6. **登录前的应用检查** `SignInGuard`（core，同步）：在密码校验通过后、签发令牌前调用，可拒绝（如 QuizBuks 的封禁），结果 `REFUSED`，写登录记录，不计入失败计数；
   刷新时同样调用（封禁在下一次刷新时生效，同 D12 第 1 条的代价）。
7. **登录记录带来源**：`sec_login_record` 增加 `client_ip` 与 `user_agent`（截断 256 字符）；IP 只在请求来自 `jabiz.security.trusted-proxies` 时取转发头，否则取连接地址。
8. 不做：图形验证码（以后可经 `SignUpGuard` 加入）、手机号注册、注册审批（应用以审批对象表达，如 QuizBuks 的商家入驻）。

**理由**：注册、验证、找回密码与登录一样是写记录的流程，沿用锁定、限流、遮蔽与默认拒绝；入口把"哪个前端接受哪些角色"放在服务端，
令牌只含该入口的权限，一个令牌泄露不会越出它所属的前端；身份合并以证明邮箱所有权为前提，避免冒名注册取得他人账号的角色。

**放弃的方案**：①注册即可用、不验证邮箱（被滥用来刷奖与冒名）；②各应用自写注册接口（安全敏感的逻辑重复）；③引入外部身份服务（Keycloak 等，多一个要运维的服务，
且会话模型与 D12 不同）；④入口只在前端区分（服务端签发的令牌仍含全部权限）。

## D37 入站 Webhook

**背景**：QuizBuks 的充值到账、向用户转账的结果、收款账户状态都由 Stripe 以 Webhook 通知；平台只有出站 Webhook（D33），功能清单明确"不做入站 Webhook"。
接收外部回调涉及验签、重放、重复投递与在请求中执行业务的超时问题，应由平台统一处理。本条取代功能清单中的"不做入站 Webhook"，补充 D14、D33。

**决策**
1. **提供方**写在配置 `jabiz.inbound-webhooks.providers.<名>`：签名方案、密钥（只来自环境变量）、接受的事件类型白名单、时间容差（缺省 5 分钟）。
   签名方案在 core（同步、纯函数）：首先实现 `stripe`（`Stripe-Signature` 的 `t=…,v1=…`，HMAC-SHA256，支持多个 `v1` 以便换密钥）与通用的 `hmac-sha256`（同 D33 的格式）。
   启动检查报告配置的全部问题。
2. **接收** `POST /api/inbound/{提供方}`：匿名，但验签失败、超出时间容差、正文超过 1 MB 一律 400，不存储（只记日志与指标）；
   验签通过后在一个事务中写只追加的 `sys_inbound_event`（提供方、外部事件号唯一、类型、接收时间、原样正文）并经 Outbox 发布 `jabiz.inbound.<提供方>.<类型>`，
   提交后返回 200。同一外部事件号再次到达直接 200（去重）；白名单外的类型 200 且不存储（避免提供方无谓重试）。
3. **处理**由应用以普通的事件订阅（`EventSubscription` → 流程，系统身份）完成：重试、只处理一次沿用 D14；接口请求中不执行业务流程（外部提供方的超时与重试语义不受业务耗时影响）。
4. 原样正文可能含个人信息：`sys_inbound_event` 的读取需要 `inbound.read`，适用保留策略（21 §3）；正文不进操作摘要与日志。
5. 公开接口的限流（15）同样适用于 `/api/inbound/**`。

**理由**：验签与去重在入口一次做完，业务只面对已验证、只投递一次的内部事件；原样存档使对账与排查有据可查；沿用 Outbox 而不新造队列。

**放弃的方案**：①应用自写接收接口（每个应用重复验签与去重，且要开放认证例外）；②在接收请求中同步执行业务流程（耗时与失败直接变成提供方的重试风暴）；
③只存解析后的字段（无法事后核对提供方实际发来的内容）。

## D38 外部调用与异步外部作业

**背景**：06 §2 允许 `BlockingStep` 调用外部 SDK（有副作用的放 `AFTER_COMMIT` 或保证幂等）；D33 第 5 条"出站调用只由平台的这一步骤进行"只针对 Webhook 投递，
但字面上易被理解为一切出站调用。QuizBuks 要调用 Stripe（创建支付页、转账）与 OpenAI（生成题目与封面，耗时数十秒）：
前者短，可在流程中；后者长，放在流程事务中会长时间占用数据库连接。本条澄清 06 §2 与 D33 第 5 条的范围，补充 D11、D14。

**决策**
1. **外部服务**以 `ExternalService` Bean 声明：名称、所需的环境变量（密钥）、超时、重试策略；客户端（官方 SDK 或 JDK HTTP 客户端）由该 Bean 提供给阻塞步骤。
   启动检查：声明的环境变量缺失即报错（`dev` 可放宽为警告）。所有调用经 `PlatformObservations` 记录（标签只放服务名与结果，D16）。
   D33 第 5 条的"不对业务开放"仍只指 Webhook 投递；业务的出站调用只在 `BlockingStep` 中、只经声明的外部服务进行。
2. **短调用**照 06 §2：`BlockingStep`，有副作用的用 `AFTER_COMMIT` 或带提供方的幂等键。
3. **长调用用异步外部作业**：流程中以平台步骤 `StartExternalJob.of(作业类型, 输入)` 登记作业（写 `sys_external_job`，状态行只追加），立即返回作业号；
   平台执行器（多实例以 `FOR UPDATE SKIP LOCKED` 领取，按作业类型限并发）在事务之外调用作业类型的 `ExternalJobHandler`（同步、不访问数据库，与阻塞步骤同样的约束），
   超时与重试按作业类型声明；完成后以系统身份调用声明的**完成流程**（输入为作业号、结果、用量），失败用尽后调用**失败流程**。请求人记录在作业上，完成流程可据此通知。
4. **用量**：处理器可返回用量（如 `promptTokens`、`completionTokens`），记在作业上，供应用统计；平台不做计费。
5. 作业可由请求人取消（尚未领取的直接取消；执行中的在完成后丢弃结果）；`GET /api/external-jobs/{id}` 供请求人查看状态（应用也可以用自己的实体展示）。
6. 不做：工作流编排、流式结果推送、跨作业的依赖。

**理由**：长调用离开数据库事务，连接不被占用；结果仍经流程写入，校验、审计、操作记录照常；领取与重试在数据库中，多实例与重启都安全，不需要另一个队列系统。

**放弃的方案**：①长调用直接放在 `BlockingStep` 中（占用事务与连接数十秒）；②用 Outbox 消费者执行长调用（消费者流程同样在事务中）；
③引入外部队列或任务框架（CLAUDE.md 不引入 Kafka、Redis）。

## D39 OIDC 自动开户

**背景**：D28 第 6 条规定外部账号只能由管理员关联、不自动开户（理由：否则外部身份提供方即可决定谁能进入系统）。
这对内部系统正确，但面向公众的应用（QuizBuks 的答题人用 Google、Apple 注册）需要首次登录即开户。本条修改 D28 第 6 条，其余各条不变。

**决策**
1. 每个提供方可配置 `auto-provision`（缺省 `false`，即 D28 第 6 条的行为）。只有当提供方开启、且登录入口允许自助注册（D36 第 1 条）时才自动开户：
   未知的外部身份 → ID 令牌的 `email_verified` 为真且该邮箱未被任何用户使用 → 建用户（邮箱视为已验证、无密码）、关联身份、授予入口的注册角色，写登录记录。
2. 邮箱已被使用时**不自动关联**（防止以外部账号接管已有账号）：拒绝并提示用原方式登录后，在账户设置中自行关联（新流程 `SEC_IDENTITY_LINK_SELF`，要求当前会话已认证且近期完成二次验证或重新输入密码），
   或由管理员关联（D28 第 6 条）。
3. **Apple 提供方**：客户端密钥是以 ES256 签名的短期 JWT（团队号、密钥号、私钥均来自环境变量，平台按需生成）；回调为 `response_mode=form_post`（回调接口接受 POST）；
   只在首次授权时给出邮箱，私密中继邮箱照常视为邮箱。Google 按标准 OIDC。
4. 自动开户的用户与自助注册的用户相同：受入口、`SignInGuard`、锁定与二次验证规则约束。

**理由**：开户的决定权仍在平台：只有显式开启的提供方、允许注册的入口、已验证且未被占用的邮箱三者同时满足才开户；已有账号永远需要其拥有者证明身份后才能关联。

**放弃的方案**：①按邮箱自动关联已有账号（外部提供方的邮箱声明即可接管账号）；②所有提供方一律可开户（内部系统不应如此）。

## D40 受控的业务参数

**背景**：QuizBuks 的创作者分成比例、提现门槛等参数要求只经平台的受控变更修改（D23 第 2 条：提出人与发布人不同）。
但受控变更只覆盖审批规则、审批人限额与职责分离规则；业务参数（D13、04 §9）任何持有 `platform.param.write` 的人都可以一个人修改、预定或取消。
本条补充 D13 与 D23，不取代任何决策。

**决策**
1. **以代码声明受控的键**：应用以 Bean `ControlledParams.of(键…)`（core `com.jabiz.param`）事先声明；可有多个 Bean，键可以尚不存在。
   是否受控只在代码中，参数的数据里没有标记——因此运行时没有任何途径（包括持有全部权限的一个人）能解除受控，解除即改代码、经评审与部署。
2. **受控键的一切写入只经发布的受控变更**：平台在 `VersionAppender`（所有时态写入的必经之处）中检查——`PARAM_CREATE` / `PARAM_SET` / `PARAM_SCHEDULE` /
   `PARAM_CANCEL_SCHEDULED`、数据视图 API、通用实体流程、其他流程的 `ChangeSet`、撤销操作写入受控键的版本一律 422 `PARAM_CONTROLLED`，
   只有操作为 `CONTROL_CHANGE_PUBLISH` 的写入放行。新建、删除、改键（键本来不可变）同样被拒，所以也不能"删掉重建"来绕过。
3. **受控变更以参数为目标**：`CONTROL_CHANGE_PROPOSE` 的 `targetEntity: SysParam`，以 `values.paramKey` 指定参数（不用 `targetId`）；
   `values` 可有 `value`、`description`，参数尚不存在时另给 `valueKind` 即新建；`effectiveTime` 为预定时间（须晚于当时，否则 422 `EFFECTIVE_TIME_NOT_FUTURE`）；
   `delete: true` 加 `effectiveTime` 取消该时刻的预定值。只有受控的键能这样修改（其他键照常用参数流程）。提出时即按参数的类型检查并规范化值（422 `PARAM_VALUE_INVALID`），
   其他问题一次报告（422 `CONTROL_CHANGE_INVALID`）；`CONTROL_CHANGE_PUBLISH` 由他人发布（`CONTROL_SAME_PERSON`），按生效时刻的版本再检查一次，经普通的参数版本写入（历史、生效时间、审计照常）。
   发布时生效时间已过的变更不再发布（重新提出）。
4. **启动检查 `PARAM`**：声明的键格式不对（小写字母数字的词，以 `.` `-` `_` 连接，至多 200 字符）即报错，全部一次报告；尚不存在的键不是问题。

**理由**：受控与否是部署时的决定，和审批对象、职责分离规则的代码声明一样经过评审；检查放在所有时态写入的必经之处，
新的写入途径无需各自记得检查。受控变更已有提案、发布、撤回与"提出人不能发布"，参数只是又一种目标。

**放弃的方案**：①`PARAM_CREATE` 带"受控"标记存在数据里（解除标记又需要自己的四眼途径，应用也不能事先声明）；
②只在四个参数流程中检查（数据视图、通用实体流程、撤销可绕过）；③把参数数据视图整体设为 `processOnlyWrites`（改变所有未受控参数的行为）；
④受控参数另设审批流程（与已有的受控变更重复）。
