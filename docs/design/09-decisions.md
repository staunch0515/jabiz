## D1 预定版本的变基规则

**背景**：实体有一个将在 T2 生效的版本 V（完整快照）。之后写入一个生效时间为 T1（T1 < T2）的修改。
若不处理，到了 T2，V 会把这次修改的字段恢复成旧值。

**决策**
1. 写入生效时间为 T 的新版本时，找出该实体所有**生效时间 > T 且尚未被覆盖**的版本，按生效时间升序逐个处理。
   这既包括将来的预定版本，也包括追溯更正时位于 T 与当前之间、已经生效的版本。
2. 每个待处理版本 V 的修改字段集合 F(V) 取自它的 `op_process_item.changed_fields`。
   - 本次修改的字段与 F(V) **无交集**：插入 V 的变基副本 = "新的前一状态 ⊕ V 在 F(V) 上的值"，生效时间与 V 相同，
     `version_no` 更大（相同生效时间下胜出），`action = REBASE`。下一个待处理版本以这个副本作为前一状态。
   - **有交集**：拒绝本次写入（409），错误中列出冲突的版本（生效时间、所属操作）。调用方必须先取消或修改该预定。
3. **墓碑版本**（删除）不参与字段冲突判断：它的变基副本仍然是墓碑，不会因为前面的修改而复活。
4. 变基副本与本次写入属于同一个操作（同一个 `process_seq_id`），同样写入 `op_process_item`。

**理由**：自动保留两边互不相干的修改；真正冲突时交给人判断，不做隐式覆盖。

**放弃的方案**：①不处理（会静默丢失修改）；②有冲突时"后写入者胜"（会静默改变已经确认的预定）；
③限制每个实体只能有一个预定版本（过于严格，价格、费率常有多个排期）。

## D2 撤销操作的冲突检测

**决策**
1. 撤销是一个**新的操作**，`reverts_seq_id` 指向被撤销的操作 P。
2. 冲突判断以**字段**为粒度：对 P 写入的每个实体，若 P 之后（按 `process_seq_id` 顺序）有其他操作修改过 P 所修改的任一字段，
   则拒绝整个撤销（409），列出阻塞的后续操作。调用方可以先撤销这些后续操作（按从新到旧的顺序），再撤销 P。
3. 恢复方式：
   - P 的 `UPDATE`：插入新版本，把 P 修改的字段恢复为 `base_version_no` 时的值（其他字段保持当前值）；
   - P 的 `INSERT`：插入墓碑版本；此时 P 之后对该实体的**任何**修改都视为冲突；
   - P 的 `DELETE`：插入恢复版本，内容为墓碑之前的状态；
   - P 产生的 `REBASE` 版本：与 P 的主版本一起按上述规则恢复。
   - 恢复版本的生效时间与被撤销版本的生效时间相同；若因此需要变基，按 D1 处理（冲突同样拒绝）。
4. P 若有子操作，按相反顺序一并撤销，全部在一个事务内完成；任一冲突则整体拒绝。
5. 撤销一个撤销操作（即"重做"）按同样规则处理，允许。
6. 撤销需要专用权限并必须填写原因。

**理由**：字段粒度的判断既能允许"后续只改了无关字段"的常见情况，又不会覆盖别人的后续修改。

## D3 数据视图范围在取得当前版本之后过滤

**决策**：对时态实体，所有查询（实体查询、计数、SQL 模板中的 `{{Entity}}`）一律先在内层用
`DISTINCT ON` 取得 `asOf` / `knownAt` 条件下的版本，**再在外层**依次应用：墓碑排除 → 数据视图范围 → 查询条件。

**理由**：若范围条件放在内层，一个已经被移出范围的实体会"退回"显示它还在范围内时的旧版本，造成越权或脏读。

**附带要求**：平台生成的 SQL 中，范围条件出现在内层视为缺陷；阶段 4 的测试必须覆盖"移出范围后不可见"。

## D4 操作表本身也只追加

**决策**
1. `op_process`、`op_process_item`、`op_process_result`、`entity_registry` 均只追加，同样受 D5 的触发器保护。
2. 不存在"状态"列的更新：撤销、重做都是新的操作记录。
3. 流程输出需要保存（用于幂等重放）时，写入单独的 `op_process_result` 表，在流程结束时、同一事务内插入：

```sql
CREATE TABLE op_process_result (
    process_seq_id  bigint PRIMARY KEY REFERENCES op_process,
    output          jsonb  NOT NULL          -- 敏感字段遮蔽
);
```

   （`op_process` 在流程开始时插入，那时还没有输出；为了不更新它，输出放在独立的表里。）
4. 带 `Idempotency-Key` 的重复请求：在 `op_process` 中按 `(actor_id, idempotency_key)` 找到原操作，返回其 `op_process_result.output`，不重复执行。

**理由**：操作记录是审计与追溯的依据，它自己不能被改写。

## D5 数据库触发器拒绝时态表的修改和删除

**决策**
1. 提供通用触发器函数 `jabiz_reject_mutation()`；每张时态表和 D4 中的操作类表都创建：
   - 行级 `BEFORE UPDATE OR DELETE` 触发器；
   - 语句级 `BEFORE TRUNCATE` 触发器。
   触发器抛出带固定错误码的异常，平台将其转为 500 并记录为严重错误（这意味着代码中有缺陷）。
2. 唯一的例外是**受控清除流程**（个人信息删除、归档）：该流程在事务内执行 `SET LOCAL jabiz.maintenance_mode = 'purge'`，
   触发器仅在该会话变量为 `purge` 且当前数据库角色属于维护角色时放行；每次清除必须写入清除记录（本身也是一次操作）。
3. 启动自检检查每张时态表上两个触发器都存在。
4. 普通业务数据库账号不授予维护角色。

**理由**：应用层的约定可能被绕过（手写 SQL、运维脚本、将来的新代码）；数据库层兜底，保证"只追加"真正成立。

## D6 时态实体的唯一性用咨询锁加检查实现

**决策**：对声明了 `eb.unique(name, fields...)` 的时态实体，写入时：
1. 在事务内执行 `pg_advisory_xact_lock(key)`，`key` 为 `(实体类型, 约束名, 规范化后的字段值)` 的 64 位哈希。
2. **取锁之后**再查询（必须是取锁后的新语句，才能看到前一个持锁者已提交的数据）：
   是否存在**当前生效版本或尚未生效的预定版本**使用了相同的值（排除实体自身、排除墓碑）。
3. 存在则返回违规 `UNIQUE_VIOLATION`（400，随其他违规一起累积返回）。

**说明**
- 哈希冲突只会导致不相干的写入多等一会儿，不会影响正确性（第 2 步仍然按真实值查询）。
- 把预定版本也纳入检查，是为了防止"某个名字已经预定给别人，现在又被另一个实体占用"，导致到期时出现重复。
- 规范化规则（大小写、首尾空格等）由约束声明决定，默认原样比较。

**放弃的方案**：①在历史表上建唯一索引（历史版本会互相冲突）；②只靠当前快照投影表的唯一索引（MVP 不引入投影表，且无法覆盖预定版本）。

## D7 SQL 模板中的列表参数统一使用 `= ANY(:name)`

**决策**
1. 列表参数在模板中一律写成 `列 = ANY(:name)`（取反用 `列 <> ALL(:name)`），头部声明 `list: true`。
2. 平台按参数的语义类型把列表转换为对应的数组（如 `String[]`、`UUID[]`、`BigDecimal[]`、`Instant[]`）后绑定。
3. 禁止 `IN (:name)` 写法；`platformCheck` 发现后报错。
4. 空列表：`= ANY` 空数组结果为假，`<> ALL` 空数组结果为真，语义符合预期，平台不做特殊处理。

**理由**：一个参数对应一个占位符，渲染后的 SQL 形状固定，可以用 JDBC 预编译做静态校验；也避免列表过长时生成超长 SQL。

## D9 时态模型的实现细则

**背景**：阶段 4 实现时需要确定 D1、D2、D5 没有写明的细节。本条只补充，不取代任何已有决策。
阶段 4 计划确认了第 1、2、4、6–10 条及第 3、5 条的前半；标注【待确认】的内容是实现中发现问题后新增的，需在 PR 评审中确认。

**决策**
1. **版本号与并发**：新版本的 `version_no` = 该实体已有的最大 `version_no + 1`（存在预定版本时 `n + 1` 可能已被占用）。
   调用方提交的 `version` 是"本次生效时间点上生效的版本"的 `version_no`（读取时用同一 `asOf` 即可得到）；
   不一致时 409。并发写入同一实体时都会插入同一个"最大值 + 1"，由 `UNIQUE(entity_id, version_no)` 拦下，409。
2. **`op_process_item.action` 与 `changed_fields`**：
   - 新增 `CANCEL`（取消预定，04 §4.1）：内容为被取消版本之前的状态（没有之前的状态时为墓碑），`base_version_no` 为被取消的版本，
     `changed_fields` 记录被取消版本的字段（撤销取消时据此恢复）。
   - `INSERT`、`DELETE` 的 `changed_fields` 为全部可修改字段（主键和系统字段除外）。
   - `REBASE` 副本的 `changed_fields` 为变基时实际带过去的字段。
3. **变基时一个生效时间点带过去的字段**（D1 第 2 条中的 F(V)）：同一生效时间的版本彼此叠加（更正、变基副本），
   取它们 `changed_fields` 的并集（遇到 `CANCEL` 重新开始）【待确认：属性测试发现，只看胜出版本的 `changed_fields`
   会丢失同一时间点更早版本的修改】，再只保留在该时间点的值与该时间点之前的值**确实不同**的字段【待确认：否则已被撤销的修改
   会继续造成变基冲突，使"先撤销后续操作再撤销 P"无法完成】。
4. **删除与变基**：删除（写墓碑）之后若还有非墓碑版本（例如预定修改），按冲突拒绝（409）；之后的墓碑照常复制为墓碑。
5. **撤销的冲突判断**（补充 D2 第 2 条）：后续操作的 `REBASE` 条目不算修改；后续操作若之后已被撤销，它与撤销它的操作一起抵消，
   不再阻塞（即 D2 所说"先按从新到旧撤销后续操作，再撤销 P"可以成立）【待确认：实现中新增】；撤销的撤销（重做）使被撤销的操作重新计入。
   撤销按实体的默认数据视图定位存储，不施加数据视图范围，要求实体与操作表位于同一存储。
6. **权限码**（默认拒绝，403 `PERMISSION_DENIED`）：`temporal.backdate`（追溯更正）、`temporal.revert`（撤销、重做）、
   `operation.read`（操作详情）。
7. **按时间点读取**：`allowTimeTravel(false)` 同时禁止 `asOf`、`knownAt` 与历史接口（400 `TIME_TRAVEL_NOT_ALLOWED`）。
   历史接口只在实体最新状态（含墓碑）位于数据视图范围内时返回，否则 404。
8. **受控清除**（补充 D5）：维护角色固定名为 `jabiz_maintenance`，由运维创建（迁移脚本不建角色）；触发器拒绝时抛出 SQLSTATE `JZ001`，
   平台转为 `AppendOnlyViolationException`（500，记录 error 日志）。时态表用 `SELECT jabiz_protect_append_only('<表>')` 安装两个触发器。
9. **操作的产生**（阶段 6 之前）：数据视图 `commit` 及现有通用增删改流程只在本批包含时态实体时写 `op_process`；
   已有操作（Reactor Context 中的 `Operation`）时加入该操作（此时不能再给出不同的 `reason`：操作记录不可更新）。
   `op_time` 取 `Clock` 并截断到微秒（与数据库精度一致）。通用流程沿用自己的 `processSeqId` 与流程名，同一流程的多次提交加入同一操作。
   自行开始操作的 `commit` 把输出摘要（实体类型、主键、版本号，不含字段值）写入 `op_process_result`；
   完整输出与遮蔽随阶段 6、7 接入。
10. **数据库字典**：时态表为 `sys_dict_item_version`（平台实体 `SysDictItem`，允许预定，唯一约束 `(dictUrn, itemCode)`）；
    `sys_dict_item` 改为当前项的只读视图，`INSERT` 经 `jabiz_dict_put(...)` 写入**基础数据**（生效时间与记录时间都为 1970-01-01，
    不读取数据库时钟；用于迁移种子），
    已有更晚版本的项拒绝经 SQL 修改。`labels` 使用扩展语义类型 `jabiz.labels`（jsonb）。缓存到下一个预定版本生效时自动过期。

11. **存储与引用**：时态实体不能使用 `physicalTableOverride`（版本、操作条目与撤销都指向实体自己的表，启动时检查）。
    指向时态实体的引用字段以 UUID 保存与比较（写入与查询时转换）。删除前的"仍被引用"检查同时查看引用方的当前版本与预定版本。

**理由**：这些都是 D1–D6 在真实数据上成立所必需的细节；写明以便后续阶段（流程引擎、账本、前端）遵守同一语义。

## D10 SQL 模板中的每个实体都经数据视图渲染

**背景**：阶段 4 之前，模板执行时只给"调用方传入的那个数据视图"的目标实体附加范围，模板中的其他实体渲染为裸表
（时态实体只包装当前版本）。手写 SQL 因此可以通过第二个实体绕过其默认视图的范围与逻辑删除。

**决策**
1. 模板中的每个 `{{Entity}}` 都按一个数据视图渲染：头部 `datasets: {实体: 视图 id}` 指定的视图，未指定的实体用其**默认视图**。
   渲染内容与实体查询相同：范围、逻辑删除排除；时态实体先取当前版本，再在外层依次排除墓碑、施加范围（D3）。
2. 视图必须存在且以该实体为目标；同一模板涉及的视图必须位于同一存储（主库与读库都相同），在启动时检查。
   有读库时模板走读库。行数上限取各视图 `maxQueryBatchSize` 的最小值，超时取各视图与 `timeoutMs` 的最小值；
   `timeoutMs` 必须短于各视图的超时。
3. 范围值取自调用方的 `RequestContext`，取不到即拒绝（403 `SCOPE_UNAVAILABLE`），与数据视图 API 相同。
4. `SqlDictionary` 的 `datasetId` 表示其目标实体经该视图读取（相当于 `datasets` 中的一项）；它以系统身份在平台内部执行，
   不经模板 API，不需要声明权限。

**理由**："所有读写都经过数据视图"（03 第 1 节）对手写 SQL 同样成立；否则验收"手写模板无法读到范围外的数据"只对一个实体成立。

**放弃的方案**：只对调用方指定的视图加范围（现状；其他实体会越权）；要求每个模板为全部实体显式指定视图（冗长，且默认视图已经表达了通用访问方式）。

## D11 流程引擎的实现细则

**背景**：阶段 6 实现流程引擎时需要确定 06 与 D4 没有写明的细节。本条只补充，不取代任何已有决策；
D9 第 9 条原本就只描述"阶段 6 之前"的操作产生方式，数据视图 `commit` 的行为不变。

**决策**
1. **每次流程执行都是一个操作**：不论是否涉及时态实体，流程开始时（在它的事务内）写入 `op_process`，结束时写入 `op_process_result`
   （输出的 JSON；遮蔽随阶段 7）。`input_summary` 在阶段 7 接入遮蔽之前留空。子流程同样写这两行，`parent_seq_id` 指向父流程，`op_time` 相同。
2. **权限在调用入口检查**：流程 API 要求调用方具备流程声明的全部权限（403 `PERMISSION_DENIED`；未声明时只有 `dev` 下放行）。
   `ProcessExecutor` 与传输方式无关，不检查权限（定时任务、场景回放以显式的 `RequestContext` 调用它）；子流程不另行检查。
   流程中的 `RunTemplate` 不检查模板自身的权限，数据视图范围照常施加（D10）。
3. **`AFTER_COMMIT` 步骤**：在根流程的事务提交之后按声明顺序执行（子流程的这类步骤推迟到根流程提交后）；
   失败不影响已提交的数据与响应。按步骤的 `RetryPolicy`（默认 3 次，200 ms 起指数退避）在进程内重试，每次尝试追加一行到只追加的
   `op_process_after_commit`（受 D5 触发器保护），用尽后记 error 日志。**不做持久化重试**：需要可靠投递时使用 `PublishEvent`（阶段 9 的 Outbox）。
   `AFTER_COMMIT` 步骤登记的变更不会被提交（记为该次尝试失败）。
4. **幂等**：`Idempotency-Key` 须匹配 `[A-Za-z0-9._:-]{1,128}`（否则 400 `INVALID_IDEMPOTENCY_KEY`）。执行前按 `(actor_id, idempotency_key)`
   查找并重放；并发的重复请求在插入 `op_process` 时被唯一约束阻塞，第一个事务提交后得到唯一约束冲突，平台随即重放第一个结果，
   第一个事务回滚时则正常执行——因此同一键只执行一次。同一键用于另一个流程名时 409 `IDEMPOTENCY_KEY_REUSED`。
   重放返回原操作的 `processSeqId`，响应头 `Idempotency-Replayed: true`。
5. **一个流程一个存储**：流程事务开在操作表所在的存储（`jabiz.storage.default-pool-ref`）上；变更经由其他存储的数据视图提交时报错，
   不会悄悄变成第二个事务。变更只能经由以该实体为目标的数据视图提交（缺省为实体的默认视图）。
6. **违规**：所有 `IN_TX` 步骤执行完后若 `violations()` 非空，422 返回全部违规且不提交；某个步骤（例如子流程）抛出 422 时，与此前已累积的违规合并返回。
   `SaveChanges` 在已有违规时拒绝提交。

**理由**：流程是"一次操作"的单位（06 §1），审计与撤销需要每次执行都有记录；权限放在入口使执行器可被非 Web 调用方复用；
进程内重试足以覆盖短暂故障，可靠投递留给 Outbox，避免为持久化上下文另建一套机制。

**放弃的方案**：在执行器中检查权限（定时任务与场景回放需要伪造权限）；`AFTER_COMMIT` 失败时让响应失败（数据已提交，会误导调用方重试）；
把重试状态写成可更新的表（违反 D4 的只追加原则）。
