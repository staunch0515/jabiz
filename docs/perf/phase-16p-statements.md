# 16p 每个事务的语句数与发货的吞吐：16p-1 前后（决策 D46）

2026-10-17，分支 `1.2/phase-16p1-ledger-post-local`。"前"是 `05f953d`（= `961b4b3`，16o 合入后，加 16p 计划），"后"是 16p-1（T1–T8；不含 T9 的写缓冲）。
目的：同样的保证下，`LEDGER_POST`、`ORDER_SHIP` 等路径每个事务的往返语句减少多少，单个实例的吞吐随之如何变化。这是本机的短时测量，用于前后比较，不是容量数字。

## 环境与做法

- 一台 4 核的开发容器，PostgreSQL 16、应用（`./gradlew :app:bootJar` 的 jar）与压测客户端同机，连接池为缺省的 10 个连接；前后各用一个新建的数据库。
- **语句数**：两种来源，结果一致。
  1. `StatementBudgetIT`（`SqlStatementLog` 按连接与事务分组，断言确切值；计数含 `COMMIT`，不含 `BEGIN`）。"前"的数字是在本分支加入该测试、尚未改代码时实测的。
  2. 压测时的 PostgreSQL 语句日志：专用库 `ALTER DATABASE … SET log_statement = 'all'`，按后端进程从 `BEGIN` 到 `COMMIT` 分组，以事务中第一条 `INSERT INTO op_process` 的流程名归类（8 秒的短跑，日志开着时不计时）。
- **吞吐**：`app` 的 `loadTest` 新增的发货模式：

  ```
  LOAD_PRODUCTS=200 LOAD_WAREHOUSES=2 LOAD_ORDERS=200 LOAD_CONCURRENCY=16 LOAD_DURATION=60s LOAD_WARMUP=10s \
  LOAD_SCENARIOS=ship LOAD_SHIP=yes ./gradlew :app:loadTest
  ```

  16 个客户端各自反复下单（1–3 行）再发货；发货取订单锁、扣库存、以子流程 `LEDGER_POST` 记销售（应收 1130 / 销售收入 4120，来源单据为订单）。下单与发货分开计时。前后各跑两轮，交替进行。

- 发货 ≈ 52 → 77 次 / 秒（+48 %），p50 205 → 129 ms（−37 %）；下单 ≈ 55 → 82 次 / 秒（+47 %），p50 89 → 67 ms。
- 评审修正（按登记顺序的 `WITH` 写出、字典经存储引擎读、触发器检查等）后再测一轮（首轮，含预热）：语句数不变（`StatementBudgetIT` 照旧通过），吞吐与延迟在两轮“后”的波动范围附近。
- 409 是同一库存行上的版本冲突（各客户端随机挑选的 200 种产品、2 个仓库，彼此相撞），前后比例相近（约 4–7 %）。
- 第一轮的最大值（约 1.1 s）出现在两边的开头（JIT 与连接池预热），第二轮没有。
- 语句数降到约三分之一，吞吐只提高约一半：同机的数据库与应用 CPU 共享 4 核，大语句（一条写十几行）的执行时间也比单行插入长（计划中的"模型偏乐观"）。

## QuizBuks 提交的预估（Q10a §4.2 的形态）

锁内的语句（取得发布锁之后到 `COMMIT`），按本阶段实测的各部分数字：

| 部分 | 前 | 16p-1 后 | 依据 |
|---|---|---|---|
| 发布锁之后恢复 `lock_timeout` | 1 | 0 | T1：与事务相同的上限只发取锁语句 |
| 重读会话、计数、卡片（应用） | 3 | 3 | 应用的改动不在本阶段；改用 `QueryEntities.all` 后为 1 |
| 钱包锁 | 4 | 1 | `HoldLock` 预算 |
| 读钱包 | 1 | 1 | |
| `LEDGER_POST`（子流程，2 条分录、2 个实体维度、来源） | 27 | 5 | `LEDGER_POST` 子流程预算 |
| 事件（`PublishEvent`） | 1 | 1 | 16p-2 才缓冲 |
| 写会话、计数、钱包（普通实体，均在本事务中读过） | 9 | 3 | 按已知版本更新预算（每次 1） |
| 幂等结果 | 1 | 1 | |
| `COMMIT` | 1 | 1 | |
| **合计** | **48** | **16**（应用改用 `QueryEntities.all` 后 14） | |

按 Q10a 测得的锁内每条语句约 0.78 ms，提交的锁内时间约 37.5 ms → 约 12.5 ms（未计大语句的额外执行时间；计划的估计为 16.5 ms）；开始的锁内 12 → 6–7 条。
计划的模型（开始 + 提交的锁内时间约 23 ms）对应单个热门发布约 38–43 次 / 秒；**以 QuizBuks 在 Q10 应用分支上的重测为准**（P-10：锁拆分在重测之后再定）。

## 限制

- 同一台机器运行数据库、应用与压测客户端；单个实例；短时测量。绝对数字偏低，只比较前后。
- 示范的发货锁内工作较少；锁内时间的收益在热门锁（QuizBuks）上最明显，那里的验收在 Q10 判定。
- T9（事务内写缓冲）不在本次：事件、幂等结果、子流程的操作记录与 `LEDGER_POST` 的写入仍各自一条（16p-2 的预算：子流程 ≤ 2、根流程 ≤ 5、`ORDER_SHIP` ≤ 12）。
