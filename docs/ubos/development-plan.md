# UBOS 数字业务芯片平台 · 第一版开发计划（v0.1）

依据：《UBOS 数字业务芯片平台 · 第一版规划书》（2026-09-30）。
本文件回答两个问题：**在 jabiz 上开发还是新建仓库**；以及**从零开始的分阶段开发计划**。
规划书会持续补充，本计划按第 10 节的方式随之修订（版本号递增，变更写在末尾的修订记录）。

> 本文件暂存于 jabiz 仓库的 `docs/ubos/`，一旦新仓库建立，应作为新仓库 `docs/plan/` 的第一个提交迁走，jabiz 中的副本删除。

---

## 1. 结论：新建独立仓库，不在 jabiz 上开发

### 1.1 判断依据

jabiz 是一个**面向企业中后台、元数据驱动、以数据正确性为核心**的业务应用平台（约 5.5 万行 Java，WebFlux + R2DBC，
双时态只追加存储，每次写入都是一个事务内的流程，启动自检、场景回放、审计封存等）。UBOS 第一版是一条
**"需求 → 芯片匹配 → AI 生成 → 冒烟测试 → 打包下载"的流水线网站**，核心负载是调用大模型、在沙箱里跑 Claude Code、
构建与启动容器、跑冒烟测试、打包文件。两者的"重活"完全不同。逐项对照：

| 维度 | UBOS 第一版需要什么 | jabiz 提供什么 | 匹配度 |
|---|---|---|---|
| 核心工作单元 | 长时间（分钟级到十分钟级）的异步任务：LLM 调用、Claude Code 会话、`docker compose` 构建与启动、冒烟测试、带上限的重试循环，中途要向用户推送进度 | 流程 = 一次短事务（06 §4，D11）：`ComputeStep` 禁止 I/O，`BlockingStep` 禁止访问平台数据库，外部副作用只能放在 `AFTER_COMMIT` 且只在进程内重试；定时任务只能"调用流程" | **不匹配**。要在 jabiz 上做，得先给平台新增"异步长任务 + 进度流 + 沙箱执行"这一整层，而这正是 UBOS 的主体 |
| 用户界面 | 面向非技术用户的向导式页面：输入需求、逐条确认功能清单、看匹配结果、看生成进度与日志、下载 | 由元数据生成的 AntD 后台（列表 / 表单 / 历史）；"元数据表达不了的工作流"要写扩展页面（12 §9，D22） | **低**。向导页全部是扩展页面，元数据生成的页面几乎用不上 |
| 数据模型 | 十来张简单表：用户、项目、需求版本、功能条目、芯片与数据手册、匹配结果、生成运行记录、产物 | 双时态只追加实体、撤销、审计记录、HMAC 封存、保留期、审批、账本、单据、报表、导入… | **过重**。这些能力第一版一个都不需要，但平台规则要求业务对象默认做成时态实体、每次写入经流程、审计记入 `sys_audit_record` |
| 技术栈 | 生成的应用是 React + Node.js + TypeScript；项目模板、冒烟测试框架、Claude Agent SDK（TypeScript）都在 TS 一侧 | JDK 21 + Spring WebFlux；业务模块禁止 `reactor.*`；请求路径禁止阻塞（BlockHound） | **不匹配**。会出现"Java 网站 + Node 工作进程"两套栈，而第一版的目标是用最少的东西验证流程 |
| 开发纪律 | 规划书：**"用最简单、最理想化的条件验证流程能跑通，凡是复杂的问题一律不考虑"** | CLAUDE.md：先改设计文档再改代码、决策 D1–D31 具有约束力、三种语言文案、覆盖率门禁、场景回放快照、`platformCheck`、每阶段先出计划 | **方向相反**。这些纪律对企业系统是资产，对一个要快速验证假设的网站是摩擦 |
| 分支模型 | 一个独立产品 | 应用分支不得改平台目录；平台缺的能力要先在平台分支做、带平台自己的测试与示范，再合并到应用分支（17 §1） | **成本高**。UBOS 需要的"异步任务 / 沙箱 / 进度流"都是平台缺的，每一项都要走两遍 |
| 安全模型 | 要运行 AI 生成的代码与容器：沙箱隔离、资源与费用上限、网络出口限制 | JWT、TOTP、OIDC、RBAC、字段遮蔽、数据期限（都很好，但第一版不需要） | **各管各的**。jabiz 没有沙箱；UBOS 第一版不需要 jabiz 的安全深度 |

结论：在 jabiz 上做，相当于用 5.5 万行与 UBOS 无关的平台代码和一整套纪律去承载一个 1 万行左右的流水线网站，
而 UBOS 真正的难点（沙箱、长任务、LLM 可靠性）jabiz 一点也没有。**两者没有共享的核心，只有共享的作者。**

### 1.2 从 jabiz 带走什么（思想，不是代码）

- **工作方式**：`CLAUDE.md` + `docs/design/` + 具有约束力的决策记录 + 路线图分阶段、每阶段先出计划再写代码。UBOS 新仓库沿用这套方式，但规则条数控制在一页以内。
- **"启动即失败"**：数据手册、项目模板、提示词包的不一致在服务启动（或 CI）时一次性全部报告。
- **固定输入 + 快照对比的回放测试**：把 LLM 的响应录下来回放，让流水线测试确定、可重复、不花钱。
- **一条命令启动**：`docker compose up` 既是 UBOS 自己的部署方式，也是交付给客户的方式。
- **前端工具链**：pnpm、React 19、TypeScript、Vite、TanStack Query、React Router、Vitest、Playwright 与 jabiz 相同，团队不换工具。

### 1.3 以后什么时候可能用到 jabiz

规划书"范围之外"里的**收费、芯片授权、客户与订单管理**，是典型的 jabiz 业务（金额、审批、账本、单据）。
如果以后做到那一步，可以让 UBOS 网站调用一个独立部署的 jabiz 应用（通过接口），而不是把 UBOS 搬进 jabiz。现在不做。

## 2. 需求理解（来自规划书）

### 2.1 第一版要做的事

一个网站，把下面的流水线串起来，中间两道人工/自动关口：

```
需求输入（自然语言） → 需求整理（AI 整理成功能清单） → 【关口 1】用户逐条确认
→ 芯片匹配（逐条对照数据手册） → 【关口 2】全部功能可映射？否 → 项目终止
→ AI 生成（Claude Code 在沙箱中生成前端与胶水代码） → 冒烟测试（启动全部服务，逐条调用功能）
→ 失败则把错误回传给 AI 修复，重试次数有上限 → 打包下载（源码 + 芯片镜像 + docker-compose）
```

固定条件：

| 维度 | 第一版 |
|---|---|
| 芯片调用方式 | 只用 sidecar：芯片是独立进程，对外提供 HTTP 接口 |
| 芯片数据 | 每枚芯片内嵌自己的 SQLite |
| 生成应用的技术栈 | 只有一套：React + Node.js，全部 TypeScript |
| 部署方式 | `docker compose` 一条命令启动（客户装 Docker Desktop 即可） |
| 业务场景 | 一个：小型网店的订单管理 |
| 芯片选择 | 场景固定，不让客户选芯片类型 |
| 首批芯片 | 商品、库存、订单（订单调用另外两枚） |
| 交付物 | `ubos-shop-app.zip`：`docker-compose.yml`、`start.sh` / `start.bat`、`README.md`、`app/`、`chips/*.tar` |

验证顺序（规划书"验证计划"）：**先做芯片 → 再手动验证 AI 生成（不建网站）→ 最后做网站**。第 2 步不成立就不进入第 3 步。
本计划的阶段划分严格遵守这个顺序。

### 2.2 本项目的范围边界

- **范围内**：网站、流水线、数据手册的格式与校验、项目模板、提示词、沙箱、冒烟测试框架、打包、客户侧启动脚本、桩芯片（见 2.3）。
- **范围外**：三枚芯片本身（Rust 开发）；规划书"范围之外"表中的全部事项（FFI/WASM、多技术栈、外部数据库、授权、升级迁移、跨芯片事务、SBOM、收费）。
- **与芯片团队的接口**（本项目负责定义、芯片团队负责遵守）：数据手册格式、镜像交付方式、健康检查、配置项约定。见 4.3。

### 2.3 为了不被芯片进度卡住：桩芯片

芯片开发不在本项目内、进度不可控。本项目自己做三枚**桩芯片**（Node.js 小程序，实现与数据手册完全相同的 OpenAPI 接口，
数据存内存或 SQLite），用来开发和测试流水线。真芯片交付后替换镜像，用同一套契约测试同时验证桩与真芯片。
桩芯片**不是**产品的一部分，不交付给客户。

### 2.4 规划书没有写明、需要补充的事项（开放问题）

以下按本计划的默认假设先做，得到答复后再调整：

| # | 问题 | 本计划的默认假设 |
|---|---|---|
| Q1 | 网站部署在哪里？沙箱需要能跑 Docker 的主机 | 一台自有 Linux 服务器（或云主机），网站与工作进程同机，`docker compose` 部署 |
| Q2 | 用户体系：第一版要注册吗？ | 邮箱 + 密码登录，**邀请码开户**（不开放注册），一个用户多个项目 |
| Q3 | 芯片镜像由谁提供、怎么交付？ | 芯片团队交付 `docker save` 的 tar 与 `datasheet.yaml`，由管理员在网站后台登记 |
| Q4 | 每次生成的费用与时间上限？ | 单次生成 LLM 费用上限、总时长上限、重试 3 次，都是配置项 |
| Q5 | 下载包大小能接受多少？三枚芯片镜像可能上百 MB | 第一版直接打进 zip，不做增量 |
| Q6 | 客户是 Windows 还是 macOS/Linux 为主？ | 两者都给启动脚本（`start.bat` / `start.sh`），Windows 以 Docker Desktop + WSL2 为前提 |
| Q7 | 界面语言 | 第一版只做中文；文案集中在消息资源里，以后加语言不改代码 |
| Q8 | 需求输入支持什么？纯文本？能上传文件吗？ | 纯文本（多行），不上传文件 |
| Q9 | 功能清单"用户修改"的粒度 | 可编辑每条的文字、删除、新增一条、要求 AI 重新整理；确认后锁定 |
| Q10 | 冒烟测试"逐条调用功能"的判定标准 | 见 4.5：每条功能对应一个由模板约定的检查脚本，全部通过才算过 |

## 3. 技术选型（新仓库）

原则：**一种语言、最少的组件、与生成物同栈**。

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript（全部） | 生成的应用、项目模板、冒烟测试框架、Claude Agent SDK 都是 TS；流水线、网站、工作进程同栈，一个人能看完整条链 |
| 运行时 | Node.js 22 LTS，pnpm workspace（monorepo） | 与 jabiz 前端工具链一致 |
| 后端 | Fastify + Zod（请求校验、OpenAPI 生成） | 轻、类型安全；不引入 NestJS 一类的框架层 |
| 数据库 | PostgreSQL 16 + Drizzle ORM + 内置迁移 | 熟悉；任务队列也放在 Postgres 里（`pg-boss`），**不引入 Redis** |
| 工作进程 | 同一仓库的 `apps/worker`，消费 `pg-boss` 队列 | 长任务与网站进程分离，可独立扩容、独立重启 |
| LLM | Anthropic 官方 SDK `@anthropic-ai/sdk`：需求整理与芯片匹配用 Messages API + 结构化输出（`output_config.format`，模型 `claude-opus-5-5`，流式）；代码生成用 Claude Agent SDK `@anthropic-ai/claude-agent-sdk`（即 Claude Code 的程序化形式）在沙箱容器中运行 | 规划书指定 Claude Code 生成；整理与匹配只需要单次结构化调用，不需要代理 |
| 沙箱 | 每次生成一个一次性容器（Node + pnpm + Agent SDK），挂载工作目录；**不挂 Docker socket**；网络只允许 Anthropic API 与 npm registry | AI 只写文件；构建、启动、冒烟测试由工作进程在容器外执行（见 4.4） |
| 前端 | React 19 + Vite + TypeScript + TanStack Query + React Router + Ant Design 5 | 向导式页面用 AntD 的 Steps / Form / List 足够；与 jabiz 相同工具链 |
| 进度推送 | SSE（`text/event-stream`） | 单向、简单，够用；不上 WebSocket |
| 文件存储 | 本地目录（产物 zip、芯片 tar、运行日志），路径与配额在配置中 | 第一版单机 |
| 测试 | Vitest（单元、流水线回放）、Playwright（端到端）、契约测试（数据手册 ↔ 桩芯片 ↔ 真芯片） | — |
| 可观测 | pino 结构化日志 + 每次运行的完整日志文件；指标暂不做 | 第一版只要能排错 |
| 部署 | 仓库根目录 `docker compose up -d`（db、api、worker、web 静态文件由 api 托管） | 与交付物同一种方式，团队只学一套 |

可替代但本计划不选的方案（记录以备追问）：Java/Spring Boot 普通 MVC 写网站也可行，Claude Code 可以作为子进程调用；
放弃的理由只有一个：模板、冒烟框架、Agent SDK 都是 TS，一种语言比两种省。**决定性因素是"不在 jabiz 上"，不是语言。**

## 4. 总体设计

### 4.1 仓库结构（monorepo）

```
ubos/
├── CLAUDE.md                     开发规则（一页）
├── docs/
│   ├── plan/                     本计划及修订
│   ├── design/                   设计文档（流水线、数据手册、沙箱、打包、安全）
│   ├── decisions.md              具有约束力的决策（D1…）
│   └── requirements/             需求条目 R-001…（规划书的补充都登记在这里，见第 10 节）
├── apps/
│   ├── api/                      Fastify：认证、项目、流水线接口、SSE、下载、芯片登记
│   ├── worker/                   队列消费：整理、匹配、生成、冒烟、打包
│   └── web/                      React 向导前端
├── packages/
│   ├── datasheet/                数据手册 JSON Schema、解析与校验、类型
│   ├── pipeline/                 纯 TS 流水线内核：整理、匹配、生成驱动、冒烟、打包（不依赖网站，可用 CLI 单独运行）
│   ├── llm/                      LLM 调用封装：提示词包、结构化输出、录制与回放、费用统计
│   ├── sandbox/                  沙箱容器的创建、挂载、限制、清理；compose 项目的启停
│   ├── template-shop/            生成应用的项目模板（React + Node BFF + 冒烟框架 + compose 片段）
│   └── stub-chips/               三枚桩芯片（product / inventory / order）+ 它们的数据手册
├── deploy/docker-compose.yml     UBOS 自己的部署
└── tools/                        脚本：录制 LLM 响应、校验数据手册、本地跑一遍流水线
```

### 4.2 数据模型（Postgres，普通表，软删除即可）

| 表 | 内容 |
|---|---|
| `user` | 邮箱、密码哈希（bcrypt）、角色（user / admin）、邀请码 |
| `project` | 所属用户、名称、当前阶段（`DRAFT` `ORGANIZING` `CONFIRMING` `MATCHING` `TERMINATED` `GENERATING` `TESTING` `PACKAGED` `FAILED`）、终止原因 |
| `requirement_version` | 项目、序号、原始需求文本（用户每次改需求都是新版本） |
| `feature_item` | 需求版本、序号、功能描述、状态（`PROPOSED` `CONFIRMED` `REMOVED`）、用户修改后的文字 |
| `chip` / `chip_version` | 芯片 id、版本、数据手册（原文 + 解析后的 JSON）、镜像 tar 路径、镜像名与标签、登记人、时间 |
| `match_result` | 项目、功能条目 → `chip.capability` / `GLUE_UI` / `UNMAPPED`，AI 的理由；项目级结论（全部可映射 / 终止） |
| `generation_run` | 项目、尝试序号、状态、开始/结束、LLM 用量与费用、沙箱容器 id、失败原因、日志文件路径 |
| `smoke_result` | 运行、功能条目、通过/失败、错误摘要 |
| `artifact` | 项目、zip 路径、大小、sha256、生成时间 |
| `download_log` | 产物、用户、时间 |
| `llm_call` | 运行/项目、用途、模型、输入输出 token、费用、录制文件路径（供回放与审计） |

### 4.3 芯片契约（本项目定义，芯片团队遵守）

规划书说数据手册是"平台的核心资产"，所以**数据手册的格式由本项目拥有并用 JSON Schema 固定**，`packages/datasheet` 提供校验器，
芯片团队在交付前自己跑一遍。第一版 `datasheet.yaml` 的结构：

```yaml
id: order                       # 芯片 id，小写字母与连字符
name: 订单芯片
version: 1.0.0
image: { name: ubos/chip-order, tag: 1.0.0, tar: order.tar }
runtime:
  port: 8080                    # 容器内监听端口
  health: GET /health           # 返回 200 即就绪
  env:
    DATA_PATH: /data/order.db   # SQLite 文件路径（挂卷）
    PRODUCT_BASE_URL:           # 依赖芯片的地址，由 compose 注入
    INVENTORY_BASE_URL:
depends_on: [product, inventory]
openapi: openapi.yaml           # 接口定义：请求、响应、错误码
capabilities:                   # 能力说明：匹配就是把功能条目对到这里的某一条
  - id: order.place
    summary: 下单（向商品芯片查价、向库存芯片预留）
    operations: [placeOrder]    # 对应 openapi 的 operationId
  - id: order.confirm-payment
    summary: 支付确认
    operations: [confirmPayment]
  - id: order.ship   …
  - id: order.cancel …          # 取消时释放库存
examples:                       # 调用示例：典型场景的完整调用序列，供 AI 参照
  - scenario: 顾客下单到发货
    steps: [ { call: placeOrder, body: {...} }, { call: confirmPayment, ... }, { call: ship, ... } ]
limitations:                    # 已知限制：明确写出不支持的情况
  - 不支持部分发货
  - 不支持多币种
```

契约测试（`packages/stub-chips` 与真芯片共用）：镜像能用 compose 启动；`/health` 返回 200；每个 `operationId` 都在 OpenAPI 里；
每条 `examples` 的调用序列能按顺序成功执行；`depends_on` 与 `env` 一致。

### 4.4 沙箱与执行分工（安全设计的核心）

```
工作进程（可信，容器外）                       沙箱容器（不可信，一次性）
────────────────────────────                 ───────────────────────────
1 准备工作目录：模板 + 数据手册 + 功能清单   →
2 启动沙箱，挂载工作目录                      →  Claude Agent SDK 读模板、数据手册、功能清单，
                                                 只做一件事：写文件（前端、BFF、冒烟检查脚本）
3 等沙箱退出（超时即杀）                      ←  退出
4 静态把关：目录白名单、没有网络地址与密钥、
  每条已确认功能都有冒烟检查脚本
5 构建应用镜像；用独立的 compose 项目名启动
  应用 + 三枚芯片（私有网络、随机端口）
6 跑冒烟：/health + 每条功能的检查脚本
7 失败 → 把错误摘要写回工作目录，回到 2（≤ N 次）
8 成功 → 打包 zip；无论成败：compose down、
  删除容器与临时目录、记录费用
```

- **AI 只写文件，从不执行容器**：沙箱里没有 Docker、没有宿主机凭据；出网只允许 Anthropic API 与 npm registry。
- API 密钥只在工作进程与沙箱的环境变量中，**绝不进入生成的代码或 zip**（第 4 步静态扫描）。
- 每次运行有 CPU/内存/磁盘/时长/费用上限；上限触发即失败并清理。
- 并发：第一版工作进程串行执行生成任务（一次一个），队列排队；并发数是配置项。

### 4.5 冒烟测试的判定

模板约定 `smoke/` 目录：每条已确认功能 `F-nn` 必须有 `smoke/F-nn.ts`，用模板提供的小框架（HTTP 客户端 + 断言）
对运行中的应用发请求并断言。工作进程先检查覆盖（每条功能都有脚本，缺一即失败，不进入运行），再按顺序执行；
任何一条失败就把错误摘要（脚本名、断言、响应）回传给下一轮 AI 修复。这样"逐条调用功能"是机器可检查的，
而不是 AI 自己说"测过了"。

### 4.6 打包

`ubos-shop-app.zip` 内容按规划书；`docker-compose.yml` 由模板生成（应用镜像在客户本地构建，芯片镜像由 `start.sh` / `start.bat`
`docker load` 后启动）；`README.md` 由模板 + 功能清单生成。zip 记录 sha256，下载时校验。

### 4.7 LLM 使用方式与可测试性

| 环节 | 方式 | 输出 |
|---|---|---|
| 需求整理 | Messages API，结构化输出（JSON Schema：功能条目数组，每条含编号、描述、输入输出要点） | 功能清单 |
| 芯片匹配 | Messages API，结构化输出；输入是已确认清单 + 全部数据手册的 `capabilities` 与 `limitations`；输出每条 → `chip.capability` 或 `GLUE_UI` 或 `UNMAPPED` + 理由；**程序再校验**每个引用的 capability 真实存在 | 匹配结果 |
| 生成与修复 | Claude Agent SDK，在沙箱内；系统提示 = 项目模板的约定 + 数据手册 + 功能清单 + （修复轮）错误摘要 | 文件 |

- `packages/llm` 支持**录制与回放**：测试用录好的响应，确定且免费；真实调用只在"金标准需求集"的夜间任务里跑。
- 每次调用记录用量与费用到 `llm_call`，项目页面显示累计费用。
- 提示词包是版本化的文件（`packages/llm/prompts/`），改动走 PR，并附带回放测试的快照差异。

## 5. 阶段计划

估算单位：人日，按 1 名全职开发者 + AI 编码助手。每个阶段开始前出细化计划（改哪些包、加哪些表、测试清单、风险），确认后再写代码。

| 阶段 | 名称 | 估算 | 对应规划书 |
|---|---|---|---|
| P0 | 立项、契约、桩芯片 | 3–4 | 验证计划第 1 步的平台侧 |
| P1 | 手动验证 AI 生成（不建网站） | 5–8 | 验证计划第 2 步 |
| **关口** | 第 2 步成立才进入 P2 | — | "第 2 步不成立，就不进入第 3 步" |
| P2 | 流水线内核（命令行可跑通全流程） | 6–8 | 第 3 步的一半 |
| P3 | 网站 | 8–10 | 第 3 步 |
| P4 | 验收、加固、发布 | 3–5 | 第 3 步完成标准 |
| 合计 | | **25–35** | 另留 20% 缓冲 |

### P0 立项、契约、桩芯片（3–4 人日）

目标：新仓库可构建、可测试；数据手册格式定稿；三枚桩芯片能用 compose 启动并互相调用。

交付：
1. 仓库骨架（4.1）、`CLAUDE.md`、`docs/design/` 初稿（流水线、数据手册、沙箱、打包）、`docs/decisions.md`（第 6 节的 D1–D8）、CI（lint、typecheck、test）。
2. `packages/datasheet`：JSON Schema v1 + 校验器 + 三份示例数据手册（商品、库存、订单）。
3. `packages/stub-chips`：三枚桩芯片 + `openapi.yaml` + Dockerfile + compose；订单桩调用商品桩与库存桩。
4. 契约测试（4.3）。
5. 与芯片团队确认契约（一次评审，记录为 R-00x）。

验收：`pnpm test` 全绿；`docker compose up` 启动三枚桩芯片，按 `examples` 的序列调用成功；校验器能拒绝格式错误的数据手册。

### P1 手动验证 AI 生成（5–8 人日）

目标：不建网站，证明"给 Claude Code 需求、数据手册和项目模板，能生成一条命令就能启动、功能全可用的应用"，并且比从零生成更少、更快。

交付：
1. `packages/template-shop`：React + Node BFF + TypeScript 模板、`smoke/` 框架、compose 片段、README 模板。
2. 提示词包第 1 版（系统提示、数据手册的呈现方式、功能清单格式、修复轮格式）。
3. 一份固定的"小型网店订单管理"需求与人工写好的功能清单（作为金标准 G-01）。
4. 手动运行 ≥ 3 次（可先用 `claude` 命令行，后换 Agent SDK），每次记录：生成时长、代码行数、修复轮数、冒烟结果、费用。
5. 对照组：同一需求不给芯片、不给模板，让 AI 从零生成，记录同样指标。
6. 报告 `docs/plan/p1-report.md`：数据、问题、模板与提示词的改进项、是否进入 P2 的建议。

验收（规划书第 2 步）：生成的应用一条命令能启动，所有功能可用；与从零生成相比代码更少、修改次数更少。
**不达标则修模板与提示词再试，仍不达标则停止，向需求方汇报。**

### P2 流水线内核（6–8 人日）

目标：`ubos run requirement.txt` 一条命令在本机跑完"整理 → 匹配 → 生成 → 冒烟 → 打包"，没有网站。

交付：
1. `packages/llm`：SDK 封装、结构化输出、录制/回放、费用统计。
2. `packages/pipeline`：整理、匹配（含程序校验与"全部可映射"判定）、生成驱动、冒烟执行、打包；每一步都是纯函数 + 明确的输入输出，状态写在工作目录的 `state.json`。
3. `packages/sandbox`：沙箱镜像、容器启停与限制、compose 项目的启停与清理、静态把关（4.4 第 4 步）。
4. 金标准需求集 G-01…G-05：3 个全可映射、2 个含不可映射功能（应判定终止），带录制的 LLM 响应与快照。
5. CLI `tools/ubos-run`：跑全流程、单独跑某一步、回放模式。

验收：回放模式下 5 个金标准全部得到预期结果；真实模式下 G-01 产出可启动的 zip；沙箱内拿不到 Docker 与密钥（测试断言）；
失败路径（超时、重试耗尽、功能不可映射）都能清理干净并留下日志。

### P3 网站（8–10 人日）

目标：把 P2 的流水线做成网站，一个人从提交需求到下载 zip 全程不需要开发者介入。

交付：
1. `apps/api`：Drizzle 表与迁移（4.2）、邀请码开户与登录（会话 cookie）、项目 CRUD、各阶段接口、SSE 进度、下载（鉴权 + 校验）、管理员的芯片登记（上传 `datasheet.yaml` + tar，校验后入库）。
2. `apps/worker`：`pg-boss` 队列消费，调用 `packages/pipeline`；任务幂等（同一项目同一阶段不重复执行）；进程重启后未完成的运行标记失败并清理。
3. `apps/web`：向导页（需求输入 → 整理中 → 逐条确认/修改 → 匹配结果（含终止页）→ 生成进度与日志 → 下载）、项目列表、费用显示、管理员的芯片页。
4. OpenAPI 由 Fastify + Zod 生成，前端类型由它生成（同 jabiz 的做法）。
5. 测试：接口集成测试（真实 Postgres）、前端组件测试、Playwright 端到端（回放模式，不花钱）。

验收：用桩芯片 + 回放模式，端到端测试覆盖"成功下载"与"项目终止"两条路径；真实模式人工走通一次。

### P4 验收、加固、发布（3–5 人日）

交付：
1. `deploy/docker-compose.yml` 与部署文档；密钥只从环境变量读取；配额（每用户并发、每日费用）与清理任务（过期产物、残留容器）。
2. 沙箱安全自查清单执行一遍（出网限制、无 socket、资源上限、密钥不落盘）。
3. 真芯片替换桩芯片，契约测试与 G-01 真实运行通过。
4. 客户侧验证：在一台干净的 Windows 与一台 macOS 上，按 README 用 `start.bat` / `start.sh` 启动下载包。
5. **外部验收**：一位未参与开发的人，独立完成从提交需求到本地运行（规划书第 3 步完成标准），记录卡点。
6. 文档：用户指南、管理员指南、运维手册；计划修订为 v1.0。

## 6. 关键设计决策（待确认后写入 `docs/decisions.md`，具有约束力）

| # | 决策 | 理由 |
|---|---|---|
| D1 | UBOS 是独立仓库，不在 jabiz 上开发 | 第 1 节 |
| D2 | 全栈 TypeScript，pnpm monorepo | 与生成物、模板、Agent SDK 同栈 |
| D3 | 数据手册格式由 UBOS 拥有，JSON Schema 固定，芯片交付前必须通过校验器 | 它是匹配、评估、生成三个环节的共同输入 |
| D4 | AI 只写文件；构建、启动、测试由工作进程在沙箱外执行；沙箱无 Docker、无密钥、出网白名单 | 运行不可信代码的最小安全面 |
| D5 | 匹配结果必须机器可校验：每条功能 → 存在的 `chip.capability`、或 `GLUE_UI`、或 `UNMAPPED`；有一条 `UNMAPPED` 即项目终止 | 规划书的关口 2 |
| D6 | 冒烟测试按功能逐条、由模板约定脚本位置、覆盖不全即失败 | "逐条调用功能"要机器可检查 |
| D7 | LLM 调用全部可录制、可回放；CI 只跑回放，真实调用只在夜间金标准任务 | 测试确定、免费、可重复 |
| D8 | 队列用 Postgres（`pg-boss`），不引入 Redis；SSE 不用 WebSocket；文件存本地 | 第一版单机，最少组件 |
| D9 | 每次运行的费用、时长、重试次数有硬上限，超限即失败并清理 | 成本与资源可控 |
| D10 | 规划书的补充需求先登记为 `docs/requirements/R-nnn`，分级后进计划，不直接改代码 | 第 10 节 |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| AI 生成不稳定：同一需求有时过、有时不过 | 核心假设不成立 | P1 先用 ≥ 3 次运行量化；模板把"自由度"收窄（固定目录、固定 BFF 骨架、固定冒烟框架）；修复轮只喂错误摘要 |
| 芯片交付晚于计划 | 流水线无法联调 | 桩芯片（2.3）；契约由本项目先定 |
| 运行 AI 生成的代码有安全风险 | 宿主被攻击、密钥泄露 | D4；静态把关；资源上限；安全自查进验收 |
| 单次生成的费用与时长失控 | 成本、用户体验 | D9；项目页显示费用；队列串行 |
| 下载包过大（芯片镜像） | 下载慢、磁盘 | 第一版接受；记录为 R 条目，以后考虑镜像仓库拉取 |
| 客户 Windows 环境（Docker Desktop、WSL2、端口占用） | "一条命令"失败 | `start.bat` 做前置检查并给出中文提示；P4 真机验证 |
| 需求持续补充打乱计划 | 范围蔓延 | 第 10 节的登记与分级；每阶段开始前冻结范围 |
| 冒烟脚本由 AI 编写，可能"写得过于宽松" | 假通过 | 模板的断言库限制为"对响应做实质断言"；人工抽查；以后加平台侧的通用检查 |
