# 两个账号完成首发的初始化与日常运营

首发期只有需求方一人，用**两个账号**完成初始化与日常运营（需求方 2026-11-17 决定；不做"单人模式"）。

平台与 QuizBuks 的规则都不改：凡是需要"另一个人"的地方，由另一个账号去做。以后有了第二个人，按 `operations.md` §3 的多人步骤分开（本页末尾"以后有了第二个人"）。

两个账号都是需求方本人的。各用**自己的邮箱**，各自设密码、各自绑二次验证，不共用。

| 账号 | 角色 | 用在哪里 |
|---|---|---|
| **账号 A**（超级管理员） | `QB_ADMIN_SUPER`，加 `QB_OPERATOR`（默认运营商的成员） | 平台管理系统：用户与角色、运营商、提出参数、部署后执行 `QB_SETUP`、编辑平台图。运营商管理系统：审核官方账号的发布 |
| **账号 B**（负责人） | 默认运营商的负责人（即官方账号，平台运营商的直营发起方），加 `QB_OPERATOR`、`QB_ADMIN_FINANCE`、`QB_ADMIN_CONTENT` | 平台管理系统：发布参数、审批平台图与钱、法律文本、帮助、邮件文字。运营商管理系统：审核发布。发起方页面：官方账号的问卷与发布 |

## 初始化（按顺序）

**0. 运维准备**
- `.env` 中设 `JABIZ_MAIL_ENABLED=true`（否则邀请邮件发不出，`MAIL_DISABLED`）；
- 设 `JABIZ_WEB_ENVIRONMENT=production`（测试系统设 `staging`）；
- 设首个管理员的两行 `JABIZ_BOOTSTRAP_ADMIN_USER` / `JABIZ_BOOTSTRAP_ADMIN_PASSWORD`；
- 其余照 `operations.md` §1。然后启动。

**1. 首个管理员：设置与提案**
- 用首个管理员登录平台管理系统 `/admin/`，在"安全设置"中绑二次验证。
- 在流程页执行 `QB_SETUP`：建角色、科目、国家、参数，提出受控参数与审批规则的提案。
- 建议在首个管理员停用之前，一并以 `CONTROL_CHANGE_PROPOSE` 提出（`operations.md` §3 第 6 步；以后也可以由账号 A 提出，同样由账号 B 发布）：
  - 收据开具方 `qb.issuer.name`、`qb.issuer.address`、`qb.issuer.registration-no`；
  - 上线清单 2.2 列出的全部科目映射 `qb.journal.account.*`；
  - 按业务定下的金额，如 `qb.reward.max-per-attempt`。

**2. 首个管理员：建账号 B 并分配角色**
- 在"用户"中新建账号 B：填用户名与**账号 B 的邮箱**，勾选 `invite`，**不填密码**。
- 需求方用这个邮箱收邀请邮件（72 小时内有效），设密码。
- 首个管理员在"用户与角色"中给账号 B 分配 `QB_ADMIN_FINANCE`、`QB_ADMIN_CONTENT`、`QB_OPERATOR`。现在仍在建立期，当即生效；这三个角色不算管理员，建立期不会因此结束。
- 首个管理员给管理员角色设"要求二次验证"（`operations.md` §3 第 4 步），未绑定的管理员即无法登录。
- 账号 B 登录平台管理系统，按提示绑二次验证，保存恢复码。

**3. 首个管理员：建账号 A，等它接受邀请**
- 同样新建账号 A（**账号 A 的邮箱**，`invite`，不填密码）。
- 需求方用邀请邮件设好账号 A 的密码。这一步就证明了邮箱、设定了本人的密码，不需要登录。
- 首个管理员在"用户"中确认账号 A 的邮箱已验证，再做下一步。

**4. 首个管理员：最后给账号 A 角色**
- 账号 A 已接受邀请之后，首个管理员给账号 A 分配 `QB_OPERATOR` 与 `QB_ADMIN_SUPER`，超级管理员放在最后。
- 当即生效；首个管理员随即退役，不能再做受保护的变更。
- 顺序不能反：账号 A 还没接受邀请就给超级管理员，邀请一旦过期或丢失，就没有人能管理用户了。
- 账号 A 登录平台管理系统，按提示绑二次验证（管理员角色要求）。
- **保存恢复码**（10 个，离线保管），并在"安全设置"中**登记两个通行密钥**（如手机与一把安全密钥）。
- 运营商管理系统要等第 7 步成为成员后才能登录：那里只让在职的运营商成员登录。

**5. 账号 A：停用首个管理员**
- 账号 A 登录平台管理系统，在"用户"中停用首个管理员的账号。
- 运维从 `.env` 删去首个管理员的两行，设 `QB_BOOTSTRAP_ADMIN_DONE=true`，重启。

**6. 账号 B：发布提案**
- 账号 B 在平台管理系统"数据 → SysControlChange"中逐行发布待发布的提案。
- 顺序同 `operations.md` §3 第 5 步与 §4"首次上线的开关"：
  - 先发布 `qb.reward.kudos.enabled`、`qb.reward.default-methods`，再发布审批规则；
  - 等前提的开关先不发布。
- **三条职责分离规则保持待发布**：`qb.sod.control-changes`、`qb.sod.security-administration`、`qb.sod.mail-texts`。原因见下文"注意事项"。
- 提案是首个管理员或账号 A 提出的，账号 B 发布，符合"提出人不能发布自己的"。

**7. 账号 A：建默认运营商**
- 账号 A 在平台管理系统"运营商"中新建运营商：名称、联系人、联系邮箱，负责人选**账号 B**。第一个运营商自动成为默认运营商。
- 账号 B 在同一事务中成为它的直营发起方，即官方账号。
- 再在运营商页面把**账号 A**加为成员（按页面提示填账号 A 的用户编号）。

**8. 账号 B：加入发起方页面**
- 账号 B 登录发起方页面 `/sponsor/`，点"加入"，取得发起方的角色。

**9. 核对**
- 平台管理系统首页不再提示"请先建默认运营商"。
- 第二天的每日核对 `qb.operator-check` 没有 `NO_DEFAULT_OPERATOR`、`FEW_REVIEWERS`（运营商有账号 A、B 两位能审核的成员）。

## 日常：谁提出、谁批准

| 事情 | 谁提出 / 准备 | 谁批准 / 发布 | 在哪里 |
|---|---|---|---|
| 参数、开关、开具方、科目映射 | 账号 A（`CONTROL_CHANGE_PROPOSE`） | 账号 B | 平台管理系统：流程页；"数据 → SysControlChange" |
| 部署新版本后的 `QB_SETUP` | 账号 A 执行 | 账号 B 发布新的提案 | 同上 |
| 官方账号（账号 B）的问卷发布 | 账号 B（发起方页面） | 账号 A | 运营商管理系统的审核 |
| 其他发起方的发布 | 发起方 | 账号 A 或账号 B | 运营商管理系统的审核 |
| 平台图（知识结构图模板） | 账号 A 编辑、提交 | 账号 B（内容管理员） | 平台管理系统 |
| 撤销点亮 | 账号 A 申请 | 账号 B | 平台管理系统 |
| 银行充值的确认、手工入账、费用请求、运营商的分成方案与结算 | 账号 A 记录或申请 | 账号 B | 平台管理系统（首发多数用不到） |
| 法律文本、帮助中心问答、AI 手册、不受保护的邮件文字 | 账号 B 自己完成（不需要第二个人） | — | 平台管理系统 |
| 给人分配角色 | 账号 A（只有一位管理员，建立期不结束，当即生效） | — | 平台管理系统"用户与角色" |
| 转账、提现 | 首发关着（`qb.transfer.enabled`、`qb.withdrawal.bank.enabled` 为 `false`） | — | — |

## 注意事项

- **操作的账号本人的邮箱须已验证，并重新登录**。
  - 建运营商、加成员、发布法律文本与帮助等，要求**当前登录的账号**自己的邮箱已验证。经邀请设定密码的账号即已验证。
  - 验证状态随登录带着，验证之后要重新登录一次才生效。
  - 提示"请先验证您的电子邮箱"说的就是当前登录的账号，不是所选的负责人。
  - 首个管理员没有邮箱，不能建运营商。
- **账号 A 的恢复码与通行密钥**。
  - 账号 A 是唯一的管理员。它丢了二次验证，没有别的账号能替它重置：账号 B 没有重置二次验证的权限。
  - 下面的破窗做法对此也无效。所以保存好恢复码、登记两个通行密钥，换手机前先登记新的。
  - 账号 B 丢了二次验证，由账号 A 在"用户"中重置。
- **破窗做法**（`operations.md` §3 末"受保护的授权"）：运维以 `JABIZ_SECURITY_PROTECTEDGRANTS_ENABLED=false` 启动一次，做完后改回，记在变更记录中。
  - 它关掉"受保护的授权要另一位管理员审批"，只在**以后**有了两位超级管理员、建立期结束、而一位离开没人能批时才需要。
  - 两账号的做法中只有一位管理员，建立期不会结束，平时用不到它。
- **受保护的邮件文字暂不改**（带登录链接或令牌的、标为受保护的，以及信纸）。
  - 改它们要"有邮件文字权限的人提出、另一位有发布权限的人发布"，而两种权限都只在账号 B 上。
  - 首发用缺省文字；不受保护的邮件文字账号 B 可以直接改。
- **三条职责分离规则为什么不发布**。
  - 账号 B 同时是财务管理员与内容管理员（规则 `qb.sod.control-changes` 不许同一人既提出又发布）；账号 A 是超级管理员又持有运营商角色的审批权（`qb.sod.security-administration`）。
  - 发布任何一条，平台就会拒绝这两个账号的操作（`SOD_CONFLICT`）。
  - 规则只在发布后生效，所以保持待发布；以后有了第二个人再发布（见下）。
- **钱的四眼只是形式**：账号 A 记录、账号 B 批准，但两个账号是同一个人。
  - 首发时转账与提现关着、充值走 Stripe，用不到这类审批；
  - 打开转账或提现之前，先有第二个人。
- **上线前的只读核对** `tools/quizbuks/ops/launch-day-check.sh`：
  - "至少两位超级管理员""建立期已结束"两项会报 `FAIL`，按本方案是**预期的**；
  - 三条职责分离规则待发布会报 `WARN`，也是预期的；
  - 其余各项照常要通过。
  - 这两项已写进上线检查清单"带着未完成项上线的决定"。

## 以后有了第二个人

1. 用邀请为新人建账号，本人接受邀请、绑二次验证。
2. 把财务管理员角色给新人（仍在建立期，当即生效），再从账号 B 收回财务管理员。
3. 由新人发布三条职责分离规则。发布前确认没有人同时持有规则两边的权限，否则发布被拒。
4. 再建第二位超级管理员（`operations.md` §3 第 5 步），建立期随即结束，此后受保护的授权由一位申请、另一位审批。
5. 运营商成员照 `operations.md` §7.13"签下一个运营商"。
