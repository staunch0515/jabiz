## 0. 需求方的决定（2026-11-05）

1. **系统发出的所有邮件都可以定制模版**，不必改程序、不必重新部署。
2. **范围**：每封邮件的**文字**（标题、正文，按语言）与所有邮件共用的**统一信纸版式**（页眉、页脚）两者都做，一起上线。
3. **阶段**：首期只做**总部管理全平台的邮件模版**。商户自定义邀请邮件（经商户自己的邮件服务器发出的 `qb.invitation`）以后单独排期（§9）。
4. **安全规则**：验证邮箱、找回密码、登录链接这一类邮件，修改后须**另一位管理员审批**才生效；普通通知类改了**即时生效**。
5. **细节全部照方案**：占位符校验、版本与审计、预览与测试发送、恢复默认、安全渲染。
6. 具体数字（长度上限、测试发送的次数等）一律是可设置的参数，不写死（`backend/quizbuks/CLAUDE.md` 第 4 节）。

## 1. 现状

- 模版是代码中的 `MailTemplate` Bean（名称、类别 `TRANSACTIONAL` / `NOTIFICATION`、参数、令牌用途、登录链接），文字是消息资源 `mail.<名>.subject|body`（Markdown，每种语言一份），打在 jar 里（平台 18 §5.6、D35）。
- 发信：`SendMail` 在流程事务中记 `MailMessage`（参数原值）→ 消费者 `MAIL_SEND`（`DeliverMail.render`）按收件人的语言读消息、生成令牌、经 core 的 `MailRenderer` 渲染（值从不当作 Markdown 或 HTML，链接只许 http(s)、mailto、相对地址），发出。
- 没有样式（"不做模板样式，只用 commonmark 的基本元素"），没有页眉页脚。
- 现有模版：平台约 12 种（验证邮箱、账号已存在、找回密码、邀请、链接登录、密码已改、邮箱已改、通行密钥已加、已关联外部账号、删除账号的链接与申请等，`AuthMailTemplates`、`AccountDeletionProcesses`），QuizBuks 约 22 种（`AccountMails`、`NotificationMails`、`InvitationMails`、获客的两种）。另有待办通知（18 §5.4）与单据发送（22 §5）的邮件，实施时逐一核对是否经同一渲染；不经的在 17zh-a 中改为经同一处取文字，范围是"系统发出的所有邮件"。

## 2. 做法总览

| 层 | 内容 |
|---|---|
| core（纯 Java） | `MailTextRules`：一份自定义文字是否合格（§3.2），一次报告全部问题；`MailLayoutRules`：信纸是否合格；`MailRenderer` 增加"套上信纸"。前后端共用的用例加进 `spec/validation-cases.json` 的思路不适用（不是字段规则），改为 core 单元测试 + 前端照抄的检查只为省往返 |
| runtime | 自定义文字与信纸的存储（只追加，带版本），写入流程，安全类的四眼（受控变更的目标），发信时取生效的文字与信纸，预览与测试发送，启动检查 |
| 通用后台（`frontend/`） | "邮件模版"页：列表、编辑器、预览、测试发送、恢复默认、历史；"邮件信纸"页 |
| QuizBuks | 授权给内容管理员、信纸的缺省值取自品牌档案、运维文档、e2e |

**原则**：程序中的文字永远是**缺省值**，自定义只是覆盖；覆盖失效（被删的参数、模版改名）时一律退回缺省并告警，**绝不发出坏掉的邮件**。

## 3. 文字的定制（17zh-a）

### 3.1 存储

- 平台实体 `MailText`（`sys_mail_text_version`，时态、只追加，D9）：键为（模版名，语言），字段 `subject`、`body`（Markdown）、`kind`（`CUSTOM` / `DEFAULT`：恢复默认即写一个 `DEFAULT` 版本，等于墓碑）、所据缺省文字的哈希 `defaultHash`（缺省文字以后被程序改了，页面提示"缺省已更新"）。迁移照时态表的规矩（唯一约束、索引、外键、`jabiz_protect_append_only`）；新的只追加表有主键（启动检查 `INTEGRITY`）。
- 审计由平台的 `VersionAppender` 照常记入 `sys_audit_record`（不另写修改日志，D27）；没有个人信息，不进抹除范围。
- 语言只能是应用所选的语言（`jabizApp { languages(…) }`）。一个语言没有自定义即用该语言的缺省；不会因为别的语言改了而改。

### 3.2 校验（`MailTextRules`，保存时一次报告全部问题，400 附 `violations`）

1. **占位符**只能是该模版声明的参数、令牌、内置占位符（`{baseUrl}`、`{entryUrl}`、`{entryUrl.<入口>}`、NOTIFICATION 的 `{unsubscribeUrl}`）；未知的即 `MAIL_TEXT_UNKNOWN_PLACEHOLDER`（指出是哪一个）。
2. **必须保留的不能删**：NOTIFICATION 必须有 `{unsubscribeUrl}`；声明了令牌的，每个令牌必须出现在链接目标中；声明了登录链接的，必须有 `{jabiz.signIn}` 的链接。缺即 `MAIL_TEXT_REQUIRED_PLACEHOLDER`。规则即现有启动检查对缺省文字的要求，挪到 core 共用。
3. **令牌与登录链接只能放在链接目标里**，不能出现在正文文字中（免得被复制、转发）。
4. **链接**只许 `http`、`https`、`mailto` 与相对地址；**原始 HTML 直接拒绝**（渲染时本来就转义，保存时拒绝是为了不让管理员以为能用）。
5. 标题是纯文本、不能换行，长度 ≤ `jabiz.mail.texts.max-subject-length`；正文 ≤ `jabiz.mail.texts.max-body-length`（配置，缺省值写在配置类中，不写死在规则里）。
6. 不能为空；与缺省相同的保存即视为恢复默认。

### 3.3 写入流程

| 流程 | 作用 | 权限 |
|---|---|---|
| `MAIL_TEXT_SAVE` | 普通类：校验后写入新版本，**即时生效**；安全类：拒绝 422 `MAIL_TEXT_NEEDS_APPROVAL`（页面改走提出） | `mail.text.write` |
| `MAIL_TEXT_RESET` | 恢复默认（写 `DEFAULT` 版本），**两类都即时生效**（缺省文字是程序中经过评审的，不需要再审） | `mail.text.write` |
| 受控变更 `CONTROL_CHANGE_PROPOSE` / `CONTROL_CHANGE_PUBLISH`，目标 `mail-text` | 安全类的修改：一位提出、**另一位**发布（平台挡住自审），发布时再校验一次；审批绑定内容哈希（提出后再改即须重新提出） | 现有的受控变更权限 |
| `MAIL_TEXT_PREVIEW`（只读） | §5 | `mail.text.read` |
| `MAIL_TEXT_TEST_SEND` | §5 | `mail.text.write` |

- 每个写入流程取命名锁 `jabiz.mail-text:<模版>`，带页面读到的版本号 `baseVersionNo`，别人先改了即 409。
- 写入声明 `requiresVerifiedEmail()`；安全类的提出与发布照受控变更要求二次验证（`ADMINISTRATION`）。
- **安全类的判定是自动的**：模版声明了令牌（`.token(…)`）或登录链接（`.signInLink(…)`）即是安全类，不另设标记，新增的同类模版自然受保护。平台的验证邮箱、找回密码、邀请设定密码、链接登录、删除账号的确认链接都在其中。§8 第 1 条待确认是否把"密码已改""邮箱已改"等安全通知也纳入。
- 受控变更的目标是平台内部的 `ControlTarget` 实现 `MailTextControlTarget`（同 `ParamControlTarget`，平台的响应式接口，不对应用开放）。

### 3.4 发信时

- `DeliverMail.render` 先取（模版，语言）当前生效的自定义文字，没有或为 `DEFAULT` 即用消息资源；渲染仍是 `MailRenderer`（安全渲染不变）。
- 取文字在投递事务中（`MAIL_SEND`，不在业务流程的事务中），业务流程的语句数不变（`StatementBudgetIT` 不变）。
- 投递记录加列 `text_version_no` 与 `layout_version_no`（可空 = 缺省），事后能查到寄出的是哪一版。重试按当时生效的版本渲染并照记。
- 自定义文字**因代码变化失效**（参数被删、令牌改名、模版被删）：渲染前按 `MailTextRules` 再查，不合格即用缺省并在日志与观测中记 `mail.text.fallback`（标签只有模版名）；启动检查 `MAIL` 对这类覆盖**告警**（不阻止启动：是数据，不是代码错误），后台列表标出"已失效，正在使用缺省"。

## 4. 统一信纸（17zh-b）

- 平台实体 `MailLayout`（`sys_mail_layout_version`，时态、只追加），每种语言一份：
  - **页眉**：显示名（纯文本）、标志图片的地址（只许本站 `{baseUrl}` 下的地址或公开文件 `/api/public/files/…`，不许外部主机：不做追踪像素）、标志的替代文字；
  - **页脚**：Markdown（公司名、住所、客服邮箱、说明），可用 `{baseUrl}`、`{entryUrl.<入口>}`；NOTIFICATION 邮件的退订行由平台自动加在页脚之后，不由信纸决定；
  - **颜色**：主色与文字色两个值（HTML 邮件只能写内联样式，读不到前端的主题 token；只用于页眉的色条与链接，`MailLayoutRules` 检查两者的对比度 ≥ 4.5:1，与前端 12 §11 同一标准）。
- 渲染：HTML 部分为固定的单栏结构（宽度上限、内联样式、无外部 CSS 与脚本），纯文本部分为"显示名 + 正文 + 页脚的纯文本"。信纸为空即与现在相同（无页眉页脚）。
- **缺省值来自应用配置** `jabiz.mail.layout.*`（按语言）：平台示范 `app` 给示范值；QuizBuks 由品牌档案生成（名称 `BRAND.names.<语言>`、标志、品牌色，客服邮箱取 `setup.Brand`），不在代码中写品牌。
- **信纸的修改**：`MAIL_LAYOUT_SAVE` / `MAIL_LAYOUT_RESET`。信纸出现在每一封邮件中（包括安全类），§8 第 2 条待确认修改是否也要四眼；未确认前按"即时生效"写计划，四眼的做法与安全类文字相同（受控变更目标 `mail-layout`），确认后只换写入的途径。
- 页脚不能含令牌、登录链接与 `{unsubscribeUrl}`（这些只属于各封邮件）。

## 5. 预览与测试发送

- **预览** `MAIL_TEXT_PREVIEW`：输入是未保存的草稿（标题、正文、语言，可选的信纸草稿），输出是校验问题与渲染出的 HTML、纯文本、标题；参数用模版声明的**示例值**（`MailTemplate` 新增 `.sample(参数, 值)`，没有即显示 `[参数名]`），令牌与登录链接换成不能用的示例值。不写任何记录。页面在沙箱化的 `iframe`（`sandbox` 不含脚本）中显示 HTML。
- **测试发送** `MAIL_TEXT_TEST_SEND`：把草稿或当前版本按预览的方式渲染后**只发给操作人自己已验证的邮箱**（不收地址参数），标题前加 `[TEST]`，令牌是不能用的示例值（不生成 `sys_mail_token`），经平台的发信服务照常记录（类别 `TRANSACTIONAL`，不进收件偏好）。次数受 `jabiz.process.rate-limits` 限制（缺省每人每小时若干次，配置）。`jabiz.mail.enabled` 关闭时同样记 `SKIPPED`，页面说明原因。

## 6. 通用后台的页面（17zh-c）

- **"邮件模版"列表**（平台 `frontend/` 的页面，按权限显示）：每个模版一行：显示名（`mail.<名>.name`，没有即模版名）、类别、是否安全类（标"修改须审批"）、各语言的状态（缺省 / 已定制 / 待审批 / 已失效 / 缺省已更新）。手机上用卡片（17zc）。
- **编辑器**：按语言分页签；标题与正文；右侧列出可用的占位符（点一下插入）与必须保留的项（缺了标红）；下方即时预览（经 `MAIL_TEXT_PREVIEW`，防抖）；"发一封测试信给我"；"恢复默认"（先确认）；普通类"保存"、安全类"提出修改"（之后显示待审批的变更与发布人，发布链到平台的受控变更页）。
- **历史**：版本列表（时间、修改人以 `UserName` 显示为名字、类型），点开看那一版并与当前对比；可"以此版为草稿"。
- **"邮件信纸"页**：同样的编辑、预览（用一封示例邮件）、测试发送、恢复默认。
- 文案三语，亮暗两种外观过 axe（`@jabiz/ui/testing`），组件只用 `@jabiz/ui`。接口变化更新 OpenAPI 快照并 `pnpm gen:api`。

## 7. 平台决策 D72 的草稿（写进 `docs/design/09-decisions.md`，待确认）

> **D72 邮件文字与信纸的在线定制**
> 1. 代码中的 `MailTemplate` 与消息 `mail.<名>.*` 是缺省；管理员可按（模版，语言）覆盖标题与正文、按语言设信纸（页眉、页脚、两种颜色），存于只追加的 `sys_mail_text_version` / `sys_mail_layout_version`，只经 `MAIL_TEXT_*` / `MAIL_LAYOUT_*` 流程与受控变更写入。
> 2. 覆盖只能使用模版已声明的占位符，必须保留退订链接、令牌链接与登录链接；不能用原始 HTML；渲染照旧是 `MailRenderer`（值不当作 Markdown 或 HTML）。
> 3. 声明了令牌或登录链接的模版，其覆盖只经受控变更（`mail-text`）由另一位管理员发布；其余即时生效；恢复默认一律即时生效。
> 4. 失效的覆盖在发信时退回缺省并告警，从不发出不合格的邮件；投递记录写明所用的文字与信纸版本。
> 5. 应用不另写邮件文字的存储或编辑页；应用以 `jabiz.mail.layout.*` 给信纸的缺省值。
> 取代：无（扩展 D35；18 §5.6 中"不做模板样式"改为"样式只有平台的信纸"）。

## 8. 待确认（不影响开工的部分照计划做）

1. **"密码已改""邮箱已改""通行密钥已添加""已关联外部账号"这类安全通知**（没有令牌，但是防冒用的通知，被改成误导的文字也有风险）：是否也算安全类、修改须审批？建议**算**（声明 `t.protectedText()` 显式纳入）。
2. **信纸的修改是否须审批**：信纸出现在包括验证、找回密码在内的每一封邮件中。建议**须审批**（与安全类文字同一途径）；不须审批则即时生效。
3. **谁来改**：建议平台权限 `mail.text.read|write` 在 QuizBuks 中授予内容管理员角色（与 FAQ、法律文本草稿相同的人），总部的超级管理员不授予（职责分离：审批的另一位管理员须持有受控变更的发布权限）。

## 9. 留待以后

- **商户自定义邀请邮件**（需求方 2026-11-05：后续单独排期）：只改文字，必须保留的链接与法律要求的页脚仍由平台加上；按商户存一份覆盖，审核方式另定。获客邮件（运营商）可照同一做法。
- 邮件的 A/B 测试、按地区的不同文字、富文本编辑器：不做。

合计约 **6–8 天**（与 2026-11-05 的估算相同；QuizBuks 的适配很小，含在其中）。

**测试**（没有测试的功能不算完成）：

- core：`MailTextRulesTest`（每条规则的正反例：未知占位符、缺退订、令牌不在链接中、令牌在正文、原始 HTML、`javascript:` 链接、超长、换行的标题）、`MailLayoutRulesTest`（外部图片、对比度、页脚中的令牌）、`MailRendererTest`（套信纸后 HTML 与纯文本、值仍不当作 Markdown）；行覆盖率 ≥ 80%。
- runtime（真实 PostgreSQL）：`MailTextIT`：普通类保存即生效、发信用新文字并记版本；恢复默认；409 并发；安全类 `MAIL_TEXT_SAVE` 被拒、提出 → 本人发布被拒 → 另一位发布后生效；失效覆盖回退缺省并告警；时态表上没有 UPDATE / DELETE；测试发送只到本人、不生成令牌、限流；预览不写记录。`MailLayoutIT`；`StatementBudgetIT` 不变。启动检查的用例。
- 前端：Vitest（编辑器的必需项提示、预览防抖、安全类显示"提出修改"）、axe 亮暗两种外观；平台 e2e：改一封通知、在邮件中看到新文字与信纸。
- QuizBuks e2e：内容管理员改 `qb.publication.approved` 的中文正文，发布获批后 Mailpit 收到新文字；改验证邮箱须另一位管理员发布（测试已有两位管理员的做法，`AccountItSupport`）。

**风险**：
