# Q54 商户的成长：邀请制入驻、资格与认证题、商户等级（计划，2026-10-30；待确认）

需求方（2026-10-30，讨论后确认的方向）：

- 答题者想成为商户的情况不少见，但同一邮箱不能再注册。App 里要有"申请成为商户"。商户的直接注册**改为邀请制**：设置一个小门槛，增加 QuizBuks 平台的价值。
- **所有商户都必须审核**；资格不跳过审核。
- 准备一种数字奖品："答得好，奖励成为商户的资格"。资格**绑定账号**，不能转让。
- 商户要有**等级**。升级是"**达标后由人审核再升**"。冷启动期**不收会员费**（支付手段太少），以后再收。
- **商户用某个功能前，必须先了解这个功能**：为功能准备一套题，商户答完合格，才把这个功能给他，否则用不了。
- 重考的间隔由**出题方**设定（隔几天）；不设就是不能重考。**合格线就是发布现有的合格分**。
- 资格**满一年审查**：一年没有用过就停用，等待激活。
- 这些对商户的管理都是**运营商的工作范畴**（Q48）。

本计划只是规划；确认 §7 的问题后再分期开发。

## 1. 概念

| 概念 | 含义 | 由谁决定 |
|---|---|---|
| **审核** | 每个商户入驻都要审核（现有的 `qb.sponsor.review`），没有例外 | 运营商终审，总部抽查（D-Q48-4/5） |
| **邀请** | 成为商户的入场券：运营商（含总部"直营"）发的邀请、AI 获客的体验链接（Q48c）、或答题赢得的"申请资格" | 运营商发出；答题自动获得 |
| **资格** | 账号上的一条记录："可以申请成为商户"，或"会用某个功能"。不能转让、可以停用与收回 | 答题合格自动授予；运营商可授予、收回、激活 |
| **等级** | 商户被信任的程度：上限、配额等。与功能资格无关 | 达标后运营商审核升级，总部抽查 |

**等级管"能承担多大"，资格管"会不会用"。** 风险大的功能两者都要，例如现金奖励要求"认证级以上 + 现金奖励的资格"。

## 2. 决定（草案）

| # | 决定 |
|---|---|
| D-Q54-1 | **入驻只有两条路，都要审核**：(1) 受邀的企业在商家后台 `/sponsor/` 注册（注册必须带有效的邀请）；(2) 已有答题者账号的人在 App 中"申请成为商户"（必须持有有效的"申请资格"或邀请）。商家后台的公开注册关闭；`QB_SPONSOR_SELF_REGISTRATION` 只作应急开关保留 |
| D-Q54-2 | **邀请**（`QbSponsorInvitation`，只经流程写入）：运营商对一个邮箱发出，或生成一次性的链接；AI 获客的体验键视同该所有者的邀请。被使用即记下是谁，归属随邀请的运营商（取代 Q48d 的 `?src=` 认领：邀请本身带归属）。有效期与每日配额由运营商级的参数决定 |
| D-Q54-3 | **平台需要的两处改动**（先在 `1.3/platform` 完成）：①`SignUpGuard`（core，同步，与 `SignInGuard` 同样以 `loads()` 声明所需数据）：应用决定某入口的注册是否允许，由此要求带有效邀请；②**已登录用户加入另一个允许注册的入口**（现在只能经"你已有账号"的邮件链接加入），同样经过 `SignUpGuard`。App 的"申请成为商户"用②给账号加上商户角色，再走现有的入驻申请；角色只经平台授予，应用不自己写 |
| D-Q54-4 | **资格**（普通表 `QbQualification`，只经 `QB_QUALIFICATION_*` 流程写入，平台照常审计）：持有人、种类、版本、状态 `ACTIVE` / `DORMANT`（停用，待激活）/ `REVOKED`、来源（`QUIZ` 某次答题 / `INVITATION` / `GRANT` 运营商授予 / `MIGRATION` 上线时补发）、经手的运营商、授予时间、**最近使用时间**。种类与版本只在代码中的目录 `Qualifications`（键、对象是答题者还是商户、所管的功能、最低等级、当前版本） |
| D-Q54-5 | **年审**：逐项任务每天检查：`ACTIVE` 且自"最近使用"（没有用过则自授予）起满一年未用 → `DORMANT`，站内信与邮件通知商户和其运营商。**激活**：重新通过该功能的认证题，或由运营商激活（见 §7 问题 1）。功能的规则变化时提升目录中的版本，旧版本的资格同样转为 `DORMANT`，提示"规则已更新，请重新认证" |
| D-Q54-6 | **"使用"的记录**只在功能自己的流程中写（如提交一个以电子奖品支付的发布、发出一封邀请邮件），**绝不在答题路径上写**（`AttemptStatementBudgetIT` 不变） |
| D-Q54-7 | **认证题就是发布**：奖励方式多一种 **"资格"**（`QUALIFICATION`），发布上写授予哪个种类；合格线是发布现有的合格分（`passScore`）。完成后由事件的消费者（`internal()`）重读会话、确认合格，再授予或续期资格（不在发布锁内写资格表）。不经钱包、不过账、平台不抽成 |
| D-Q54-8 | **谁能出认证题**：只有运营商（含总部"直营"）的官方发布；普通商户的发布不能选"资格"（防止滥用）。实现方式见 §7 问题 2 |
| D-Q54-9 | **认证题的受众**：功能认证题的受众是新的 `SPONSORS`（已通过审核、未封禁的商户本人，运营商的认证题限其名下商户）；"申请资格"的题面向答题者（公开或指定邮箱，沿用现有受众） |
| D-Q54-10 | **重考**是所有发布都可以设的选项：`retakeAfterDays`（空 = 不能重考；1–365）。只有**没有合格**的人才能在上次提交满该天数后再答；**每人每个发布的奖励至多一次**（防止反复刷奖励）。引擎现在以 `qb_attempt_once UNIQUE (user_id, publication_id)` 保证一人一次，要改为"一人多次、同时至多一个进行中"，这是本计划中**风险最大**的改动（§5） |
| D-Q54-11 | **功能的门**：每个受管的功能在**服务端**的流程中检查资格（与等级），不只是页面。页面上没有资格的功能照样可见但锁着，显示"先完成认证"，并链接到对应的认证题。冷启动必需的路径（出题、平台 Kudos、到店兑换）是否也要先认证，见 §7 问题 3 |
| D-Q54-12 | **老商户不被突然锁住**：上线时为已经在用某功能的商户补发 `MIGRATION` 资格（年审照常从此开始计算）；现在由管理员逐家放开的支付方式（`QbSponsorRewardMethods`）并入资格：放开即视同授予 |
| D-Q54-13 | **等级**（时态实体 `QbSponsorTier`，带历史）：见习 → 认证 → 专业 → 合作伙伴（合作伙伴由总部指定）。等级本身只是**一组参数的取值**：现在全平台一个值的上限（新商户充值上限、同时进行的发布数、每次答题的最高奖励、邀请的每日配额、站内通知条数、AI 额度等）改为"按等级取值，没有就用全局值"，受控参数 `qb.tier.<等级>.<名>`。不新造功能开关 |
| D-Q54-14 | **升级**：逐项任务按"达标条件"（完成的发布数、没有下架与争议、充值或答题量、运营时长）找出候选，给其运营商开待办；运营商审核后升级，留理由与历史；总部抽查（同 D-Q48-5）。降级（违规、争议）由运营商或总部处理，附理由，商户可见 |
| D-Q54-15 | **不收会员费**：等级在本期只影响上限与配额，不影响抽成；收费以后另立计划 |
| D-Q54-16 | **运营商的范围**：发邀请、审核入驻（现有）、出认证题、授予 / 收回 / 激活资格、审核升级，都在运营商后台，限其名下商户；只有一个对外运营商期间照 D-Q48-2（看到全部普通商户）。直营商户由总部做同样的事。Shopify 商店不在本计划内 |

## 3. 现状与改动的对照

| 现状 | 改动 |
|---|---|
| 商家后台公开注册（`registration-roles: QB_SPONSOR`） | 只有带邀请才能注册（`SignUpGuard`） |
| 答题者想成为商户：只能在商家后台用同一邮箱"注册"，收"你已有账号"的邮件再加入 | App 中"申请成为商户"（已登录加入入口 + 入驻申请） |
| Q48d：商家后台记住 `?src=`，申请后调用 `QB_PROSPECT_CLAIM` 认领归属 | 体验键即邀请，注册时就带上归属；`QB_PROSPECT_CLAIM` 保留给已注册的旧链接 |
| 支付方式由管理员逐家放开 | 放开 = 资格；新的功能由认证题解锁 |
| 一人一次（数据库唯一约束） | 发布可设重考间隔；一人多次，奖励至多一次 |
| 全局的上限与配额 | 按等级取值 |

## 5. 风险

| 等级 | 风险 | 对策 |
|---|---|---|
| 高 | **重考改动答题引擎**：一人一次是唯一约束兜底，开始、提交、计数、分析、邀请都以"每人一个会话"为前提；答题路径的语句数有确切预算 | 单独一期（Q54d2）；"进行中至多一个"仍由部分唯一索引兜底；开始的锁内仍只读本人最近的会话（语句数不变，由 `AttemptStatementBudgetIT` 证明）；分析的人数与次数分开 |
| 中 | **关掉公开注册拖慢冷启动的商户获取** | 邀请由运营商与 AI 获客大量发出（Q48c 每天几十封）；应急开关可以临时打开；先观察入驻申请的数量再收紧 |
| 中 | **认证题答案外流**（答完显示正确答案） | 合格线用较高的合格分；定期出新一轮；以后再做"题库随机抽题" |
| 中 | **年审误停**：商户只是淡季没用 | 停用前 30 天提醒；激活只需重新答题或运营商一键激活；停用不影响已在进行的发布 |
| 低 | 老商户在上线时被锁 | `MIGRATION` 补发，测试按现有数据核对 |

## 6. 测试（各期）

- 平台：`SignUpGuard` 拒绝与允许、已登录加入入口（经守卫、角色只加注册角色、受保护的角色不能经此授予）、示范应用的用例。
- 资格：目录的启动检查、授予 / 收回 / 激活的权限与运营商范围、年审的逐项任务（固定时钟：364 天不停、366 天停、停用前提醒）、版本提升使旧资格停用、"使用"只在功能流程中写（答题路径的预算不变）。
- 邀请：无邀请不能注册、邀请只用一次、过期、归属随邀请；App 申请的门槛与审核。
- 认证题：只有官方发布能选"资格"、受众 `SPONSORS`、合格即授予或续期、不合格不授予、`SPONSORS` 以外的人不能开始。
- 重考：间隔未到拒绝、合格后不能重考、奖励至多一次、进行中至多一个、语句数预算不变、场景回放。
- 功能门：每个受管功能没有资格即 422（服务端）、页面显示锁、`MIGRATION` 的商户不受影响。
- 等级：候选任务、升降级的权限与历史、参数按等级取值与回退到全局值。
- e2e：受邀注册 → 审核 → 答认证题 → 解锁功能；答题者在 App 申请成为商户；axe。

## 7. 待确认的问题

1. **停用后怎样激活**：(a) 只能重新通过认证题；(b) 只能由运营商激活；(c) 两者都可以（我建议 c：商户自己答题即可恢复，运营商也能直接激活）。
2. **认证题由谁发布**：(a) 每个运营商（含直营）指定一个"官方发布账号"（就是一个商户账号，被总部标记为官方），沿用现有的出题与发布流程，改动最小；(b) 新的发布方类型"运营商"（`publisherKind = OPERATOR`），运营商后台自己出题，改动大但更干净。建议先 (a)、以后 (b)。
3. **"入门认证"**：出题、平台 Kudos、到店兑换这些冷启动必需的功能，是否也要先通过一套简短的入门认证（例如 5 题）才能**提交第一个发布**？（不挡注册与编辑）。按"用前先了解"的原则应当要；但会增加冷启动的摩擦。
4. **重考的规则**：是否同意"只有没合格才能重考、每人奖励至多一次"？还是合格后也能再答（不再发奖励）？
5. **运营商能否不经答题直接授予功能资格**（例如给大客户开通）？建议可以，但要留理由，总部抽查。
6. **升级的终审**：运营商终审、总部抽查（同入驻与发布，D-Q48-5）；还是"专业"以上由总部审核？
7. **"申请资格"的有效期**：答题赢得的申请资格多久内要用掉（建议 90 天，过期即停用、可重新赢得）？
