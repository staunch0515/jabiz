# Q47 客户匹配（计划，2026-10-27 确认；Q47a 实现中）

编号说明（2026-10-28 需求方确认）：本计划原编为 Q39（分支 `1.3/quizbuks-39a-audience`、PR #265 的早期提交说明仍写 Q39a），与 1.3 上的"普通商户的店员"（`Q39-sponsor-staff.md`，决策 D-Q39-1…8）重号，改为 **Q47**（Q42、Q43、Q45、Q46 只在 1.2 的分支名中用过，同 `Q44-public-quiz-pages.md` 的做法跳过），决策为 D-Q47-1…9。

需求方（2026-10-27）：落实"客户资料越完善，能看到的答卷越多"。商户在发布中以匹配规则精准选定答题者范围，选定后可看到平台上满足条件的答题者数量；
规则对象化，以后可以补充；**以后按规则收费**：规则由发布使用，费用按发布、按其有效期折算到天。平台的技术含量将以匹配规则体现，以后可能设专用服务器做匹配。

需要新表，按版本线规则只做在最新线 **1.3**（1.2 不加迁移）；迁移 **V36**（原为 V32；1.3 上 V31–V35 已由 Shopify S1–S3、店员与渠道发布所用，Flyway 版本在 `quizbuks`、`quizbuks-shopify` 间共用一个序列）。

## 1. 决定（2026-10-27 确认）

| # | 决定 |
|---|---|
| D-Q47-1 | **理念**：发布可以对答题者资料设条件；答题者没填的那一项不满足针对该项的条件。没有条件的发布人人可见（与现在相同）。邀请制（Q25）的发布不看条件 |
| D-Q47-2 | **规则对象化**：每种条件是一个登记的**条件定义**（`AudienceCriterion`）：键、类型（`SET` 选项型 / `RANGE` 范围型）、取值（选项字典或上下限）、对应的资料项、计费项、三语显示名。同一条件的多个选项为"或"，不同条件为"且"。新增规则 = 登记一个定义 + 资料项（一次迁移）+ 消息；匹配、首页筛选、开始答题的复查、计数都不改 |
| D-Q47-3 | **第一批资料项与条件**：出生年（条件"年龄"，范围型，以发布期间的年份换算）、性别（含"不回答"）、职业类别、兴趣（多选）。不收集要配慮個人情報 |
| D-Q47-4 | **商户后台**：发布向导新增一步"客户匹配"（规则与确认之间）；地区与"公开 / 邀请"移到这一步。条件与地区一样在提交审核后固定；管理员审核时看得到（Q47b） |
| D-Q47-5 | **查看符合人数**：按当前条件统计有效答题者（已验证邮箱、未封禁、在所选地区）；不足 20 显示"少于 20"，其余取整到 10；限流；商户永远看不到任何个人的资料。计数不收费 |
| D-Q47-6 | **首页与开始答题**：首页只列满足条件的发布，开始答题时服务器以同样的条件复查 |
| D-Q47-7 | **计费（Q47c，以后做）**：规则由发布使用；费用 = 该发布所用各计费项的日价之和 × 有效期天数（按天折算）；从商户 Kudos 钱包扣、记账并出收据；地区为免费的基础项；日价为受控的业务参数（四眼）；收费开关缺省关闭。Q47a 已在条件定义上带计费项，发布的条件与期间在提交时固定，费用可以精确计算 |
| D-Q47-8 | **匹配可以换成专用服务器**：匹配的语义只在一处定义（Java 的 `AudienceMatch`，SQL 中同样的写法由测试对照）；以后改为专用服务器时，以它预先算出的"发布 × 答题者"资格替换 SQL 部分，商户后台与 App 不变 |
| D-Q47-9 | **隐私**：隐私政策须补充"资料用于匹配问卷"（律师确认后经 `QB_LEGAL_PUBLISH` 发布新版本，答题者照常重新同意）；资料可随时清空 |

## 3. Q47a 的实现

- 迁移 V36：`qb_profile_attribute`（用户、条件键、选项码或数值；普通表，答题者可清空）、`qb_publication_criterion`（发布、条件键、选项码或上下限；随发布的草稿保存，提交后不再改）。
- `com.jabiz.quizbuks.audience`：`AudienceCriterion`、`AudienceCriteria`（登记的四种）、`AudienceMatch`（纯函数：资料是否满足条件）、`AudienceCount`（取整与阈值）。
- 流程：`QB_PROFILE_ATTRIBUTES_SAVE`（本人的资料，整体替换，账户锁内）；`QB_PUBLICATION_AUDIENCE_SAVE`（草稿的条件，整体替换，发布锁内，带 `baseRevision`、使发布的 revision + 1；校验键已登记、选项属于该条件、范围在上下限内且不颠倒；`INVITED` 不能有条件）；`QB_AUDIENCE_COUNT`（商户自己的发布：流程中运行计数模板，只返回取整后的数）。条件没有放进 `QB_PUBLICATION_SAVE`：那样要改它众多的输入构造与快照，单独的流程同样在发布锁内、同样只对草稿。
- 模板：`qb.app.feed` 不列出不满足的；`qb.app.publication` 多一列 `matched` 并进入 `canStart`（页面照常显示，以便请答题者完善资料）；`qb.system.audience-count`（权限 `qb.audience.system` 不给任何角色，只在流程中运行）。开始答题在锁外既有的一条语句（`QueryEntities.all`）中多读条件与本人的回答，`AttemptStatementBudgetIT` 的确切值不变。
- 复制发布时条件随之复制，删除草稿时一起删除。

### 实施记录

- 持有 `*` 的账号（只有首个管理员）照平台规则能读默认数据视图与运行计数模板，与 QuizBuks 其他"不授予任何角色"的权限相同；授予角色的权限中没有能读原始回答的。
- 商户后台的向导由三步变为四步：内容 → 时间与奖励 → **客户匹配**（受众、地区、条件与计数按钮）→ 检查并提交。计数按钮先保存草稿（含条件），再按保存的地区与条件计数。
- 评审（Q47a 合并前）后改正：草稿改为 `INVITED` 时清除条件、复制 `INVITED` 的发布不带条件；年龄只接受出生年份、空选项报为 `QB_AUDIENCE_OPTION`、选项列表至多 20 项；`QbProfileAttribute` 的值 `auditMasked`、流程输入 `@Sensitive`（审计与 `op_process` 的摘要中都没有所填的内容）；计数只算启用且邮箱已验证的账号；向导在条件保存被拒时仍记下草稿的新 revision，打开而未选的条件在页面上先拦下。
- **已知的隐私界限（待定）**：(1) 中奖者的显示名出现在商户的兑换、电子奖品与现金记录中，条件定得很窄（如"41 岁、女性、公务员"）时，商户由此知道这些中奖者的资料；(2) 取整与阈值挡不住刻意的差分（用自己控制的已验证账号把人数推到边界，再加一个条件看是否少一人），频率限制只是增加成本。可选的缓解：每个条件的最小人群、计数加噪、条件过窄时不显示中奖者姓名；由需求方决定后作为 Q47b 的一部分。
- 未做：`qb.audience.system` 没有列入受保护的授权（与 QuizBuks 其他"不授予任何角色"的权限一致，`jabiz.security.protected-grants.permissions` 未改）；首页与发布页的年龄按页面给的 `at` 计算，开始答题按服务端时钟（跨年时开始可能被拒，只影响本人）；商户通知只按地区投递，不按条件（Q47b 再定）。
- App 的账户页多一节"关于我"（`/account?section=details` 直接打开），发布页在 `matched = false` 时以提示与链接代替开始按钮。

## 4. 测试

- 单元：`AudienceMatch`（选项"或"、条件"且"、没填即不满足、年龄换算的边界）、`AudienceCount`（阈值与取整）、条件定义的校验。
- 集成：首页与开始答题按条件筛选；计数只给自己的发布、只返回取整后的数、直接调用模板被拒；SQL 与 `AudienceMatch` 对同一组数据结论相同。
- 场景回放：现有场景的快照不变（条件为空即所有人）；带条件的流程由 `AudienceIT` 与 e2e 覆盖。
- 前端与 e2e：答题者填资料后看到原来看不到的发布；商户在"客户匹配"中选条件并查看人数。
