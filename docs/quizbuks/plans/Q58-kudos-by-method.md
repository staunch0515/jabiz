# Q58 答题者的 Kudos 按奖励方式分类（2026-10-30）

需求方（2026-10-30）："四种……方式，都有明确的等值 kudos，所以……分类别记录 kudos，在支付时，分别从对应的类别减少。四个合集就是总 kudos。另外要显示累计的到总 kudos。
以后，可能还有当年累计的 kudos，当月累计的 kudos。打开这些分类汇总，可以看到几种……方式的不同的数据。"四种是**奖励方式**，不是支付方式（需求方确认）。

## 1. 现状

- 只有 PLATFORM（平台 Kudos）经过账本：奖励记入 2120（答题者，扣除手续费后的额），转出时从 2120 借出（`QbTransfer`）。
- 现金（`QbCashReward`）、到店兑换（`QbRedemption`）、电子奖品（`QbDigitalPrize`）各有自己的记录（金额即折合的 Kudos、不收手续费），不记账（Q22、Q33 的决定）。
- 钱包页只显示 PLATFORM；没有按方式或按期间的汇总。

## 2. 设计

**不另记一套账**：每种方式自己的记录已经说明了获得与兑现，按它们汇总即可（模板 `qb.app.kudos`），不会与账本或奖励记录不一致；
需求方所说的"分类别记录、兑现时从对应类别减少"即：每类的待兑现 = 获得 − 已兑现 − 已失效。

| 方式 | 获得（期间按） | 已兑现（期间按） | 已失效 | 待兑现（总是当前） |
|---|---|---|---|---|
| PLATFORM | 2120 的贷方减去非转账的借方（奖励被冲正即不算获得），记账时间 | 转账从 2120 取走的（转账的借方减去退回的），记账时间 | — | 2120 余额（另显示等待商家充值的奖励） |
| SPONSOR_CASH | 未作废的现金奖励的金额，`dueAt` | 答题者确认收到（或管理员裁定已付）：`confirmedAt` | — | DUE、MARKED_PAID、OVERDUE、DISPUTED |
| OFFLINE_REDEEM | 未作废的到店奖品，`dueAt` | 已领取：`redeemedAt` | 过期未领：`expiresAt` | DUE、CLAIMED |
| DIGITAL_PRIZE | 未作废的电子奖品，`dueAt` | 已发放（含答题者确认）：`deliveredAt` | — | DUE、OVERDUE、DISPUTED |

- **总 Kudos** = 四类之和（前端相加）。PLATFORM 记的是钱包实际收到的（扣除手续费后），其他三种是奖励记录的金额（不收手续费）。
- **期间**：模板的 `from` / `to`（都可省略：累计）。获得、已兑现、已失效按各自的时间落在期间内计；待兑现与期间无关，总是当前的。
  钱包提供"累计 / 今年 / 本月"，边界按设备的时区；以后要选某年某月只需传别的 `from` / `to`。
- **页面**：钱包页顶部"按奖励方式的 Kudos"：期间切换、全部奖励的合计（获得、已兑现、待兑现、已失效）与四张卡片（每种方式的获得、"已转出 / 已收到 / 已领取 / 已发放"、"钱包中 / 待收 / 待领取 / 待发放"）。
  点开卡片到 `/wallet/kudos/<方式>`：该方式的数字（PLATFORM 另显示等待商家的奖励）与它的奖励列表（记录 `qb.app.history` 按 `rewardStatus` 筛选），每条可打开结果页（确认收到、出示编码都在那里）。
  原来的钱包摘要（可转出、保留中、转出中）与交易记录照旧在下面。

## 3. 测试

- `KudosByMethodIT`：四种各得一次奖励，现金经商家标记、答题者确认；四行的获得、已兑现、待兑现；结算当天的期间只有已兑现、期间之前全为零（待兑现仍是当前的）；
  奖品过期后计为已失效；别的答题者什么也看不到；PLATFORM 经真实的转账：转出后已兑现、余额为零，转账的期间里只有已兑现。
- `wallet/kudos.test.tsx`：期间边界（本地时区、跨年的十二月）、四类相加、方式页的路径；钱包页的合计与卡片、切换期间时的 `from` / `to`、打开现金卡片后只列现金奖励、期间保持、底部导航仍是钱包、axe。
