# Q105 平台费 Kudos：赠送给发起方、只能用来付平台费（计划，2026-11-05；需求方确认 §1）

需求方 2026-11-05 的讨论（以最后一次为准）：

1. **对发起方不免费**：平台的工具与资源要收费。
2. 一段时期内**赠送**发起方平台费额度，用来试用系统、支付平台费账单。以后可能还送，但会越来越少；**活动怎么搞，账都不能乱**。
3. 赠送的叫"平台费 Kudos"，界面上也叫 Kudos，但**和发起方能发给答题者的 Kudos 不是同一个账户**，只能用来在平台消费，**不能给人做奖励**。
4. 发起方**资料录入完整、入驻审核通过后**即发：**未认证 1,000，已认证 10,000**。
5. 也可以在发起方**答对某个题之后**赠送（如平台知识结构图上的挑战，Q90 §2.8）。
6. **都要记账**，记在与奖励 Kudos 不同的科目中。
7. 赠送的成本由谁承担（运营商、直营发起方）由**财务在线下记录，平台不反映**；平台上不记负账。
8. **首次上线就做**；送到什么时候、以后送多少，另定（受控参数，§3.4）。

编号 Q105：Q104 之后的第一个空号。**这只是计划**：§6 的待确认定下后再细化、开发，在工作分支上经 PR 合入。

## 1. 决定

| # | 决定 |
|---|---|
| D-Q105-1 | **独立账户**：每个发起方多一个"平台费 Kudos"余额（`QbWallet` 新种类 `FEE_CREDIT`），与学分钱包（`SPONSOR`，发奖）、现金账户（`CASH`，Q87a）并列，三者在同一把锁 `qb.wallet:SPONSOR:<发起方>` 内修改；余额照样有 `>= 0` 的检查约束，从不为负 |
| D-Q105-2 | **只能付平台费**：平台费账单与各项工具和资源的费用（`QB_FEE_CHARGE` 的各种类：月费、受众规则、配送费 Q101、AI、手工记费等）。**不能换成学分、不能发奖、不能转让、不能提现或退款**。没有任何流程把它转出到别的账户，所以永远流不到答题者手里 |
| D-Q105-3 | **支付顺序**：记费时先用平台费 Kudos，不够的部分照 Q87 的规则走（预付从现金账户扣、不够即成未付账单；后付记应收）。一笔费用可以由两部分支付，账单上分开写明 |
| D-Q105-4 | **赠送只经一个流程** `QB_FEE_CREDIT_GRANT`（`subProcessOnly()`），每笔都有来源（§3.1），记录 `QbFeeCreditGrant`（只写一次）。同一发起方、同一来源键至多一笔（唯一约束），重复触发不会多发 |
| D-Q105-5 | **开户赠送自动发放**：入驻审核通过、资料录入完整（§3.2）且未被封禁时发；未认证发 `qb.fee-credit.grant.basic`（1,000），已认证发 `qb.fee-credit.grant.certified`（10,000）；先领了未认证的、之后通过认证的，**补差额**（另一笔，来源"认证补发"），合计不超过已认证的金额 |
| D-Q105-6 | **答题赠送**：平台的挑战发布（点亮者为发起方的平台知识结构图，Q90 §2.8，由运营商的官方账号发布）可以把"平台费 Kudos"设为合格时的奖励；发起方合格即以 `QB_FEE_CREDIT_GRANT`（来源"挑战"，来源键为发布与发起方）发放。这正好代替 Q90 §2.8"发起方答题暂时不给学分"，所以不动答题者的学分 |
| D-Q105-7 | **全部记账**（§3.3），平台的账只记"送出、用掉、作废"；赠送背后谁出钱，由财务线下记录，平台不反映，也不进运营商的结算 |
| D-Q105-8 | **运营商的分成**：用平台费 Kudos 支付的平台费**不计入**运营商的分成基数（Q87b / Q92 的"其发起方付的工具与资源费"），结算单上单独列出。否则平台会按自己送出去的额度给运营商分真钱（待需求方确认，§6 第 4 条） |
| D-Q105-9 | **首次上线即做**。开关与金额都是受控参数（四眼修改），活动的开始、结束与以后的金额只改参数、不改代码 |

## 2. 首次上线的范围（对 Q94 的影响）

Q94 §4 原定"首次上线平台不收钱"。需求方 2026-11-05 改为：**对发起方不免费**，赠送平台费 Kudos 首次上线就做（Q94 §3 第 7 项）。

**首次上线向发起方收哪些费用**，需要另定（§6 第 1 条）。已经能收的：
- Q87b 的月费与手工记费；
- Q47c 的受众规则费（扣款的 Q47c-2 尚未开发）；
- Q101 的配送费（只有计划）；
- AI 的费用（还没有收费的种类）。

在定下来之前，平台费 Kudos 照样发放、照样记账，只是暂时没有地方用。

## 3. 设计

### 3.1 赠送的来源

| 来源 | 来源键（唯一） | 金额 |
|---|---|---|
| `ONBOARDING`（开户） | `onboarding` | 未认证 `qb.fee-credit.grant.basic`，已认证 `qb.fee-credit.grant.certified` |
| `CERTIFIED_TOP_UP`（认证补发） | `certified` | 已认证金额 − 已领的开户金额 |
| `CHALLENGE`（答题） | `challenge:<发布>` | 挑战发布上设定的金额 |
| `MANUAL`（以后需要时） | 申请编号 | 总部经四眼申请（照 Q87b 的 `QB_FEE_REQUEST`）；首次上线不做 |

### 3.2 何时检查开户赠送

- **事件**：入驻审核通过、资料保存、主页审核通过、认证通过时，各发布一次检查。由逐项的消费者 `QB_FEE_CREDIT_ONBOARDING_CHECK`（`internal()`）在钱包锁内重读，条件全部满足才发。
- **条件**：
  - 开关 `qb.fee-credit.grant.enabled` 为真（不是真即什么也不发，以后打开也不补发此前的）；
  - 入驻已通过；
  - 资料完整；
  - 未被封禁。
- **资料完整的标准**：沿用商户中心概况的完成度清单（Q79）。服务端写同一条规则，例如基本信息、头像、公开主页已发布、至少一个商品，具体条目待确认（§6 第 2 条）。前端的清单与服务端的规则用同一组用例检查，不一致即失败。

### 3.3 账

新科目（科目代码由 Q9d 的映射参数 `qb.journal.account.<科目>` 给出，受控，首个值为空）：

| 科目 | 性质 | 维度 |
|---|---|---|
| 平台费 Kudos（赠送额度） | 负债 | 发起方 |
| 推广费 | 费用 | 来源（开户、认证补发、挑战、手工） |

| 事件 | 分录（来源单据） |
|---|---|
| 赠送 | 借 推广费 / 贷 平台费 Kudos（`QbFeeCreditGrant`） |
| 用平台费 Kudos 付费 | 借 平台费 Kudos / 贷 4120 平台使用费收入 + 2150 应付消费税（`QbFeeCharge`，同现金支付，只是借方换了） |
| 作废（若定了有效期，或发起方注销） | 借 平台费 Kudos / 贷 推广费（`QbFeeCreditGrant` 的作废记录） |

- **每日核对**加一项：平台费 Kudos 科目按发起方的余额 = 各发起方 `FEE_CREDIT` 钱包的余额。
- **月报** `qb.admin.monthly` 加三类：`FEE_CREDIT_GRANTED`、`FEE_CREDIT_USED`、`FEE_CREDIT_VOIDED`，并加一列平台费 Kudos 的余额（`AdminFinanceIT` 逐行）。
- **分录导出**（Q9d）按发起方列出平台费 Kudos 的行。
- **消费税**：用赠送额度支付的平台费，在会计与消费税上算"値引き"还是"販促費"，要请财务或税理士确认。上表是按"販促費"写的：收入照常计、另记推广费。若定为"値引き"，则使用时冲减收入，账单的税基随之改变。两种系统都能做到。

### 3.4 受控参数（`ControlledParams`，四眼）

| 参数 | 缺省 | 说明 |
|---|---|---|
| `qb.fee-credit.grant.enabled` | false | 开户赠送的开关（活动开始、结束） |
| `qb.fee-credit.grant.basic` | 1000 | 未认证的金额 |
| `qb.fee-credit.grant.certified` | 10000 | 已认证的金额 |
| `qb.fee-credit.valid-days` | 空（永久） | 有效期（待确认，§6 第 3 条） |

### 3.5 界面

- **发起方后台**：
  - 钱包页单独一块"平台费 Kudos（赠送）"，写明"只能用于支付平台费用，不能发奖"；显示余额、每笔赠送（来源、金额、有效期）与使用；
  - 概况加一张卡；
  - 账单与收据写明"其中以平台费 Kudos 支付 X"；
  - 资料未完整时，概况的完成度清单旁提示"完成后可获赠平台费 Kudos"。
- **总部后台**：赠送列表（按来源、发起方、期间）与合计；受控参数页照常出现新参数。
- **运营商后台**：自己的发起方领到的赠送（只读）。

## 4. 测试

- `FeeCreditRulesTest`（纯 Java）：支付顺序（先赠送额度、再现金或应收，一笔两部分）、开户与补发的金额、资料完整的规则（与前端同一组用例）。
- `FeeCreditIT`：
  - 开关关着不发；通过且完整才发；未认证 1,000，之后认证补 9,000；重复事件不多发；
  - 封禁的不发；
  - 付费先用赠送额度，不够的照预付或后付；
  - 赠送额度不能换学分、不能发奖（没有这样的流程，学分钱包不变）；
  - 每日核对与月报的新项；
  - 运营商结算不计赠送额度支付的部分；
  - 注销时作废并记账。
- 挑战赠送随 Q90 T1a 的挑战发布一起测试。
- 前端：钱包的新卡、账单的两部分、完成度提示、axe；e2e：发起方补全资料、入驻通过 → 收到 1,000 → 记一笔月费（或手工记费）→ 账单显示由平台费 Kudos 支付。
