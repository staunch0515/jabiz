# Q48 运营商（代理）模式（计划，2026-10-28，待确认）

需求方（2026-10-28）：平台以后可以找多个地区或行业的**代理**，代理就是**运营商**：在受限的后台中管理自己的商户，审核由运营商终审、总部抽查，收费全部记在运营商名下。
地区与行业只是运营商自己的经营思路，平台不按地区或行业做限制。运营商暂时不需要很多员工，像商户一样（一个负责人加几位成员）即可。
**还没有正式的运营商之前，先做"一个运营商"的模式**；资金先由平台代收、按月结算，以后再支持运营商直接收款；平台按比例分成。

在 1.3 上开发（需要新表）。

## 1. 决定

| # | 决定 |
|---|---|
| D-Q48-1 | **运营商是商户的归属方**：每个普通商户（`SPONSOR`）归属一个运营商。系统先有一个运营商"直营"（总部自己），现有与新入驻的商户都归它；签下第一个真正的运营商后，由总部建运营商并按约定把商户改派过去（改派留历史）。Shopify 商店（`SHOPIFY_SHOP`）不属于运营商 |
| D-Q48-2 | **第一阶段只支持一个对外的运营商**：运营商后台看到的是**全部**普通商户（直营之外只有它一家时，它的商户就是全部对外商户）——不需要平台按行限制数据。多个运营商同时存在、互相看不到对方，是第二阶段（Q48c，需要平台的"按分配范围限制行"，见 §4） |
| D-Q48-3 | **运营商后台**：新的登录入口 `operator`（只接受角色 `QB_OPERATOR`，令牌只含运营商的权限，**必须二次验证**），复用 `/admin` 的页面，菜单按权限只显示允许的部分。成员像商户的店员：负责人在后台添加、移除成员 |
| D-Q48-4 | **运营商能做**：商户入驻审核、发布审核（**终审**）、商户与发布的查看、发布的下架与恢复、商户的封禁（附原因）、答题统计（汇总）、现金奖励 / 兑换 / 电子奖品的争议处理、群发通知、本运营商的结算单。**不能做**：财务（充值核对、银行设置、手工加币、转账审核与付款、账本与凭证）、法律文本、业务参数、角色与权限、投资人指标、答题者的个人资料（只看汇总） |
| D-Q48-5 | **总部抽查**：总部后台多一页"运营商审核记录"：按运营商、时间列出运营商通过与驳回的商户和发布，可标记"已抽查 / 有问题"；有问题时总部照常可下架、封禁（总部的操作优先，运营商不能撤销总部的处理） |
| D-Q48-6 | **收入记在运营商名下**：商户的答题奖励抽成（4110）按商户的运营商记账（账本维度"运营商"）；答题者提现的手续费不属于任何运营商（总部）。商户的充值是预收款（负债），不是收入，照旧由平台代收 |
| D-Q48-7 | **按月结算、按比例分成**：每月为每个运营商出结算单：该月其商户的抽成合计 × (1 − 平台分成比例) = 应付运营商。分成比例按运营商设置，以受控参数（四眼）修改。结算单为单据（PDF 存档），总部财务确认付款（银行转账，登记后另一位管理员批准，与现有的银行转账一致）；"直营"不出结算单 |
| D-Q48-8 | **以后改为运营商直接收款**：数据模型中运营商带"收款方式"（`PLATFORM` 代收 / `DIRECT` 直收，第一阶段只有 `PLATFORM`）；直收（运营商自己的 Stripe 账户、以运营商名义开收据、各自的提现资金）是另一个阶段，届时另写计划 |

## 2. 分期

| 分期 | 内容 | 估计 |
|---|---|---|
| Q48a | 运营商与成员、商户归属（直营与改派）、`operator` 入口与 `QB_OPERATOR` 权限、运营商在 `/admin` 中可见的页面、审核为终审、总部抽查页 | 5–6 天 |
| Q48b | 账本维度"运营商"与抽成按运营商记账、月结算单（单据）、分成比例（受控参数）、付款登记与审批、运营商后台的结算页 | 4–5 天 |
| Q48c | 多个运营商互相隔离（平台的按分配范围限制行 + 流程中核对对象归属）、商户入驻时按运营商的邀请链接归属 | 平台 4–5 天 + QuizBuks 3–4 天，有第二个运营商时再做 |
| （以后） | 运营商直接收款（D-Q48-8） | 另写计划 |

## 3. Q48a、Q48b 的实现要点

- **迁移**（1.3 当时的下一个号）：
  - `qb_operator`（运营商：名称、联系人、联系邮箱、收款方式、分成比例的参数键、状态）与 `qb_operator_member`（运营商、用户、负责人 / 成员，与店员表 `qb_sponsor_staff` 同样的写法）；
  - 商户的运营商：`QbSponsor` 是只追加表，按 D58 **只加列** `operator_id`（旧行为空即"直营"，由迁移以常量给出直营的编号）；改派是新版本，历史自然保留；
  - 结算：`qb_operator_settlement`（运营商、月份、抽成合计、比例、应付、状态、单据编号、付款）。
- **流程**：
  - `QB_OPERATOR_CREATE` / `UPDATE`、`QB_OPERATOR_MEMBER_ADD` / `REMOVE`、`QB_SPONSOR_OPERATOR_ASSIGN`（改派，总部）；
  - 现有的商户与发布审核流程**不变**，只是把 `QB_OPERATOR` 列入它们的权限（终审）；
  - `QB_REVIEW_SPOT_CHECK`（总部抽查标记）；
  - `QB_OPERATOR_SETTLEMENT_RUN`（月度任务，`JobDefinition`，每个运营商一项）、`QB_OPERATOR_SETTLEMENT_PAY`（登记付款，审批后过账）。
- **权限与入口**：`QB_OPERATOR` 只给 §1 D-Q48-4 列出的权限；角色 `requireMfa`；入口 `operator` 的 `app-path` 为 `/admin/`（同一前端，按入口登录）。
  - 后台扩展的菜单本来就按权限隐藏，运营商看不到财务、法律、参数等页面。
  - 通用后台的实体页：运营商只拿到它需要的数据视图的权限。第一阶段只有一个对外运营商，看到全部普通商户是预期的（D-Q48-2）。
  - Shopify 商店的数据不给运营商。
- **账本**（02-design §4）：
  - 加维度"运营商"（位置 3），`QB_ATTEMPT_SUBMIT` 等结算奖励时 4110 行带上商户的运营商；
  - 新科目 `2140 应付运营商分成`（负债，维度运营商）与 `5130 运营商分成`（费用）。结算单确认：借 5130 / 贷 2140；付款批准：借 2140 / 贷 1120。
  - 汇总凭证（Q9d）的映射要加这两个科目。
- **单据**：版式 `qb.operator-settlement`（三语），发出方信息来自数据（平台的开具方），收件方为运营商。
- **测试**：
  - IT：运营商入口只给 `QB_OPERATOR`、没有二次验证即拒绝；运营商能审核、不能做财务、法律与参数；抽查标记；改派的历史；抽成按运营商记账；月结算的金额与过账；付款审批的四眼。
  - 场景：一个月内两个商户的答题、结算与付款。
  - e2e：运营商登录后台、只看到允许的菜单、审核一份发布。
  - 现有场景的快照：4110 行多一个维度，快照会变，属预期的改动。

## 4. 平台需要的（Q48c 时）

- **按分配范围限制行**（新决策）：角色分配带"范围值"（如 `operator = op_01`），像现有的 `dataFrom` / `dataTo` 一样进入令牌与请求上下文；数据视图与模板声明 `scope(s -> s.withinAssignment("operator", "operatorId"))`，或经引用（发布 → 商户 → 运营商）；没有范围值即什么都看不到。
- **流程中核对对象归属**：审核、下架、封禁等以对象为参数的流程，平台步骤核对对象在调用者的范围内（不能只靠页面）。
- 第一阶段不需要这两项，所以 Q48a、Q48b 不改平台。

## 5. 待需求方确认

1. D-Q48-4 中运营商能做与不能做的清单。
2. 平台分成比例的初始值（例如 20%），以及结算周期是否按自然月（UTC 还是日本时间：建议日本时间，与会计年度一致）。
3. 直营之外的第一个运营商，是在 Q48a 完成后由总部建立，商户按约定改派，还是新商户一开始就由它招募。
4. 运营商结算单与付款是否需要扣除 Stripe 手续费（5110）的分摊（建议不扣，简单）。
5. 隐私政策：运营商处理商户资料，属于委托处理，政策第 5 条要加一行（发布运营商模式前更新）。
