# Q48 运营商（代理商）与 AI 获客（计划，2026-10-28；需求方 2026-10-29 确认 §6）

需求方（2026-10-28）：
- 平台以后可以找多个地区或行业的**代理商**，代理商就是**运营商**：在受限的后台中管理自己的商户。
- 地区与行业只是运营商自己的经营思路，**平台不按地区或行业做限制**。
- 运营商的审核就是**终审**，总部只做**抽查**。
- **收费全部记在运营商名下**；资金先由平台**代收、按月结算**，以后再支持运营商**直接收款**；平台按**比例**分成。
- 运营商暂时不需要很多员工，像商户的店员那样即可。
- 还没有正式找到运营商之前，先做"**一个运营商**"的模式。
- **AI 获客助手**是运营商的功能：在网上找商户、分析与 QuizBuks 的匹配度，匹配度高的用 AI 以商户自己的产品出题，每天发几十封定制邮件，天天持续。总部（"直营"运营商）同样使用它。

做完后平台有四个登录入口：**答题者**（`app`，`/taker/`）、**商户**（`sponsor`，`/sponsor/`）、**管理**（`admin`，`/admin/`）、**运营商**（`operator`，`/operator/`）。另有只在 Shopify 后台内嵌使用的 `shopify` 入口，不面向一般用户。

在 1.3 上开发（需要新表）。全部分期在工作分支 `1.3/quizbuks-48-operators` 上完成后一次合并到 `1.3/quizbuks`（需求方 2026-10-29）。

## 1. 决定

| # | 决定 |
|---|---|
| D-Q48-1 | **运营商是商户的归属方**：每个普通商户（`SPONSOR`）归属一个运营商。系统先有运营商"直营"（总部自己），现有与新入驻的商户都归它；签下第一个真正的运营商后，由总部建运营商；现有商户**留在直营**，新运营商只招新，个别商户经双方同意后由总部逐个改派（改派留历史）。Shopify 商店（`SHOPIFY_SHOP`）不属于运营商 |
| D-Q48-2 | **第一阶段只有一个对外运营商**：它在运营商后台看到全部普通商户，不需要平台按行限制数据。多个运营商同时存在、互相看不到对方，是 Q48e（需要平台的"按分配范围限制行"，§5） |
| D-Q48-3 | **运营商后台 `/operator/`**：新的登录入口 `operator`（只接受角色 `QB_OPERATOR`，令牌只含运营商的权限，**必须二次验证**）。页面复用管理后台的前端，另以入口 `operator` 构建一份，挂在 `/operator/`，菜单按权限只显示允许的部分。成员像商户的店员：负责人在后台添加、移除成员 |
| D-Q48-4 | **运营商能做**：商户入驻审核、发布审核（**终审**）；商户与发布的查看、下架与恢复；封禁商户（附原因）；答题统计（汇总）；兑换与电子奖品这类**不动钱**的争议处理（涉及退款或改付现金奖励的交总部财务）；**只给本运营商商户**的群发通知（给答题者的公告仍由总部发）；本运营商的结算单；**AI 获客**（§3）。**不能做**：财务（充值核对、银行设置、手工加币、转账审核与付款、账本与凭证）、法律文本、业务参数、角色与权限、投资人指标、答题者的个人资料（只看汇总） |
| D-Q48-5 | **总部抽查**：总部后台多一页"运营商审核记录"，按运营商、时间列出运营商通过与驳回的商户和发布，可标记"已抽查 / 有问题"。有问题时总部照常可以下架、封禁；总部的处理优先，运营商不能撤销 |
| D-Q48-6 | **收入记在运营商名下**：商户答题奖励的抽成（4110）按商户的运营商记账（账本维度"运营商"）；答题者提现的手续费归总部。商户的充值是预收款（负债），照旧由平台代收 |
| D-Q48-7 | **按月结算、按比例分成**：每月为每个运营商出结算单，应付运营商 = 该月其商户的抽成合计 × (1 − 平台分成比例)。分成比例按运营商设置，以受控参数（四眼）修改，初始值 20%；结算的月份按日本时间（`jabiz.fiscal-year-zone` = `Asia/Tokyo`，与分录导出的期间相同）。运营商的收入来源是抽成 4110：`qb.creator-fee-rate` 为 0 时应付即为 0，开始结算前由总部以四眼把它调到 0 以上（需求方 2026-10-29 选 (a)）。结算单是存档的 PDF 单据，总部财务登记付款、另一位管理员批准；"直营"不出结算单。运营商的 AI 获客费用（§3）按实际用量按月从应付中扣除，不足的差额结转到下月（应付不为负）；每个运营商另有获客的月度费用上限（受控参数），到上限当月停跑 |
| D-Q48-8 | **以后改为直接收款**：运营商带"收款方式"（`PLATFORM` 代收 / `DIRECT` 直收，第一阶段只有 `PLATFORM`）；直收届时另写计划 |
| D-Q48-9 | **AI 获客属于运营商**：搜索方向、候选商户、发件服务器、每日上限、体验问卷都归运营商；经它的邀请链接注册的商户自动归属它（这也是多运营商时归属的主要来源） |

## 2. 分期

| 分期 | 内容 | 估计 |
|---|---|---|
| Q48a | 运营商与成员、商户归属（直营与改派）、入口 `operator` 与 `/operator/`、`QB_OPERATOR` 的权限、审核为终审、总部抽查页 | 5–6 天 |
| Q48b | 账本维度"运营商"、抽成按运营商记账、月结算单（单据）、分成比例（受控参数）、付款登记与审批、运营商后台的结算页 | 4–5 天 |

| Q48d | AI 获客（二）：漏斗统计、按来源追踪注册（注册即归属该运营商）、一次自动跟进、高分自动发送、按效果调整搜索方向、获客费用计入结算 | 约 1 周 |
| Q48e | 多个运营商互相隔离：平台按分配范围限制行、流程中核对对象归属（§5）；有第二个运营商时再做 | 平台 4–5 天 + QuizBuks 3–4 天 |
| （以后） | 运营商直接收款（D-Q48-8） | 另写计划 |

建议顺序：Q48a → Q48c → Q48b → Q48d（Q48e 等第二个运营商）。直营运营商一建好就可以用 AI 获客做冷启动，结算要等真正的运营商出现才需要。

## 3. AI 获客（Q48c、Q48d）

### 3.1 每天的流程

1. **找商户**：按运营商设定的"搜索方向"（行业、关键词、地区，例如"新上市的护肤品牌""用 Shopify 开店的咖啡品牌"），用 Claude 的网页搜索找新的候选；按域名去重，跳过找过的、拒绝过的与不发名单中的。
2. **研究网站**：读首页、产品页与联系页面，整理出公司名、主要产品、网站语言、国家或地区、是否网上销售或用 Shopify、**网站上公开的联系邮箱**。遵守 `robots.txt` 并限速；网站写明拒收营销邮件的，直接跳过。
3. **匹配度打分**（0–100，附理由）：
   - 产品是否需要解释、有没有故事；
   - 是否面向消费者；
   - 规模：不是个人小摊，也不是全国连锁；
   - 有无促销习惯；
   - 语言是否在日、中、英之内；
   - 是否 Shopify 店（推荐 Shopify 应用）。
   
   低于门槛（运营商可设，缺省 70）的只记录。
4. **AI 出题并发布体验问卷**：以商户自己的产品页为素材，用现有的 AI 出题（Q8）生成 5 道题，以运营商的"体验"商户账号发布为**不设奖励**的公开问卷；生成带来源标记的分享链接（Q15）与二维码。
5. **写定制邮件**：按网站语言写，短得像个人来信：
   - 提到对方的具体产品，附问卷链接与二维码；
   - 一句话说明 QuizBuks 能做什么（是 Shopify 店的话，推荐 Shopify 应用）；
   - 附带来源标记的注册链接；
   - 每封都有**退订链接**、发件人名称与地址。
6. **人工批准**：运营商后台的"今日待发"页，按分数列出问卷与邮件，可以批准、修改或丢弃。用别人的品牌出题，题目要准确、不能有贬低的内容，所以先全部人工批准；Q48d 后可设"高于某分自动发送"。
7. **按每日上限发送**：经运营商自己登记的发件服务器（与 Q29 商户邮件服务器同样的 `SendMail.via` 与密封密码），专门的发件域名，设好 SPF / DKIM / DMARC；不经平台的系统邮件服务器，不用 `quizbuks@gmail.com`。每日上限从 20 封开始，几周内逐步加到 50；退信与投诉自动停发并告警。
8. **跟踪**（Q48d）：漏斗：找到 → 合格 → 已发 → 点开问卷 → 答完 → 回复 → 注册商户 → 首次发布。按搜索方向与行业比较转化率，调整方向。
9. **跟进**（Q48d）：7 天没有回应，发一次简短的跟进后停止。退订或回复"不需要"的，进永久不发名单（按运营商，也对全平台生效）。

### 3.2 实现要点

- **调用 Claude**：全部经外部作业（`StartExternalJob`），处理器用 Anthropic 的网页搜索与网页读取工具；用量记录、支出上限、没有回答的尝试按估计计费（D52）。每个候选的费用估计为几美分到二三十美分。
- **每天运行**：定时任务 `JobDefinition.forEach`，每个候选一项、各自提交；每个运营商一个开关（布尔参数，`enabledBy`）。
- **数据**（新迁移）：搜索方向、候选商户（域名、研究结果、分数与理由、状态）、体验问卷的对应、发出的邮件（内容、发送时刻、退信与回复状态）、不发名单（邮箱与域名）。
  - 候选与邮件都属于运营商。
  - 公开邮箱属于对方的业务信息，只用于这一用途；不发名单永久保留，其余按 `RetentionPolicy` 保存一段时间后删除。
- **退订页**：给不是用户的收件人用的简单公开页面（带签名的链接，不需要登录）。
- **页面**：运营商后台的"获客"组（搜索方向、今日待发、已发与漏斗、不发名单、发件服务器）；总部后台能看所有运营商的获客情况。
- **测试**：
  - 单元：评分表的解析、去重与不发名单、每日上限、退订链接的签名；
  - IT：从找到到发送的整条流程（外部服务以桩代替）、没有批准不发送、超出上限不发送、退信与退订后不再发送、费用计入结算；
  - e2e：运营商登录后批准一封并在漏斗中看到。

### 3.3 发送的底线

内置在系统里，不靠人记：
- 每封都有退订与发件人信息；
- 退订与拒绝永久生效；
- 只用网站上公开的业务邮箱，跳过声明拒收的网站；
- 每日上限与退信、投诉时自动停发。

## 4. Q48a、Q48b 的实现要点

- **迁移**（1.3 当时的下一个号）：
  - `qb_operator`：名称、联系人、联系邮箱、收款方式、分成比例的参数键、状态；
  - `qb_operator_member`：与店员表 `qb_sponsor_staff` 同样的写法，负责人与成员；
  - 商户的运营商：`QbSponsor` 是只追加表，按 D58 **只加列** `operator_id`。旧行为空即"直营"，改派是新版本，历史自然保留；
  - 结算：`qb_operator_settlement`（运营商、月份、抽成合计、比例、获客费用、应付、状态、单据编号、付款）。
- **流程**：
  - `QB_OPERATOR_CREATE` / `UPDATE`、`QB_OPERATOR_MEMBER_ADD` / `REMOVE`、`QB_SPONSOR_OPERATOR_ASSIGN`（改派，总部）；
  - 现有的商户与发布审核流程不变，只把 `QB_OPERATOR` 列入它们的权限；
  - `QB_REVIEW_SPOT_CHECK`（总部抽查标记）；
  - `QB_OPERATOR_SETTLEMENT_RUN`（月度任务）与 `QB_OPERATOR_SETTLEMENT_PAY`（登记付款，审批后过账）。
- **入口与前端**：
  - `jabiz.security.entries.operator`（`accepted-roles: QB_OPERATOR`、`app-path: /operator/`、会话按标签页、闲置 30 分钟）；
  - `jabizApp { spa("/operator/", 管理后台的前端, entry = "operator") }`：同一份管理后台以入口 `operator` 另构建一次。
- **账本**（02-design §4）：
  - 加维度"运营商"（位置 3）；
  - 新科目 `2140 应付运营商分成`（负债）与 `5130 运营商分成`（费用）。结算单确认：借 5130 / 贷 2140；付款批准：借 2140 / 贷 1120；
  - 汇总凭证（Q9d）的映射加这两个科目。
- **单据**：版式 `qb.operator-settlement`（三语）。
- **测试**：
  - IT：入口只给 `QB_OPERATOR`、没有二次验证即拒绝；运营商能审核、不能做财务与参数；抽查标记；改派的历史；抽成按运营商记账；月结算的金额与过账；付款审批的四眼；
  - 场景：一个月内两个商户的答题、结算与付款；
  - e2e：运营商登录后只看到允许的菜单并审核一份发布；
  - 现有场景的快照：4110 行多一个维度，属预期的改动。

## 5. 平台需要的（Q48e 时）

- **按分配范围限制行**（新决策）：
  - 角色分配带"范围值"（如 `operator = op_01`），像现有的 `dataFrom` / `dataTo` 一样进入令牌与请求上下文；
  - 数据视图与模板声明 `scope(s -> s.withinAssignment("operator", "operatorId"))`，或经引用（发布 → 商户 → 运营商）；
  - 没有范围值即什么都看不到。
- **流程中核对对象归属**：审核、下架、封禁、获客等以对象为参数的流程，平台步骤核对对象在调用者的范围内，不能只靠页面。
- Q48a–Q48d 不需要这两项，不改平台。

## 6. 需求方的确认（2026-10-29）

1. 运营商能做与不能做：照 D-Q48-4，另改两处：群发通知只发给本运营商的商户；争议处理只限不动钱的（兑换、电子奖品），退款与改付现金交总部财务。
2. 平台分成比例初始 20%；结算按日本时间的自然月。运营商的收入来源为抽成 4110（做法 (a)），开始结算前把 `qb.creator-fee-rate` 调到 0 以上。
3. 现有商户留在直营；第一个运营商只招新，个别商户由总部逐个改派。
4. 获客费用按实际用量从结算中扣除，直营不扣；扣不完结转下月，不出现负的应付；每个运营商有获客的月度费用上限，到上限当月停跑。
5. 发件用**独立的域名**（不用 `quizbuks.com` 的子域名，冷邮件的信誉不连累系统邮件）；不用 Amazon SES（其条款不允许未经同意的邮件），用该域名的普通邮箱（Google Workspace 或 Zoho）经 SMTP 发送（`SendMail.via`）；第一批搜索方向只做日本（《特定電子メール法》允许给公开且未声明拒收的业务邮箱发送），暂不做欧盟。
6. 隐私政策三语写明运营商受托处理商户资料、获客使用对方公开的业务邮箱与退订方法；条文在 Q48a 中起草，上线前由需求方或律师确认。

## 7. 实施记录

### Q48a（2026-10-29）

做成的与计划的差异（都按平台规则，不改平台）：

1. **成员由总部添加，负责人只能移除。** `QB_OPERATOR` 含 `approval.decide`，是受保护的权限（平台 D48）：授予它只经平台的 `SEC_USER_ROLE_ASSIGN` 与另一位超级管理员的审批，业务流程不能自己授予。所以"谁是哪个运营商的成员"（`qb_operator_member`，`QB_OPERATOR_MEMBER_ADD` / `REMOVE`，总部）与"能做什么"（角色）分开：
   - 两者都有才能登录 `/operator/`（`QbSignInGuard` 在入口 `operator` 另查当前的成员关系与运营商的状态）；
   - 每个运营商的动作再查一次成员关系（`OperatorChecks.member`：共享锁 `qb.operator-member:<用户>`，移除取排他锁，下一次动作即生效）；
   - 负责人以 `QB_OPERATOR_MEMBER_DROP` 移除本运营商的成员（两把成员锁按用户编号排序），不能移除自己；
   - 成员须已验证邮箱、不能有商户入驻（审核商户的人不是商户），一人同时只属于一个运营商，每个运营商至多 50 人。
2. **直营没有记录。** 没有归属的商户即总部的（D-Q48-1）；不建"直营"运营商行。
3. **商户的归属是普通表 `qb_sponsor_operator`**，不是 `QbSponsor` 的新列：入驻行只在申请后才有、绑定着审批内容、又是被封存的只追加表；改派（`QB_SPONSOR_OPERATOR_ASSIGN`，必填原因）改这一行，历史在平台审计中。改回总部即删除该行。
4. **运营商的下架与封禁是自己的流程**（`QB_OPERATOR_PUBLICATION_PAUSE` / `RESUME` / `END`、`QB_OPERATOR_SPONSOR_BAN` / `UNBAN`，权限 `qb.operator.use`），与总部的同一套代码，多查成员关系、多记运营商：
   - 发布加列 `takedown_operator_id`、封禁加列 `operator_id`（V37，只加列）；
   - 运营商只恢复、结束自己下架的发布，只解除自己的封禁，只封禁有入驻的商户；
   - 总部对运营商下架的发布再暂停、对运营商封禁的用户再封禁，即变成总部的（D-Q48-5：总部优先）。
5. **抽查**：运营商的决定 = 审批人在决定时是某运营商成员的平台审批决定（`ApprovalDecision`，按成员的加入、移除时间判断；移除的成员行保留）。模板 `qb.admin.operator-reviews`，`QB_REVIEW_SPOT_CHECK` 记 `OK` 或 `PROBLEM`（须写说明），每个决定一行、可再改。
6. **运营商读不到用户资料**（无 `qb.admin.users.read`）：商户的列表、审核页的入驻内容与邮箱都经它自己的模板 `qb.operator.sponsors`；概况 `qb.operator.overview` 只给合计；团队经只读流程 `QB_OPERATOR_TEAM`（模板一个实体只能经一个数据视图读，而"调用者自己的成员关系"是单独的数据视图）。
7. **入口与前端**：`jabiz.security.entries.operator`（只接受 `QB_OPERATOR`，角色要求二次验证，会话在标签页、闲置 30 分钟，不开放注册）；同一个管理后台前端以入口 `operator` 再构建一份挂在 `/operator/`，菜单按权限：运营商看到"运营商"组（首页、商户）与审核、Quiz、发布、兑换、电子奖品；看不到用户、答题记录、财务、法律文本、公告、AI、运营商管理。
8. **隐私政策**三语草稿已加：第2条第4项（事业者的公开信息）、第3条第8–9项、第5条两行（运营商、获客时的 Anthropic）、第8条一行（获客记录最后一次介绍后 1 年删除，退订的邮箱与域名无限期保存）。

测试：`OperatorIT`（总部建运营商与成员、入口只放行当前成员、运营商下架与恢复、封禁与解封、改派、抽查）、`QbRolesTest`（运营商的权限清单）、扩展的 `operator.test.tsx`（五个页面与运营商看到的审核页）。

### Q48c 的实施设计（2026-10-29）

计划 §3 的流程不变；做法上的决定：

1. **获客的所有者**是 `owner`：运营商编号，或总部的 `direct`（直营没有运营商行，§7 Q48a 第 2 条）。调用者是某运营商的当前成员即为该运营商，否则为直营（只有持有 `qb.prospect.use` 的总部角色，即内容管理员与超级管理员）。
2. **两种外部作业**（D38，处理器不访问数据库，只经外部服务 `anthropic`）：
   - `qb.prospect.find`：按一个搜索方向，Claude 以网页搜索（`web_search_20260318`，至多 5 次）找候选的网站，输入带上已知的域名与不发名单的域名（至多 300 个）以免重复；
   - `qb.prospect.research`：按一个候选，Claude 以网页读取（`web_fetch_20260318`，至多 4 次，每次至多 20 000 tokens；只能读对话中出现过的地址，读取遵守对方的 `robots.txt`，被拒即 `url_not_allowed`）与搜索，**一次**给出：公司名、商品、网站语言与国家、是否网上销售与 Shopify、公开的业务邮箱、网站是否声明拒收营销邮件、匹配度分数与理由、体验问卷（标题、简介、5 题，每题 4 个选项与正确答案）、定制邮件（标题与正文，按网站语言）。
   - 两者都不用结构化输出（网页搜索总带引用，与 `output_config.format` 不兼容），而是要求以一个 JSON 对象结尾，服务器按 schema 逐项核对，不合格即重试；`pause_turn` 时原样续发（至多 3 次）。用量按 tokens 与搜索次数（每千次 10 美元）记入 `QbProspectUsage`，没有回答的尝试按预估计入（与 Q8 相同，D52）。
3. **体验问卷不建成 QuizBuks 的发布**（与计划 §3.1 第 4 步不同）：发布要有商户账户、钱包与审核，而对方不是我们的用户。问卷存在候选行上，批准后经公开模板 `qb.public.prospect-trial`（只给已发出的、未退订的，按随机的公开令牌）在商家后台的公开页 `/sponsor/try/<令牌>` 显示：不需登录即可作答（浏览器中判分），页面上是"用自己的商品出这样的问卷——注册商户"，注册链接带来源 `?src=<令牌>`（Q48d 据此归属运营商）。
4. **邮件**：模板 `qb.prospect`（`NOTIFICATION`，入口 `sponsor`），正文 = 批准的定制正文 + 体验问卷的链接 + 发件人名称、住所与联系方式（《特定電子メール法》的表示义务）+ `{unsubscribeUrl}`；发给地址（`MailRecipient.address`），平台按地址退订（D55），只经 `SendMail.via("prospect:<owner>")` 从所有者登记的服务器发出（复用商户邮件服务器的表与 `MailSenderSource`，键为 `prospect:<owner>`），没有验证过的服务器即不发。
5. **不发名单** `QbProspectBlock`（邮箱或域名，全平台生效）：退订（读平台的 `MailAddressOptOut`）、对方说"不需要"（人工标记）、退信与投诉（人工标记）、网站声明拒收；找与研究都先查它，发送前再查一次。
6. **人工批准**："今日待发"列出 `DRAFTED` 的候选（按分数），可修改邮件的标题与正文、问卷的题目，然后批准（`APPROVED`）或丢弃；**每日发送**由逐项任务在日本时间 10 点起发出已批准的，至多当天的上限（所有者的设置，20–50），每项一个事务。
7. **设置** `QbProspectSetting`（每个所有者一行）：开关、每日上限、分数门槛（缺省 70）、每月费用上限（美元）、发件人名称、住所、联系邮箱；总开关是受控参数 `qb.prospect.enabled`（两种作业类型 `enabledBy` 它）。
8. **每日任务** `qb.prospect-daily`（逐项任务，每个开启的所有者一项）：每个启用的方向在待研究的候选少于需要时开一个找的作业；为 `FOUND` 的候选开研究作业，至多当天上限的两倍；当月费用已到上限即不开新作业。
