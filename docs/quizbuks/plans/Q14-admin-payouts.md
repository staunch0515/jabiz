# Q14 后台：答题情况、Kudos 与立即转账

需求方 2026-10-23："在管理端无法看到用户的答题情况以及得到的 Kudos，也不把 Kudos 转到他的银行账户（经 Stripe）。"
确认的范围（全部）：答题记录页、用户列表与用户页的 Kudos 合计、收款状态（为什么没有转）、财务的"立即转账"。先 Q14、再 Q13b。

## 1. 为什么"没有转"

自动转账（`QB_TRANSFER_CREATE`，每日 01:07 UTC）只在以下全部成立时发出：开关 `qb.transfer.enabled`（**缺省关闭**，受控参数）、
收款账户 `ENABLED`、余额 ≥ 门槛、未封禁、没有未结束的转账、未暂停、手续费不超过金额等（`TransferRules` 的跳过码）。
以前后台看不到是哪一条挡住了；Q14 让财务直接看到原因。

## 2. 做了什么

| 部分 | 内容 |
|---|---|
| `QB_TRANSFER_PREVIEW` | 财务（`qb.admin.finance.read`）。与每日任务同一组读取与同一条规则（`TransferProcesses.planOf`），只返回结论：会不会转、跳过码、金额 / 手续费 / 实付、是否进审核、余额与保留中的奖励。不写业务数据（只有平台的操作记录），不取锁 |
| `QB_TRANSFER_NOW` | 新权限 `qb.transfer.now`（财务角色），要求已验证邮箱。与每日任务相同的步骤（`createSteps`：取用户钱包锁、同样的检查）；不能转给自己（422 `QB_TRANSFER_NOW_OWN`）。不满足条件时不写记录，返回原因。超过审核额时也不写（`REVIEW_NOT_NOW`），由每日任务以收款人为准备人提出审批：否则点击的财务自己就能审批自己发起的转账 |
| 模板 `qb.admin.taker-kudos` | 财务。每个用户：答题次数、完成次数、已得 Kudos（已付奖励减手续费）、完成（已提交）、待付奖励、余额与转账中（钱包缓存，账本为准）、已转出（SENT 的实付减去被撤回的部分） |
| 后台扩展 | 答题记录页 `/qb/attempts`（按用户、发布、状态、奖励状态筛选；财务另见每次的 Kudos）；用户列表的财务列；用户页的 `PayoutPanel`（Kudos 合计、收款状态与原因、"立即转账"） |

不改表，没有迁移。`QB_SETUP` 给财务角色加上 `qb.transfer.now`（四眼发布，同其他角色变更）。

## 3. 独立评审的修正

| 级别 | 问题 | 处理 |
|---|---|---|
| H1 | 大额"立即转账"进审批时准备人是收款人，点击的财务可以审批自己发起的转账 | 立即转账不提出审批（`REVIEW_NOT_NOW`，不写记录），由每日任务提出；后台在超过审核额时不显示按钮 |
| M1 | 已转出没有减去部分撤回 | `sum(net - reversedAmount)` |
| M2 | 答题记录页对未付的奖励也显示 Kudos | 只显示 `PAID` 的 |
| M3 | 预览写操作记录，与"不写任何东西"的说法不符 | 改说法为"不写业务数据" |
| L1 | 换到另一用户时上一次转账的结果仍显示 | 面板以 `key={userId}` 重建 |
| L2 | 不是自己的判断依赖原样的字符串 | 去空白、不分大小写比较（大小写不同的编号本就找不到账户） |
| L3 | "完成"包含超时的答题 | 只计已提交 |
| L4 | 商家的用户页也有收款面板 | 保留：商家也可以答题 |

## 4. 测试
