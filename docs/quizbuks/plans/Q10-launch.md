# Q10 上线准备（计划，2026-10-16 确认）

需求 6.1；设计缺省 Q11（单个发布峰值 50 次提交 / 秒、同时进行的发布 ≤ 1 000、用户 ≤ 100 万）。
分支 `1.2/quizbuks-10<x>-…`（从 `1.2/quizbuks` 拉出）；平台需要的改动先在 `1.2/platform` 的 `1.2/phase-…` 分支上完成再合并过来（CLAUDE.md §8）。

## 1. 现状与最大的风险

Q5 的吞吐基线（`PlayThroughputIT`，本机、进程内）：**同一发布约 7.6 次完成 / 秒，提交 p95 约 5.7 秒**；目标 50 次 / 秒、提交 p95 < 1 秒。
单个发布的提交在发布锁（与商家钱包锁）上串行，每次提交在锁内约 30 条语句、约 120 ms，其中 `LEDGER_POST`（维度与来源核对、审计、变更事件）约占一半。
要达到 50 次 / 秒，锁内时间须降到约 20 ms 以下——这是 Q10 中唯一可能改变设计或体验的部分，所以排在最前面。

## 2. 拆分

| 阶段 | 分支 | 内容 | 预估 |
|---|---|---|---|
| Q10a | `1.2/quizbuks-10a-perf` | 压测工具与测量；按结果实施退路（见 §3 与问题 L-1、L-2） | 3–6 天（视退路） |

| Q10d | `1.2/quizbuks-10d-ops` | 部署与运维文档、首个生产环境的检查清单 | 1–2 天 |

## 3. Q10a 性能

1. **压测工具** `./gradlew :quizbuks:loadTest`（不在 `check` 中；参照平台 `app` 的 `loadTest`）：经 HTTP 与真实令牌，N 个答题人对同一发布开始并提交；
   另一组同时刷首页与详情（检查热门发布是否拖慢其他请求）；输出每秒完成数、p50 / p95 / p99、错误率、连接池等待，报告写入 `docs/quizbuks/perf/`。
2. **测量**：打包的 jar + 独立 PostgreSQL（规格写进报告）；基线、`EXPLAIN` 与锁内语句的耗时分解。
3. **退路**（按代价从小到大；L-1 决定做到哪一步）：
   - R1 降低锁内成本（应用内）：合并语句、只读的检查移到锁外、减少锁内的往返；
   - R2 降低 `LEDGER_POST` 的成本（**平台**，平台缺口 14：维度与来源核对的批量化、审计写入合并）；
   - R3 取锁前在进程内排队 + 入口限流（**平台**，缺口 13、15）：排队的请求不占数据库连接，热门发布不拖垮首页；
   - R4 分批过账：提交在发布锁内只写结果与"结算中"，后台每约 1 秒把一个商家的若干笔奖励合成一笔过账。锁内时间降到约 10 ms，
     但结果页要等约 1 秒才显示"已入账"（U-34 的体验改变），且分录不再一笔对应一次答题（Q9d 导出的明细粒度随之改变）。
4. **验收**：在报告的规格上，单个发布达到 L-2 选定的目标；热门发布期间首页 p95 不超过平时的 2 倍；错误率 0（除预期的 422：名额、预算）。

## 4. Q10b 安全审查

- 独立的全应用审查（认证与入口、权限矩阵、数据视图范围、模板参数、文件、入站 Webhook 与 Stripe、资金流程的幂等与锁、前端），按严重程度修正。
- 一并处理已登记的跟进：
  - 答题人经 `GET /api/files/{id}` 读到题目图片的原始文件名（可能泄露答案）——需要平台的文件策略选项（**平台**改动）；
  - 汇总凭证、导出文件与收据的保留期（`RetentionPolicy`，会计 7–10 年，见问题 L-4）。
- 依赖与镜像：`gradle dependencies` / `pnpm audit` 的已知漏洞（Reactor Netty CVE 的升级此前已决定推迟，在此重新评估）。

## 5. Q10c Stripe 测试模式全流程

- 用真实的 Stripe **测试**密钥（不是桩）：充值（Checkout）、Webhook、Connect Express 开户（测试账户）、自动转账、打款到银行（`payout.paid`）、退款与争议各一次。
- 形式：手动运行的脚本 + 记录（`docs/quizbuks/perf/` 旁的 `stripe-test-mode.md`），可选的 CI 作业（只在仓库有测试密钥的 secrets 时手动触发）。
- 需要：Stripe 测试账户的密钥与 Webhook 签名密钥、一个可从 Stripe 访问的地址（见问题 L-3）。

## 6. Q10d 部署与运维

- `deploy/quizbuks/README.md` 扩充为生产手册：环境变量与密钥清单（哪些必须、来源、轮换）、数据库备份与恢复演练、首次启动（`QB_SETUP`、两位管理员与二次验证）、
  正式模式切换前的检查（`StripeModeCheck`、`TransferScheduleCheck` 的含义）、监控（OTLP、关键指标与告警建议）、常见故障（Webhook 被拒、核对差异、导出被拒）。
- 上线检查清单（法务意见：Q6b 的转账；收据措辞；隐私与条款）。

## 7. 已确认（2026-10-16，全部按建议）

| 编号 | 问题 | 结论 |
|---|---|---|
| L-1 | 性能退路允许做到哪一步 | **先测再定**：Q10a 先做 R1 与测量；R2、R3 是平台改动，测量结果出来后再确认；R4 改变用户体验，需要需求方同意 |
| L-2 | 目标是否仍为单发布 50 次 / 秒、提交 p95 < 1 秒 | **是**（设计缺省 Q11）；若实际业务峰值更低，请给出数字 |
| L-3 | Q10c 是否现在做（需要 Stripe 测试密钥与公网地址） | **做脚本与手册，由你在本机或测试服务器上运行**；CI 作业只在提供 secrets 后启用 |
| L-4 | 导出、凭证与收据的保留期 | **10 年**（日本法人税法 7 年、欠损金 10 年，取长者） |
| L-5 | 顺序 | **Q10a → Q10b → Q10c → Q10d**（性能可能改设计，先做；Q10b 可与 Q10a 的测量并行） |
