# Q10 上线准备（计划，2026-10-16 确认）

需求 6.1；设计缺省 Q11（单个发布峰值 50 次提交 / 秒、同时进行的发布 ≤ 1 000、用户 ≤ 100 万）。
分支 `1.2/quizbuks-10<x>-…`（从 `1.2/quizbuks` 拉出）；平台需要的改动先在 `1.2/platform` 的 `1.2/phase-…` 分支上完成再合并过来（CLAUDE.md §8）。

## 1. 现状与最大的风险

Q5 的吞吐基线（`PlayThroughputIT`，本机、进程内）：**同一发布约 7.6 次完成 / 秒，提交 p95 约 5.7 秒**；目标 50 次 / 秒、提交 p95 < 1 秒。
单个发布的提交在发布锁（与商家钱包锁）上串行，每次提交在锁内约 30 条语句、约 120 ms，其中 `LEDGER_POST`（维度与来源核对、审计、变更事件）约占一半。
要达到 50 次 / 秒，锁内时间须降到约 20 ms 以下——这是 Q10 中唯一可能改变设计或体验的部分，所以排在最前面。

## 3. Q10a 性能

1. **压测工具** `./gradlew :quizbuks:loadTest`（不在 `check` 中；参照平台 `app` 的 `loadTest`）：经 HTTP 与真实令牌，N 个答题人对同一发布开始并提交；
   另一组同时刷首页与详情（检查热门发布是否拖慢其他请求）；输出每秒完成数、p50 / p95 / p99、错误率、连接池等待，报告写入 `docs/quizbuks/perf/`。
2. **测量**：打包的 jar + 独立 PostgreSQL（规格写进报告）；基线、`EXPLAIN` 与锁内语句的耗时分解。
3. **退路**（按代价从小到大；L-1 决定做到哪一步）：
   - R1 降低锁内成本（应用内）：合并语句、只读的检查移到锁外、减少锁内的往返；
   - R2 降低 `LEDGER_POST` 的成本（**平台**，平台缺口 14：维度与来源核对的批量化、审计写入合并）；
   - R3 取锁前在进程内排队 + 入口限流（**平台**，缺口 13、15）：排队的请求不占数据库连接，热门发布不拖垮首页；
   - R4 分批过账：提交在发布锁内只写结果与"结算中"，后台每约 1 秒把一个商家的若干笔奖励合成一笔过账。锁内时间降到约 10 ms，
     但结果页要等约 1 秒才显示"已入账"（U-34 的体验改变），且分录不再一笔对应一次答题（Q9d 导出的明细粒度随之改变）。
4. **验收**：在报告的规格上，单个发布达到 L-2 选定的目标；热门发布期间首页 p95 不超过平时的 2 倍；错误率 0（除预期的 422：名额、预算）。

## 4. Q10b 安全审查

- 独立的全应用审查（认证与入口、权限矩阵、数据视图范围、模板参数、文件、入站 Webhook 与 Stripe、资金流程的幂等与锁、前端），按严重程度修正。
- 一并处理已登记的跟进：
  - 答题人经 `GET /api/files/{id}` 读到题目图片的原始文件名（可能泄露答案）——需要平台的文件策略选项（**平台**改动）；
  - 汇总凭证、导出文件与收据的保留期（`RetentionPolicy`，会计 7–10 年，见问题 L-4）。
- 依赖与镜像：`gradle dependencies` / `pnpm audit` 的已知漏洞（Reactor Netty CVE 的升级此前已决定推迟，在此重新评估）。

## 5. Q10c Stripe 测试模式全流程

- 用真实的 Stripe **测试**密钥（不是桩）：充值（Checkout）、Webhook、Connect Express 开户（测试账户）、自动转账、打款到银行（`payout.paid`）、退款与争议各一次。
- 形式：手动运行的脚本 + 记录（`docs/quizbuks/perf/` 旁的 `stripe-test-mode.md`），可选的 CI 作业（只在仓库有测试密钥的 secrets 时手动触发）。
- 需要：Stripe 测试账户的密钥与 Webhook 签名密钥、一个可从 Stripe 访问的地址（见问题 L-3）。

## 实施记录（Q10a，2026-10-16，分支 `1.2/quizbuks-10a-perf`）

报告：`docs/quizbuks/perf/Q10a-load-test.md`（环境、方法、逐次结果、锁内时间分解、退路预估与建议）。

- **压测工具** `./gradlew :quizbuks:loadTest`（`backend/quizbuks/src/loadTest/`，不在 `check` 中）：经 HTTP 与真实令牌驱动打包的 jar，准备全部走真实流程
  （`QB_SETUP` 与四眼发布、商家注册经 Mailpit 验证、入驻批准、经 Stripe 桩充值、发布批准上架、答题人注册验证；用户可复用，每次运行新建发布）；
  输出每秒完成数、p50 / p95 / p99、按状态与错误码的计数、首页 p95 的前后对比与钱包一致性检查；可选读取 `pg_stat_statements` 与采样 `pg_stat_activity`。
- **测量**（本机 4 vCPU，压测、应用、数据库同机；连接池 10）：分支头约 **20.7 次完成 / 秒**、提交 p95 约 2.3 秒，首页 p95 在压力下升 30–60 倍。
  每次完成在发布锁内：开始 12 ms / 13 条语句、提交 40 ms / 50 条语句；数据库执行只占约 15 %，其余是每条约 0.78 ms 的客户端往返，所以吞吐取决于锁内的语句条数。
  提交锁内 50 条中 27 条是 `LEDGER_POST`。进程内 `PlayThroughputIT` 在本机为 13.9 次 / 秒（Q5 记录的 7.6 是另一台机器）。
- **R1**（应用内，已做）：提交只读卡片，发布与排程行只在会结束或使发布预算不足时由新的子流程 `QB_PUBLICATION_COMPLETION_MOVE`（`subProcessOnly()`）读取并移动；
  开始时钱包的软检查移到发布锁之前。锁内 52.1 → 49.5 ms，吞吐 20.7 → 21.2 次 / 秒（HTTP），13.9 → 15.2 次 / 秒（`PlayThroughputIT`）。不变式与锁序不变；
  `QuotaBudgetIT` 增加断言（只有结束的那次完成调用移动子流程）。加大连接池实测无益（不改配置）。
- **退路的证据**（未实施，待决定）：R2（平台）预估约 30 次 / 秒，加上平台的通用开销（`HoldLock` 一条语句、提交前不重读、引用检查合并）约 40；R3（平台）不提高吞吐，但是首页不被拖累的唯一办法；
  R4 以实验 jar 实测上限 37.5 次 / 秒（单独不够）。另提出应用内的设计改动"锁拆分"（开始与提交各一把锁、计数拆成两行，§6.5）：与 R2 + 平台通用开销一起预估约 55–60 次 / 秒，与 R4 一起约 60–65。
  **结论：不做 R4 也可能到 50 次 / 秒，但需要平台的 R2 与通用开销改动以及锁拆分；建议顺序 R3 → R2（+ 通用开销）→ 锁拆分 → 视实测再决定 R4。**
- 验证：`./gradlew :quizbuks:check`（含 `platformCheck`）通过；对 jar 的 e2e 全部 41 项通过；`tools/check-app-paths.sh origin/1.2/platform` 通过。
- 未完成：R2、R3、锁拆分见下面的决定；报告的数字来自共用一台 4 vCPU 机器的测量，上线前应在目标规格上重测。

### 评审后的修正（Q10a，2026-10-16）

- 独立评审：R1 的两项生产改动正确，无严重或高危问题；风险在压测工具。已修正：
  - 工具只驱动本机（`LOAD_BASE_URL` 须为回环地址，否则须 `LOAD_ALLOW_REMOTE=yes`）；只支付与应用同一主机的 Checkout、遇正式模式的充值即停（在发起新的充值前先查已有的）；
    只发布本次 `QB_SETUP` 输出中、由本次管理员提出、创建于本次运行之后的提案；`LOAD_PASSWORD` 必填；`pg_stat_statements` 只重置应用库；`check` 编译工具的源码。
  - 新增开环模式 `LOAD_RATE`（固定到达率）：每秒 15 人时提交 p95 0.42 秒、首页 1.9 倍；18 人时 0.55 秒、2.5 倍；50 人时过载（提交 p95 16 秒、88 次 503、首页 110 倍）。
  - `QB_PUBLICATION_COMPLETION_MOVE` 在找不到发布、或发布上的判断与卡片不同时抛出异常（整次完成回滚）；补测试：并发抢名额与两发布的预算不足各恰好一次移动、
    开始读到的余额在等锁时被花光（仍放行、待支付、预算不足一次、账平）、超时自动提交经子流程结束发布、卡片与发布不一致时提交 500。
  - 报告：锁拆分成立的条件（开始在锁内读自己的行、一条语句读完成的行；其他读者一条语句读两行或持两把锁；移动发布的完成也取开始锁，每个发布一次的排队停顿；被拒的开始与超时也取锁）、
    模型的省略、R1 的提升在噪声之内、移动那次完成的额外成本约 7–8 条语句。
- **决定（需求方）：做 R3（取锁前在进程内排队 + 入口限流，平台）、R2（降低 `LEDGER_POST` 的成本，连同平台的通用开销：`HoldLock` 一条语句、提交前不重读、引用检查合并）与锁拆分（应用）；不做 R4。**
  三者各自另写计划，不在本分支实施。
