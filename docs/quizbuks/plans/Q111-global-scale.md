# Q111 为全世界的大规模使用做准备：关键技术的试验

**状态**：需求方 2026-11-06 确认："这些关键技术都要尝试，为未来的全世界大规模使用做好准备。"本文件是试验计划：每项先在测试环境中试、量出结果、写成报告，再由需求方决定是否采用；试验与首次上线的开发并行，不计入 `Q94-first-launch.md` §3 的天数，也不阻塞它。开工前按 CLAUDE.md 第 7 节给出每项的细化计划。

## 0. 目标与现状

**目标**：日本、美国（及其他地区）的用户感觉一样快；用户量增长时能加服务器扩展，换服务器、换数据库不搬文件、不停太久。

**现状**（2026-11-06）：
- 一台共用的服务器（4 vCPU）运行一个应用容器、Caddy 与共用的 PostgreSQL 16；`quizbuks.com` 经 Cloudflare，`staging.quizbuks.com` 视 DNS 设置。
- 已经适合多台的：访问令牌无状态、定时任务与事件投递靠数据库协调（多实例只执行一次）、外部作业以 `FOR UPDATE SKIP LOCKED` 领取、答题的正确性靠数据库的命名锁、页面程序的文件名带指纹并缓存一年（`SpaFallbackFilter`）。
- 只能一台的：上传的文件在本机目录（`LocalFileStore`）；登录与流程的限流、公开计数器的去重在各台的内存中（`SignInRateLimits` 等）；热门发布的排队每台各自计算。
- 美国用户每次往返东京约 0.1–0.17 秒，打开一页比日本用户多等约 0.5–0.8 秒（估计，T1 实测）。
- 单个热门发布的结算是串行的（压测约每秒 40 次提交，`docs/quizbuks/perf/Q10a-load-test.md`），加服务器不改变这个上限。

### T1 测量基线

- 用 WebPageTest 一类的工具，从东京、美国西海岸、美国东海岸各打开：App 首页、发布详情、开始答题页、发起方后台的首页与发布列表、公开主页；记首字节时间、可交互时间、往返次数。
- 结果写 `docs/quizbuks/perf/Q111-global-latency.md`，之后每项试验改完再测一次、写进同一份报告。

### T2 文件改存对象存储（R2）

- 平台（`1.3/platform` 的阶段）：`FileStore` 的 S3 兼容实现 `S3FileStore`（写入、大小、按范围读、按前缀删除、分页列出；大文件分段上传），配置 `jabiz.files.store = local | s3` 与 `jabiz.files.s3.*`，密钥只取自环境变量；启动检查配置完整、桶可达。
- 存储契约测试：本机与 S3 两种实现都通过（S3 用 MinIO 的测试容器）；现有的文件集成测试以 S3 配置再跑一遍。
- 迁移工具：按同样的键复制、按 `sys_file` 的 SHA-256 核对。
- 部署：`deploy/quizbuks/DEPLOY.md` §3b（两个桶、各自的密钥）；`operations.md` 的密钥清单。
- **通过的标准**：staging 切到 R2 后 e2e 全绿；上传、下载、断点续传、删除、清扫、删除账号的抹除都正常；文件读取的耗时写进报告。

### T3 CDN 第一步

- Cloudflare：两个域名经代理；缓存规则（`/<前端>/assets/*` 按源站的一年、`/api/public/*` 按源站的 60 秒、其余 `/api/*` 不缓存、HTML 不缓存）；HTTP/3、Brotli、分层缓存；webhook 的放行规则不变。写进 `DEPLOY.md`。
- 平台：公开查询以网址上的 `lang` 参数选语言（现在靠 `Vary: Accept-Language`，Cloudflare 不认，会串语言）；`@jabiz/client` 的公开查询带上它。
- QuizBuks：检查首页、发布详情、发起方后台首页打开时依次发出的接口调用，能并行的并行、能合并的合并（`QueryEntities.all` 的思路用于页面）。
- **通过的标准**：美国用户首屏比 T1 的基线快，并量出多等的时间（目标：比东京多等不超过约 0.3 秒）；登录后的接口从不被缓存（检查响应头与 Cloudflare 的缓存状态）。

### T4 多台应用服务器

- 在测试环境起两台（及以上）应用容器，Caddy 轮流转发；同一个数据库、同一个 R2 桶（依赖 T2）。
- 逐项验证：定时任务每次只执行一次；事件只投递一次；外部作业不重复领取；字典缓存经 LISTEN 在两台都失效；热门发布的压测（两台各自排队，正确性不变：名额、预算不超发）；登录与流程的限流在两台下的实际放行量（现在是每台各算，合计约为 N 倍）。
- 写出多台部署时的配置原则：限流按台数分摊，或在网关（Cloudflare 或 Caddy）上做；排队上限按台数设置；数据库连接数 = 台数 × 连接池大小，不超过数据库的上限（需要时加连接池）。
- **通过的标准**：e2e 对两台全绿；压测中没有超发；报告写明每台的承载与合计。

### T5 PlanetScale Postgres

- 在东京（AWS ap-northeast-1，以控制台为准）建最小的 PostgreSQL 17（及 18）数据库；应用一律**直连**（5432 端口），不经其连接池（LISTEN 只能直连，Flyway 也要直连）。
- 兼容性：平台与 QuizBuks 的迁移、集成测试与 `platformCheck` 指向它跑一遍；重点是只追加表的触发器、命名锁、LISTEN、完整性封存；我们的迁移没有用任何扩展。
- 维护登录：PlanetScale 不给超级用户，用其 `postgres` 角色试 `create-maintenance-login.sh`（建 `jabiz_maintenance` 角色、授予成员关系），再跑删除账号的抹除（`ERASURE_PURGE`、`ErasureIT`）。不行就写出替代做法。
- 延迟：在 AWS 东京开一台临时服务器跑应用（与数据库同一区域，最好同一可用区），用现有的压测工具测热门发布，与现在的结果比较锁内每条语句的耗时与每秒提交数；另测"应用在现在的服务器、数据库在 AWS"的组合，确认它不可取的程度。
- 运维：备份与时间点恢复、主备切换时应用的表现（连接断开后的重连）、大版本升级的做法（不能原地升级，只能新建再迁移）、费用（东京的价格）。
- **需要的决定**：技术栈中的"PostgreSQL 16"改为 17 或 18（平台决策：CI、本机开发、测试容器一起改）。试验期间只在试验分支上改，不动主线。
- **通过的标准**：全部测试通过；维护登录与抹除可行；同区域时热门发布的承载不低于现在；写出迁移到 PlanetScale 的步骤与停机时间的估计。

### T6 题目图片的临时链接

- 答题时的内容图片改为几分钟有效的临时链接，由 R2 经 Cloudflare 直接发给浏览器，不经应用（答题者本来就能看这些图片）；单据、生成的文件、私密的文件照旧经应用。
- 写清"这次读取不经应用"对读取记录与撤下的影响（公开撤下时清 CDN 的缓存）。
- **通过的标准**：美国用户翻题时图片不再等待东京；权限与撤下的规则不变。

### T7 实际用户的速度

- 页面记下真实的加载时间，按国家统计（Cloudflare Web Analytics，或平台已有的 OTLP 推送前端的计时）；要放宽内容安全策略、隐私政策补一句，届时再定。
- **通过的标准**：上线后能按国家看到首屏时间的分布。

## 2. 顺序

1. T1（立即，用现在的 staging）。
2. T2 → T3 → T4（T4 依赖 T2；T3 与 T2 可并行）。
3. T5 可以与 T2–T4 同时做（在独立的试用环境，不影响 staging）。
4. T6、T7 在 T2、T3 之后。
5. 每项完成后在报告中写结论，需求方决定是否采用；采用的，正式环境在首次上线前或上线后按计划切换。

合计约 12–15 天（不含 Cloudflare 上的设置与费用），可以由几个会话按项并行（各自的分支，平台工作在 `1.3/platform` 上）。

## 3. 以后视规模再定（本计划不做，只写前提）

- **美国区域**：美国用户很多时，在美国部署应用与数据库的只读副本，读在本地、写回东京（答题提交、领奖、扣预算必须在主库加锁）。要处理"刚写完、副本还没到"的情况；项目规则"读写分离保持现状、不扩展"要改成新的平台决策；PlanetScale 的只读区域是候选（T5 一并了解）。
- **共享的限流与缓存**：多台很多时，内存中各算各的限流误差变大；用网关的限流，或引入 Redis（项目规则"MVP 阶段不引入 Redis"，届时改决策）。
- **按角色分开部署**：同一个程序，一组只处理网页请求，一组只跑定时任务、事件、邮件、AI 作业（不是微服务，代码仍是一套）。
- **超大的单场活动**：单个热门发布的串行上限不随服务器增加；名额分批放出、先报名后开考、拆成几个发布，属于产品设计。
- **中国大陆**：Cloudflare 在大陆没有一般的节点；大陆的速度与合规（ICP 备案、个人信息出境）另议。
- 不做：微服务、Kafka、Kubernetes（CLAUDE.md 第 4 节）。
