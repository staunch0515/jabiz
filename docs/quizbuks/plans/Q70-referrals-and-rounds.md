# Q70 推荐广告、推荐资格与认证题的门槛（计划，2026-11-01；第三稿，需求方确认，开发中）

承接 Q69（`Q69-certifications.md`）：认证不是奖励方式，而是"合格"的用途；第一步"申请成为商户"已上线。
本计划把 2026-11-01 几轮讨论定下来的业务写清楚。**这只是计划**；确认 §12 的问题后分期开发。

**第三稿（需求方 2026-11-01 确认并要求开发）**：认证题的每月换模版重新发布是**业务操作，系统不改**，保持既有控制（题库、自动排程、补考间隔都不做；只做方案 B）；被推荐人的范围像发布的客户匹配一样做成**商户自选的规则**（平台不承担这类责任），"熟客不能被推荐"同样是商户在规则中设定的（有规则才能设定，平台不单独实现这类控制）；**不另设**推荐专用的电子奖品池；**四种方式一起上**；推荐期限**缺省 7 天**，超过即作废；推荐是朋友之间顺手发个链接，**要避免乱发**。下文以第三稿为准，与之不符的第二稿内容已删去。

第二稿依需求方的更正改写：
- 删去"同一模版只考一次"（方案 A）；
- 推荐的成交改为"被推荐人答题合格"，由系统自动判定，不再由商户确认；
- 平台使用费不在本计划内；
- 新增被推荐人的范围。

## 0. 需求方的决定（2026-11-01，按讨论的顺序）

1. **推荐不是平台的通用功能，是"推荐广告"**：例如"我看到一个好东西，推荐给你"。推荐的是商户的这个发布（它的产品、店铺），不是平台本身。
2. **推荐和发布绑定**：商户在发布时可以选择"欢迎推荐"，设置名额，以及每推荐一个人给多少。把这件事交给商户。
3. **推荐奖励是一次性的**：一位被推荐人只给一次。
4. **推荐费就是推荐奖励**：四种奖励方式（平台 Kudos、商户现金、到店兑换、电子奖品）都可以用。
5. **被推荐人可以是还没注册的人**：经推荐链接注册成为答题者即可。
6. **推荐人可以不答题，也可以答题，由商户选择**：发布上设定"推荐人须答过 / 须合格 / 不要求"。
7. **钱的归属**（澄清）：
   - 平台管的是平台使用费与经平台流转的 Kudos，运营商的结算、提现属于这一类；
   - 商户直接给答题者的现金，是商户自己的事，平台只记录。
8. **推荐要先有资格**：推荐资格也是一种认证，必须考试通过才能推荐。
9. **资格考试每个月自动发布一次，每月换一个新模版**；上次没通过的人，可以在不小于这个发布周期之后再考。
10. **方案 B**：持有某种资格的人，不能答这个资格的考题。
11. **不采用方案 A**（"同一模版合格后不能答其他发布"或"每个模版只能考一次"）。"每月一轮换新模版"和方案 B 是两件事，都采用；方案 A 不做。
12. **奖励记录加"来源"**，扩展系统：同意。
13. **平台使用费**不在本计划内，以后统一规划。本计划中推荐奖励**不收**平台使用费。
14. **推荐的"成交"就是被推荐人在这个发布上答题合格**：合格即给推荐人发放推荐奖励，由系统判定，不需要商户确认。
15. **被推荐人要有范围**：至少应该是没有在这个商户答题合格过的人（§2.3 D-Q70-12，我的考虑）。第三稿之后改为自选规则，见 18。
16. ~~电子奖品的推荐奖励另设奖品池~~：第三稿取消，**不另设**，推荐奖励与答题奖励共用发布的码池。
17. **每月换模版、重新发布是业务操作**：系统没有变更，保持既有控制（运营商每月手工发布新一轮并登记，Q69）。不做题库、自动排程与补考间隔。
18. **被推荐人的范围是商户自选的规则**：和发布中的客户匹配类似，有多条规则，由商户自己选择使用；平台不承担这类责任（写进商户条款）。**"熟客不能被推荐"也是一条规则**（2026-11-01 需求方补充）：商户在规则中设定；有规则就能设定，没有规则就不能设定，平台不单独实现这种逻辑控制。
19. **四种奖励方式一起上**（不再分 Q70b、Q70c）。
20. **推荐期限缺省 7 天**：认领之后 7 天内没有合格的，推荐作废。
21. **避免乱发**：推荐的场景是两个朋友聊天时推荐一下，为了方便对方找到这个问卷，受累发一个链接；不能看见一个电子邮件就发出推荐。

沿用的前提（Q69 与之前的决定）：
- 所有商户都要审核；
- 资格绑定账号、不能转让，满一年审查；
- 对商户的管理是运营商的工作；
- 每个发布至少要有一个奖励大于 0 的档位（官方账号的认证题付少量 Kudos）；
- 答题引擎保持"一人一个发布只答一次"。

## 1. 概念一览

| 概念 | 是什么 | 谁定 | 在哪 |
|---|---|---|---|
| 认证（资格） | "通过了哪些发布，就算持有认证 X"，一年有效（Q69） | 目录在代码中；轮次由运营商（含总部）登记 | `certification` 包 |
| 认证题的"轮" | 官方账号的一个发布，计入某认证 | 运营商每月发布并登记（业务操作） | `QbCertificationRound` |
| **持有即不能答**（新，方案 B） | 持有认证 X 的人不能答 X 的考题 | 系统（对轮次自动生效） | 开始答题时检查 |
| **推荐资格**（新） | 认证 `REFERRER`：持有它才能在发布上推荐 | 目录（代码） | `Certifications` |
| **欢迎推荐**（新） | 发布上的一项设置：名额、推荐奖励（方式与数额）、推荐人条件、被推荐人范围 | 商户 | 发布的新字段 |
| **推荐**（新） | 一条记录：哪个发布、推荐人、被推荐人、状态 | 被推荐人经链接认领；系统按答题结果完成 | `QbReferral` |
| **推荐奖励**（新） | 被推荐人在该发布上答题合格后，给推荐人的一次性奖励，按发布选定的方式发放 | 商户设定，系统发放 | 复用四种奖励的记录与流程，奖励带"来源" |

**三条线互不混淆**：
- **答题奖励**：被推荐人自己答题合格，照常得到答题奖励。不变。
- **认证**：答题合格的用途，不是奖励。
- **推荐奖励**：被推荐人合格时给推荐人的奖励。与推荐人自己的答题无关，发放方式复用答题奖励的四种。

## 2. 决定（草案）

### 2.1 认证题：持有即不能答（Q70a）

| # | 决定 |
|---|---|
| D-Q70-1 | **方案 B：持有即不能答**。一个发布是认证 X 的轮次时，**正持有 X 的人不能开始答它**：首页不列出，详情显示"你已持有该资格（至 …）"，开始答题返回 422 `QB_CERTIFICATION_HELD`。资格过期或被收回后，自动重新可以答（续期、重新认证）。普通发布不受影响 |
| D-Q70-2 | **每月换模版、重新发布是业务操作**（决定 17）：运营商的官方账号每月出新一轮（新模版）、照常提交审核与上架，再以 Q69 的 `QB_CERTIFICATION_ROUND_ADD` 登记为轮次。系统不做题库、自动排程或补考间隔；"一人一个发布只答一次"保持不变，没合格的人答下一轮 |

### 2.2 推荐资格（Q70b）

| # | 决定 |
|---|---|
| D-Q70-8 | **新认证 `REFERRER`（可以推荐）**：目录中第二种认证，对象是答题者，自合格起一年有效。考题讲推荐的规则：推荐是朋友之间的口碑，只推荐自己认可的东西；只发给认识、会感兴趣的人，不能见到邮箱就发；不能骗人注册、不能推荐自己；奖励在被推荐人合格后由商户承担；违规的后果。考题的轮次照 D-Q70-2 由运营商每月发布 |
| D-Q70-9 | **推荐要有资格，在服务端检查**：生成推荐链接（`QB_REFERRAL_LINK`）时，推荐人必须持有 `REFERRER`。资格之后过期的，已生成的链接仍然有效（被推荐人不受推荐人资格变化的影响），但不能再生成新的 |

### 2.3 推荐广告（Q70b）

| # | 决定 |
|---|---|
| D-Q70-10 | **发布上的"欢迎推荐"**（草稿中设置，提交即冻结，复制时一起复制）：<br>• `referralEnabled`；<br>• 名额 `referralQuota`（1–1000）；<br>• 推荐奖励的方式 `referralRewardMethod`：四种之一，受商户被允许的方式约束，同 `PublicationEditing.methodProblems`；<br>• 数额 `referralAmount`：平台 Kudos 与现金为金额，兑换与电子奖品为奖品的价值，用于预算；<br>• 奖品说明 `referralDescription`：兑换、电子奖品必填；<br>• 电子奖品的交付方式同发布的（与答题共用码池，D-Q70-19）；<br>• 推荐人条件 `referrerRequires`：`NONE` / `ANSWERED` / `PASSED`；<br>• 被推荐人的规则 `refereeRules`：商户自选，D-Q70-12；<br>• 期限 `referralDays`：被推荐人自认领起几天内合格才算，缺省 7 天（1–30），超过即作废 |
| D-Q70-11 | **只给公开发布**：`INVITED`（指定邮箱）的发布不能开启推荐（`QB_REFERRAL_INVITED`）。问卷可以开启；问卷没有合格，以**完成**视为合格；推荐人条件不能选 `PASSED` |
| D-Q70-12 | **被推荐人的范围**（决定 15、18）。被推荐人能不能算推荐，**全部由商户自选的规则决定**；平台只按规则执行，不对规则的选择负责（商户条款写明），不单独实现某种范围控制。<br>**规则目录**在代码中 `RefereeRules.ALL`（像客户匹配的条件种类），商户在发布上勾选，可以不选（不选即谁都能被推荐）：<br>• `NOT_REGULAR`（不是熟客）：在这个商户的任何发布上合格过的人不算。认领时查，发放时再查：认领之后、合格之前在这个商户别的发布上先合格了的，同样不算；<br>• `NEW_TO_PLATFORM`：被推荐人在认领前 7 天内才注册（专为拉新）；<br>• `MATCHES_AUDIENCE`：被推荐人在认领时就须符合这个发布的客户匹配条件（不符合的不占名额）；<br>• `SAME_REGION_AS_REFERRER`：被推荐人资料中的国家与推荐人相同。<br>以后新增规则只加进目录与三语文案，同客户匹配的条件种类；商户后台的向导缺省勾选 `NOT_REGULAR`（只是缺省，商户可去掉）。<br>**推荐本身的成立条件**（不是范围规则，而是"推荐"这件事的定义与防刷，所有推荐都一样）：推荐在答题之前（在这个发布上已经开始答过的人不能再被推荐）；不是推荐人本人；不是这个商户本人或其店员（自己给自己付推荐费）；已验证邮箱 |
| D-Q70-13 | **最高支出**：发布的预计最大支出加上"名额 × 推荐数额"，提交时照常显示与审核。推荐奖励**不计入**答题的预算 `budgetCap` 与计数（答题路径不碰推荐） |
| D-Q70-14 | **推荐链接**：推荐人对一个发布生成自己的推荐键（随机值，不是用户编号；`QbReferralLink`，每人每发布一个，再次请求得到同一个），链接为 `/p/<发布>?ref=<键>`，复用分享链接（Q15）与二维码。条件：<br>• 推荐人持有 `REFERRER`；<br>• 发布开启推荐、`LIVE`，名额未满；<br>• 推荐人满足 `referrerRequires`；<br>• 推荐人未被封禁 |
| D-Q70-15 | **被推荐人认领**：打开链接时，未登录的由 App 记住推荐键（同分享链接的做法），登录或注册后运行 `QB_REFERRAL_CLAIM`；已登录的打开链接即运行。在推荐锁 `qb.referral:<发布>` 内写一条 `QbReferral`（状态 `REFERRED`，到期时刻 = 认领 + `referralDays`），条件：<br>• 满足 D-Q70-12 的范围；<br>• 被推荐人在这个发布上还没有推荐记录：谁先推荐算谁，一位被推荐人在一个发布上只算一次；<br>• 名额没用完：`REFERRED` + `REWARDED` 的条数 < 名额，过期与作废的不占名额。<br>不满足即不记录，页面照常打开，被推荐人照常可以答题，只是这次不算推荐；推荐人不会得知原因 |
| D-Q70-16 | **成交 = 被推荐人在这个发布上合格**（决定 14），由系统判定：<br>• 每 5 分钟一次的逐项任务 `qb.referral-reward` 以模板 `qb.system.referrals-due` 选出"状态 `REFERRED`、被推荐人在这个发布上已完成且合格（问卷为完成）、提交时刻在认领之后、在到期之前"的推荐；<br>• 每一项运行 `QB_REFERRAL_REWARD`（`internal()`）：在推荐锁内重读，再查 D-Q70-12 所选的规则（如选了 `NOT_REGULAR`：这个商户的其他发布没有更早的合格），然后按发布的方式**发放推荐奖励**（D-Q70-18），状态转为 `REWARDED`。<br>**答题路径一条语句也不加**：开始、提交、超时与 `AttemptStatementBudgetIT` 都不变，发放在答题完成之后由任务单独做。推荐人的站内信"推荐成功"在发放的事务中经事件发出 |
| D-Q70-17 | **期限与作废**：<br>• 到期仍是 `REFERRED` 的（被推荐人没在期限内合格，或答了没合格），由每日的逐项任务 `qb.referral-expire` 转为 `EXPIRED`，释放名额。被推荐人在这个发布上答了没合格的，任务看到其完成即可提前转为 `EXPIRED`，不必等到期；<br>• 发放时发现不再符合（例如已在这个商户别的发布上先合格、商户被封禁），转为 `VOID` 并记下原因代码 |
| D-Q70-18 | **推荐奖励的发放复用四种奖励**（一次性），都在 `QB_REFERRAL_REWARD` 的同一事务中：<br>• **平台 Kudos**：在商户钱包锁内从商户钱包付给推荐人，按 `QbWallets.pays` 的规则：有待支付或余额不足时，推荐保持 `REFERRED` 并记 `fundsShort`，下一次任务再试，商户收到"余额不足"的提醒，期限照算。过账同答题奖励（推荐人负债 2120 贷方），**来源单据是 `QbReferral`**。本计划中不收平台使用费（决定 13）；<br>• **商户现金**：写一条 `QbCashReward`（来源推荐），之后完全照现金奖励的流程：商户标已付、推荐人确认、争议、逾期；<br>• **到店兑换**：写一条 `QbRedemption`（来源推荐），推荐人到店领取，同现在；<br>• **电子奖品**：写一条 `QbDigitalPrize`（来源推荐），从推荐专用的奖品池取码（D-Q70-19），或共用码、商户寄送，同现在 |
| D-Q70-19 | **电子奖品不另设推荐池**（决定 16，第三稿）：推荐奖励与答题奖励共用发布的码池（`POOL`）、共用码（`SHARED`）或商户寄送。提交时检查码池的可用码不少于"答题可能用到的最多份数 + 推荐名额"（`PublicationReadiness.pool` 加上名额） |
| D-Q70-19b | **避免乱发**（决定 21）：推荐是朋友之间顺手发一个链接。<br>• 平台**不提供**以邮箱或电话代发推荐的功能，只给推荐人一个链接与二维码，由他自己发给认识的人；<br>• 每位推荐人在一个发布上每天至多带来 **3 位**、合计至多 **10 位** 被推荐人（认领的条数；超出的认领不记录，页面照常打开），数字是普通参数 `qb.referral.per-referrer-daily` / `qb.referral.per-referrer-total`；<br>• 推荐人的推荐资格可以由运营商收回（Q69 的 `QB_CERTIFICATION_REVOKE`），收回后不能再生成链接；<br>• 推荐资格的考题讲清"不能见到邮箱就发" |
| D-Q70-20 | **奖励记录加"来源"**（决定 12）：现金、兑换、电子奖品三张奖励表都是**被封存的只追加表**，`attemptId` 必填且唯一。封存的列不能改名、改类型（平台 D58），所以给三张表**加一列** `sourceKind`（`ATTEMPT` / `REFERRAL`，旧行为空即 `ATTEMPT`），推荐来源的行在 `attemptId` 中**存推荐的编号**（UUIDv7，与答题编号不会重复，唯一约束照常成立）。所有按 `attemptId` 连到 `QbAttempt` 的读取都改为先看 `sourceKind`（§5.3 列出）。这是本计划改动面最大的部分 |
| D-Q70-21 | **推荐奖励的保留期**：平台 Kudos 的推荐奖励照答题奖励一样，受转账保留期（`qb.transfer.hold-days`）与争议冻结约束。`RewardHolds` 与模板 `qb.wallet.taker-transferable` 把来源 `QbReferral` 的 2120 贷方行也算作奖励，由 `TransferHoldIT` 覆盖 |
| D-Q70-22 | **封禁与删除**：<br>• 商户被封禁时：其发布的推荐不能再认领；`REFERRED` 的转 `VOID`。<br>• 推荐人被封禁时：不能再生成链接；已有的推荐，在其后合格时照发推荐奖励，发放后照现有规则冻结。<br>• 账号删除时：`QbReferral` 与 `QbReferralLink` 在 `PersonalDataEraser` 中声明，推荐人、被推荐人编号清空，记录保留，用于统计与名额 |
| D-Q70-23 | **不做的**：多级推荐（推荐人的推荐人）、按成交金额比例的推荐奖励、平台出钱的推荐奖励、推荐排行榜、推荐奖励的平台使用费（以后统一规划） |

## 3. 状态与规则

### 3.1 推荐的状态

```
              认领（QB_REFERRAL_CLAIM）
                     │
                     ▼
                 REFERRED ──(到期，或被推荐人答了没合格)──▶ EXPIRED   （释放名额）
                  │    │
  被推荐人合格     │    │  发放时不再符合（已在本商户别处先合格、商户被封禁…）
  （任务发奖励）   ▼    ▼
             REWARDED   VOID                                         （VOID 释放名额）
```

- `REWARDED` 是终态：推荐奖励已按方式发出。之后现金、兑换、电子奖品的状态在各自的记录上。
- 名额 = `REFERRED` + `REWARDED` 的条数；`EXPIRED`、`VOID` 不占。
- 一位被推荐人在一个发布上只有一条记录，不论状态（`(publicationId, refereeId)` 唯一）：过期或作废后，不能再被推荐到这个发布。
- 平台 Kudos 方式下商户钱包不够时，仍是 `REFERRED`（带 `fundsShort`），由下一次任务重试，直到期限。

### 3.2 认证轮次的开始条件（开始答题时，只对轮次检查）

按顺序，第一条不满足即拒绝：
1. 正持有该认证 → `QB_CERTIFICATION_HELD`（D-Q70-1）。
2. 其他照常（发布开放、受众、一人一次等）。

首页不列出；详情页显示"你已持有该资格，至 …"。

### 3.3 推荐与被推荐人自己的答题

- 被推荐人照常答题、照常得到自己的答题奖励。推荐奖励是另外一笔，给推荐人。
- 推荐奖励只看被推荐人"是否合格"，不看得分高低与他自己得到多少。

## 5. 流程、模板与任务

### 5.1 认证（Q70a）

只改开始答题与首页、详情（实施见 §14）：
- **开始答题**：锁外既有的那一条语句中多查一项"这个发布是不是轮次"（`QbCertificationRound` 按发布）。不是轮次时其余查询的条件为空、不发语句，普通发布的语句数不变（`AttemptStatementBudgetIT` 不改）。是轮次、且是新的开始时，锁外再读两条：调用者在该认证上的记录与该认证的全部轮次（一条），调用者在这些轮次上的答题（一条）。按 `CertificationHolding` 判断，**还没认领的合格同样算**（与 `QB_CERTIFICATION_CLAIM` 同一段补记规则，`CertificationProcesses.unrecordedPasses`，只读、不写记录），持有即 422 `QB_CERTIFICATION_HELD`；继续答到一半的会话不受影响。
- **首页 `qb.app.feed` 与详情 `qb.app.publication`**：写同一段 SQL（记录经限本人的 `me:QbCertificationRecord`，答题经本人的 `taker:QbAttempt`，同样算上没认领的合格）。首页不列出；详情多一列 `heldUntil`，有值时 `canStart` 为假，App 显示"你已持有该资格（至 …）"。认证目录（键、版本、有效期秒数）在模板中写成 `VALUES`，与 `Certifications` 由 `CertificationTemplatesTest` 核对。

### 5.2 推荐（Q70b）

| 流程 | 谁 | 锁 | 说明 |
|---|---|---|---|
| `QB_PUBLICATION_SAVE`（已有） | 商户 | 发布锁 | 增加推荐字段与检查（`PublicationReadiness`：名额、方式、说明、推荐池、问卷与 `PASSED`、`INVITED`） |
| `QB_REFERRAL_LINK` | 推荐人（`qb.me`） | — | D-Q70-14，返回链接键 |
| `QB_REFERRAL_CLAIM` | 被推荐人（`qb.me`） | `qb.referral:<发布>` | D-Q70-15 |
| `QB_REFERRAL_REWARD` | 系统（`internal()`；逐项任务 `qb.referral-reward`，每 5 分钟） | `qb.referral:<发布>` →（电子奖品）码池锁 `qb.digital-pool:<发布>` /（平台 Kudos）`qb.wallet:SPONSOR:<商户>` | D-Q70-16、18 |
| `QB_REFERRAL_EXPIRE` | 系统（逐项任务 `qb.referral-expire`，每日） | `qb.referral:<发布>` | D-Q70-17 |

**锁序**：推荐的流程从不取发布锁或开始锁，答题路径不受影响。新的锁在现有锁序中的位置：`qb.referral:<发布>` → `qb.cash:<记录>` / 码池锁 → `qb.wallet:SPONSOR:<商户>`。

事件与站内信（由消费者写，照 Q7c）：
- `qb.referral.claimed`：给推荐人"你推荐的一位朋友来了"，不给名字；
- `qb.referral.rewarded`：给推荐人"推荐成功：<奖励>"；
- `qb.referral.expired`：给推荐人"一位朋友没在期限内合格"，不给名字；
- `qb.referral.funds-short`：给商户"推荐奖励因余额不足未能发放，请充值"（同预算不足的节流，每 24 小时至多一封）。

### 5.3 改为认"来源"的地方（Q70c，D-Q70-20）

逐个读 `QbCashReward`、`QbRedemption`、`QbDigitalPrize` 并连到 `QbAttempt` 的地方，都要按 `sourceKind` 分开。实施时以 grep `attempt_id`、`attemptId` 列全清单，写进实施记录；下表是已知的：
- **App**：`qb.app.cash-rewards`、`qb.app.redemptions`、电子奖品列表、钱包"按方式"（Q58）、结果页的奖励卡片。推荐来源的奖励显示为"推荐奖励：<发布名>"，链接到发布而不是结果页。
- **商户后台**：`qb.sponsor.cash-rewards`、`qb.sponsor.redemptions`、电子奖品页、交易页（Q9b）、分析的支出。
- **管理后台**：`qb.admin.cash-rewards`、兑换与电子奖品的争议页、月报 `qb.admin.monthly` 加一类 `REFERRAL_REWARD`（来源 `QbReferral`，`AdminFinanceIT` 有逐行期望）、投资人指标中推荐奖励单列。
- **流程**：现金的提醒与逾期（`CashRewardChecks.refuseOverdue`：逾期的推荐现金奖励同样禁止该商户的新发布开始答题）、站内信的种类与链接、`QB_MESSAGE_FROM_EVENT`。

## 10. 风险

| 等级 | 风险 | 对策 |
|---|---|---|
| 高 | **三张被封存的奖励表加"来源"**：读它们的地方很多，漏改会把推荐奖励当成答题奖励显示或计算 | 单独一期（Q70c）；实施时以 grep 列全清单，写进实施记录；每个读处都加测试；月报有逐行期望 |
| 高 | **刷推荐**：成交改为"被推荐人合格"后，由系统自动发放，有人可能注册小号、自己答对来领推荐奖励 | 推荐人要考推荐资格；被推荐人要已验证邮箱，商户可选"不是熟客""本平台新注册"等规则（D-Q70-12，向导缺省勾选"不是熟客"）；名额与数额由商户控制；推荐奖励受保留期约束，可以冲正；封禁照常；管理后台按推荐人汇总，可以发现异常（同一推荐人短时间大量合格的被推荐人） |

| 低 | **答案在月内流传** | 运营商每月换新模版发布新一轮（业务操作）；合格分定高 |
| 低 | **开始答题多读一次** | 只对轮次；普通发布的语句数不变 |

## 11. 与现有功能的关系

- **答题奖励**：不变。被推荐人照常得到自己的答题奖励。推荐奖励复用答题奖励的方式与流程，但来源不同、单独记账。
- **客户匹配（Q47）**：认证轮次的"持有即不能答"是轮次自带的规则，不是客户匹配条件。"持有某资格才能答"作为普通商户发布的受众条件，仍放在以后（Q69 的 D-Q69-10）。
- **指定邮箱回答（Q25）**：不能开启推荐。
- **店员（Q39）**：店员不能被推荐到自己商户的发布，也不参与推荐的确认（成交由系统判定）。
- **分享链接（Q15）**：推荐链接就是带 `ref` 的分享链接。没有推荐资格的人照旧可以分享，只是没有推荐奖励。
- **运营商（Q48）**：认证的轮次是运营商的（每月手工发布并登记）；推荐奖励由商户出。平台使用费以后统一规划。
- **App 中的商户（Q68）**：推荐的汇总可以以只读方式加进"我的商户"（以后再定）；不加任何操作。

## 12. 需求方的确认（2026-11-01）

1. 被推荐人的范围：全部是商户自选的规则，"熟客不能被推荐"也是其中一条（D-Q70-12）。
2. 认证题每月换模版、重新发布是业务操作，系统不改（D-Q70-2）。
3. 不另设推荐专用的电子奖品池（D-Q70-19）。
4. 四种方式一起上。
5. 推荐期限缺省 7 天，超过即作废。
6. 避免乱发（D-Q70-19b）。

## 13. 应用场景

以下各例中的金额与人物都是示意。

### 场景 1：小王考到推荐资格

1. 10 月 1 日，北区运营商的官方账号发布"推荐须知 · 10 月"（模版 A），审核通过上架，运营商在认证页把它登记为认证"可以推荐"的一轮。合格得 10 Kudos。
2. 小王答题合格，得到 10 Kudos。账户页显示"推荐资格，有效至明年 10 月 1 日"。
3. 之后小王在首页看不到"推荐须知"的考题（持有即不能答，D-Q70-1）。
4. 第二年 10 月资格到期后，考题重新出现在他的首页；他答当时的那一轮即可续期。

### 场景 2：小张没考过，下个月答新的一轮

1. 小张在 10 月 5 日答"推荐须知 · 10 月"（模版 A），没合格。这一轮他不能再答（一人一个发布只答一次）。
2. 11 月 1 日，运营商照常发布"推荐须知 · 11 月"（模版 C），并登记为新一轮；10 月那一轮结束。这是运营商的业务操作。
3. 小张答 11 月的一轮：题目是新的，合格，得到推荐资格。

### 场景 3：咖啡店开"欢迎推荐"，用平台 Kudos 付推荐奖励

1. 咖啡店（商户）发布"秋季新品知识问答"：
   - 答题合格得 50 Kudos；
   - 开启"欢迎推荐"：名额 20，朋友合格，推荐人得 300 Kudos（平台 Kudos）；
   - 推荐人须答过这套题，被推荐人规则选"不是熟客"（NOT_REGULAR），期限 7 天。

   预计最大支出 = 答题部分 + 20 × 300。
2. 审核通过上架。小王有推荐资格，答完这套题后，发布页出现"推荐给朋友：朋友答题合格，你得 300 Kudos（名额剩 20）"。
3. 小王把链接发到朋友群。朋友小李没有账号，点开链接，用邮箱注册、验证后进入这个发布。系统记下"小李 ← 小王"，名额剩 19。小王收到站内信"你推荐的一位朋友来了"。
4. 小李的发布页上方显示"你是经朋友推荐来的：在 11 月 8 日前答题合格，朋友就能得到推荐奖励"。
5. 小李看完资料答题合格，自己得到 50 Kudos 的答题奖励。
6. 几分钟内，推荐任务发现小李已合格：从咖啡店的钱包付 300 Kudos 给小王，推荐转为"已发"。小王收到站内信"推荐成功：300 Kudos"；"我的学分"里多一笔"推荐奖励：秋季新品知识问答"，保留期过后可以提现。
7. 小李以后再经别人的链接来咖啡店的其他发布，不再算推荐：他已在这个商户合格过，是熟客了，而这些发布选了"不是熟客"。

### 场景 4：选了"不是熟客"，熟客不算推荐

1. 小赵上个月在咖啡店的"夏季问答"中合格过；"秋季新品知识问答"的推荐规则选了"不是熟客"。
2. 小王把"秋季新品知识问答"的推荐链接发给小赵。小赵打开链接，系统不记录推荐（他已是这个商户的熟客），页面照常打开。
3. 小赵答题合格，照常得到自己的 50 Kudos；小王没有推荐奖励，名额也不减。
4. 如果咖啡店没有选"不是熟客"，小赵就算推荐：规则由商户设定，平台不另加。

### 场景 5：美容店用到店兑换做推荐奖励（Q70c）

1. 美容店开启推荐：名额 10，推荐奖励为"免费护理一次"（到店兑换），推荐人不要求答题，被推荐人规则选"不是熟客"与"本平台新注册"（NOT_REGULAR、NEW_TO_PLATFORM）。
2. 小陈有推荐资格，没答题就生成了推荐链接，推荐给还没注册的同事小周。
3. 小周注册后答题合格。
4. 小陈的"我的奖励"里出现"待领取：免费护理一次（推荐奖励）"。他到店时出示领奖码，前台确认后交付。

### 场景 6：补习班用现金付推荐奖励

1. 补习班开启推荐，推荐奖励为现金（商户现金）。
2. 被推荐的家长答完"课程介绍问答"合格后，系统给推荐人生成一笔"待付现金奖励（推荐）"。
3. 补习班线下付款后在后台标"已付"，推荐人在 App 确认收到。
4. 推荐人说没收到的，走现金奖励的争议流程，由总部或运营商处理。

### 场景 7：名额、过期与余额不足

1. 咖啡店的 20 个名额：已认领 15 个。其中 8 个已发放；3 个在 7 天内没合格，作废；1 个答了没合格，提前作废；3 个还在期限内。
2. 当前占用名额 = 待合格的 3 个 + 已发放的 8 个 = 11 个，还能再认领 9 个。
3. 某天咖啡店钱包余额不够：一位被推荐人合格了，推荐奖励没发出，推荐仍待发；咖啡店收到"推荐奖励因余额不足未能发放，请充值"。咖啡店充值后，下一次任务补发给推荐人。

### 场景 8：避免乱发

1. 小王想把咖啡店的推荐链接发给通讯录里所有人。App 没有"填邮箱代发"的功能，他只能自己把链接发给朋友。
2. 当天经他的链接来了 3 位朋友后，第 4 位打开链接时不再记录推荐（每天至多 3 位）；页面照常打开，那位朋友照常可以答题。
3. 运营商发现小王把链接贴在公开论坛，按推荐须知收回了他的推荐资格；他已有的推荐照常结算，但不能再生成新的链接。

### 场景 9：推荐资格过期以后

1. 小王的推荐资格到期了，还没续。
2. 他以前生成的推荐链接仍然有效：朋友照样可以认领，合格后小王照样得到推荐奖励。
3. 他不能再对新的发布生成推荐链接。发布页显示"推荐资格已到期，答新一轮考题即可恢复"。

## 14. 实施记录

### Q70a（2026-11-01）

- 推荐资格 `REFERRER`（一年、版本 1）加进 `Certifications.ALL`、字典与后台扩展的名字（三语）；Q70b 才用到它。
- 方案 B：`certification.RoundHolders`（开始的查询与拒绝）、`CertificationProcesses.unrecordedPasses`（认领与开始共用的补记规则）；错误码 `QB_CERTIFICATION_HELD`（三语）。
- 与 §5.1 草案的不同：开始时**不写**补记（只读），记录仍由认领写入，开始的事务因此不取认证锁、锁序不变；轮次的开始在锁外多两条语句，没有另加预算项（轮次是官方账号每月一次的发布，不是热门发布；普通发布的预算由 `AttemptStatementBudgetIT` 照旧断言）。
- 测试：`CertificationIT.whoHoldsTheCertificationStartsNoneOfItsRoundsUntilItEnds`（未认领的合格即算、首页与详情、拒绝开始、普通发布与不持有的人不受影响、收回后可以再答）、`CertificationTemplatesTest`、App 的 `Play.test.tsx`（详情页的提示）。

### Q70b-1：推荐的后端（2026-11-01）

- 发布的"欢迎推荐"存为**一列 JSON** `referral`（`publishing.ReferralPolicy`，键排序的规范 JSON），发布（封存表只加列）与卡片各一列，而不是 §4 草案的多列：保存、复制、上架、审批内容（只在开启时写入，旧的哈希不变）各只多一个字段。最大支出加上"名额 × 数额"；检查在 `ReferralPolicy.problems`（问卷不能要求合格、指定邮箱不能开启、电子奖品的推荐奖励要求发布本身是电子奖品），码池的可用码要覆盖获奖人数与推荐名额（`PublicationReadiness.Draft.poolNeeded`）。
- 被推荐人的规则 `publishing.RefereeRules`：`NOT_REGULAR`、`NEW_TO_PLATFORM`（以答题者资料的创建时间计，还没有资料的算新人）、`MATCHES_AUDIENCE`（以认领时的资料计，没有资料即不符合）、`SAME_REGION_AS_REFERRER`（资料的国家相同）。推荐的成立条件与上限在 `referral.ReferralRules`，"每天"按最近 24 小时计。
- 流程 `QB_REFERRAL_LINK` / `_CLAIM` / `_REWARD` / `_EXPIRE`、任务 `qb.referral-reward`（每 5 分钟）与 `qb.referral-expire`（每小时，草案为每日：失败与到期的名额释放得更快）、模板 `qb.system.referrals-due` / `-over`。站内信四种（`REFERRAL_CLAIMED` / `_REWARDED` / `_EXPIRED` 给推荐人、`_FUNDS_SHORT` 每天至多一条给商户），去处 `REFERRALS`；推荐来源的现金、兑换、电子奖品消息也去 `REFERRALS`。
- 来源列：三张奖励表加 `source_kind`；列出它的模板（App、商户后台、店员、管理后台的现金、兑换、电子奖品列表）都返回 `sourceKind`，`RedemptionProcesses.Prize` 也带上它。`qb.app.history` 只按答题连接，推荐来源的记录不出现在其中（它们在各自的列表与推荐页）。投资人指标的"奖品"计数包括推荐的奖品，暂不单列。
- 商户被封禁时不在封禁流程中逐个作废：认领时拒绝，发放时作废（`SPONSOR_BANNED`），其余到期结束。QuizBuks 还没有接入账号删除（平台 D62），D-Q70-22 的抹除随其接入时一起声明；两张表的推荐人、被推荐人列已允许为空。
- 测试：`ReferralPolicyTest`、`ReferralRulesTest`、`ReferralIT`（平台 Kudos 的完整流程与账本来源、不计入的各种情形与"不选规则即熟客也算"、失败与到期、其余三种方式的记录与来源、余额不足的等待与提醒、草稿的问题）；`AdminFinanceIT` 多一行、`SetupIT` 多两个参数、场景的编号随之后移。
