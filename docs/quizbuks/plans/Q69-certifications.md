# Q69 认证（"驾照"）：答题合格换来的身份，第一步"申请成为商户"（计划，2026-10-31；需求方 2026-10-31 确认，开发中）

取代未合并的草案 `Q54-sponsor-growth.md`（分支 `1.3/quizbuks-54-sponsor-growth`，2026-10-30；编号 Q54 后来给了品牌档案）。
草案中的"邀请制入驻""商户等级"等仍是需求方定下的方向，本计划只在 §7 列为以后的分期，不在第一步做。

## 0. 需求方的决定

2026-10-30：

- 所有商户都要审核，资格不跳过审核。
- 资格绑定账号、不能转让。
- 商户用某个功能前必须先了解它：答一套题，合格才给这个功能。
- 合格线就是发布现有的合格分。
- 资格满一年审查，一年没用就停用、等待激活。
- 对商户的管理是运营商的工作。
- 不做重考。

2026-10-31（本次讨论）：

- **认证不是一种兑现方式**，而是"合格"这件事的用途。四种兑现方式（平台 Kudos、现金、到店兑换、电子奖品）与它们的结算、钱包、账本、争议、报表**一律不动**。
- **第一步只做"申请成为商户"。**
- **"商户自己发认证"先不做**：例如咖啡店的"咖啡入门"认证，持有者才能答它的进阶题。设计上留余地。
- 答题者的认证自合格起一年有效；商户功能的认证按"一年没用"计算（第二步）。

## 1. 三层，互不相干

可以把它想成考驾照：

| 层 | 比喻 | 是什么 | 本计划 |
|---|---|---|---|
| 奖励 | 考试的奖品 | 合格得到的 Kudos 或奖品，照现在的规则 | **不改** |
| 认证 | 驾照 | "通过了哪些发布，就算持有认证 X"，带有效期与版本 | 新增 |
| 门槛 | 上路查驾照 | 某个功能入口要求"持有认证 X" | 新增，只在代码固定的几处 |

**认证题就是普通的发布**：照常出题、审核、上架、答题、算分、发奖。它不是新的发布类型，也没有新的奖励方式；只是被运营商登记为"某认证的一轮"。

## 2. 决定（草案）

| # | 决定 |
|---|---|
| D-Q69-1 | **认证的种类只在代码中**（目录 `Certifications`）：键、对象（答题者 / 商户）、所管的门槛、有效期规则、当前版本。第一步只有一种：`SPONSOR_APPLY`（可以申请成为商户，对象是答题者，自合格起一年）。新增种类要改代码与三语文案，不在后台随意建立；`PlatformCheck` 检查目录与门槛一一对应 |
| D-Q69-2 | **"轮"**（普通表 `QbCertificationRound`，只经 `QB_CERTIFICATION_ROUND_ADD` / `_REMOVE` 写入）：哪个发布计入哪个认证的哪个版本。只能登记**官方账号**的发布（D-Q69-5）。一个发布至多属于一个认证。不合格的人等下一轮，即运营商再发布一次（复制上一轮），一人一次的规则不变 |
| D-Q69-3 | **持有不另存一份，按需算出**：门槛检查时，读调用者在该认证各轮发布上的答题记录：已完成、`passed = true`、在有效期内（`SPONSOR_APPLY` 为合格起一年）、所在轮的版本等于当前版本；或者有一条有效的人工授予。读取在门槛所在的流程中进行（`qb_attempt` 已有 `(user_id, publication_id)` 唯一索引）。**答题路径一条语句也不加**（开始、提交、超时与 `AttemptStatementBudgetIT` 不变），也不需要新的事件 |
| D-Q69-4 | **人工授予与收回**（只追加的 `QbCertificationGrant`，只经 `QB_CERTIFICATION_GRANT` / `_REVOKE` 写入）：运营商对其名下（或直营由总部）的人授予或收回，必须填理由，总部抽查（同 D-Q48-5）。收回压过此前的合格与授予；之后再合格的仍然有效。答题者在账户页看到自己持有的认证与到期日 |
| D-Q69-5 | **官方账号**：每个运营商（含直营总部）可以把一个商户账号标记为官方（普通表 `QbOfficialPublisher`，只经总部的 `QB_OFFICIAL_PUBLISHER_SET`）。它照常出题、发布、充值、付奖励。只有官方账号的发布能登记为"轮"（草案问题 2 的 (a)） |
| D-Q69-6 | **奖励照旧**：发布至少要有一个奖励大于 0 的档位（`QB_TIER_NO_REWARD`），认证题也一样。官方账号付一点 Kudos（例如合格得 10 Kudos），就当平台的推广费用。不为认证题放宽这条规则（放宽会改发布的检查，见 §6 问题 3） |
| D-Q69-7 | **门槛"申请成为商户"**：App 的账户页有"成为商户"。没有认证时显示条件，并链接到当前一轮的认证题（公开发布，进首页）；有认证时可以申请。申请经平台的"已登录用户加入另一个入口"（D-Q69-8）给账号加上商户角色，**守卫检查持有 `SPONSOR_APPLY`**。之后在商户后台填写入驻资料，照常审核（`qb.sponsor.review`），运营商终审、总部抽查 |
| D-Q69-8 | **平台需要的一处改动**（先在 `1.3/platform` 完成）：已登录的用户加入另一个允许注册的入口。现在只能经"你已有账号"的邮件链接加入（Q68 的端到端测试就是这样做的）。加入要经应用的守卫 `SignUpGuard`（core，同步，以 `loads()` 声明所需数据，同 `SignInGuard`），由应用决定允不允许；角色只加该入口的注册角色，受保护的角色不能经此获得，角色只经平台授予（应用不自己写）。`SignUpGuard` 以后也用于邀请制注册（§7 Q69d） |
| D-Q69-9 | **商户后台的注册暂不改**：第一步只多一条路（App 申请），商户后台照旧可以直接注册。改为邀请制是以后的分期（§7） |
| D-Q69-10 | **商户自己的认证不做**，但模型留余地：目录的"对象"与"轮只能是官方账号的发布"两处限制，以后放宽为"商户认证只计入、只被该商户自己的发布使用" |

## 3. 一次完整的流程（第一步）

1. 总部（或运营商）标记官方账号。官方账号出一套"成为商户须知"题，照常提交审核、上架，合格档位给 10 Kudos。
2. 运营商把这个发布登记为认证 `SPONSOR_APPLY` 的一轮。
3. 答题者小王在首页看到这套题，答完合格，照常拿到 10 Kudos。答题流程与平时完全一样。
4. 小王在账户页点"成为商户"：系统读到他在这一轮上的合格记录（一年内），显示"可以申请"。
5. 小王点"申请"：平台的加入接口经守卫确认他持有认证，给账号加上商户角色。App 提示"到商户后台填写入驻资料"（链接 `/sponsor/onboarding`）。
6. 小王提交入驻资料，运营商审核通过。之后 Q68 的"我的商户"就出现在 App 的顶栏。
7. 没合格的人在第 4 步看到"先通过认证题"与链接；一年后认证到期，未申请的需要答新一轮。

## 5. 测试（第一步）

- **平台**：守卫允许与拒绝；已登录加入只加注册角色，受保护的角色不能获得；未登录与未验证邮箱被拒。
- **持有的规则**（单元测试，固定时钟）：合格算、不合格不算；364 天算、366 天不算；当前版本才算；收回压过之前的、之后的合格又算；人工授予在有效期内算。
- **集成**：
  - 只有官方账号的发布能登记为轮；
  - 运营商只管其名下的人（别的运营商的 404）；
  - 申请成为商户：有认证可以、没有 403，并给出原因；
  - 答题路径的语句数不变（`AttemptStatementBudgetIT` 照旧通过，不改预算）；
  - 授予与收回只追加、有理由。
- **App**：账户页的三种状态（没有认证、有认证、已是商户）、链接、申请后的提示；axe。
- **e2e**：官方账号发布认证题 → 登记为轮 → 答题者合格 → App 申请 → 商户后台入驻 → 审核 → 顶栏出现"我的商户"。

## 6. 需求方的确认（2026-10-31：四个问题都按建议）

1. **人工授予**：可以，必须填理由，总部抽查（`QB_CERTIFICATION_OVERVIEW` 列出全部人工记录与理由）。
2. **申请之后**：入驻资料在商户后台填写（第一步）；App 里填写以后再考虑。
3. **认证题的奖励**：保持"至少一个档位有奖励"，官方账号付少量 Kudos，不改发布规则。
4. **到期提醒**：第一步不提醒，账户页显示到期日。

## 6a. 实施记录（Q69b）

- **持有的计算**：`QB_CERTIFICATION_CLAIM`（`qb.me`，账户页打开"成为商户"时运行）在锁 `qb.certification:<用户>` 内读该认证的轮、本人的记录与本人在这些轮上的答题，把未记下的合格（已完成、`passed`、在轮关闭之前提交）补记为 `PASSED`（`attemptId` 唯一、记 `roundId`，有效期自提交起一年），再以纯 Java 的 `CertificationHolding` 算出到期日。答题路径不变。
- **守卫**读的是记录表（`QbCertificationRecord`，按 `userId`），不读答题记录：申请前页面已运行过 `CLAIM`。
- **只有平台的已登录加入受认证约束**（`SignUpPath.SIGNED_IN_JOIN`）：商户后台的注册与"你已有账号"的邮件加入照旧（D-Q69-9）；以后的邀请制（Q69d）再收紧它们。
- **运营商的官方账号须是它名下的商户**：运营商只看得到名下商户的发布卡片（平台 D64 的入口范围），所以先以 `QB_SPONSOR_OPERATOR_ASSIGN` 归属，再由总部设为官方账号；别的运营商的发布对它是 404。
- **读取**：三张表的缺省数据视图只给总部（`qb.certification.admin`）；运营商经只读流程 `QB_CERTIFICATION_OVERVIEW` 看自己的轮（每轮的持有人数）与人工记录。
- **权限**：`qb.certification.manage`（内容管理员与运营商）、`qb.certification.admin`（内容管理员：官方账号）。部署后执行一次 `QB_SETUP`。

## 8. 风险

| 等级 | 风险 | 对策 |
|---|---|---|
| 中 | 认证题答案在答题者之间流传（答完会显示正确答案） | 合格分定高一些；定期出新一轮（旧轮可以取消登记）；以后再考虑题库随机抽题 |
| 中 | 平台改动"已登录加入入口"关系到账号安全 | 只加注册角色，受保护的角色不能获得；要已验证邮箱；守卫默认拒绝；平台自己的测试与示范先行 |
| 低 | 官方账号的奖励支出 | 合格档位给少量 Kudos，用发布的预算上限控制 |
| 低 | 门槛读取答题记录的成本 | 每次申请读一次，按已有的唯一索引查；不在热门路径上 |
