# F-INIT 上线初始化：一份文件、按人分段导入：实施计划（S1，2026-11-17，待 Fable 审查与总控批准）

状态：计划，未写代码。分支 `1.3/quizbuks-init-plan`（只改 `docs/**`）。

需求方的要求（总控 2026-11-17 转述）：重新彩排上线初始化时觉得步骤太多太累，希望"做一个导入，直接都初始化到位"。首发至少要 8–9 个账号；他已建了用户，但角色分不上去。

总控提出的要求：
- 一份初始化文件，加尽量少的导入，把能自动做的全部做完。
- 不绕过平台的安全规则。
- 可重复执行；先预览，再提交。
- 能接着页面上已经做了一半的数据继续做。
- 最后给需求方一页"导入后你只需做这几件事"。

依据：
- 文档：`operations.md` §3（首次启动）、§4、§7.13（运营商）；`launch-checklist.md` 第 2 部分；平台 `docs/design/20-imports.md`、`10-security.md` §15–§16；决策 D26、D36、D41、D48、D51、D63。
- 代码（读的是 `origin/1.3/quizbuks`）：`QbSetupProcesses`、`OperatorProcesses`、`UserProcesses`、`InvitationProcesses`、`ProtectedChangeProcesses` / `ProtectedGrants`、`ControlChanges`、`ImportDefinition` / `ImportAccess` / `RunImport`、`LegalProcesses`、`HelpMaterialsProcesses`、`MailTextProcesses`、`ParamProcesses`、`VerifiedEmailPolicy`、`BootstrapAdmin`、`QbRoles`。
- launch-loop e2e（`quizbuks-web/e2e/tests/launch-loop.*`）已经用接口走过建运营商、加成员、受控变更的提出与发布、法律文本发布，本计划沿用它验证过的顺序。

**结论先说**：

- **"一个人、一次导入、全部到位"做不到，也不应该做到**。平台有几条硬规则，任何导入都不能代替：
  - 密码只能由本人经邀请设定；
  - 二次验证只能由本人绑定；
  - 受控变更须另一位管理员发布（提出人不能发布自己的）；
  - 建立期结束后，受保护的授权须另一位超级管理员审批；
  - 职责分离规则不让超级管理员持有发布与审批的权限。
- 所以计划是：**一份工作簿 + 五段导入，每段由该做这件事的人在同一个页面上"预览 → 提交"一次**。
  - 每一段都把这个人当下能做的全部做完；
  - 做不了的，预览时就逐条说明原因、该由谁做、何时能做。
- 需求方剩下的手工是：
  - 每人收邀请邮件、设密码、绑二次验证（本人才能做）；
  - 每段导入点一次"提交"；
  - 法律文本逐份发布（4 次，每次二次验证）；
  - 负责人在发起方页面点"加入"；
  - 打开开关前的前提核对（上线清单第 3 部分，本来就逐项决定）。
- 第 5 节是给需求方的一页清单。

## 0. 名词

| 名词 | 含义 |
|---|---|
| 首个管理员 | 由 `JABIZ_BOOTSTRAP_ADMIN_USER` 建的账号（`BootstrapAdmin`）：持有 `*`，**没有邮箱**，所以永远不是"已验证邮箱"的调用者 |
| 建立期 | 首个管理员之外的管理员（持 `*`、`security.user-role.write` 或 `security.role.write` 的启用账号）不足两位的时期。期内受保护的授权当即生效；出现第二位即结束，永不回退（`ProtectedGrants` :345-362，D51） |
| 退役 | 首个管理员之外出现**任何一位**管理员，首个管理员即不能再做受保护的变更（403 `BOOTSTRAP_ADMIN_RETIRED`，`ProtectedGrants` :374-391） |
| 受保护的授权 | 给人（或给已有持有人的角色）它还没有的 `*`、`security.user-role.write`、`security.role.write`、`approval.decide`、`security.protected-change.decide`、`control.publish`、`ledger.*`、`platform.param.write`、`job.run`（`ProtectedPermissions` :34-36）。QuizBuks 的 `QB_ADMIN_SUPER`、`QB_ADMIN_FINANCE`、`QB_ADMIN_CONTENT`、`QB_OPERATOR` 都含受保护的权限 |
| 本人的凭据 | 建立期结束后，被授予者的密码须是本人设定的（经邀请或自己改的；管理员设过的不算），否则批准后应用时 `TARGET_CREDENTIALS_NOT_OWN`（`LoadProtectedChange` :207） |

## 2. 初始化文件：一个 XLSX 工作簿（建议），不用 YAML

**建议 XLSX**：
- 需求方用 Excel 填写，不必学语法；
- 平台自己读 XLSX（`ImportFormat.xlsx()`，不引第三方库，禁 DTD 与外部实体，有解压上限）；
- 导入的策略只允许 `TEXT` / `XLSX` / `XML`（D26），YAML 只能写自定义解析器，还要另加 YAML 库的安全审查（别名膨胀、类型构造）。

缺点是长文本（法律正文）在单元格里不便编辑，且单元格上限 32 767 字：
- 法律正文超过上限时，那一行报问题，提示"在法律文本（草稿）页粘贴"；
- 问答与手册都远小于上限。

工作簿由代码生成的模板开始（第 6 节"模板与同步"）：
- 预填平台已知的键与首次上线的值（取自 `setup.FirstLaunchSwitches` 与 `QbParams` 的声明），需求方只填空白处与要改的值；
- 每张表第一行是表头，第二行起是数据；
- 表头是固定的中文名，另有英文别名（导入定义的缺省列名可写多个）。

| 工作表 | 每行一件事 | 列（* 必填） | 由哪一段导入 |
|---|---|---|---|
| `账号` | 一个人 | 邮箱*、姓名*、用户名（空 = 邮箱）、语言（ja/zh/en，空 = ja）、角色*（`财务` / `内容` / `超级1` / `超级2` / `运营商成员` / `无`）、所属运营商（`运营商` 表的名称）、负责人（是/否）、重发邀请（是/否） | S1（建号、财务与内容角色、第一位超级管理员）；S3（第二位超级管理员、运营商成员）；S4（批准） |
| `运营商` | 一个运营商 | 名称*、联系人*、联系邮箱*、语言、默认（是/否，至多一行"是"）、备注 | S3 |
| `参数` | 一个受控参数或普通参数 | 键*、值*、类型（模板预填）、说明、发布时机（`现在` / `以后`；模板按首次上线的清单预填） | 提出：S1；发布：S2 |
| `规则` | 一条审批规则或职责分离规则 | 键*（如 `qb.sponsor.review`、`qb.sod.security-administration`）、发布时机 | S2（规则由 `QB_SETUP` 提出，本表只决定发布与否和顺序；不另提内容） |
| `帮助问答` | 一条问答 | 键*（稳定的标识，如 `sponsor-onboarding-1`）、对象*（APP / SPONSOR / ALL / OPERATOR）、顺序、问题（日、英*、中）、答案（日、英*、中）、公开中（是/否） | S5 |
| `法律文本` | 一种文本、一种语言 | 种类*（TERMS_APP / TERMS_SPONSOR / PRIVACY / TOKUSHO）、语言*、标题*、正文*、改定的概要 | S5（只换草稿，不发布） |
| `手册` | 一个入口的 AI 手册 | 入口*（app / sponsor）、载入（是/否）、发布（是/否） | S5 |
| `邮件文字` | 一个模板、一种语言（可选，首发多用缺省） | 模板*、语言*、主题、正文 | S5（只做不受保护的；受保护的报"须经受控变更"） |

**按邮箱认人**（总控的补充 c）：
- `账号` 表以邮箱（不分大小写）为键，其他表引用人时也写邮箱；
- 用户名缺省等于邮箱，也就是需求方登录时填的那个；
- 已经存在的用户（今天在页面上建了一半的）按邮箱找到即视为同一个人：已有的跳过并报告，缺的补上。

## 3. 导入的设计

### 3.1 为什么是"五段"而不是"一次"

平台的导入（D26，`20-imports.md`）是：一次导入由一个人提交；每行作为该人的子流程运行；提交时全部行在同一个事务中，有任何问题即整体拒收；同一文件只能成功提交一次。下面几件事不可能在同一个人的同一次提交中发生：

1. **四眼**：
   - 提出受控变更的人不能发布它（`CONTROL_CHANGE_PUBLISH` 比较 `ctx.request().actorId()`，`CONTROL_SAME_PERSON`）；
   - 建立期结束后，受保护的授权须另一位超级管理员审批（`APPROVAL_OWN_REQUEST`）。
2. **职责分离**：
   - 超级管理员不持有、也不能持有 `control.publish` 与 `approval.decide`；
   - 只有财务管理员能发布受控变更；
   - 内容管理员与财务管理员不能是同一个人（`qb.sod.control-changes`）。
3. **退役与建立期的先后**：
   - 首个管理员只能建**第一位**超级管理员（之后退役）；
   - 第二位必须由第一位建；
   - 职责分离规则必须在第二位出现**之前**发布，而发布要等财务管理员接受邀请、绑好二次验证。
4. **本人**：
   - 邮箱的验证、密码、二次验证只能本人完成，导入只能"等"；
   - 建运营商要求负责人的邮箱**已验证**（`QB_OPERATOR_MEMBER_UNVERIFIED`），也就是负责人已接受邀请。

因此按"谁、在什么前提下"分为五段。每段都是一个 `ImportDefinition`，读同一个工作簿：

| 段 | 导入 id | 执行人 | 前提（预览时检查，不满足即逐条说明） | 做什么 |
|---|---|---|---|---|
| S1 起步 | `qb.init.start` | 首个管理员（建立期内且未退役）；首个管理员已退役时，由第一位超级管理员执行（见 3.5） | 邮件已开启；执行人有近期二次验证；建立期未结束（否则只做不受保护的部分） | `QB_SETUP` → 建全部账号并发邀请 → 财务、内容的角色 → 普通参数 → 提出受控参数 → **最后**给第一位超级管理员角色 |
| S2 发布 | `qb.init.publish` | 财务管理员 | 执行人不是这些提案的提出人；`参数`/`规则` 表"现在发布"的行都有待发布的提案，且值与文件一致 | 按文件顺序发布（先 `qb.reward.kudos.enabled`、`qb.reward.default-methods`，再审批规则，职责分离规则在内） |
| S3 运营商 | `qb.init.operators` | 第一位超级管理员（邮箱已验证并已重新登录） | 三条职责分离规则已发布；第二位超级管理员与全部负责人、成员已接受邀请 | 给第二位超级管理员角色（建立期结束）→ 建运营商（默认的那个）与负责人 → 加成员 → 为成员申请 `QB_OPERATOR`（待审批） |
| S4 批准 | `qb.init.approve` | 第二位超级管理员 | 待批准的请求正是 S3 为文件中的成员提出的；执行人不是申请人、不是对象 | 逐条以 `APPROVAL_DECIDE` 批准（见 R1；也可以不用这一段，在"待办"中逐条批） |
| S5 内容 | `qb.init.content` | 内容管理员（邮箱已验证并已重新登录） | — | 问答（新增或更新）→ 法律文本草稿 → AI 手册载入与发布 → 不受保护的邮件文字 |

**一个页面**：管理系统扩展新增"QuizBuks → 上线初始化"（`/admin/qb/init`）。
- 上传一次工作簿（文件策略 `qb.init`，五段共用；文件编号在页面上保留）。
- 页面列出五段的卡片：谁执行、现在能不能做、还在等什么（读状态模板 `qb.admin.init-status`，见 3.4）。
- 当前用户能执行的那一段显示"预览""提交"两个按钮，结果按行列出：新建、已存在跳过、发起审批、问题。
- 需求方不需要知道导入的 id。每个人登录后打开同一页，看到的就是轮到自己的那一段。

### 3.2 每一段的行与调用的现有流程

所有业务写入都调用**现有流程**（以 `CallProcess.of` 作为子流程），不直接写表，不另写业务规则。唯一的例外是第 4 条中三个"薄流程"：现在只能经数据视图写的问答与草稿，没有可调用的流程（`ADD_ENTITY` / `UPDATE_ENTITY` 是 `entryOnly()`），所以各加一个只做这一件事的流程。

**行流程**：一个 `QB_INIT_ROW`。
- 声明 `subProcessOnly()`：只能作为导入的子流程运行，流程接口不提供。
- 声明 `qb.init.run`（新权限，不受保护）与 `requiresMfa(ADMINISTRATION)`。
- 按行的 `section` 分派。每个分派先做 **"如同入口"的检查**（`InitEntryChecks.asEntry(ctx, 目标流程)`）：调用者须持有目标流程声明的**全部权限**，并满足它声明的二次验证与已验证邮箱，方式与 `ImportAccess`、`ProcessController` 对入口的检查相同。
- 原因：平台对子流程**不查**权限、二次验证与邮箱（`VerifiedEmailPolicy`、`MfaRequirement` 的约定，`CallProcess` 也不查）。不这样做，持有 `qb.init.run` 的内容管理员就能经这个行流程建账号、分配角色，即提权。

| 段 | `section` | 每行做的事（顺序即工作簿解析后记录的顺序） | 调用的现有流程 | 已存在时 |
|---|---|---|---|---|
| S1 | `CHECK` | 检查前提（合成的第一条记录，见 3.4），任何问题都在这里给出 | — | — |

| S2 | `PUBLISH` | `参数`、`规则` 表中"现在发布"的行，按文件顺序找到对应的待发布提案（键与值都相同）并发布 | `CONTROL_CHANGE_PUBLISH` | 已生效且值相同即跳过；"以后发布"的行报"保留" |
| S3 | `ROLE_SUPER2` | 第二位超级管理员的角色（S3 的第一行，之后建立期结束） | `SEC_USER_ROLE_ASSIGN` | 已持有即跳过 |

| S4 | `APPROVE` | 找到 S3 为该成员、该角色提出且仍待审批的请求并批准 | `APPROVAL_DECIDE` | 已批准即跳过；不是由文件中的请求产生的待办一概不碰 |
| S5 | `FAQ` | 按（对象, 键）新增或更新问答 | **新** `QB_FAQ_SAVE`（薄流程，`qb.admin.content.write`） | 内容相同即跳过 |
| S5 | `LEGAL_DRAFT` | 把该种类、该语言的草稿换成文件中的文本（只改草稿） | **新** `QB_LEGAL_DRAFT_SAVE`（薄流程，`qb.admin.content.write`、已验证邮箱） | 与草稿相同即跳过；与已生效的版本相同 → 报"已是生效文本，无需发布" |

| S5 | `MAIL_TEXT` | 不受保护的模板 | `MAIL_TEXT_SAVE` | 与现值相同即跳过；受保护的报 `MAIL_TEXT_NEEDS_APPROVAL` 的说明并跳过（不算问题） |

三个薄流程（`QB_FAQ_SAVE`、`QB_LEGAL_DRAFT_SAVE`，以及主题词若需要时的同类流程）的约束：
- 只经 `ctx.changes()` 写，走平台的写入路径（审计、版本、字段规则照常）；
- 权限与数据视图的写权限相同（`qb.admin.content.write`），并声明 `requiresVerifiedEmail()`，与页面上一致；
- 不加任何业务规则；
- 它们也是普通流程，以后页面可以直接用。

### 3.3 子流程调用的可行性（已在代码中核对）

- 可作为子流程调用的流程须是 OPEN 或 `subProcessOnly()`（`ProcessExecutor.requireCallable` :254-263）。上表全部现有流程都是 OPEN。
- `IMPORT_RUN` 的目标须是 OPEN 或 `subProcessOnly()`，`QB_INIT_ROW` 符合。
- 被调用流程体内的检查照常生效，不会被导入绕开，因为它们比较的是 `ctx.request()`，也就是导入人：
  - `ProtectedGrants` 的评估与退役检查；
  - `CONTROL_SAME_PERSON`；
  - `ProtectedChangeDecisionCheck`（申请人、对象、近期二次验证、审批人须持有的权限）；
  - `MailTextControlTarget` 对 `mail.text.write`、邮箱与二次验证的检查；
  - `InvitationProcesses.checkAccount` 对已有密码者要求 `security.user.password`。
- 试运行（预览）回滚整个事务，不执行提交后步骤，因此**预览不寄任何邀请邮件**；提交后才寄。

### 3.4 预览就把会失败的原因说清楚（总控的补充 b）

每段的第一条记录是合成的 `CHECK`。其后每一行在调用流程**之前**先检查自己的前提，失败时给出 QuizBuks 自己的错误码（三语消息），带上：哪一行、为什么、该由谁做、何时能做。

问题文本中**不写邮箱与姓名**，只写行号、工作表与角色（如"账号表第 4 行（超级2）"），因为被拒的导入记录会保存问题（R4）。

| 失败原因（平台的码） | 何时发生 | 导入怎么避免 / 报告（新码） |
|---|---|---|
| `MAIL_DISABLED` | 邮件未开启时邀请 | S1 的 `CHECK`：`QB_INIT_MAIL_DISABLED`（"运维先设 `JABIZ_MAIL_ENABLED=true` 并重启"），整段不做 |
| 二次验证不够新 / 未绑定 | 行流程声明 `requiresMfa(ADMINISTRATION)`，入口即拒 | 平台的入口错误；页面提示"先在安全设置中验证一次" |
| `BOOTSTRAP_ADMIN_RETIRED` | 首个管理员在已有其他管理员之后再做受保护的变更 | S1 的 `CHECK` 读 `sec_bootstrap_retired`：已退役时 S1 只能由第一位超级管理员执行（`QB_INIT_BOOTSTRAP_RETIRED`，说明由谁执行）。S1 内部把 `ROLE_SUPER1` 排在最后，自己不会触发它 |
| 建立期已结束 → 需审批（`PENDING`） | 第二位管理员出现之后再授受保护的角色 | S1 的 `CHECK` 读 `sec_protected_grants_armed`：已结束时，财务、内容、超级管理员的角色改为"发起审批"并在报告中写明"须另一位超级管理员在待办中批准"（`QB_INIT_NEEDS_APPROVAL`，报告项而非问题）。S3 的成员角色本来就是待审批 |
| `TARGET_CREDENTIALS_NOT_OWN` | 建立期结束后，被授予者的密码不是本人设的（批准后应用时才失败） | 申请之前先查被授予者已接受邀请（已验证邮箱且密码来自邀请或本人修改）：未接受 → `QB_INIT_INVITE_NOT_ACCEPTED`（"等 X 接受邀请；72 小时内有效，过期则把重发邀请填'是'再执行 S1"）。用临时密码建的旧账号 → 同一个码，提示"重发邀请"（替换已有密码需要 `security.user.password`，首个管理员持有） |
| `PROTECTED_CHANGE_REQUIRES_APPROVAL`（邀请时） | 建立期结束后邀请已持有受保护权限的人 | 只在建号之后、授权之前邀请（S1 的顺序）；已持有的人报告状态，不再邀请 |
| `QB_SETUP` 在第二位超级管理员之后才执行 | 角色加 `security.protected-change.decide` 需要审批而无人能批，整个 `QB_SETUP` 被拒 | S1 的 `CHECK`：建立期已结束而 `QB_SETUP` 从未执行 → `QB_INIT_SETUP_TOO_LATE`，说明 `operations.md` §3"已有的安装"的出路（运维以 `JABIZ_SECURITY_PROTECTEDGRANTS_ENABLED=false` 启动一次），不尝试绕开 |
| 职责分离规则未发布就要建第二位超级管理员 | 之后任命内容、财务管理员和批准 `QB_OPERATOR` 都无法批准（D51 修订 H1） | S3 的 `CHECK`：`qb.sod.security-administration`、`qb.sod.control-changes`、`qb.sod.mail-texts` 未全部生效 → `QB_INIT_SOD_NOT_PUBLISHED`（"财务管理员先执行 S2"），整段不做 |
| 一人同时被写成内容与财务 | `qb.sod.control-changes` 拒绝 | 解析时即报 `QB_INIT_ROLE_CONFLICT` |
| `EMAIL_NOT_VERIFIED`（调用者本人） | 首个管理员没有邮箱；超级管理员验证后没重新登录（令牌里的声明仍是"未验证"） | S3、S5 的 `CHECK` 读**令牌中的**验证状态：`QB_INIT_CALLER_EMAIL_NOT_VERIFIED`（"当前登录账号的邮箱未验证，或验证后尚未重新登录"） |
| `QB_OPERATOR_MEMBER_UNVERIFIED` | 负责人或成员尚未接受邀请 | `QB_INIT_INVITE_NOT_ACCEPTED`（同上），指明是哪一行的负责人或成员 |
| `MEMBER_ELSEWHERE` / `MEMBER_IS_SPONSOR` | 负责人已在别的运营商，或已是发起方 | 原样报告，指明行号（不另写规则） |
| `CONTROL_SAME_PERSON` | S2 由提案人执行 | S2 的 `CHECK`：执行人提出过其中任何一条 → `QB_INIT_PUBLISHER_IS_PROPOSER` |
| 提案的值与文件不同 | `QB_SETUP` 的首次上线值与需求方的值不同，或页面上手提过别的值 | S1 报 `QB_INIT_PROPOSAL_DIFFERS`（"提案 #…（值 …）与文件不同：由提案人撤回后重新执行 S1"）；S2 不发布值不同的提案 |
| 首次上线开关的前提未满足 | 如 AI 使用说明未发布就发布 `qb.ai.enabled` | 模板把这些行预填为"以后发布"，S2 不动；改成"现在发布"时，S2 对照 `FirstLaunchSwitches` 的前提表给出警告（不是问题，需求方书面决定） |

**状态模板** `qb.admin.init-status`（只读，持有 `qb.init.run` 的人可读）给页面的五张卡片提供数据：
- 每段：是否已提交（`sys_import_run`）；
- 建立期与退役的状态；
- 待发布的提案数；
- 待审批的请求数；
- 每个账号的状态：已邀请 / 已接受 / 已绑二次验证 / 已持角色。只列人数与行号，不输出邮箱。

### 3.5 已经做了一半的现状（总控的补充 c）

导入不假设空库，每一行都"先看现状再决定"（3.2 表的最后一列）。常见的几种半成品：

| 现状 | 导入的做法 |
|---|---|
| 页面上已建好用户（可能设了临时密码，可能还没分到角色） | 按邮箱认人。已接受邀请的照常授权。设过临时密码、没接受邀请的，建立期内仍可当即授权（不查本人凭据）；建立期结束后报 `QB_INIT_INVITE_NOT_ACCEPTED` 并建议"重发邀请=是" |
| 首个管理员已退役（已有一位超级管理员） | S1 改由那位超级管理员执行：他做不了的（普通参数需要 `*`）报告为"首个管理员已退役：普通参数请在参数页由持 `*` 的人修改，或略过"。超级管理员能做的照做 |
| 建立期已结束（已有两位超级管理员） | 受保护的角色一律"发起审批"，由另一位超级管理员批（S4 或待办） |
| `QB_SETUP` 的提案已被部分发布 | S2 跳过已生效且值相同的，只发布剩下的 |
| 已建过运营商 | 按名称认运营商；负责人相同即跳过 |

同一文件成功提交后不能再提交同一段（平台 409 `IMPORT_ALREADY_IMPORTED`）。之后若改了文件（加了一个人），文件的哈希即不同，各段可以重新执行，已做的行全部跳过。

被拒的提交只留下记录，不算"已提交"，所以"等某人接受邀请"之后**用同一个文件**重新提交即可。

## 4. 平台的安全规则：逐条说明导入怎么守、剩下哪几下手工

| 规则 | 导入的做法 | 需求方剩下的手工 |
|---|---|---|
| A1 密码只能由本人经邀请设定（D63） | 建号一律 `invite: true`、不设密码；绝不调用 `SEC_USER_SET_PASSWORD`；重发邀请只在"重发邀请=是"时做 | 每人点邀请邮件的链接、设密码（72 小时内） |
| A2 二次验证本人绑定（D28） | 不碰 `SecUserMfa`；行流程本身要求导入人有近期二次验证 | 每人首次登录时绑定（管理员角色与 `QB_OPERATOR` 都要求） |
| A3 受控参数与审批规则须另一位管理员发布（D40） | S1 只提出，S2 由财务管理员发布；提出人与发布人由平台比较（`CONTROL_SAME_PERSON`），导入不提供"自己提、自己发" | 财务管理员执行一次 S2（代替逐行点几十次） |
| A4 受保护的授权须另一位超级管理员审批（D48、D51） | 建立期内由平台当即生效（这是平台的规则，导入不扩大它：只在 S1、S3 中、按 `operations.md` §3 的顺序用到）。建立期后由 S3 申请，S4（或待办）批准；审批人的条件由平台查 | 第二位超级管理员执行一次 S4，或在待办中逐条批准（每个成员一条，首发约 2–4 条） |
| A5 首个管理员只建第一位超级管理员，之后退役 | S1 把它排在最后；第二位由 S3 建 | 无（S3 本来就由第一位超级管理员执行） |
| A6 职责分离规则在建立期结束之前发布（D51 修订 H1） | S3 的 `CHECK` 不满足即整段不做 | 无（S2 已包含这些规则） |
| A7 调用者本人的邮箱已验证（D36 第 3 条，令牌的声明） | 建运营商与内容的段要求调用者的令牌是"已验证"；首个管理员没有邮箱，所以 S3、S5 不由他执行 | 验证邮箱后**重新登录一次**（经邀请设定密码的账号在设定时即已验证，之后的第一次登录就带着新声明） |
| A8 负责人与成员的邮箱已验证（F-S1） | 由 `QB_OPERATOR_SAVE` / `MEMBER_ADD` 自己查；导入在调用前先查并说明 | 负责人与成员接受邀请 |
| A9 子流程不查权限 | `QB_INIT_ROW` 对每一行按目标流程做"如同入口"的检查；`subProcessOnly()`，不能经流程接口调用 | 无 |
| A10 法律文本每次发布要求二次验证、留审计 | 导入只换草稿，**不发布** | 内容管理员在 `/qb/legal` 预览并发布 4 次 |
| A11 受保护的邮件文字与信纸是受控变更，提出时要求内容管理员近期二次验证（`MailTextControlTarget`） | 本计划不做（首发多用缺省文字）；报告列出 | 需要时在 `/mail/texts` 提出、财务管理员发布 |
| A12 个人信息 | 问题与状态模板不输出邮箱、姓名；文件策略 `privateMetadata()`（只有上传者与 `file.read` 看得到）；初始化完成后页面提示删除工作簿（`FILE_DELETE`） | 完成后点"删除工作簿" |

建立期内当即生效的规则不是导入新开的口子：平台对任何人、任何入口都一样（`ProtectedGrants` 的 `armed`）。导入只在 `operations.md` §3 已规定的两处用到它：S1 的财务、内容与第一位超级管理员，S3 的第二位超级管理员。

## 5. 给需求方的一页："导入后你只需做这几件事"

（实施时放进 `docs/quizbuks/launch-init.md`，并在 `/admin/qb/init` 页面顶部链接。下文是草稿。）

> **准备**：从"上线初始化"页下载模板，填 `账号`（8–9 人：邮箱、姓名、角色、所属运营商、是否负责人）、`运营商`、`参数`（开具方、科目代码、金额）、`帮助问答`、`法律文本`。运维已开启邮件。
>
> 1. **首个管理员**：登录，绑二次验证；在"上线初始化"上传工作簿 →「预览」→ 没有红字就「提交」（S1）。所有人随即收到邀请邮件。运维把首个管理员的两行环境变量删掉。
> 2. **每个人**：点邀请邮件的链接设密码 → 登录 → 绑二次验证。
> 3. **财务管理员**：打开"上线初始化" →「预览」→「提交」（S2：一次发布全部"现在发布"的设置）。
> 4. **第一位超级管理员**：打开"上线初始化" →「预览」→「提交」（S3：第二位超级管理员、运营商、成员）。预览说"等 X 接受邀请"就请 X 去点邮件，之后再提交。
> 5. **第二位超级管理员**：打开"上线初始化" →「预览」→「提交」（S4：批准运营商成员）。
> 6. **内容管理员**：打开"上线初始化" →「预览」→「提交」（S5：问答、法律文本草稿、AI 手册）；然后在"规约类"页逐份看过并「发布」4 种法律文本（每次输入二次验证码）。
> 7. **负责人**：登录发起方页面，点"加入"。**运营商成员**：登录运营商管理系统，绑二次验证。
> 8. 完成后在"上线初始化"页点「删除工作簿」。
>
> 之后：上线清单第 3 部分的开关（赠送额度、AI 等），在前提满足时由财务管理员在同一页勾选发布（第 5.1 节）。

步骤数对比：
- 今天：本人以外的页面操作约 60–80 次。按 SysControlChange 逐行发布数十次，每个账号建号、分配角色各一次，参数逐个提出。
- 之后：5 次"预览 → 提交"，4 次法律文本发布，外加每人的本人操作。

### 5.1（第二批，可选）以后发布的开关

`参数` 表中"以后发布"的行，S2 第一次不动。前提满足后（上线清单第 3 部分）：
- 财务管理员把文件中那一行改为"现在发布"，或在页面上勾选该行；
- 再执行一次 S2，只发布这些行（文件已变，哈希不同，可再次提交）。

不另写发布逻辑。

## 8. 风险

- **R1 一次批准多条受保护的授权（S4）**。是否允许，请 Fable 判断。
  - 支持：批准仍由另一位超级管理员本人执行，且有近期二次验证；平台对每一条照常检查申请人、对象与审批人须持有的权限；只批 S3 为文件中的成员提出的请求，预览逐条列出。
  - 反对："一次批多条"减弱了逐条审视。
  - 备选：不做 S4，在待办中逐条批准（首发约 2–4 条，差别不大）。
  - **推荐**：先不做 S4（PR c 不含），首发在待办中逐条批。
- **R2 导入人持有的权限面更大**。`QB_INIT_ROW` 是 `subProcessOnly()` 并对每行做"如同入口"的检查。要防的是将来有人加一个新的 section 却忘了检查，所以：
  - 分派表写成"section → 目标流程"的数据，检查由分派统一做，不由各分支各自做；
  - 测试逐个 section 断言"缺目标流程的权限即 403"。
- **R3 全有或全无**。一段中只要一行未就绪（某人没接受邀请），整段被拒。这是平台导入的语义（D26）。好处是不会半做；代价是要等齐了再提交。预览把等待的人列清楚，页面卡片也显示，需求方据此催人。
- **R4 个人信息**。
  - 工作簿含邮箱与姓名；被拒的导入记录保存前 1000 个问题；状态模板对持 `qb.init.run` 的人可读。
  - 因此：问题文本只写行号与角色；文件策略 `privateMetadata()`；完成后提示删除工作簿。
  - 实施时核对 `sys_import_run` 保存的报告是否含单元格的值。若含，在 `ErasurePurger` 的范围中确认，并在 PR 中说明（CLAUDE.md"账号删除与个人信息抹除"）。
- **R5 `QB_SETUP` 的提案与文件的值冲突**。
  - `QB_SETUP` 先提出首次上线的值，文件再改，会有同一个键的两条待发布提案。
  - 规则：文件的值与 `QB_SETUP` 的待发布提案不同时，S1 报问题，不再提第二条；由提案人（就是 S1 的执行人）撤回后重跑。
  - 模板预填首次上线的值，多数行不会冲突。
- **R6 环境**。`JABIZ_WEB_ENVIRONMENT` 不是 `production` / `staging` 时，`QB_SETUP` 提出声明值，S1 会对每个不同的键报 R5 的问题。`CHECK` 先报"环境不是 production/staging"，作为警告，测试系统按需继续。
- **R7 法律正文的单元格上限**（32 767 字）。超过时那一行报问题，需求方在草稿页粘贴。日文条款多在上限之内，彩排时用真实文本验证一次。
- **R8 邀请邮件的寄送**。提交后寄出，8–9 封，在平台限流之内。邮件服务器失败只影响寄送，邀请记录已在，可"重发邀请"。

## 9. 顺带的两处小修（PR a，可以先做）

1. **`EMAIL_NOT_VERIFIED` 的提示指明是当前登录的账号**。
   - 这个错误只针对调用者本人：`VerifiedEmailPolicy` 读的是调用者令牌中的声明。今天的文字是"请先验证您的电子邮箱。"，让人误以为说的是负责人。
   - 改为三语"**当前登录的账号**的邮箱尚未验证。请先验证邮箱，再**重新登录**后重试。"：
     - 中：`当前登录的账号的邮箱尚未验证：请先验证邮箱，并重新登录后再试。`
     - 日：`ログイン中のアカウントのメールアドレスが未確認です。確認後、ログインし直してから再度お試しください。`
     - 英：`The e-mail address of the account you are signed in with is not verified yet. Verify it, sign in again, and retry.`
   - 消息在平台（`backend/core/src/main/resources/jabiz/messages_*.properties:36`），对所有入口都成立（该码只用于调用者）。按 CLAUDE.md 第 8 节，**平台的改动先在 `1.3/platform` 做**（一个小 PR 加 `MessagesTest` 的断言），再同步到 `1.3/quizbuks`。
   - 不想动平台文字的备选：QuizBuks 的消息覆盖同一个键。是否可行要先确认平台的消息源顺序；推荐改平台。
   - 同时把 `QB_OPERATOR_MEMBER_UNVERIFIED` 的文字改为明确说"**所选负责人（或成员）**的邮箱尚未验证：请他先接受邀请"（QuizBuks 的消息，PR a 内），把两种情况区分开。
   - 管理系统扩展的运营商页在提交前提示一行："建运营商要求当前登录的您本人邮箱已验证；首个管理员（引导账号）没有邮箱，请由超级管理员操作。"
2. **文档**：
   - `operations.md` §3 第 5 步末（默认运营商）与 §7.13"第一个运营商"第 2 步补一句："**操作的管理员本人**的邮箱须已验证（经邀请设定密码的账号即已验证），验证后须**重新登录**（验证状态随登录令牌）。首个管理员没有邮箱，不能建运营商，由超级管理员建。"
   - `launch-checklist.md` 2.2"第一个运营商"一项补同样的一句；`troubleshooting.md` 加一条 `EMAIL_NOT_VERIFIED`（建运营商时）的排查。
