## 1. 现状与范围

### 1.1 已合并的代码里已经有的（读代码得到的事实）

规格 F-M13 的许多条已经由 F-M1 做完，**本项不重做**：

### 1.2 还没有的（本项要做的）

1. **账单与 PDF 写明付款来源**：现在 PDF 只有总额、税和"状态"，没有"赠送额度 X、预付款 Y、现金 Z、未付 W"（F-M.md 也把"PDF 分列"留到 M9）。
2. **自动付**：开关 `qb.fee.auto-pay.enabled` 只有 `FirstLaunchSwitches.java:89` 的一行 `waiting(…, "F-M13")`，参数本身不存在，也没有任何地方在到账后自动付账单。
3. **税的显示**：PDF 只印税额，不印税率，也没有按税率的小计；开出时间印的是 UTC 时刻（每月 2 日 01:17（日本时间）开出的月账单会印成 1 日 16:17）；"状态"一行印的是签发那一刻的状态，之后会过时。

6. **每日核对**：没有"账单已付额 = 付款行之和"、"该自动付的没有付"这两项。

### 3.2 PDF 里的付款来源（核心）

**定义就是 SQL（H2）。** 单据的区块只显示 SQL 模板的列（决策 D30），PDF 走不到 Java；`jabiz-core` 是平台目录，应用不能往里加类。所以付款来源的唯一定义写在模板里：发起方的 `qb.sponsor.fee-invoice-sources` 与平台管理的 `qb.admin.fee-invoice-sources` 写**同一段 SQL**，两个文件的头部与这一段上面都注明"改一处即改两处"（不再有第三份：不另设管理员专用的配置或 Java 副本）。如果要 Java 版，只作应用包里的纯 Java 对照（测试用，不在核心层），并加一个"模板与 Java 对照"的 IT（照 `AudienceIT` 的做法：同一批造出的账单，模板的行与 Java 逐行相等），防止两处各改各的。

**共同定义只落到"行"这一层（H1）：** 一张账单的付款行 = `QbFeePayment` 中对象为该账单、或为它涵盖的费用（含提前付清的单笔账单、含带预付款编号的行）的行（`fee-payments.sql` 已有同样的找法）。按行分类：

| 行 | 来源 |
|---|---|
| 行带预付款编号 | 预付款 |
| 否则子账户为赠送额度（`FEE_CREDIT`） | 赠送额度 |
| 否则子账户为现金 | 现金 |

- "**赠送额度付**"（与 F-M12 共用的那一个定义）= 子账户为 `FEE_CREDIT`、对象为该费用或账单的行（含带预付款编号的行）的含税净额；带预付款编号的那部分另作一行"其中来自赠送额度"。
- 再加已被贷项凭证抵减的 `creditApplied`（依赖 F-M7（未合并），读账单上的列）；未付 = 合计 − 以上四项之和（作废时退回的负行已冲减）。**恒等式**：赠送额度 + 预付款 + 现金 + 贷项抵减 + 未付 = 合计（"其中来自赠送额度"一行不计入和）。

**它和 F-M12 的"赠送支付"不是同一个数**（F-M12 §3.3），本项不声称对得上结算单：F-M12 的数折成税前、按累计取整，含贷项凭证退回的负数行（对象是凭证，经 `chargeId` 归到费用），只取"费用已有 `CHARGE` 行"的、按结算算入的那次归月而不是账单月，只算进了基数的比例（AI 等 `excluded = amount` 的为 0），且按来源分甲、乙；账单 PDF 则是含税、按账单、不含对象为凭证的行、签发时刻的快照。两边共用的只是上面的行分类。**交叉测试**（F-M12 合入后补）：取同一批费用，本项的"赠送额度付"（逐账单求和）= F-M12 `GIFT` 行的 `giftGross`（排除对象为凭证的行）之和；或只断言逐行分类一致。（依赖 F-M12（计划中））

- **实现：** 新模板 `qb.sponsor.fee-invoice-sources`（参数账单号与"截至"日，多行：来源代码、金额；`UNION ALL` 出赠送额度、预付款、其中来自赠送额度、现金、贷项抵减、未付六行，没有的为 0；走发起方自己的数据视图，别人的账单没有行）。**同一个模板既给 PDF 的新区块（`table`），也给发起方页面的"付款情况"**，两处不会不一致。
- **"未付"与四个来源必须在同一条语句里算出（H2）。** 签发流程（`QB_FEE_INVOICE_DOCUMENT`）只持账单锁 `qb.fee-invoice:<账单>`，不持钱包锁；自动付上线后"签发时正好在付款"会常见，如果分两条语句读（先读付款行、再读 `creditApplied` 或合计），读到的数可能不平，而 PDF 一旦签发就永久存档。所以模板用一条语句、一个快照：付款行、账单上的 `creditApplied` 与合计在同一个 `SELECT`（CTE）里取，未付在 SQL 里算出，不在页面或 Java 里再减。并发测试见第 7 节。
- **这是签发那一刻的快照**（PDF 在发起方第一次下载时才签发）：PDF 上写明"付款情况截至 <日期>"，金额、税、明细永不变；之后的付款在页面上看（实时）。不为"已付清"另出 PDF（问题 1）。PDF 里原来的"状态"一行去掉（它会过时，见"删除的功能"）。
- 预付发起方的账单是记费时当场开的，大多数当场就付清，快照是完整的；后付的月账单在开出的第二天才可能被下载，快照多半是"未付"。这就是问题 1 要确认的后果。

### 3.5 自动付 `QB_FEE_AUTO_PAY`（新）

**触发（M2）：事件只为"快"，只在三处发**同一个事件 `qb.fee-account.funded`（`{sponsorId}`，只带发起方）：
1. 卡或银行充值进现金（现有 `qb.topup.paid`，`TopUpCrediting.java:109`，订阅时**只看去向为 `CASH` 的**；去向为学分的充值不触发，要有反例测试）；
2. 赠送额度发放（`QB_FEE_CREDIT_GRANT`）；
3. 运营商转入（`OperatorTransfers.java:232` 的 `CashLots.add`）。

其余使可用额增加的路径**一律等每日任务**，不各发事件：预付款退回（`QB_PREPAYMENT_RELEASE`）、账单作废的退回（`QB_FEE_REFUND` 的 `backTo` 直接改笔的 `remaining`，不经 `CashLots.add`，`FeeSettlement.java:331-343`）、F-M7 的凭证退回现金或赠送、争议冻结解除（冻结额减少，完全不经笔）、报名费入账、学分换回现金。`CashLots.add` 是流程计算步骤里的静态方法（`CashLots.java:42`），发不了事件，所以**不用 ArchUnit 去盯它**；靠测试覆盖每条路径（第 7 节）。
**兜底**：每日任务 `qb.fee-auto-pay`（`JobDefinition.forEach`，每项一个发起方；取项模板 `qb.system.fee-auto-pay-due`，条件 = **有未付账单 ∧ 可用额 > 0**，可用额 = 余额 − 冻结额；cron 在部署设置里，缺省 02:27 日本时间，在 02:37 的逾期任务之前，实施时对照 `FeeConfig` 的各 cron 避免撞车）。事件丢了、开关晚打开、付款途中失败、上面那些不发事件的路径，都由它补。**开关打开后的第一个夜里**，有钱又有未付账单的发起方会被付清——这是预期，写进上线步骤（问题 8）。
**流程**（`internal()`，输入发起方）：只取 `qb.wallet:SPONSOR:<发起方>`（之后不再取任何锁；与 `QB_FEE_INVOICE_PAY` 同一把锁，同一个顺序）→ 在锁内一条合并读取：该发起方未付账单（状态在 `QbFees.UNPAID`，含 `OVERDUE`，按开具时刻、账单号，最早的先，至多 `qb.fee.auto-pay.max-invoices` 张）及其 `creditApplied` 与 `paidAmount`、赠送笔、现金笔与现金钱包 → 对每张调用同一个子流程 `QB_FEE_SETTLE`，付 min(欠额, 可用额) → 与手工付共用同一个"记付款"辅助方法 → 发一个邮件事件。付不完的账单变 `PARTIAL`，一分钱也付不了就什么都不写。
- **欠额与贷项（M5）：** 自动付**自己不抵贷项**、不写 `QbFeeCreditNoteUse`。F-M7 里未用贷项只在开凭证时和以后开账单时抵，所以未付账单与未用贷项正常不会并存。欠额用 F-M7 的公式 合计 − `creditApplied` − `paidAmount`（F-M7 分支 `FeeProcesses.java:187` 的注释）；"记付款"用 **F-M7 改后的 `FeeProcesses.recordPayment`**（F-M7 分支 `:733-737`，它的 `PAID` 判断含 `creditApplied`），不用合并前的那个。已被贷项抵清的账单欠额为 0，不取。
- **开关（M1）：** `qb.fee.auto-pay.enabled` 按**运行时刻**读，用 `LoadParams.optional`（已有先例：`QuizBankLimits.java:16` 的说明），**不是 `true` 即关**；每日任务的取项模板同样。受控参数在 `QB_SETUP` 提出后、另一位管理员发布前没有值，这段时间就是关。登记的首次上线值照规格是 `true`：**发布这一步就是"打开"**，所以上线清单写明发布前先通知发起方（问题 8）。关则流程直接结束，不重试。不追溯：关着时进账的钱，打开后由每日任务统一补付。
- **一次最多付几张（L1）：** `max-invoices` 范围 1–50、缺省 20。理由：流程是在钱包锁内连续做 `QB_FEE_SETTLE`，占锁的时间与张数成正比；人手点的"提前付清"一次至多 `MAX_EARLY = 100` 笔费用（`FeeProcesses.java:214`），自动付不该比它更久地占着同一把锁，所以上限取它的一半，缺省再取其不到一半。事件触发的那次付不完（张数超限、仍有未付而且可用额 > 0）时，**再发一次同一事件**继续；还是不行就等每日任务。
- **不是"同一个事务链"（L3）：** 到账与自动付是两个事务——自动付是事件消费者的另一个事务，中间有事件投递的延迟。测试要 `deliverEvents`（场景用 `deliverEvents: true`）。
- 与别的流程并发：与手工付、`QB_FEE_PAY_EARLY`、提交发布的资金检查（都取钱包锁）串行；与作废审批结果（`QB_FEE_REQUEST`）、F-M7 的凭证开具、每月 2 日的月账单开具任务，凡是改同一张账单或同一个钱包的，都要取同一把锁（钱包锁或 `qb.fee-invoice:<账单>`，次序按平台的取锁约定，同一次只往一个方向取）。实施时逐个对照它们已取的锁，缺的补取，各有并发 IT 证明串行且不多付（第 7 节）。自动付先于提交时，提交的可用额就是付完之后的；提交先于自动付时，预付款已冻结的钱不在可用额里，自动付只花剩下的。
- 作废后退回的钱（退回到旧笔，可用额增加）会被每日任务用于**另一张**未付账单：这是预期，写进 `operations.md`。
- 被封禁或注销中的发起方照付（欠的是平台的钱；F-M15 另定，风险 8）。**自动付不经 `ConsentChecks.sponsor()`、不查封禁、不要求本人操作**，所以发起方条款要有对应的一句（问题 13，法务项）。正在申请作废的账单照付（问题 16）。
- 邮件：新模板 `qb.fee.auto-paid`，**一次运行一封**，不是一张账单一封。细节见 H4：`TRANSACTIONAL`（不进偏好，没有退订；写明）、`protectedText()`、`sample`、三语 `mail.qb.fee.auto-paid.name`；文字在消息 `mail.qb.fee.auto-paid.*`，在线修改走受控变更 `MailText`（另一位管理员发布）；列入 `MailTemplatesCoverageTest.PROTECTED`（`MailTemplatesCoverageTest.java:39-41`，现有 `qb.fee.invoice-issued` 等同类）。**事件载荷**带发起方、各张账单的编号与各次付款的 `transactionId`（不带金额）；消费者按这些 `transactionId` 汇总 `QbFeePayment` 得到付款合计，并重读各账单的欠额得到仍欠合计，**不信事件里的数字**。跳过过时的事件（超过 `NotificationMails.TRANSACTIONAL_MAX_AGE`，`NotificationMails.java:146`、`MailProcesses.java:518`）、被封禁的与没有邮箱的收件人（照现有同类邮件的规则）。
- 语句数：新的写入路径，`FeeAutoPayStatementBudgetIT` 断言一张、三张时的确切语句数，**再加"无事可做"一例**（只有取锁与一条读）；`QB_FEE_INVOICE_PAY` 抽出共用辅助方法后语句数必须不变（现有的相关预算测试照跑）。
- 权限：`internal()`，`ProcessAccessIT` 加一行。

## 8. 风险

1. **适格请求书的字样与要求需要财务或法务确认（不是工程能定的）**：PDF 印出登记号、税率、按税率的小计、交易月份、付款方名称，但**不写"适格请求书"**，直到书面确认（问题 4）。已签发的 PDF 不能改，确认前不要对真实发起方签发；上线检查清单已有一项，本项把它写实。
2. **税的取整**：现在每笔费用各自向下取整，月账单的税是各笔之和。适格请求书要求"每张账单每个税率取整一次"。预付发起方的账单一张只有一笔费用，天然满足；后付月账单多笔费用可能差几日元（问题 5）。若要按账单取整，差额记到哪里、1130 如何平，是会计决定，且要改 F-M5 到 F-M8 的记费口径——**不在本项做**，只在问题 5 里让财务选。
3. **快照的含义**（问题 1）：PDF 是第一次下载时的样子，发起方可能以为 PDF 会随付款更新。靠"截至日期"和页面说明缓解；不做的话需要"再签发一份新的"，而单据的约定是更正要另出一张，不是改。
4. **自动付的意外**：打开开关后第一夜会付清所有"有钱又有未付账单"的发起方（问题 8）；后付的发起方也会在收到月账单当晚被付，充值本想换学分的会先被未到期账单占用（问题 7）；充值后被自动付掉、又申请退款的怎么办（问题 14）。靠上线通知与邮件缓解，开关是受控参数，关掉即停（已付的不退）。开关"发布即打开"，所以发布前必须先通知。
5. **漏掉使可用额增加的路径**：事件只为快，只在三处发；其余路径靠每日任务兜底，所以"每日任务的取项条件"（有未付 ∧ 可用额 > 0）必须覆盖每一条路径——用逐路径的 IT 钉住（第 7 节），不依赖 ArchUnit（`CashLots.add` 是静态方法，发不了事件，退回到旧笔的路径甚至不经它）。新增使可用额增加的路径时，同样加一例。
6. **与 F-M7 的合入顺序**：本项在 F-M7 之上做（`creditApplied`、凭证版式、凭证模板）。F-M7 的修订若改了 `creditApplied` 的读法或 `CreditNotes` 的辅助方法，本项的付款来源模板与自动付的读取要跟着改；两个 PR 共用 `FeeProcesses`、`FeeDocuments`、`FeeConfig`、`QbParams`、`FirstLaunchSwitches`、messages 三个文件和 `operations.md`，冲突会多，所以等 F-M7 合入后再开 PR。
7. **说明列的取数**：配送费、曝光费、AI 费的对象各来自不同的结算行，说明模板是多种来源的合并，容易漏一种；用"每种费用种类各一例"的测试覆盖，新种类加入时同步（F-M8、F-M9 合入后各补一例）。
8. **封禁与注销**：被封禁或正在注销的发起方要不要自动付，等 F-M15 定；本项先按"照付"（欠的是平台的钱），并在 F-M15 的计划中提醒。
9. **账单年份取费用所属月的年**：12 月的月账单在次年 1 月开出，号码是上一年的（取舍，已是现状，不改，`operations.md` 写明）。
10. **PDF 语言**：以发起方第一次下载时的界面语言为准，之后固定；要另一种语言的只能由财务线下处理（现状，不改）。

## 9. 要问需求方的问题（简单说法，每条带数字例子和建议）

下面的数字都是例子；平台费都含 10% 消费税。

1. **账单 PDF 上的"已付多少、未付多少"，写的是哪一刻的？** 例：11 月 2 日开出一张 11,000 日元的月账单，发起方 11 月 5 日第一次下载 PDF，这时已用赠送额度付了 4,000，还欠 7,000；11 月 20 日他又付清了。PDF 是第一次下载时做的，永远不变，所以它一直写"已付 4,000、未付 7,000"。最新的情况在页面上看。**建议：这样做**，PDF 上明写"付款情况截至 11 月 5 日"，金额、税、明细永不变，不为"已付清"再出新的 PDF（账单只是一份请求付款的文件，付清的证明是页面和充值的收据）。如果您希望付清后能拿到一份"已付清"的 PDF，请告诉我们，那是另一份新文件。
2. **用预付款付的部分，要不要写出这笔预付款原来有多少是赠送额度？** 例：一笔 11,000 日元的费用从预付款付，这笔预付款当初是 3,000 赠送额度加 8,000 现金。规格只要求写"预付款 11,000"。**建议：付款情况里写一行"预付款 11,000"，再单独一行"其中来自赠送额度 3,000"**（只在大于 0 时写），因为赠送额度付的部分税务怎么处理还没定（问题 12），以后追溯方便。注意：这行和运营商结算单上的"赠送支付"不是同一个数（结算单是折成税前、按月累计算的），不要拿两者直接核对。
3. **账单上的日期写哪个时区？** 例：每月 2 日凌晨 1:17（日本时间）开出月账单，现在 PDF 写成"11 月 1 日 16:17（UTC）"，日本的发起方会觉得日期错了一天。**建议：改成写开具日（日本时间的日期，如"11 月 2 日"），去掉 UTC 时刻**；到期日本来就是日期。已签发的 PDF 不变（现在还没有真实的发起方）。
4. **要不要在上线时就写"适格请求书"？** 发起方是企业，想抵扣消费税就需要适格请求书。例：开具方登记号 T1234567890123，发起方想用这张账单抵扣 1,000 日元的消费税。**建议：上线前由财务或法务书面确认后，才在 PDF 上写这几个字**；确认前 PDF 照样印出登记号、税率、按税率的小计、交易月份和付款方名称，但不写"适格请求书"。已签发的 PDF 无法修改，所以这件事要在第一张真实账单签发之前定。收据继续写明"不是适格请求书"。
5. **税的尾数怎么算？** 例：后付的月账单有 3 笔费用，每笔 1,005 日元（不含税）。现在每笔各算税：每笔 100，合计 300 日元，账单含税 3,315。适格请求书的算法是整张账单一起算：3,015 × 10% = 301.5，取整 301，含税 3,316，差 1 日元。预付发起方一张账单只有一笔费用，没有这个差别。**建议：上线时保持现在的做法（各笔分别算税）**，由财务决定后付月账单是否一定要按整张账单取整；若要，是单独的一项改动（会影响记账口径），不在本项做。
6. **预付的发起方，每笔费用一张账单，对吗？** 例：一位预付的发起方这个月有 5 个发布，每个发布一笔配送费，会得到 5 张各有编号的已付账单，而不是一张 5 行的月账单。后付的发起方是一张月账单。**建议：上线时保持**（编号一个不缺、每笔费用的凭证各自独立；也不会因为月底才汇总而拖延凭证）。以后可以在页面上加"按月合计"的清单（只是页面，不是新的法律文件）。
7. **自动付款是不是到账就立刻付，哪怕还没到期？** 例：后付的发起方 11 月 2 日收到一张 8,000 日元的月账单，到期日 12 月 2 日；11 月 5 日他充值了 100,000 日元。规格是"到账后自动付最早的未付账单"，所以 11 月 5 日就付了 8,000，而不是等到 12 月 2 日。**后果：** 后付的发起方充值如果本想换学分（例：充 10,000 想换学分），钱会先被未到期的账单占用，可用额变少（首次上线学分奖励关着，影响小）。**建议：立即付**（规格原意；平台少一笔挂账，发起方也不会因逾期被拦发布）。备选"后付的只自动付已到期的"**不推荐**（要多一个按到期日判断的分支，而且到期前账单长期挂着）。是否给发起方一个"我要自己控制付款"的个人开关？**建议：首次上线不做**，只有总部的总开关。
8. **打开自动付款的那天晚上，已经有钱又有未付账单的发起方会被一起付清，可以吗？** 例：打开开关时，有 3 位发起方各有 8,000 日元未付账单和 20,000 日元现金，当晚（凌晨 2:27）每人被付 8,000，并收到一封"已自动支付"的邮件。**注意：开关的首次上线值是"打开"，而受控参数在发布之前没有值，没有值就是关着——所以"发布"这一步就是"打开"。** **建议：可以，但发布之前先通知这些发起方**（上线清单写明）；不想一起付清，就在通知发出之前不要发布这个参数，开关一直是关着的。
9. **账单作废后，发起方看得到什么？** 例：财务作废了 11 月 2 日的账单 QBF-2026-00012，发起方之前下载过它的 PDF。已签发的 PDF 无法收回。**建议：页面上这张账单显示"已作废 + 作废日期"，仍可下载原件（发起方做账可能还要它；不去掉他已有的能力），发起方收到一封邮件说明"该账单已作废，已付的 X 日元已退回您的平台费账户"，作废的内部理由只给总部看**；作废的账单号不会被重新使用（编号不缺号）。
10. **账单要不要能直接发到发起方的邮箱（带 PDF）？** 例：现在发起方在页面上自己点下载；"账单已开出"的邮件只写账单号、金额、到期日，不带附件。**建议：首次上线不做**（带附件需要先替发起方签发 PDF，而一旦签发就固定了，见问题 1）；发起方嫌麻烦再加一个"发到我的邮箱"按钮，只发到他已验证的登录邮箱。
11. **收据号现在是一长串字母数字（例：019a3c…），要不要改成顺序号（例：QBR-2026-00031）？** 现在每张收据用充值记录的编号当收据号，唯一但不好读。改成顺序号要重新安排"先取号、再出单据"的次序，是一项独立的小改造。**建议：上线后再做**；法律上收据不要求连续号码，账单和贷项凭证已经是不缺号的顺序号。
12. **用赠送额度付的部分，账单上的消费税照常写吗？（请财务确认）** 例：一笔 1,000 日元的费用（税 100，合计 1,100）全部用赠送额度付。**建议：账单照常写不含税 1,000、税 100、合计 1,100**，付款情况明写"赠送额度 1,100"；记账和申报怎么处理由财务定，PDF 把"哪一部分是赠送额度付的"写清楚，不管最后怎么处理都能追溯。需求方说过"系统内记账、按真实进账报税"，这与上面一致，请财务书面确认。

13. **自动付款不需要发起方本人操作，条款里要不要写明？这是法务问题。** 自动付是平台在钱到账后替发起方付账单：不经过发起方本人的"同意"页面，不查封禁，也不要求本人点按钮。例：发起方 11 月 5 日充值 100,000 日元，平台当晚替他付了 8,000 的月账单，他没有点任何东西。**建议：发起方条款加一句"到账后自动支付未付账单"，随上线前那一版一起同意**（首次上线只有这一版，不需要另发新版、让已有发起方重新同意）；是否另发新版、是否要重新同意，请法务在上线前定。这一项已写进上线检查清单的"法务与合规"。
14. **充值后立刻被自动付掉，之后要退款或起争议怎么办？** 例：发起方充了 10,000 日元，当晚自动付掉 8,000，次日申请退 10,000，账户里只剩 2,000。**建议：只能退账户里还剩的部分（例中 2,000）**，已付掉的 8,000 是付给平台的账单，不退；帮助页和充值页写明这一点。若发起方认为不该付，走账单作废（四眼），按原分摊退回。
15. **后付发起方充值想换学分、却被未到期账单先占用，可以接受吗？**（问题 7 的后果，单列请需求方明确答复）例：后付的发起方有 8,000 日元未到期账单，充值 10,000 想换学分，结果到账后先付了账单，可用额只剩 2,000。首次上线学分奖励关着，影响小。**建议：接受**；备选"后付的只自动付已到期的"**不推荐**（理由见问题 7）。若您不接受，请告诉我们，那是另一个分支，要改规格。
16. **正在申请作废的账单，要不要暂时不自动付？** 例：财务已提出作废账单 QBF-2026-00012（8,000 日元），另一位管理员还没批准，这时发起方充值，平台把它自动付了；之后作废批准，8,000 按原分摊退回。发起方会先收到"已自动支付"、再收到"已作废"两封邮件。**建议：照付**（作废时按原分摊退回，钱不会丢；暂不付要多一个状态判断）；请需求方知情，并在运营文档里写明会有这两封邮件。

## 11. 删除的功能

**无功能删除。** 只有两处**已有 PDF 版式里的显示**被替换，请同意（已作废账单的原件仍可下载，没有减少任何已有的能力，L5）：

- PDF 上的"状态"一行去掉（它是签发那一刻的状态，之后会过时，由"付款情况（截至某日）"取代）；
- "开出时间（UTC）"一行由"开具日（日本时间）"取代（问题 3 答"否"则保留）。

两处都只影响今后签发的 PDF；**已经签发并存档的 PDF 一个字节都不变**（上线前只有测试数据）。其余都是加项：账单与凭证的列表、流程、状态、编号、作废、收据、保留与现有行为照旧；自动付款的总开关关闭时，行为与现在完全相同。
