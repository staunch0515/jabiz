# Q90 知识结构图：平台的与商户的（多起点、多终点）、节点的组合条件、资格、挑战发布与证书（计划，2026-11-04；待需求方确认）

需求方 2026-11-03 至 11-04 的讨论定下的模型（本文 §0），取代现有的"认证 + 轮 + 发布上的前置 + 画出来的树"（Q69、Q76、Q85、Q86、Q88）。
需求方的判断："目前的实现偏离我的要求，没有使用的价值，必须这么改"；平台在测试，**不考虑已有数据与已有商户**（重置数据库）。
编号 Q90：Q89 之后的第一个空号。**这只是计划**：确认 §10 后按 §8 分期开发，每期开发前再给该期的细化计划。

## 0. 需求方的决定（2026-11-03 / 04）

1. **树是事先定义好、整体可见的**：打开即看到全部节点，看的人知道自己在哪、哪些能做、哪些"系统有但我还做不了"。
2. **两大类树，严格区分**：
   - **平台树**：平台定义。点亮者是**商户**（解锁平台提供给商户的功能）或**答题者**（平台给答题者的功能）。可以有多棵，按类别分。
   - **商户树**：商户定义，点亮者是答题者。节点给两种东西：①**平台赋予商户的控制权利**，由商户交给答题者用；②**商户线下的商务功能与权利**。
3. **最基本的商户只有最基本的功能**，更多功能在平台树上解锁。
4. **节点的点亮需要多个条件**；答题合格只是满足其中一个。条件可以**组合**（全部、任一、至少 N 个），以实现难度不大为限。
5. **平台事实做成一种资格**（如邮箱已验证、已实名、已签约），可以用在节点的条件中。
6. **每个条件可以选择"答题前必须满足"**：前置节点、平台事实都可以选。
7. **每个条件可以选择"必须一直存在"**：失去即节点熄灭；**在有效期内重新满足即自动重新点亮**。
8. **有效期由树的主人设置**（平台不替商户决定）。
9. **挑战发布**：发布在建立时绑定一个节点；答题前条件满足才能答；合格即满足该节点的"挑战"条件。不合格就等下一个绑定同一节点的发布（商户定期提交）。**一个发布只答一次**的规则不变。
   平台树节点的挑战发布由官方账号出题，商户树的由商户出；奖励照常（学分等，同普通发布）。
10. **商户树可以以平台树的节点、平台事实作条件；平台不依赖商户**：平台树的条件不能引用商户树。
11. **证书由树的主人颁发**（平台树：平台；商户树：商户），证书上写颁发方；节点证书与全网证书都如此（见 16）。
12. **商户默认只能建一棵树**；"多棵树"本身是平台树上一个节点给的功能。
13. **树的定义版本化并审批**：修改是新版本，经审批生效。
14. 平台功能目录与平台事实目录由需求方**逐条审核**（本文附录 A、B 是草稿）。
15. **是网，不是树**（2026-11-04）：可以**多个起点、多个终点**，中间可以分叉、汇合。没有前置节点的节点都是起点；没有被别的节点作前置的节点都是终点。唯一不允许的是成环。
    下文的"树"一律指这种网（界面上的名称待定，见 §10）。
16. **每个节点都可以挂证书**（点亮即颁发，网的主人颁发）；**全网节点全部点亮，颁发全网的证书**（2026-11-04）。
17. 以后节点还可以有**达成奖励**（学分、权益等）：本计划在节点定义里预留，单独一期做（T6）。
18. **名称**（2026-11-04）：这种网的统称是**"知识结构图"**；每一张知识结构图的名字由定义它的人（平台或商户）自己起。
    下文仍以"树"指代知识结构图，界面与用户文档一律用"知识结构图"与它自己的名字。
19. **事前学习成为文化**（2026-11-04，Q91 中提出）：付费或有风险的能力（如购买称呼）先要求点亮一个"先了解方法与使用"的节点——强制看使用手册或帮助文档，以挑战发布证明看过。附录 A 中可门控的功能，凡是付费的，都建议配一个这样的入门节点。
20. **发起方自己答题**（2026-11-04）：点亮者为发起方的平台知识结构图，由发起方**在后台里**答挑战发布，不用换到 App；答题者在 App 中照旧以普通答题者答题。
    发起方答的都是平台的题目，**暂时不给学分**。**只有持有人能代表发起方答**（发起方的账号本人；以后有成员时再议）。见 §2.8。
21. **平台知识结构图 = 平台的模板 + 运营商的副本**（Q92 §4.1、§11-2，2026-11-04）：平台定义模板并版本化（平台四眼审批）；运营商基于模板的某个版本修改成自己的图，在运营商内部四眼生效。运营商能改：条件、有效期、挑战、证书、增删节点与连线；不能改功能目录、不能门控核心功能、授予只能从功能目录选。副本**沿用模板的节点编号**，自己加的另起编号（改派后两边都有的节点照样算数）。模板升级不自动覆盖，运营商逐项采用。**答题者的平台图不分运营商**（只有平台的一份）。**发起方只答所属运营商的官方账号出的挑战**。T1a 的细化计划按此设计数据（模板、副本、节点编号的来源）。

## 2. 概念模型

### 2.1 资格

"一个人此刻是否具备某项事实"的统一说法，条件只引用资格。三种来源：

| 来源 | 键 | 说明 |
|---|---|---|
| 节点 | `node:<节点编号>` | 该人此刻点亮了这个节点 |
| 平台事实 | `fact:<键>` | 平台计算的事实（附录 B）；目录在代码中，每项有对象（答题者 / 商户）、说明、会不会失去 |
| 挑战 | `challenge`（只在本节点的条件中） | 该人合格过一个绑定本节点的挑战发布（在本节点当前规则版本下） |

### 2.2 树

| 项 | 内容 |
|---|---|
| 主人 | 平台，或某商户 |
| 点亮者 | 答题者或商户（商户树固定为答题者） |
| 类别 | 平台树：代码中的类别目录（附录 A 的分组）；商户树：无 |
| 版本 | 每次修改是一个新版本：草稿 → 待审核 → 生效（旧版本随之停用）；驳回可改后再提交 |
| 结构 | 网：多起点、多终点，可分叉、可汇合，不成环（§2.4 第 3 条）；起点与终点由条件推出，图上标出 |
| 全网证书 | 可设"全部节点点亮后颁发证书"（名称三语、有效期），颁发方是网的主人 |
| 数量 | 平台树不限；商户默认一棵，平台功能 `sponsor.tree.multiple` 解锁多棵（§0-12） |

### 2.3 节点

节点有**稳定的编号**（跨版本不变，点亮记录挂在它上面），每个版本里有自己的定义：

| 项 | 内容 |
|---|---|
| 名称、说明 | 三语 |
| 位置 | 图上的坐标（编辑器里拖动），父子关系由前置条件推出，用来画边 |
| **条件** | 一个组合表达式（§2.4） |
| **授予** | 平台树（商户）：平台功能目录中的键；平台树（答题者）：答题者功能键；商户树：①可授予权利目录中的键，②线下权益（文字 + 可选出示码）。T1 只存，T3/T4 才生效 |
| **有效期** | 永久 / 点亮后 N 天 / 到某日为止 |
| **规则版本** | 新版本中勾"规则变了"即加一：此前的点亮与挑战合格从此不算（同现在认证的版本） |
| **节点证书** | 可设"点亮即颁发证书"（名称三语；有效期随节点）；颁发方是网的主人 |
| **达成奖励** | 预留（T6）：点亮时给的学分或权益；T1 只在定义里留空位，不生效 |

### 2.4 条件表达式

```
条件   = 全部(条件…) | 任一(条件…) | 至少 N 个(条件…) | 资格要求
资格要求 = { 资格, 答题前必须满足: 是/否, 必须一直存在: 是/否 }
```

为了好实现、好看懂，加三条限制（编辑器与启动检查都检查）：

1. **"答题前必须满足"只能出现在最外层的"全部"中**：答题门槛就是这些条目的"全部"，没有"任一"之类的门槛；
2. 每个节点**至多一个** `challenge`，且它不能标"答题前必须满足"（自相矛盾）；没有 `challenge` 的节点不能绑定挑战发布，只靠其他条件点亮（如"汇合"节点）；
3. 平台树的条件**不能引用商户树的节点**；商户树可以引用平台树节点与平台事实（§0-10）；引用不能成环（同树内与跨树都查）。

### 2.5 点亮

- **何时判断**：与这个人有关的事件发生时，对受影响的节点重新判断：挑战合格、某节点点亮或熄灭或过期（连带依赖它的节点，含其他树）、平台事实变化（T2）。
- **记录**：满足全部条件的那一刻写一条**点亮记录**（只追加）：人、节点、规则版本、点亮时刻、有效至、依据（哪次挑战等）。有效期内不重复写。
- **此刻是否点亮**（读时算出，不存状态）：存在一条规则版本当前、未过有效期的点亮记录，**且**所有"必须一直存在"的条目此刻仍满足。
  于是"失去即熄灭、有效期内重新满足即自动点亮"不需要额外的状态和事件（§0-7）。
- **过期之后**：要再次满足全部条件（含再挑战）才写新记录。
- **节点证书**：节点点亮（写点亮记录）时，若该节点设了证书，签发一张，有效期同这次点亮（T5）。
- **全网证书**：一张网的全部节点此刻点亮时，若设了全网证书且该人没有有效的全网证书，签发一张（T5）。

### 2.6 挑战发布

- 发布向导的第一步选"挑战哪个节点"（可选：不选即普通发布）。只能选**自己的树**的节点；平台树节点只有官方账号能选——**总部与各运营商的官方账号都可以**（需求方 2026-11-04）。
- 开始答题时检查该节点的"答题前条件"，不满足即不能开始（首页不列出，发布页说明缺什么，同现在的前置）。
- **已点亮的人可以答同一节点的其他挑战发布**（需求方 2026-11-04）：照常列出、照常给奖励；合格时若该节点有有效期，则以这次合格重新计算有效期（写新的点亮记录）。"一个发布只答一次"不变。
- 合格 → 触发 §2.5 的判断。不合格 → 节点显示"等下一场"，可订阅提醒（T5）。

### 2.8 发起方作为点亮者（§0-20）

现状的问题：发起方要以答题者身份到 App 去答，结果按个人的用户编号记，只是碰巧与后台的检查对得上；给发起方的题出现在所有答题者的首页；答题的学分进个人钱包、记录算进答题者统计；Shopify 店进不了 App。新的做法：

| 项 | 做法 |
|---|---|
| 点亮记录的对象 | 点亮者为发起方的图：记在**发起方**身上（发起方编号；Shopify 店为店的编号）。点亮者为答题者的图：照旧记在**人**（用户编号）身上。同一个人既是发起方又是答题者时，两边分开记、分开看 |
| 在哪里答 | **发起方后台的"挑战"页**，复用 App 的答题组件（开始、作答、交卷、结果），不需要答题者角色与资料 |
| 谁能答 | 只有发起方的**持有人**（发起方账号本人）。Shopify 店：店的登录（外部令牌）即持有人 |
| 谁能看到这类挑战 | 绑定"点亮者为发起方"节点的挑战发布**只给发起方**：不出现在答题者首页、答题者不能开始（422），受众规则、地区与人数估算不适用 |
| 奖励 | **暂时不给**：这类挑战发布不设奖励档位（向导不显示奖励一步；提交时检查），不动任何钱包 |
| 统计 | 不计入答题者的统计、受众人数与发布方的分析；单独按节点统计（多少发起方点亮、多少在等） |
| 出题方 | 只有官方账号（总部与各运营商，§2.6）；一个发布只答一次照旧，以发起方为单位 |

数据上：`qb_tree_lit` 的对象列为 `subject_kind`（USER / SPONSOR / SHOPIFY_SHOP）+ `subject_id`；答题记录（`qb_attempt`）加"代表的发起方"一列（发起方后台的答题），答题者一侧不变。

### 2.7 看树（每个节点对看的人的状态）

| 状态 | 条件 |
|---|---|
| 已点亮 | §2.5，显示有效至 |
| 已熄灭 | 有有效的点亮记录，但某个"必须一直存在"的条目失去了（列出是哪条） |
| 可挑战 | 答题前条件都满足、未点亮、此刻有开放的挑战发布（链到它） |
| 等下一场 | 答题前条件都满足、未点亮、此刻没有开放的挑战发布 |
| 差条件 | 挑战已合格（或节点无挑战），但其他条件未满足（列出缺哪几条） |
| 锁定 | 答题前条件不满足（列出缺哪几条） |

每个节点都写明**点亮后得到什么**。平台树与商户树在界面上分开、标识不同（平台树用平台标志与"平台"字样，商户树用商户名）。

## 3. 两个目录（代码中声明）

- **平台功能目录**（T3）：分"商户功能"与"答题者功能"，按类别分组；每项有键、说明、是否**核心**（核心功能永不门控：提现、账单与收据、删除账号、联系客服、同意条款、登录与资料等）。
  不挂在任何节点上的非核心功能人人可用；挂了的，服务端在对应流程中检查（QuizBuks 的步骤 `RequireFeature.of(键)`，没点亮即 422 `QB_FEATURE_LOCKED`，问题中给出节点），前端按同一结果显示"可用 / 系统有、你还做不了"。草稿见附录 A。
- **平台事实目录**（T2）：草稿见附录 B。
- **可授予权利目录**（T4）：商户能交给答题者的权利（答我的进阶发布、成为我的推荐人、做我的店员、领取我的某项权益……）；商户只能使用自己在平台树上已解锁的那些。

## 4. 审核与版本

- **审批对象** `qb.tree`（平台 `ApprovalSubject`，内容哈希绑定该版本的全部定义，同商户页 Q60a）：
  - 商户树：商户提交，所属运营商审核（Q92：没有"直营即总部"，每个发起方都属于一个运营商），同发布审核；驳回附原因。
  - 平台树：总部一位管理员提交，**另一位**管理员批准（四眼，`qb.tree.platform.review` 规则）。
- 生效：批准即成为当前版本，旧版本停用；点亮记录挂在节点上，不受新版本影响，除非节点的规则版本加了一（§2.3）。
- 停用整棵树：不再显示给新人；已点亮的照常到期；绑定它节点的发布不能再开始（下架）。

## 9. 风险

1. **核心功能被门控**：附录 A 中标为核心的功能永不进树（法律与应用商店的要求：提现、账单、删除账号、联系客服等）；启动检查拒绝把核心功能挂到节点上。
2. **连锁判断的规模**：一个节点点亮会连带判断依赖它的节点（含其他商户的树）。按"人"判断，只读该人的点亮记录与相关事实，规模与该人参与的树成正比；连带深度设上限（启动检查树的深度）。
3. **"一个发布只答一次"与等待**：商户不再出题时答题者卡住；"等下一场"的人数给商户看，并在 T5 提醒订阅者。
4. **商户树的误导**：节点名称与权益说明（如冒用"英语四级证书"）经运营商审核；证书上写颁发方。
5. **工作量**：结构性的重做，牵涉发布、开始答题、审核、三个前端与旧模型的拆除；分五期、每期可单独上线。

- **没有"实名"**：平台目前没有独立的实名认证，身份核实只在 Stripe 开通收款时发生（F18）。要单独的实名认证，需要另立一项工作。

- "通过某个发布"不需要作为事实：挑战的合格就是节点的 `challenge` 条件。
