# Q7c 收件箱徽标的查询（评审 H1，2026-10-18）

App 每个在线用户在进入、回到前台与每 5 分钟问一次未读数（`qb.app.inbox-unread`）。评审发现它扫描**发出过的全部公告与通知**：
`qb_broadcast_feed` 的索引 `(audience, live, sent_at DESC)` 上 `live` 永远为真（只有撤回才变），`sent_at <= at` 不排除任何行，
探针规模（一年 3 万个发布、每个 3 条通知、2 千条平台公告：92,000 行；100 万条回执）下顺序扫描每次 32 ms，并随历史增长。

## 修正

1. **只有当前的行是 `live`**：每分钟的逐项任务 `qb.broadcast-expire`（`QB_BROADCAST_EXPIRE`，取 `qb.broadcast:<编号>` 锁后重读）把已过期的、
   以及发布已结束的通知的行关掉。部分索引改为 `(audience, expires_at) WHERE live`，只含当前的行（探针中 2,331 行），与历史无关。
   商家通知在暂停或预算不足时只隐藏（卡片 `SCHEDULED` / `LIVE` 才显示，评审 M1），结束才关掉。
2. **不收页面的时间**（评审 L1）：过期由任务处理，模板不再需要 `at`，也就没有了用旧时间看到过期公告的可能。
3. **读者的已读水位 `readThrough`**：`QB_MESSAGE_MARK` 在写入已读之后以同一模板的 `oldestUnread` 把它推进到最早的仍未读的公告（没有则为
   现在 − 10 分钟：定时公告以到期时刻作发送时刻、由任务稍后带进来），从不后退。徽标只看 `sent_at >= readThrough` 的行：读完了的人
   不再逐行查回执。它不是阅读：列表的未读、统计都不用它。后来才变得可见、发送时刻又更早的公告（恢复的发布的通知、重新打开推广、换了国家）
   在列表中仍是未读，徽标不计——这是有意接受的少计。

## 结果（PostgreSQL 16，本机；同评审探针的数据规模与生成方式，模板改写成等价的 SQL 以 `EXPLAIN ANALYZE` 测量，预热后）

| 读者 | 修正前（评审） | 只有 1、2 | 1、2、3 |
|---|---|---|---|
| 全部逐条读过（1,398 条回执） | 32 ms（顺序扫描 92,000 行） | 7.1 ms（1,398 次回执查找） | **0.73 ms**（部分索引，0 行） |
| 一小时前"全部已读" | — | 0.66 ms | 0.66 ms |
| 什么都没读（取满 99 条即停） | — | 1.1 ms | 0.90 ms |
| 任务的选取 `qb.system.broadcasts-expired`（无到期） | — | 8.0 ms（每分钟一次；卡片 3 万行顺序扫描） | 同左 |

目标"读完了的人 < 5 ms"满足。也试过的两种不采用：把匹配用到的列全放进索引（仅索引扫描，10 ms：瓶颈是逐行的地区判断与回执查找，不是读堆），
以及地区改成位掩码并去掉 `LIMIT`（13–16 ms：规划器改用哈希连接扫全部卡片）。在 `QbInboxState` 中缓存读者的地区与推广开关不必要：
它们是两次主键查找，不随公告数增长。

## 观察

- 指标 `jabiz.query.template{template="qb.app.inbox-unread"}` 的耗时；任务 `qb.broadcast-expire` 的项（`jabiz.job.item`）不应持续失败（停了它，过期的公告与已结束发布的通知会留在收件箱中，读取也随之变慢，直到它恢复后补做）。
- 商家的统计改为每日快照（评审 M2），商家列表不再逐行统计回执（评审 L4 的第二项）；后台的列表照常实时统计（每页 20 行）。
