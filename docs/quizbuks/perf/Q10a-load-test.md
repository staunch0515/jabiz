# Q10a 压测报告：单个热门发布的答题吞吐（2026-10-16）

计划：`docs/quizbuks/plans/Q10-launch.md` §3；目标（L-2）：**单个发布 50 次完成 / 秒，提交 p95 < 1 秒**；热门发布期间首页 p95 不超过平时的 2 倍；错误率 0（预期的 422 除外）。
L-1：先测再定，本阶段只做 R1（应用内），R2、R3、R4 给出证据与预估，由需求方决定。

## 1. 结论

- **现状（Q10-launch 分支头）：约 20.7 次完成 / 秒，提交 p95 约 2.3 秒**；热门发布期间首页 p95 从 21–30 ms 升到 0.8–1.2 秒（**约 30–60 倍**）。错误 0，钱包与奖励逐笔一致。
- **瓶颈完全在发布锁内**：每次完成要在同一把锁里串行走两段——开始约 12 ms（12–13 条语句）、提交约 37–40 ms（48–50 条语句）。
  吞吐 = 1 /（两段之和），实测与锁内时间的推算一致（52 ms → 19 次 / 秒，开语句日志时）。
- **锁内时间的 85% 不在数据库**：数据库执行合计每次完成约 7 ms，其余是每条语句约 0.75 ms 的客户端往返（R2DBC、Reactor 步骤调度、实体映射）。
  所以决定吞吐的是**锁内的语句条数**，不是 SQL 的快慢。CPU 在压测期间约 45 % 忙，不是瓶颈。
- **R1（本阶段已做）**：锁内少 3 条语句（提交 50 → 48，开始 13 → 12），锁内时间 52.1 → 49.5 ms（−5 %，开语句日志时测得）。
  **吞吐的提升在噪声之内**：经 HTTP 20.7 → 21.2 次 / 秒（各次运行之间相差约 ±1 次 / 秒），`PlayThroughputIT` 13.9 → 15.2 次 / 秒（各次相差约 ±1.5）。应用内已没有不改设计就能拿掉的锁内语句。
- **以固定到达率（开环）测**：每秒到达 15 人时提交 p95 0.42 秒、首页 1.9 倍（满足验收）；18 人时提交 p95 0.55 秒、首页 2.5 倍；**50 人时过载**：完成仍约 20 次 / 秒，
  开始 p95 11 秒、提交 p95 16 秒，88 次提交 503 `QUERY_TIMEOUT`，首页 p95 4.7 秒（110 倍）。闭环（64 并发）的 p95 只是 Little 定律的结果（并发数 / 吞吐），不检验目标。
- **提交的 48 条语句中 27 条是 `LEDGER_POST`**（约 21 ms，56 %），8 条是钱包锁、读、写，9 条是平台提交时的"先读后写 + 审计"。
- **不做 R4，单靠 R1–R3 到不了 50 次 / 秒**：R2（平台降低 `LEDGER_POST` 的成本）预估约 30 次 / 秒，再加平台的通用开销（锁、提交前重读、引用检查）约 40 次 / 秒；R3 不提高吞吐。
  **R4 的上限已实测：37.5 次 / 秒**（提交 p95 1.1 秒）——R4 单独也不够。
- **能到 50 次 / 秒的组合都要把"开始"和"提交"分到两把锁**（§6.5，应用内的设计改动，不改体验，需确认）：R2 + 平台通用开销 + 锁拆分预估约 55–60 次 / 秒（不做 R4）；
  R4 + 锁拆分预估约 60–65 次 / 秒。不拆锁时最好的组合（R4 + R2 + 平台通用开销）约 46 次 / 秒。首页不受拖累只能靠 R3（等锁的请求不占连接）。建议见 §7。
- **Q10a2（R3 之后，§8）**：首页 p95 在一切负载下都在平时的 1.0–1.4 倍，等咨询锁的连接平均约 0.5 个，没有 503 `QUERY_TIMEOUT`，过载以 503 `PROCESS_BUSY` 在 2 秒内结束、App 自动重试。
  **吞吐不变只在机器的 CPU 不饱和时成立**：读者限速（CPU 约 70 %）时稳定 20–22.5 次 / 秒，每秒 15、18 人时提交 p95 66 / 80 ms；读取量与准入关的对照相同时两者都是 15 次 / 秒。
  在这台共用的 4 vCPU 上，不再被饿住的连续读者把 CPU 用到约 88 % 时，热门发布降到约 9.5–10 次 / 秒，答题人看到的提交 p95 24–33 秒（排队加重试）。容量规则见 §8.3 第 4 条。
- **Q10a3（平台 16p-1 之后，§9）**：锁内开始 12 → 5、提交 48 → 14 条（`AttemptStatementBudgetIT`），每次完成锁内 49.5 → 31.5 ms（开日志时）。稳定吞吐约 37–40 次 / 秒（同日的 Q10a2 对照 22.5–24），连续读者时 22（对照 10.5）；
  每秒 30 人时提交 p95 44 ms，40 人时 0.7 秒，**每秒 50 人时仍过载**（稳定 36 次 / 秒）。瓶颈仍是发布锁（许可 3 个时吞吐不变，CPU 约 50 %）。每秒 50 次并留余量时 16p-2 与锁拆分各自都必要，两者合起来是否足够由重测确认（§9.4）。
- **Q10a4（锁拆分之后，§10）**：开始离开发布锁，串行的关键路径 31.5 → 24.9 ms（开日志时）。读者每秒 24 次、饱和时的稳定吞吐约 41–45 次 / 秒（同日对照 34.8–36.5；饱和的各行 +16–30 %，读者更多时也是如此），**低于预估的 45–50 的下端或在其下端**：提交在发布锁内的一段因与开始同时争 CPU 而变慢（22.4 → 24.9 ms）。
  每秒 40 人时提交 p95 271 → 61 ms。**过载时 503 从开始移到了提交**：开始一侧有余量、不再被拒（0），排队与 503 全落在提交上——每秒 50–60 人时提交 503 有 150–1345 次、答题人看到的提交 p95 3.3–18.8 秒，
  截止前不久按下的提交可能因此以 EXPIRED 结束（由超时任务以已保存的答案结束，§8.3 第 6 条）；这是上线的风险（Q10 计划的已知问题）。**每秒 50 人仍未达到**（稳定 44.8）。连接池 16 / `max-active` 8 没有一致的收益，配置不改（§10.3 第 4 条）。下一步平台 16p-2。
- **Q10a5（平台 16p-2 之后，§11）**：锁内开始 5 → 3、提交 14 → 7 条（`AttemptStatementBudgetIT`），提交在发布锁内 26.0 → 21.5 ms（开日志时；剩下的约 83 % 是锁内的 Java 工作，不是数据库）。同一个 jar 以应急开关开 / 关做同场 A/B（本机安静时）：饱和吞吐 34–39 → **45–54 次 / 秒**（约 +30–40 %）；
  **每秒 50 人时 4 次中 3 次提交 p95 158–579 ms、没有 503，第 4 次 1048 ms**——目标在本机达到，但饱和点约是目标的 1.0 倍，没有 1.3 倍余量。首页 p95 每秒 50 人时 1.4–1.7 倍。本机被其他测试占用时（load average 6–17）两种设置都只有 15–42 次 / 秒，不用于比较。
  过载仍落在提交上。下一步：在目标规格上重测，剖析锁内的 Java 工作；平台合并"取锁 + 读取"、开始一侧的背压与 R4 作为备选（§11.4）。

## 3. 压测工具 `./gradlew :quizbuks:loadTest`

源码 `backend/quizbuks/src/loadTest/java/com/jabiz/quizbuks/load/QuizbuksLoadTest.java`（不在 `check` 中，照平台 `app` 的 `loadTest`）。经 HTTP 与真实令牌驱动打包的 jar：

1. **准备，全部走真实流程**：`QB_SETUP` 与其提案（由第二位管理员 `load-publisher` 发布）；商家注册（经 Mailpit 打开验证链接）、入驻并批准、经 Stripe 桩的 Checkout 充值；
   模版、两道题、版本、一个发布（大预算、**不设人数上限**、答对两题奖励 10），批准后 `LIVE`；N 个答题人与若干读者注册并验证。用户在后续运行中复用（每次运行新建一个发布）。
2. **读者单独**：读者轮流读首页（`qb.app.feed`）与详情（`qb.app.publication`、`qb.app.publication-tiers`），得到平时的 p95。
3. **压力**：N 个答题人以 `LOAD_CONCURRENCY` 并发对同一发布 `QB_ATTEMPT_START` → `QB_ATTEMPT_SUBMIT`（照 App：带 `Idempotency-Key` 与 `currentIndex`，全部答对、全部付奖），读者同时继续读。
4. **输出**：每秒完成数；开始、提交、一人全程与三种读取的 p50 / p95 / p99 / 最大值、按状态与错误码的计数（名额、预算、商家资金、发布未开放的 422 视为预期，其余都算错误）；
   首页 p95 的前后对比；商家钱包减少额必须等于付出的奖励之和（不等或有错误即以非 0 退出）。
5. **数据库（可选，`LOAD_DB_URL`）**：压力前重置、压力后读出 `pg_stat_statements`（按总时间的前 25 条与每次完成的调用数），并每 100 ms 采样 `pg_stat_activity`（忙的连接、等咨询锁的连接）。

6. **开环（`LOAD_RATE`）**：给出每秒到达人数时，第 n 个答题人在 n / 速率秒时开始，不论前面的人等了多久（不设并发上限）；不给时为闭环（`LOAD_CONCURRENCY` 人轮流）。
   闭环的延迟由并发数与吞吐决定（Little 定律），只有开环的 p95 能回答"每秒 50 次时提交 p95 是否 < 1 秒"。
7. **安全**：`LOAD_BASE_URL` 必须是本机回环地址（否则须 `LOAD_ALLOW_REMOTE=yes`，绝不用于生产）；只支付与应用同一主机的 Checkout（旁边的 Stripe 桩），
   充值记录为正式模式（`livemode`）即停止，且在发起新的充值之前先检查已有的充值记录；只发布本次 `QB_SETUP` 输出中的提案，并核对其提出人是本次的管理员、
   创建于本次运行开始之后，否则一个也不发布；`LOAD_PASSWORD` 必须给出（仓库中没有缺省值）。应用不对外报告 Stripe 的模式，所以第一笔充值之前无法确认：
   新库上第一笔充值仍会向应用配置的 Stripe 创建一个 Checkout，工具只是不支付它。
8. `pg_stat_statements` 只重置应用库的语句（`pg_stat_statements_reset(0, 库, 0)`）；工具的源码由 `check` 编译（不运行），不会悄悄坏掉。

参数：`LOAD_BASE_URL`、`LOAD_ALLOW_REMOTE`、`LOAD_MAILPIT_URL`、`LOAD_ADMIN_USER` / `LOAD_ADMIN_PASSWORD`、`LOAD_PUBLISHER_ROLE`（须在 `QB_ADMIN_ROLES` 中）、`LOAD_PASSWORD`（必填）、`LOAD_TAKERS`（1000）、
`LOAD_CONCURRENCY`（64）、`LOAD_RATE`（开环的每秒到达人数）、`LOAD_READERS`（8）、`LOAD_BASELINE`（15s）、`LOAD_SETUP_CONCURRENCY`（8）、`LOAD_REWARD`（10）、`LOAD_LABEL`、`LOAD_REPORT`（写 Markdown）、
`LOAD_DB_URL` / `LOAD_DB_USER` / `LOAD_DB_PASSWORD` / `LOAD_DB_NAME`（装有 `pg_stat_statements` 的库与应用库的名字；不要装进应用库，它的 `public` 属于迁移）；
Q10a2 起另有 `LOAD_TIMEOUT`、`LOAD_RETRY_BUSY`、`LOAD_READ_RATE`（§8.1），Q10a3 起 `LOAD_METRICS`（§9.1）。

```

LOAD_DB_URL=jdbc:postgresql://localhost:5432/postgres LOAD_DB_USER=postgres LOAD_DB_PASSWORD=… LOAD_DB_NAME=quizbuks_perf \
```

首次注册 1000 个答题人约 6 分钟（BCrypt 强度 12，每人注册、验证、登录各一次），之后每次运行约 1.5 分钟。

**锁内时间的分解**不在工具里：平台的观测只到流程一级，没有步骤级的计时。做法是对该库临时 `ALTER DATABASE … SET log_min_duration_statement = 0`，重启应用（连接重建），
跑一次同样的压力，再按 PostgreSQL 日志逐个事务找出取得 `qb.pub:` 咨询锁的语句到 `COMMIT` 的时间，以及其间每条语句的数据库耗时与语句之间的客户端间隔（脚本只在本机，未入库）。
开日志时每条语句多一次写日志，吞吐约低 5 %，只用于分解，不用于结论中的吞吐。

## 5. R1：应用内的优化（本阶段已做）

### 5.1 改动

1. **提交只读卡片，不读发布与排程行**（`play.AttemptFinishing`、`publishing.PublicationMoves`）：卡片的状态在发布锁内随发布同步、限额是发布冻结的副本，
   所以 `PublicationMoves.moveAfter` 在卡片上就能判断这次完成会不会结束或使发布预算不足。只有会移动时，才以子流程 `QB_PUBLICATION_COMPLETION_MOVE`
   （`subProcessOnly()`，权限 `qb.publication.system` 不授予任何角色）在锁内读发布与排程行，并以发布本身再判断一次、照旧经 `PublicationEditing.write` 改变状态、排程与卡片。
   平常的完成锁内少读 2 行。移动的那一次比原来多约 7–8 条语句（子流程的序号与操作记录 2 条、重入的锁 4 条、重读发布、排程与卡片 3 条，减去平常省下的 2 条），
   通常每个发布只有一次（结束一次；预算不足在补足后可能再发生）。子流程若找不到发布，或在发布上判断的移动与卡片上的不同，即抛出异常，整次完成回滚（不让两者分开）。
2. **开始时商家钱包的软检查移到发布锁之前**（`play.AttemptProcesses`）：它本来就不取钱包锁、只是软检查（D-Q5-5，付不出的奖励成为待支付），放在锁外语义不变。锁内少 1 条。
   区别只在读到的余额可能早了等锁的那段时间（高峰时约 1–2 秒）：其间余额用完时，这个开始仍会被放行，到提交时奖励成为待支付——与原来"开始之后、提交之前余额用完"的情形相同。

不变的：一人一次（锁内重读 + 唯一约束）、名额与预算（锁内的计数）、钱包只在钱包锁内改、过账与钱包同一事务、每个奖励只付一次（会话状态在锁内重读，版本号兜底）、幂等键。
新增测试：`QuotaBudgetIT` 断言名额与预算未用完时没有任何完成调用移动子流程、结束的那次恰好调用一次（含 32 人同时抢最后名额的那项），
卡片与发布不一致时提交 500 且什么也不写；`PlayConcurrencyIT` 断言两个发布各恰好一次预算不足，并新增"开始读到的余额在等锁时被另一发布花光"：
另一事务持有发布锁、开始在其后等待，期间另一发布的提交花光余额，开始仍被放行、奖励成为待支付、预算不足恰好一次、账平；`AttemptExpireIT` 断言超时自动提交（系统身份）用尽预算时经子流程结束发布；结束、预算不足、待支付的原有测试（`QuotaBudgetIT`、`PendingIT`、`SettlementIT`、
`PlayConcurrencyIT`、`AttemptExpire*IT`、场景回放）照旧通过。

### 5.2 考虑过但没做的

| 想法 | 为什么不做 |
|---|---|
| 提交锁内不重读会话，靠更新时的版本号兜底 | 省 1 条（约 0.8 ms），但重复提交（两个标签页）会在锁内白做评分与过账、最后 409 而不是 422 `QB_ATTEMPT_FINISHED`，超时任务与提交相撞会留下任务失败记录。不值得 |
| 开始锁内不重读本人会话，靠唯一约束 | 同上：双击开始会得到 409 而不是继续同一个会话 |
| 会话的发布、版本字段不声明为引用（省开始锁内 2 条引用检查） | 改变元数据语义（后台显示与引用校验），应在平台把引用检查合并或跳过（列入 §6.2） |
| 缓存不可变的版本快照，提交时不重读版本 | 读版本在锁外，不影响锁内时间；且平台的查询步骤不能跳过（条件为空时仍发一条 `1 = 0` 的语句），省不下往返 |
| 换钱包锁与发布锁的顺序（先取钱包锁） | 违反锁序；钱包锁会被热门发布的队列一直占着，拖住同一商家的其他发布 |
| 加大连接池（30） | 实测吞吐反而降到 18.2（等锁的人更多、锁外工作更多），首页 p50 好转但 p95 仍 0.6 秒：等锁的请求会占满任何大小的池。不改配置 |

## 6. 退路的证据与预估

预估方法：锁内每条语句约 0.78 ms（本机实测），吞吐 ≈ 1 / 每次完成的锁内时间；p95 < 1 秒还需要容量比到达率高（§4.1a：在容量的约 70 % 时提交 p95 0.42 秒，约 85 % 时 0.55 秒）。

模型的省略：被拒绝的开始（名额、预算、资金）与超时自动提交同样要取发布锁，占用锁的时间未计入；没有奖励的提交不取钱包锁、不过账，比全部付奖的压测便宜。
前者使真实吞吐低于预估，后者使之高于预估；压测全部付奖，所以对提交而言预估是保守的。

### 6.1 R2：降低 `LEDGER_POST` 的成本（平台，缺口 14）

- 证据：提交锁内 48 条中 27 条（约 21 ms，占提交锁内时间 56 %、每次完成的 42 %）在 `LEDGER_POST`。逐条见 §4.2。
- 可做的：维度与来源核对合成一条查询（现在 3 条：用户、发布、会话）；科目读一次后分录不再重读交易与科目（现在每条分录 2 条）；
  交易与分录的"查是否已有、登记、插入、操作明细、审计"改为多行插入（现在每个实体 4–5 条）；序号与操作记录合并。目标约 6–8 条。
- 预估：提交 37.5 → 约 22 ms，每次完成约 34 ms → **约 29–30 次 / 秒**（+40 %）。所有使用账本的应用都受益；风险在平台的审计与操作明细（D27）的格式不变、多行插入的错误定位。
- 同类的**平台通用开销**（不在 R2 的原定范围，同为平台缺口）：`HoldLock` 一条语句完成（现在 4 条；省钱包锁 3 条、两次恢复超时各 1 条）、提交时已带版本的更新不先读
  （省 4 条，审计前值可取自上下文中的实例）、引用存在检查合并或对锁内刚读过的引用跳过（开始省 2 条）。合计约 11 条、约 8.6 ms：与 R2 一起 **约 40 次 / 秒**。

### 6.2 R3：取锁前在进程内排队 + 入口限流（平台，缺口 13、15）

- 证据：64 并发时 10 个连接中 6.9 个在等发布锁，首页 p95 从约 25 ms 升到 0.8–1.2 秒（30–60 倍，验收要求 ≤ 2 倍）；把池加到 30，等锁的连接变成 25.8 个，首页 p95 仍 0.6 秒。
- 作用：同一把锁的等待者在进程内排队、不占数据库连接，超过队列长度或等待时限即 429（带 `Retry-After`）。**不提高吞吐**（锁内时间不变），
  但首页与详情不再被拖累（预估回到平时的 1–2 倍），提交在过载时快速失败而不是排几秒；p95 < 1 秒只在到达率低于容量时成立。
- 风险：多实例部署时每个实例各有队列（数据库仍以咨询锁兜底，正确性不变）；限流的阈值要按发布可配。

### 6.3 R4：分批过账（改变体验，需需求方同意）

- **已实测上限**：实验 jar 在提交时不取钱包锁、不读写钱包、不过账（只记"已付"，其余不变；未入库），**37.5 次 / 秒**，提交 p95 1.1 秒，开始 p95 0.9 秒，首页 p95 0.46 秒。
  锁内：开始约 12 ms、提交约 15 ms。真正的 R4 还要在锁内写"结算中"，后台每约 1 秒为一个商家合成一笔过账（持钱包锁、不持发布锁），预估在 33–37 次 / 秒之间。
- 代价：结果页约 1 秒后才显示"已入账"（U-34 的体验改变），分录不再一笔对应一次答题（Q9d 导出的明细粒度、Q9c 月报的分类随之改变）；结算失败需要补偿流程。
- **R4 单独到不了 50 次 / 秒。**

### 6.4 组合

| 组合 | 每次完成锁内 | 预估吞吐 | 是否改体验 | 平台改动 |
|---|---|---|---|---|
| 现状（R1） | 49.5 ms | 21 次 / 秒（实测） | 否 | 否 |
| R1 + R2 | 约 34 ms | 约 30 次 / 秒 | 否 | 是 |
| R1 + R2 + 平台通用开销 | 约 25 ms | 约 40 次 / 秒 | 否 | 是 |
| R1 + R4 | 约 27 ms | 33–37 次 / 秒（上限实测 37.5） | 是 | 否 |
| R1 + R4 + R2 + 平台通用开销 | 约 22 ms | 约 43–46 次 / 秒 | 是 | 是 |
| R1 + 锁拆分（§6.5） | max(12, 37.5) ms | 约 27 次 / 秒 | 否 | 否 |
| R1 + R4 + 锁拆分 | max(12, 15) ms | **约 60–65 次 / 秒** | 是 | 否 |
| R1 + R2 + 平台通用开销 + 锁拆分 | max(约 9, 约 16.5) ms | **约 55–60 次 / 秒** | 否 | 是 |

R3 与以上任何组合正交：只决定过载时首页是否受影响、提交是否快速失败。

### 6.5 另一条应用内的路：把"开始"与"提交"分到两把锁（设计改动，需确认）

- 现在开始与提交用同一把发布锁，吞吐是 1 /（12 + 37.5 ms）。两者只在**一行计数**上相遇：开始加 `starts` 与 `reserved`，提交加 `completions`、`spent` 并减 `reserved`。
- 把计数拆成"开始的"与"完成的"两行（`reserved` = 开始加的 − 完成释放的），开始只取 `qb.pub-start:<发布>`，提交只取 `qb.pub:<发布>`：
  开始在锁外读到的完成计数可能是旧的，但每次完成只会让"已花 + 预留"与"中奖 + 进行中"变小或不变，所以用旧值判断名额与预算只会**更保守**（偶尔多拒一个刚好能进的开始），不会超出。
  改变发布状态的流程（暂停、结束、预算不足、到期）同时持两把锁（锁序 `qb.pub` → `qb.pub-start`），开始看到的状态因此仍是一致的。
- 成立的条件（独立评审补充）：
  - 开始必须在开始锁内读**自己的一行 S**，并以**一条语句**读完成的一行 C（两次读之间完成可能提交，分开读会得到不一致的组合）；
  - 其他一切读计数的地方（流程步骤、统计刷新 `QB_PUBLICATION_STATS_REFRESH`、核对、后台与财务模板、首页的开始条件）都必须在**一条 SQL 语句**中读 S 与 C，
    或者同时持两把锁；否则可能看到为负的"进行中"或"预留"；
  - 使发布移动的那次完成（结束、预算不足）也必须取开始锁：它持着发布锁排在开始的队列后面，其间所有提交都等着它——每个发布一次的停顿（高峰时约为开始队列的长度乘 12 ms）；
  - 被拒绝的开始与超时自动提交也取锁（前者取开始锁，后者取发布锁；后者结束发布时同样要取开始锁），它们的时间同样计入各自的锁。
- 收益：吞吐变为 1 / max(开始, 提交)：只有 R1 时约 27 次 / 秒；与 R2 + 平台通用开销一起约 55–60 次 / 秒（不改体验）；与 R4 一起约 60–65 次 / 秒。**预估超过 50 的组合都包含它。**
  拆锁后两段并行，锁外的工作与数据库负载随之增加，预估比单纯的 1 / max 偏乐观；须实测。
- 代价：迁移（新计数行或新列）、读计数的模板（首页的开始条件、统计、后台与财务模板）、锁序文档与 `QuotaBudgetIT` 一类的并发测试都要改；约 2–3 天。

## 7. 建议与决定

**决定（2026-10-16，需求方）：做 R3（取锁前排队）、R2（降低过账成本，连同平台的通用开销）与锁拆分；不做 R4。**
三者各自另写计划，本分支不实施。以下是作出决定所依据的建议。

1. **50 次 / 秒不需要 R4，但需要锁拆分**：R2 + 平台通用开销 + 锁拆分预估约 55–60 次 / 秒（不改体验，余量约 10–20 %，提交 p95 < 1 秒处在边缘）；
   R4 单独（实测上限 37.5）或 R4 + R2 + 平台通用开销（约 46）都不够。要更大的余量，再加 R4（约 60–65，且 R4 后锁拆分的收益更大）。
2. 建议的顺序：
   - 先做 **R3**（无论吞吐目标如何，首页被拖慢 30–60 倍不可接受；平台改动，所有应用受益）；
   - 再做 **R2 + 平台通用开销**（不改体验，约 2 倍：20 → 40 次 / 秒）；
   - 然后做 **锁拆分**（应用内的设计改动，不改体验，需确认；R2 之后收益最大），实测是否达到 50 次 / 秒；
   - 只有仍不够或需要更大余量时，再请需求方决定 **R4**（改体验）。
   - 若实际峰值低于 30–40 次 / 秒（L-2 问过），R3 + R2 即够。
3. 以上数字来自压测程序、应用与数据库共用 4 个 vCPU 的一台机器；锁内每条语句约 0.78 ms 主要是客户端的往返开销，数据库独立部署时网络往返还会增加（同机房约 +0.1–0.3 ms / 条），
   正式环境上线前应以 `./gradlew :quizbuks:loadTest` 在目标规格上重测。


## 8. Q10a2：取锁前排队（R3，平台 16o）之后的重测（2026-10-16，评审后重测）

分支 `1.2/quizbuks-10a2-admission`：合并平台 16o（决策 D45）后，`QB_ATTEMPT_START`、`QB_ATTEMPT_SUBMIT`（`publicationId` 必填）与超时任务的 `QB_ATTEMPT_EXPIRE`
声明准入 `qb.pub`（每个发布每个实例 2 个许可、队列 50、至多等 2 秒，所有排队的流程合计至多半个连接池 = 5），App 在 503 `PROCESS_BUSY` 时按 `Retry-After` 与加倍退避以同一个键重试。
锁内的工作不变（R2、锁拆分未做）。

### 8.1 方法

- 同一台机器、同样的 PostgreSQL 与连接池 10；新库（`quizbuks_perf_q10a2`，首次运行注册 1000 个答题人，之后复用），每次运行一个新发布，全部付奖。
  本节的数字来自**同一个暖机后的实例**（先跑一次热身，再连续跑各行；准入关的对照是另一个同样暖机的实例）；冷启动的实例在前几十秒明显更慢，不用于比较。
- 工具新增（§3 的参数之外）：`LOAD_TIMEOUT`（客户端时限，照平台 `loadTest`；本节开环用 5 秒，没有一次超时）、`LOAD_RETRY_BUSY`（缺省照 App 重试：503 `PROCESS_BUSY` 或超时后以同一个 `Idempotency-Key`、
  不早于 `Retry-After`、1/2/4/8 秒加倍、至多 6 次、等待合计至多 60 秒；仍忙的提交由答题人"再按"（同一个键），计入调用与完成；仍忙的开始在压测后补完，不计入，所以钱包核对每次都逐笔一致——全部一致，下表不再列出）、
  `LOAD_READ_RATE`（读者限速，每个读者每秒几轮，一轮读首页、详情、档位三次）；提交照 App 带上 `publicationId`；玩家线程的异常使运行失败。
  报告分开"每次调用"（每个 HTTP 回答，含 503）与"答题人看到的"（含重试的整段时间）；**稳定吞吐**取第 10 到第 90 百分位的完成之间（去掉开头与退避的尾巴）。
- **许可的持有时间**：`jabiz.process` 观测（成功的运行，从调用到结束）减去 `jabiz.process.admission`（结果 `ADMITTED` 的排队等待），按开始与提交，取每次运行前后的计数快照之差
  （本机压测时打开指标端点只为测量；平台闸门自己的 `averageHold` 不对外。Q10a3 评审后的做法见 §9.1：只开在绑定回环地址的独立管理端口上——应用端口上的指标端点不要认证，不能那样打开）。
  许可在借连接之前取得、根事务结束才归还，所以它是"锁前的读取 + 等锁 + 锁内 + 提交"的时间。
- **读者**的负载以每秒读首页的次数表示（每次还读详情与档位，读取合计为其 3 倍）：限速 3 轮约 24 次 / 秒；限速 10.6 轮约 85 次 / 秒（= 准入关的对照中连续读者实际得到的量）；
  限速 25 轮约 185 次 / 秒；**连续**（同 Q10a：8 个读者一个回答接一个请求）在准入开时约 165–180 次 / 秒，准入关时约 105 次 / 秒（等连接，被饿住）。

### 8.3 解读

1. **首页在一切负载下都在 2 倍之内**（1.0–1.4×；Q10a 1.9–110×，准入关的对照在连续读者时 1.8×）。等咨询锁的连接平均约 0.5、至多 1 个（Q10a 6.9 个、池 30 时 25.8 个；对照 4.5 个、至多 8 个），
   读取总有连接。**没有任何 503 `QUERY_TIMEOUT`，也没有超时**；过载以 503 `PROCESS_BUSY` 结束：队满的立即回答，排队的至多 2 秒（每次调用 p95 1.3–2.2 秒），不再排十几秒。
   **目标"首页 ≤ 2 倍、过载快速失败"达到。**
2. **读取负载相同时，准入不降低吞吐**：读者限速到与对照相同的每秒约 85 次首页时，准入开 15.1 次 / 秒、提交 p95 214 ms，准入关 15.0 次 / 秒、154 ms，首页都是 1.3×；
   读者每秒 24 次时（机器约 70 % 忙）吞吐与 Q10a 相同（稳定 20.1–22.5 次 / 秒），到达率低于容量时提交 p95 66–80 ms（Q10a 415–545 ms：没有在锁上排队的连接）。
3. **CPU 饱和时吞吐让给了读取**：读者连续读时，准入开的热门发布只有 9.4–10.0 次 / 秒，准入关的对照 15.2 次 / 秒（首页 1.8×）。
   - 原因是读者不再被饿住：同样 8 个连续读者，对照中每秒只读到约 105 次首页（等连接），准入开时约 165–180 次；4 个 vCPU 上同跑压测程序、应用与数据库，CPU 约 87–89 %。
   - 机制在许可的持有时间：每次完成（开始 + 提交）持有 62 ms（读者 24 次 / 秒）、99 ms（85 次）、209 ms（185 次）——CPU 竞争使锁前、锁内与提交的每条语句都变慢。
     每个发布 2 个许可，容量约 2 / 持有时间：约 32、20、9.6 次 / 秒，与实测相符；锁本身并不空着等（`concurrency` 4 时，评审前的测量，等锁的连接升到 2.4，吞吐仍约 10 次 / 秒：锁内的语句同样变慢）。
   - 对玩家：读者连续读时答题人看到的提交 p95 为 24–33 秒（排队加退避），每秒 15 人时只有 6 / 12 人在重试用尽后仍忙。
   - 这台机器上是零和：准入把连接让给了读取，CPU 不足时热门发布的吞吐也让给读取。正式部署中压测程序不在同机，8 个连续读者每秒 500 多次读取也远超真实首页的负载。
4. **容量规则**（上线前在目标规格上照此重测，§7 第 3 条）：
   - 压测程序放在另一台主机；读者按预期的读取量限速（`LOAD_READ_RATE`），不用连续读者。
   - 在预期读取量下，应用与数据库的 CPU 保持在约 60–70 % 以下（本机 68–77 % 时吞吐与 Q10a 相同、许可持有约 60–100 ms；88 % 时持有翻倍、吞吐减半）。
   - 热门发布的容量按 2 / 每次完成的许可持有时间估算（`jabiz.process` 减去排队等待），它应高于预期峰值的约 1.3 倍；
     语句预算：每次完成约 130 条语句（§4.2）、每条约 0.8 ms 的客户端往返，目标峰值 50 次 / 秒即约 6 500 条语句 / 秒只给答题，读取的语句另算，合计时 CPU 仍须在上一条之内。
5. **App 的重试**：过载时答题人看到的时间是排队加退避（每秒 50 人、读者限速时 p95 约 27 秒），少数人重试用尽后仍忙，看到"人多，请稍后再试"。
   再按**提交**用同一个键（会话只结束一次，同键得到第一次的回答）；再按**开始**是新的键，正确性来自"一人一次"的唯一约束与第二次开始继续进行中的会话。
   这是吞吐（约 20 次 / 秒）不够时的必然结果；要缩短只能提高吞吐（R2、锁拆分）。
6. **提交的宽限**（评审 M1）：`opTime` 在取得许可之后才取，所以排队（至多 2 秒）与重试会吃掉 5 秒的提交宽限，截止前不久按下的提交可能以 EXPIRED 结束，由超时任务以**已保存的**答案结束。
   App 因此提交前先保存未存的答案（保存不排队）、截止前 2 秒再保存一次、过了截止加宽限即停止重试。本节的压测不受影响（时限 600 秒，答题人立即提交）。
7. **`concurrency` 保持 2**（不改缺省）：机器不饱和时 2 个许可的容量（约 32 次 / 秒）已高于锁的容量（约 20）；改 4 在饱和时也没有提高吞吐，只是多占 2 个等锁的连接。
8. 平台的 `max-wait` 2 秒与 `max-queue` 50 在本机合适。

### 9.4 解读与建议

1. **吞吐约提高 60–110 %，过载时首页仍在 2 倍之内**：读者 24 / 85 次时稳定 36–40 次 / 秒（Q10a2 与同日对照 20–24），连续读者时 22（对照 10.5）。每秒 30 人以下提交 p95 只有 44–89 ms（对照每秒 30 人已过载，答题人看到 5.9 秒）；
   每秒 40 人时 p95 0.7 秒（接近饱和）。CPU 同负载下低得多（每秒 15 人、读者 24：32 % 对 68 %）：被省掉的往返本身就是 CPU。首页 p95 在一切负载下 1.1–1.6 倍。
2. **本机没有达到每秒 50 次**：每秒 50 人到达时稳定 36.4 次 / 秒（读者 85 时 29.5），答题人看到的提交 p95 8.6 秒（排队加 App 的退避），开始与提交各有数百次 503 `PROCESS_BUSY`。达到验收（提交 p95 < 1 秒）的峰值约为每秒 40 人。
3. **容量规则（2 ÷ 许可持有）**：
   - 不饱和时持有约 34–38 ms（每秒 15–30 人），规则给出约 53–59 次 / 秒——**偏高**：持有中包括在锁上等的时间，饱和时第二个许可在锁上等，持有升到约 52–55 ms，规则于是给出约 37 次 / 秒，与实测（36–40）相符；
     读者 85 时 70 ms → 28.4（实测 29.5），连续读者时 99 ms → 20.2（实测 22.0）。所以规则在**饱和时**成立，用它估容量要用接近峰值时的持有，或直接用锁内时间：容量 ≈ 1 / 每次完成的锁内时间（约 25–26 ms → 38–40 次 / 秒）。
   - **瓶颈是发布锁，不是许可，也不是 CPU**：许可 3 个时吞吐不变（37–41 次 / 秒），只是持有变长（76–83 ms，第三个也在锁上等）、等锁的连接从 0.3 升到 1.0；CPU 只有 47–55 %。所以不改许可数（保持 2）。
   - 验收的余量（§8.3 第 4 条：容量应高于峰值的约 1.3 倍）：每秒 50 次需要容量约 65 次 / 秒，即每次完成的锁内时间约 15 ms（拆锁后为两把锁中较长的一段）。
4. **16p-2 单独**（事务内写缓冲，平台计划的预算：开始锁内 5 → 约 3，提交 14 → 约 8）：每次完成锁内 19 → 约 11 条。按每少一条省 0.7–1.0 ms（一次往返；合并后的语句更大，本节的分解说明按条数的收益递减），锁内约 26 → 18–20 ms，**约 50–55 次 / 秒的上限**，
   每秒 50 人时没有余量（需要约 65）。
5. **锁拆分单独**（§6.5，应用内，约 2–3 天）：开始的约 7.5 ms 离开提交的锁，容量 ≈ 1 / 提交锁内约 18.5 ms ≈ **54 次 / 秒的上限**；两段并行、读计数改为一条语句、使发布移动的那次完成取两把锁，CPU 会从约 50 % 升到 65–75 %，实际预估约 45–50 次 / 秒。同样没有余量。
   它的收益不依赖"每少一条省多少"的假设（开始整段离开关键路径），比 16p-2 单独更确定。
6. **两者都做**：两把锁中较长的提交锁内约 18.5 ms，16p-2 再省其中 6 条（每条 0.7–1.0 ms），即约 12.5–14.3 ms，上限约 **70–80 次 / 秒**；锁外的工作与 CPU 可能先成为限制，本机预估约 60–70 次 / 秒，即每秒 50 次的 1.2–1.4 倍——下端达不到 1.3 倍的余量。所以 **16p-2 与锁拆分各自都是必要的**（任何一个单独只到约 50 次 / 秒的上限），**两者合起来是否足够要由重测确认**。
7. **建议**（P-10）：
   - 若峰值目标仍是每个发布每秒 50 次、提交 p95 < 1 秒：**16p-2 与锁拆分都还需要**（各自必要；任何一个单独都只到约 50 次 / 秒的上限、没有余量），两者是否足够要由重测确认。先做锁拆分（应用内、收益更确定、不等平台），再做 16p-2，两者之后以本节的设置重测；仍不够 1.3 倍时再看锁外的工作与 CPU（或目标规格上的重测）；
   - 若需求方能接受每个发布每秒约 30–35 次的峰值（本机每秒 30 人时提交 p95 44–89 ms，余量约 1.2–1.3 倍），**两者都可以暂缓**，上线前在目标规格上重测（§7 第 3 条：数据库独立部署时每条语句多 0.1–0.3 ms 的网络往返，锁内 19 条约多 2–6 ms，容量约降 10–20 %）；
   - 许可数保持 2；R4（分批过账，改体验）仍不需要。
8. 本节的数字同 §8：压测程序、应用与数据库同在 4 vCPU 上，绝对值偏低，适合前后比较；同日对照与 §8 的 Q10a2 稳定吞吐相差至多 2.4 次 / 秒（对照略高）。

### 10.3 解读与建议

1. **实测与预估（约 45–50 次 / 秒）相比：在下端或略低。** 读者每秒 24 次时稳定吞吐 42.9（闭环）、40.0（每秒 40 人）、44.8（每秒 50 人）、40.9（每秒 60 人），同日对照 34.8–36.5；饱和的各行**提高 16–30 %**（闭环 36.5 → 42.9 +18 %、读者 85 时 28.8 → 35.6 +24 %、连续读者 20.9 → 26.0 +24 %，每秒 50 人 34.8 → 44.8 +29 %、读者 85 时 26.1 → 33.9 +30 %，每秒 60 人 35.3 → 40.9 +16 %）；每秒 30、40 人时未饱和，两者都跟上到达率。
   池 16 的一次每秒 50 人的运行到了 47.9，但同设置的其他行没有更高（见第 4 条），按全部运行看本机的饱和吞吐约 **41–45 次 / 秒**。**仍没有达到每秒 50 次**：每秒 50 人时稳定 44.8，答题人看到的提交 p95 3.3 秒（对照 8.7 秒）。
2. **为什么低于上限 54**：拆分后关键路径只剩提交在发布锁内的一段，但这一段从 22.4 变成 24.9 ms（开日志时）：开始不再排在它前面，而是与它**同时**在 4 个 vCPU 上跑，锁内的每条语句都更慢（客户端往返中的 CPU 与调度，数据库部分 3.4 → 4.3 ms）。
   按 §9.2 的比例换算到不开日志约 20–21 ms，即**约 48–50 次 / 秒的上限**，实测稳定吞吐在其 85–90 %。开始锁几乎没有人等（平均 0.01–0.04 个连接），等锁的都在发布锁上（约 0.4）；503 几乎都来自提交（开始 0、提交 150–1345），说明拆分后开始一侧有充分余量。
3. **不饱和时延迟的改进比吞吐大**：每秒 40 人时提交 p95 271 → **61 ms**（不再在锁上等开始），每秒 30 人时 65 → 49 ms。首页 p95 在一切负载下 1.2–1.8 倍（目标 ≤ 2 倍仍成立）。
   **过载时 503 从开始移到了提交**：开始的 503 从 753–1697 降到 0，而提交的 503 在每秒 50–60 人时为 150–1345 次（对照 540–1028 次，但对照的答题人有一部分先在开始上被拒、晚到提交），答题人看到的提交 p95 3.3–18.8 秒。
   拆分前过载先挡在开始（被拒的人还没开始答题），现在开始照常放行、人人进入答题，过载落在提交上：**截止前不久按下的提交可能排队、重试到截止加宽限之后，以 EXPIRED 结束**（由超时任务以已保存的答案结束，App 已在截止前保存，§8.3 第 6 条），即答题人看到的结果比按下时晚、可能少了最后不到一秒的改动。
   这是上线的风险，记入 Q10 计划的已知问题。**可选的后续缓解（现在不改代码）**：开始一侧的背压——发布的 `qb.pub` 队列已深（如排队数超过许可数的若干倍、或最近的提交等待超过阈值）时拒绝新的开始（503 `PROCESS_BUSY` 或"人多，请稍后"），把过载挡在开始而不是提交；需要平台给出准入队列的深度，或应用自己估计。
4. **LS-7（连接池 16、`max-active` 8）**：与池 10 相比没有一致的变化（闭环 42.9 → 37.7、读者 85 时 35.6 → 38.6，每秒 40 人 40.0 → 40.5，每秒 50 人 44.8 → 47.9，每秒 60 人 40.9 → 41.3；各行之间的差都在本机约 ±3 次 / 秒的波动之内）。
   单个热门发布的瓶颈是发布锁，不是许可或连接（等咨询锁的连接至多 2、许可持有中开始约 20 ms、提交约 45 ms，后者大部分在锁上等），所以**建议不改配置**：池 10、`max-active` 缺省（5）、两族的 `concurrency` 保持 2。
   容量规则：一个热门发布至多占 4 个许可（开始 2 + 完成 2），`max-active` 应至少为"同时热门的发布数 × 4 + 1"，否则其他发布的答题在队列里等许可；若预期同时有两个以上热门发布，按此规则提高 `max-active` 并把连接池设为它的两倍（读取另有一半连接）。上线前在目标规格上重测时确认。
   **开始族 `concurrency: 1`**（评审后另测，`-Djabiz.process.admission.families[qb.pub-start].concurrency=1`，不入配置）：在同一个库上紧接着与 `concurrency: 2` 成对地跑（库里已累积二十多个上架的发布，首页平时 p95 约 31–41 ms，所以只与同时的一组比，不与上表比）：

5. **对 P-10 的意义**：锁拆分做到了"开始整段离开关键路径"（锁内的串行时间 31.5 → 24.9 ms，开日志时），但本机只到约 41–45 次 / 秒，不到每秒 50 次，更没有 1.3 倍的余量。下一步照需求方的决定做平台 16p-2（提交锁内 14 条 → 约 8 条）：

### 11.2 方法

- 照 §10.1：同一类机器（4 vCPU 的 Firecracker 虚拟机，PostgreSQL 16、应用、压测程序、Mailpit 与 Stripe 桩同机）、连接池 10、准入每族 2 个许可 / 队列 50 / 至多等 2 秒、`max-active` 缺省；新库 `qb_perf_q10a5`（首次运行注册 1000 个答题人），每次运行一个新发布、全部付奖；读者 8 个限速 3 轮（每秒约 24 次首页）；开环的客户端时限 5 秒；照 App 重试忙；`LOAD_METRICS=yes`（回环的独立管理端口）。
- **同场 A/B**：同一个 jar、同一个库，实例之间只换环境变量 `JABIZ_STORAGE_WRITE_BATCHING_ENABLED=false|true`（重启）；每个实例先热身一次，再连续跑各行。三轮共 12 个实例：第一轮 关、开、关、开（闭环与每秒 30–60 人），第二轮 开、关、开、关（闭环、每秒 40、50 人），第三轮 关、开、关、开（每秒 30、50、60、70 人）。所以每秒 50 人开 / 关各 4 次，其余各行各 2 次。
- **本机的负载**：压测期间每 9–10 秒采样 `/proc/loadavg` 与 `top`（前 5 个进程）。**第一轮（12:30–14:22）本机同时跑着其他会话的重测试**（另一个工作树的 `:quizbuks:test` 与平台测试的 Gradle 工作进程、Playwright 的 e2e），它们平均占 0.5–1.7 个 CPU，load average 6–17（4 vCPU），整机 CPU 78–100 %。
  这一轮的吞吐整体低（开、关都在 15–42 次 / 秒之间，各行之间比开关的差别大），**只能说明 CPU 饱和时两者都受 CPU 限制，不用于比较**（11.3 末尾）。第二、三轮（14:22–16:02）本机安静：load average 平均 3.7–5.1，其他进程合计约 0.1 个 CPU；下表只用这两轮。
- 锁内时间的分解照 §10.1（`log_min_duration_statement = 0`，闭环、读者 24，同样开 / 关各一个实例、各跑两次取第二次，16:02–16:20，本机安静），并按位置列出每条锁内语句之前的客户端间隔与数据库耗时。

### 11.4 解读与建议

1. **写缓冲让单个热门发布的饱和吞吐提高约 30–40 %**：同场比较，饱和的各行开关关时 34.4–39.0 次 / 秒，开时 45.2–53.8（闭环 37 → 45–53，每秒 60 人 32–36 → 45–54，每秒 70 人 37–38 → 47–50）。
   开关关的数字比 §10 的 Q10a4（41–45）低几次 / 秒：同一份代码，库里累积的发布与账本更多（三轮共约 70 个发布），本节只做同场比较，不与 §10 的绝对值比。
2. **每秒 50 人、提交 p95 < 1 秒：在本机安静时达到，但没有余量。** 开关开时 4 次中 3 次稳定吞吐跟上到达率（50.1–50.6），提交 p95 158 / 291 / 579 ms、没有 503；第 4 次稳定 47.3、p95 1048 ms（9 次提交 503），在边上。
   开关关时 4 次都过载（稳定 34–39，答题人看到的提交 p95 17–19 秒，880–1249 次提交 503）。饱和点约 **45–54 次 / 秒**，每秒 50 人约为饱和点的 1.0 倍，不到 §9.4 第 3 条要求的 1.3 倍余量（容量约 65）。
   首页 p95 在每秒 50 人时是平时的 1.4–1.7 倍（目标 ≤ 2 倍成立）；闭环 64 的一次到了 2.2 倍（CPU 79 %），过载时首页可能越过 2 倍。每秒 30、40 人时提交 p95 61–97 ms（关时 108–1477 ms）。
   本机 CPU 被其他工作占用时（第一轮）每秒 50 人远达不到，与 §8.3 第 4 条的容量规则一致。
3. **与预估（§10.3 第 5 条：本机约 55–65 次 / 秒）相比在下端之下。** 语句数照预估减半（提交锁内 14 → 7），但提交在发布锁内的时间只少了 17 %（26.0 → 21.5 ms，开日志时）：
   锁内时间的 83 % 是**客户端**（每条语句之前约 2 ms：Reactor 的调度、实体映射、评分与过账校验、审计与事件的 JSON），数据库只有 3.7 ms；缓冲的写入那一条之前的 5.7 ms 是把整笔写入渲染成一条语句（约 115 个参数），它的数据库耗时 1.7 ms。
   所以"每少一条省 1.0–1.2 ms"的估计对剩下的语句仍大致成立（每条约 2 ms，开日志、两段并行），但被省掉的写入的 Java 工作没有消失，而是集中到了最后一条之前。**现在的瓶颈仍是提交在发布锁内的一段，其中主要是锁内的应用与平台的 Java 工作和本机的 CPU，不再是往返的条数。**
4. **过载仍落在提交上**（§10.3 第 3 条照旧）：开时每秒 60–70 人有 216–1037 次提交 503、答题人看到的提交 p95 3.5–17 秒，开始一侧 503 几乎为 0。上线风险与可选的缓解（开始一侧的背压）不变。
5. **选项**（按代价从小到大，都不改变保证）：
   - **在目标规格上重测**（上线检查清单的一项）：本机的压测程序、读者与数据库占了同一个 4 vCPU，每秒 50 人时整机 CPU 68–72 %；应用独占 CPU 时锁内的客户端间隔会变短，数据库独立部署则每条往返多 0.1–0.3 ms（锁内 7 条约 1–2 ms）。先确认目标规格上的饱和点，再决定要不要做下面几项。
   - **锁内 Java 工作的剖析**（不需要设计改动）：对提交在发布锁内的一段做一次 CPU 剖析（async-profiler 或 JFR），看缓冲写入的渲染、过账校验、审计 JSON 与 Reactor 调度各占多少；平台的观测只到流程一级，没有步骤级计时。可能的平台改进：缓冲写入的语句文本随行数变化，预备语句缓存（`jabiz.storage.prepared-statement-cache-queries`，缺省 256）对它命中率低。
   - **平台：取锁与随后的读取合成一条**（钱包锁 + 钱包、科目锁 + 账本的读取），提交锁内 7 → 5 条，约省 4 ms（开日志时），饱和点约 +15–20 %。需要平台确认"读在锁之后"（D46 第 5 条）在一条语句中如何保证，另写计划。
   - **开始一侧的背压**（§10.3 第 3 条）：不提高吞吐，但把过载挡在开始，避免截止前的提交以 `EXPIRED` 结束。
   - **R4 分批过账**（改变体验，§6.3）：`LEDGER_POST` 与钱包移出发布锁，锁内只剩重读与一条写入，预估容量约 70–80 次 / 秒；需求方曾决定不做，若目标规格上仍不够 1.3 倍余量再议。
   - 接受每个发布约 45–50 次 / 秒的峰值，运维上以暂停与限流应对（`operations.md` §6、§7.6）。
6. **应急开关**：保持缺省开。关掉（`JABIZ_STORAGE_WRITE_BATCHING_ENABLED=false`）即回到 Q10a4 的语句数与吞吐，场景快照与全部测试在两种设置下相同（平台以 `…WithoutHeldWritesIT` 与 `ScenarioWithoutHeldWritesTest` 验证；QuizBuks 的语句预算在两种设置下各断言一次）。
7. 本节的数字同 §8–§10：压测程序、应用与数据库同在 4 vCPU 上，绝对值偏低，适合同场的前后比较；本机是共用的，数字只取其他工作安静时的两轮。
