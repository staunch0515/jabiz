## 一、商户的题目编辑页太长

### 现状

- 编辑器（`sponsor/src/content/QuizEditorPage.tsx`）已分六个标签页（模版、题目、资料、语言、版本、商品）。页头有标题、种类与状态徽章、版本号、四个按钮（保存版本、预览、复制、删除），其下按情形出现"内容已被修改"、版本被拒的问题清单、"版本已保存"、"译文不完整"等告警。
- "题目"页（`QuestionsPanel.tsx`）：上方常驻 AI 出题面板（`AiQuestionsPanel`），下方**每题一张卡片**：题号、分数徽章、单/多选、题干全文、题图、**全部选项**（正确的打勾、选项图）、四个按钮（编辑、上移、下移、删除）。一题约 10–15 行；上限 100 题（`ContentLimits.MAX_QUESTIONS`），二三十题的模版就要滚很久；上下按钮每题两个，排序一次一格。
- 编辑在对话框中进行（`QuestionDialog`），列表本身只读：列表只需"认得出是哪题"。

### 方案（纯前端，不改流程与数据）

1. **题目列表默认折叠成一行**：题号、题干首行（截断）、分数、单选/多选、选项数、有图标记；点击展开为现在的卡片（Accordion，一次展开一题，`aria-expanded`）。键盘可达，展开态记在 URL 查询（`?q=<题号>`）以便刷新保留。
2. **排序**：上下按钮改为一个"移到…"的下拉（题号列表）或拖拽（`@dnd-kit` 不引入新依赖的话用下拉），已有的 `QB_QUESTION_REORDER` 流程不变。
3. **AI 面板收起**：改为一条按钮（"用 AI 出题"）打开对话框，进行中的作业显示为一条状态行；面板只在有候选待校对时展开。
4. **页头**：告警区只保留当前成立的一条（优先级：stale > 版本被拒 > 译文不完整 > 已保存）；按钮在窄屏收进"更多"菜单。工具条（添加题目、保存版本）在滚动时 sticky。
5. 列表上方给一行摘要：题数、总分、单选/多选各几题、没有正确答案的题数（现在只能逐题看）。

### 测试与估计

- `content.test.tsx`：折叠与展开、键盘、摘要、移到；e2e `content.spec.ts` 的选择器按新结构改；axe 两种外观。
- **估计 1–1.5 天**。**风险**：低；e2e 选择器要跟着改。

## 二、发布从题库抽几题

### 现状

- 版本快照（`QuizSnapshot`）是全部题目按序；满分 = 题目分数之和（`fullScore()`），卡片冻结 `questionCount`、`fullScore`；`passScore ≤ fullScore`；档位必须覆盖 0..满分（`TierCoverage`）；版本切换（Q51）要求满分相同。
- 开始时按会话打乱**选项**（`OptionShuffle`，HMAC 种子），题目顺序不打乱；评分 `Scoring.scoreShown`；答案与结果按版本题号；题目统计按（发布、版本、题号）累计，分母是该版本的完成数（`QuestionTotals`）。店面（S2，`ChannelPlay`）走同一快照。

### 方案：发布层的"抽题"

| # | 决定（草案） |
|---|---|
| D-1 | **抽题是发布的设置**：`questionCount` k（1 ≤ k < 版本题数；空 = 全部，现状不变）。同一版本可以一个发布全考、另一个抽 5 题。 |
| D-2 | **只允许同分的题库**：抽题的发布要求版本全部题目分数相同（提交检查 `QB_PUBLICATION_PICK_UNEQUAL_POINTS`），满分 = k × 每题分，冻结到卡片；档位、及格线按这个满分。不等分的抽题会让每人的满分不同，档位无法定义。问卷（SURVEY）不抽题。 |
| D-3 | **每次开始抽一组**：种子同选项打乱（HMAC(`JABIZ_INTEGRITY_KEY`, `qb.question-pick`) 对 用户 \| 发布），从 n 题中取 k 题，**保留版本的题序**；抽到的题号列表记在会话 `questionSet`（JSON，`processOnly`、不可变，像 `optionOrder`）；开始、继续、保存、提交、结果都只涉及这 k 题，题号仍是版本题号（本来可见）。一人一次，所以一人只有一组。 |
| D-4 | **评分**只对抽到的子集（`Scoring.score(snapshot.subset(questionSet), …)`），满分 k × p；结果页按会话的题；`Answers`/`result` 不收子集外的题（422 `QB_ATTEMPT_ANSWER_INVALID`）。 |
| D-5 | **题目统计**：每题多记"被抽到的完成数"作分母（`QuestionTotals` 每题多一个计数；`QbQuestionStat` 加列 `shown`）；最小分组 k 按被抽到的人数算。 |
| D-6 | **版本切换**（Q51）：新版本须同样同分且题数 ≥ k，满分 k × p 相同即可（比现在"满分相同"宽）。 |
| D-7 | **店面**（S2）：第一步不支持抽题（店铺的活动没有这个设置），`CampaignProcesses` 照旧全考；以后再接。 |
| D-8 | 复制随发布复制；审批内容含 k（卡片与审核页显示"抽 k / n 题"）；App 的发布页显示"每人随机 k 题"。 |

### 为什么能提高难度

相邻两人的题不同、选项顺序也不同，答案无法照抄；题库越大、k 越小越难猜。配合 Q75（看完视频）与 Q76（前置条件）形成"学—考"链。

### 影响与估计

- 后端：发布字段与卡片列（迁移 V61 起，视合入顺序）、`PublicationReadiness`、`QuestionPick`（纯 Java）、`AttemptProcesses.start` 与 `AttemptFinishing`、`Scoring`、`QuestionTotals` / 分析任务、模板（`qb.app.publication`、`qb.sponsor.analytics.questions`）、`AttemptStatementBudgetIT` 不变（抽题在内存中进行，不加语句）。
- 商户后台：向导第二步"抽题数"；分析页的分母说明。App：发布页与答题页的题数来自开始的输出（已如此）。
- **估计 4–5 天**。**风险**：题目统计的分母是最大的改动；e2e 的答题流程按题号找题（现有测试全考，不受影响）。

## 三、商户的所有列表页加卡片模式

### 现状

- 商户后台 11 个列表页（模版、发布、现金奖励、电子奖品、兑换、店员、交易、通告、统计、钱包、邀请清单）都用平台 `@jabiz/ui` 的 `DataTable`（TanStack Table，服务端分页排序筛选）。它没有响应式行为：手机上横向滚动，列多的页（交易、发布）难用。
- 规则（根 `CLAUDE.md` 第 4 节与决策 D34）：界面组件只在 `@jabiz/ui`，应用不自己复制组件。所以**先在平台做**。

### 方案

**平台（`1.3/platform` 的一期，编号由平台 ROADMAP 定）**：`DataTable` 新增卡片模式。

- `columns[i].meta.card`：`'title'`（卡片标题，一列）、`'subtitle'`、`'badge'`、`'actions'`（卡片底部）、`'hidden'`，其余列按"标签：值"排成描述列表（复用 `DescriptionList`）。给了任一 `meta.card` 即可用卡片；没给的照旧只有表格。
- 视图切换：表格 / 卡片的 `SegmentedControl`（`aria-label`），记在 `localStorage`（按表的 `label`）；窄屏（< `md`）**默认卡片**、宽屏默认表格。
- 卡片模式下的排序用一个下拉（可排序的列 + 升降），筛选照旧用 `FilterBar`；分页同一个分页器；展开行（`renderExpanded`）在卡片内展开；`rowProps` 的 `data-*` 照样加到卡片上（e2e 选择器不变）。
- 测试：`data-table.test.tsx`（切换、记忆、排序下拉、axe）；`app` 示范的一个列表给 `meta.card`；设计文档 12 §x 加一节。**估计 2 天**。

**QuizBuks（Q80）**：合入平台后，11 个页面各加 `meta.card`（标题列、徽章、金额、操作），行点击在卡片上整卡可点；后台扩展不改（管理员用桌面）。统计页的六张表只给卡片标题。**估计 1.5 天**。

## 五、答题者与商户之间的手工通信

### 现状

- 答题者收件箱（Q7c）只有**系统消息**（`QbMessage`，由事件消费者写：奖励、现金、兑换、电子奖品、推荐）与**商户通告**（`QbBroadcast`：商户→答过题的人，纯文本、不许链接与联系方式（`BroadcastRules.hasAddress`）、条数与间隔节流、可撤回）。
- 答题者→商户没有渠道：只有"举报"（Q49a，`QbReport`，给平台/运营商）与现金/兑换/电子奖品的**争议状态**（`CASH_DISPUTED` 等，没有自由文字）。
- 商户看到答题者只有显示名与 `userKey`，不给邮箱与用户编号（Q9b）；邮件只经平台或商户验证过的服务器发出，不给对方地址。

### 方案：**有上下文的对话**，不是开放私信

| # | 决定（草案） |
|---|---|
| D-1 | 对话 `QbConversation`（商户的发布方那一对、答题者、**上下文**：会话 / 兑换 / 现金奖励 / 电子奖品 / 推荐 的种类与编号、状态 OPEN / CLOSED、最后一条时间）；消息 `QbConversationMessage`（对话、发送方 `TAKER` / `SPONSOR`、发送人（商户或其店员的用户编号，对答题者只显示商户名）、纯文本 ≤ 1000、时间）。普通表，只经流程写入。 |
| D-2 | **只有答题者能开启**（从自己的结果页、领奖记录、电子奖品页），每个上下文一个对话；商户与店员回复。商户不能向没有对话的人发起（已有通告）。 |
| D-3 | 文字规则同通告：纯文本、不许链接 / 邮箱 / 电话 / 社交账号（`BroadcastRules.hasAddress`，防止把人带出平台）；每人每对话每日条数上限（普通参数 `qb.conversation.daily-cap`，缺省 20）；对话 90 天无消息自动关闭（逐项任务）。 |
| D-4 | 答题者可关闭对话、**屏蔽商户**（04 §5-K 的一半）、举报（复用 `QB_REPORT_SUBMIT`，理由新增 `MESSAGE`，带对话编号）；商户可关闭。封禁的商户与答题者不能发。 |
| D-5 | 身份：商户侧显示公司名（入驻的 `company`），答题者侧显示资料显示名；两边都看不到邮箱、用户编号与店员是谁。 |
| D-6 | 通知：新消息经现有收件箱写一条 `QbMessage`（种类 `CONVERSATION_REPLY`，每对话每小时至多一条）并走 17k 的推送；商户后台"消息"页加"对话"标签，未读数进菜单徽标。不发邮件。 |
| D-7 | 平台与运营商可读（纠纷处理；默认数据视图经 `OperatorScopes`）；审计照常。删除账号（Q71）：`PersonalDataEraser` 清空其文字留墓碑；保留期随会话。 |
| D-8 | 锁 `qb.conversation:<编号>`，不与发布锁、钱包锁同时持有；答题路径一条语句也不加。 |

### 产品上要说清

- 条款与隐私政策各补一条（对话内容平台可见、用于纠纷处理、不含联系方式）；日文为准（Q7b）。
- 商户的"客服负担"：对话只从具体的事（领奖、争议）开启，不是营销渠道。

### 估计与风险

- 后端 2.5 天（两张表、五个流程、两三个模板、任务、文案、IT）、商户后台 1.5 天、App 1.5 天、文档与 e2e 0.5 天：**5–6 天**。
- **风险**：骚扰与把人带出平台（D-3、D-4 兜底）；商户不回复（显示"通常 x 天内回复"或不承诺）；运营商读取的范围要测试（Q59c-2）。**决定**：是否允许商户发起（建议不）；是否允许图片（建议不）。

## 六、商户资料页的布局

### 现状

- `/onboarding`（菜单"入驻"）一页两大段，单列 `max-w-xl`：（1）入驻信息（状态与审核结果、显示名、公司、简介及其语言、头像、提交）；（2）**公开主页编辑器**（`page/SponsorPageEditor.tsx`，390 行：链接名、主要语言、标语、各语言标语、网站、封面、状态、保存 / 提交审核 / 撤下、打开与复制链接）。两套状态与告警叠在一起，内容多、层级平。
- 相关的设置散在"设置"组的七项（入驻、商品、统计、邮件服务器、消息、账户、帮助）；店员在"奖励"组；允许的支付方式由管理员设定、只在向导里看得到。

### 方案：**商户中心**（一个带子导航的页组）

- 路径 `/profile`（旧 `/onboarding`、`/page` 301 到对应子页），子导航在左（lg）/ 顶部可横向滚动的 Tabs（手机）：
  1. **概况**：审核状态、完成度清单（基本信息 → 公开主页 → 商品 → 店员 → 邮件服务器，各一行"已完成 / 去完成"）、公开主页的预览卡片（标志、公司、标语、封面）、链接与二维码（商户主页是 App 的 `/s/<handle>`）、允许的支付方式（只读）。
  2. **基本信息**：现在的入驻表单（两栏：左表单、右"审核时看什么"的说明与头像预览）。
  3. **公开主页**：编辑器拆成区块卡片（链接与语言 / 标语 / 封面与网站 / 发布状态），保存条固定在底部，右栏实时预览（复用 App 的主页组件经 `@jabiz/ui`？不行——组件在 App 目录；用商户后台的预览页 `PreviewPage` 的 iframe）。
  4. **商品**（现页搬入）、5. **店员**（第四项）、6. **邮件服务器**（现页搬入）。
- 统一：`PageHeader` + 面包屑、每区块一张 `Card` 带标题与一句说明、表单两栏在 lg、错误与成功提示各只一处、品牌 token 的留白与字号（12 §11）。
- 菜单"设置"组收为：商户中心、统计、消息、账户、帮助。
- **估计 3 天**（结构 1、三个表单页 1.5、测试与 e2e 选择器 0.5）。**风险**：e2e `sponsor.spec.ts` 等按旧路径与选择器写，须同步改；旧链接靠 301。

## 七、商户发布赚钱的视频：看要扣答题者的学分

### 现状

- 学分（Kudos）的流向只有一条：商户充值（日元 → 2110）→ 作为奖励付给答题者（2120）→ 答题者提现（Stripe，`TransferRules`，保留期 `RewardHolds`）。答题者**没有充值**，也没有任何"花学分"的地方。
- 视频是外链（YouTube / Vimeo，04 §2 既有决定"平台一个视频都不保存"）；能看到发布页的人都读得到资料的 URL（`qb.app.publication` 的 `materials`；匿名的分享页不含资料）。

### 方案（草案）：发布的**解锁价**

| # | 决定（草案） |
|---|---|
| D-1 | 发布新增 `unlockPrice`（Kudos，空 = 免费）。有价的发布：首页与发布页显示封面、简介、价格，**资料与开始按钮锁住**；答题者点"用 X 学分解锁"→ 流程 `QB_UNLOCK`（用户钱包锁内：账本借 2120（答题者）贷 2110（商户预付款，扣除平台抽成记 4110），写 `QbUnlock`（用户、发布唯一））；此后资料可读、可开始答题（答题与奖励照常：学了还能赢回）。 |
| D-2 | **只能花"可转"的学分**（`RewardHolds` 的自由部分：不在保留期、不被争议冻结），否则争议扣回时追不回；余额不足 422 `QB_UNLOCK_FUNDS_SHORT`。 |
| D-3 | 退回：视频资料被商户换掉或发布被下架 / 结束前解锁的人…**不退**（学过就算，与 Q76 一致）；但商户**被管理员下架**时自动退回（`QB_UNLOCK_REFUND`，冲正）；答题者 24 小时内未开始可自助退（一次）。 |
| D-4 | 不能与完播奖励（八）同设：一个发布要么付费看，要么看了有奖。 |
| D-5 | 店面（S2）不做：店铺顾客没有学分。 |

### 必须先解决的问题
