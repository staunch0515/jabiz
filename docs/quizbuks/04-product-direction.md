# QuizBuks 产品方向整理（2026-11-01 的讨论）

来源：需求方 2026-11-01 与一个 AI 助手（Gemini）的一段对话，从"抖音的推荐算法为什么显得厉害"开始，
逐步谈到 QuizBuks 的定位、视频、防作弊、科技树、认证、企业培训、线下场景、招聘、学分与社会价值。
本文把这段对话**完整地**整理进项目：先按原文顺序摘要，再提炼理念与场景，对照现状，最后分成
**线 1.3 能做的候选阶段**（§5）与**放在未来规划的**（§6）。

读法：

- 对话中**需求方自己的提法**是方向，记在 §1 的"需求方"列与 §2；**助手的发挥**（架构图、估值、口号、文案）只作参考，记在"助手"列与 §8，
  不作为需求。助手在后半段明显迎合（"降维打击""万亿级""抖音不配"），§7 给出客观评估。
- 本文**不是实施计划**。§5 的候选每一项开工前仍按根 `CLAUDE.md` 第 7 节另出计划并经需求方确认；编号在确认时取（下一个空号自 **Q75** 起）。
- 与既有决定相左的地方逐条标出（§5、§6 的"与现有决定的关系"）；改变决定要先改计划文档，再改代码。

## 2. 提炼出的理念（需求方的立场）

1. **注意力要有回报。** 看视频不是浪费时间：看完有少量 Kudos，答题合格有更多 Kudos 与奖品。"完播低保 + 答题暴击"是两层激励。
2. **谁发视频谁出学分。** 商户（或任何发布者）为自己的内容出 Kudos；平台只做验证与结算，不垫资、不独吞广告费。
3. **平台不保存、不管理视频。** 视频在 YouTube 等处，QuizBuks 只保存链接、题目、规则与凭证（这是 2026-10-10 已确认的决定，01 §0"视频只保存链接"）。
4. **路径与门槛。** 用"科技树"把孤立的发布连成有前置关系的路径：先懂基础再看进阶，进阶的奖励更大；持有某认证才能看、才能答、才能领。
5. **精准，不骚扰。** 买过的、答过的不再推；企业的内容只给顺着路径走过来的人看；按"有效认知"而不是曝光计价。
6. **权威与可验证。** 高含量的题目像资格考试：有门槛、有有效期、不可转让、第三方可验证；可以由品牌或专家背书。
7. **一套机制插进各行各业。** 营销（高认知成本产品）、线下等待时间（餐饮等）、企业内部 SOP 培训与检查、招聘辅助。
8. **无危害。** 不做让人沉溺的推荐；用户知道自己为什么看、看了得到什么。
9. **学分本位。** Kudos 是唯一的记账单位（1 Kudos = 1 JPY），四种兑现方式照旧。

## 5. 线 1.3/quizbuks 能做的（候选阶段，待需求方确认与排序）

原则：都在现有模型上加一步，不改钱的流转、不改四种奖励方式，每项一个计划。估计只算 QuizBuks 自己的工作，
"迁移"一栏指是否要加表或列（按版本线规则只做在 1.3）。

### A. 视频播放的校验：知道答题者看过、看完

> **已实现**（Q75，`plans/Q75-video-playback.md`，需求方 2026-11-01 确认，顺序 A → D → E）。下文是候选时的概述，细节以计划为准。

- **内容**：开始页与首页卡片的播放器改用 YouTube IFrame Player API 与 Vimeo Player API（`enablejsapi=1` / `postMessage`，仍是无 Cookie 的嵌入）；
  App 记录播放开始、进度与结束，在开始答题与提交时一并交给服务器（`QB_ATTEMPT_START` / `QB_ATTEMPT_SUBMIT` 的输入多几个字段，不加语句：写进会话的现有行）。
  "看完这个视频即可答题"的资料（Q19）从此**真正要求看完**：没有结束事件不显示"开始答题"（客户端），服务器核对"开始答题的时刻 − 开始播放的时刻 ≥ 视频时长 × 0.9"（时长由商户在资料上填写，
  或上线时经 oEmbed / Data API 取得；不依赖客户端自报的时长）。
- **为什么先做**：§5-B、§5-C、§5-G、§5-J 都要它；Q19 的已知风险"平台不检查答题人是否看完视频"由此关闭。
- **迁移**：`qb_attempt` 加三列（播放开始、结束、客户端自报的时长），或新表 `qb_attempt_playback`；视频资料加 `durationSeconds`。
- **风险**：客户端事件可以伪造，服务器只能保证"时间过去了"；YouTube 播放器 API 的加载受浏览器扩展与网络影响，取不到事件时退回现在的做法（可以开始但不计"看完"）。
- **估计**：2–3 天。**决定**：看完的判定阈值；取不到事件时是否允许开始。

### B. 完播奖励：看完视频即得少量 Kudos（不答题）

- **内容**：新的 Quiz 种类 `WATCH`（与 `QbContent.KIND_QUIZ`、`KIND_SURVEY` 并列，字典加值）：没有题目，只有一条"看完即可"的视频资料，看完即"合格"，奖励一档，每人一次，预算与名额、审核、暂停、统计照旧；四种奖励方式都可（实际多为平台 Kudos）。
  首页卡片标"看完即得"；开始页就是播放器，看完出现"领取"；提交经 `QB_ATTEMPT_SUBMIT` 的同一条路（空答卷，以 §5-A 的校验为合格条件）。
- **与现有决定的关系**：D-Q12-4"问卷只奖励完整的回答"是同一思路；发布须至少一档奖励 > 0（`QB_TIER_NO_REWARD`）照旧成立。
  `qb.reward.max-per-attempt`（Q28，景品表示法的上限）照用。
- **风险**：（1）**法务**：为观看支付报酬不是"取引に付随する景品"，但平台 Kudos 可以提现，须由法务确认其性质（01 §4.6 的資金決済法问题在此更突出）；
  （2）**刷量**：没有题目，只剩时间与账号两道门：须 §5-A 与 §5-G 先行，并建议完播奖励只给已验证邮箱、注册满 N 天的账号（受控参数）；
  （3）单价很低（几 Kudos）时提现门槛（`qb.transfer.threshold`）会让多数人攒不到，产品上要说清。
- **迁移**：Quiz 种类字典加值；没有新表。**估计**：3–4 天（依赖 A）。**决定**：是否做；最低注册天数；是否只允许平台 Kudos。

### C. 视频到指定时间点插题（可选）

- **内容**：视频资料可登记"题 n 在第 t 秒弹出"；开始页播放到 t 秒暂停、显示该题、答后继续（答案仍在提交时统一评分，不改评分与结算）。
  只影响 App 的答题页与商户后台的资料对话框；不改会话模型。
- **风险**：iOS Safari 的全屏播放会遮挡题卡（对话第 4 项提到的坑）：在 iOS 上退回"看完再答"。
- **迁移**：`qb_material` 或题目加"时间点"列。**估计**：2 天（依赖 A）。**决定**：是否值得；与"一页一题"的关系。

### D. 发布的前置条件（科技树的第一步）

> 实施计划已出：`plans/Q76-prerequisites.md`（2026-11-02，待确认）。下文是候选时的概述，细节以计划为准。

- **内容**：发布可以要求"答题者在本商户的发布 X 上合格过"或"持有认证 Y"（Q69 的认证目录放宽为**商户自己的认证**：D-Q69-10 已留余地）；
  不满足时首页不列出（同 Q47 的 `matched`），发布页显示"先完成 X"并链到 X；满足后才能开始。商户后台的向导"客户匹配"一步加"前置"；
  App 的商户主页按前置关系分层显示该商户的发布（基础 → 进阶），就是最小的"品牌体验树"（S6）；售后延伸（S4）与"企业的广告不乱投"（S5）都由它表达。
- **与现有决定的关系**：Q69 §7"以后：商户自己的认证与学习路径"提前到现在；仍是"认证不是奖励方式"，兑现与结算不动；
  前置条件像客户匹配一样是商户自选的规则（Q70 第 18 条的思路），平台不承担责任。
- **迁移**：`qb_publication_prerequisite`（发布、前置发布或认证键）；商户认证的轮表复用 `QbCertificationRound`（放宽"只能是官方账号"）。
- **估计**：4–5 天。**决定**：前置只限同一商户还是可跨商户（跨商户涉及对方同意）；前置的发布结束后是否仍算；"合格过"与"答过"哪个算。

### E. 答题者的认证页与可验证的证书

> 实施计划已出：`plans/Q77-certificates.md`（2026-11-02，待确认）。下文是候选时的概述，细节以计划为准。

- **内容**：（1）App 账户页"我的认证"列出持有的认证、合格的轮、有效期（Q69 已有一部分）；（2）本人可开启**公开的认证页** `/taker/u/<handle>`（公开模板白名单：显示名、持有的认证与到期日，不含分数与个人资料），
  与一张可下载的证书 PDF（平台 `DOCUMENT_ISSUE`：存档、内容哈希、重印取存档字节），证书上的二维码指向 `/verify/<编号>`（公开模板：有效 / 已过期 / 已收回）；
  （3）商户的发布可以登记为"商户认证"的一轮（§5-D），证书上写商户的名字，即对话中的"品牌官方认证"；专家联名只是证书上的署名字段。
- **与现有决定的关系**：认证绑定账号、不可转让、一年有效、不做重考——照旧。
- **迁移**：答题者的 `handle` 与公开开关（`qb_user_settings` 加列）；证书是单据运行，不加表。
- **估计**：3–4 天。**决定**：公开页缺省关闭；是否显示合格的分数（建议不）。
- 这也是招聘场景（S10）现在就能给的最小形态：求职者把公开认证页发给企业。视频回答与企业端见 §6.8。

### F. 中国大陆可用的视频源：Bilibili（及可能的腾讯视频、西瓜）

- **内容**：`VideoEmbeds` 加 Bilibili 的播放器地址（`player.bilibili.com/player.html?bvid=…`），CSP `frame-src` 相应放开；首页卡片与开始页照旧。
  Bilibili 播放器的事件 API 不如 YouTube 完整：§5-A 的校验在它上面退回"时间过去了"。
- **为什么**：03-plan §6 的中国大陆策略：YouTube 在中国大陆打不开，现在中国的商户没有可用的视频源。
- **迁移**：无。**估计**：1 天。**决定**：选哪几家；隐私政策中列出播放器。

### G. 低成本的防刷加强

- **内容**：（1）**最短作答时间**：每题不少于 N 秒（按题数算，受控参数），快于它的提交记为可疑并不发奖、进入运营商抽查（不是直接拒绝，避免误伤）；
  （2）同一地址、同一天注册并完成同一发布的账号数超过阈值即标记（平台已有地址与限流能力，`ClientAddresses`）；
  （3）可疑记录的列表给运营商与总部（后台扩展），处理方式沿用封禁与作废。
- **不做**：设备指纹、手机号实名——隐私与成本，需求方另议（§6.7）。
- **与现有决定的关系**：补 02 §9；Q10b 的保留期与争议冻结照旧；需求方立场"防作弊成本是边界不是否决票"。
- **迁移**：会话表加"可疑原因"列。**估计**：2–3 天。**决定**：阈值；标记后奖励是"暂扣待审"还是照发。

### H. 定位与文案：招商网站与 App 的说法

- **内容**：按 §8 的草稿更新招商网站（Q31，六页三语）：主标语、"按有效认知付费、不为曝光付费"、"看过的不再推"、"看完有回报"、"无危害"；
  新增**企业内部培训**一页（S9 的试点做法：企业作为商户、指定邮箱的发布、到店兑换表示内部福利）与**线下等待场景**一页（S2、S3）。
  App 的欢迎页一句话随之改。**文案由需求方审定**，助手的"CPK""认知型营销网络""降维打击"等词是否对外使用由需求方决定（§7.1 的保留意见）。
- **迁移**：无。**估计**：1–2 天。

## 6. 放在未来规划的（为什么现在不做）

### 6.1 推荐算法与数据飞轮

对话第 1 项的召回 → 精排 → 重排、多目标学习、探索与利用。**不做的理由**：没有数据（日活与内容都还少）；需求方的理念正是"用户自己选路径，不被算法喂"；
首页按语言、匹配、前置、关注排序已经够用（§5-K）。**以后**：当完播、合格、领取的信号积累起来，可以按"同类用户在这个发布上的合格率"排序，仍是可解释的规则，不是黑盒。

### 6.2 纯娱乐内容与随机掉落

无奖励、无题的娱乐视频流；刷几个随机掉落一个奖励节点；娱乐视频结尾的轻量测试。**不做的理由**：
（1）发布必须有奖励是现行规则，无奖励的内容是另一种对象（更像商户主页的视频区）；（2）随机奖励在日本是"懸賞"，有总额与单价上限，须法务；
（3）用户心智：需求方的立场是"看了有回报"，混入无回报内容与之相反；（4）内容供给要靠创作者生态。**以后**：先在商户主页允许挂视频（不奖励、不计时）看效果。

### 6.3 完整的科技树

DAG 的可视化、消耗 Kudos 解锁、节点的四态状态机、勋章与养成、闯关地图与连击、全站的领域树与信任等级、平台出根节点与商户赞助分支节点。
**现在只做 §5-D 的前置条件**（它就是 DAG 的边）。**以后**：用户数据足够时再做跨商户的领域树；"消耗 Kudos 解锁"动钱，需要账本与法务；"信任等级"即 Q69e 商户等级的答题者版。

### 6.4 严肃考试模式

题库随机抽题、每题限时、重考冷却、视频中的防伪节点。**与 2026-11-01 的决定相左**：Q70 第 17 条"每月换模版重新发布是业务操作，不做题库、自动排程与补考间隔"。
Q69 §8 把"题库随机抽题"列为以后的对策。**以后**：需求方改决定时，先改 Q70 计划，再出"考试模式"的计划（只对认证轮的发布生效）。

### 6.5 企业内部 SOP 培训与检查模块

私有树、每日 / 每班的重复答题、SOP 更新触发重认证、部门排行榜、按员工数计费、企业自己的管理员。**现在能做的试点**：企业注册为商户，用指定邮箱的发布（Q25）发给员工，
用到店兑换（Q22b）表示内部福利，用版本切换（Q51）更新内容，用 §5-D 的前置表示上岗资格；§5-H 写一页说法。
**不做模块的理由**：一人一次是答题模型的根（唯一索引、结算、统计都建立在它上面），"每天答"要新的对象（任务 / 班次）；按员工数计费是新的商业模式；
企业数据的隔离与导出是新的合规面。**以后**：有一家真实的企业客户再出计划。

### 6.6 认知画像与对企业开放

"用户懂什么、在研究什么、买意向到哪一步"的结构化画像。**不做的理由**：现行 D-Q47-5"商户永远看不到任何个人的资料"是隐私立场；
把答题记录变成画像并对外开放触及 APPI / GDPR 的目的限制与同意。**以后**：只做**本人主动分享**（§5-E 的公开认证页）；汇总统计照 Q9e 的最小分组。

### 6.7 更强的防作弊：设备指纹、地理位置、桌号

**不做的理由**：设备指纹与定位都是个人信息，隐私政策与商店审核（Q49）都要改；餐饮场景的"只在本店范围答题"可以用轮换码（Q22b 已有）达到同样的效果：
码在店里的屏幕上，不在店里拿不到。**以后**：出现有组织的刷量再议。

### 6.8 招聘：视频回答、企业端、人才标准树

录制回答过程的视频并保存、企业查看、协会与大厂发布人才树、对企业收费。**不做的理由**：（1）"平台不保存视频"是既定方向，录像要改它或依赖外部托管并涉及大量个人数据（人脸、声音）；
（2）企业端是第五个入口与新的商业模式；（3）"免面试"的法律责任（歧视、数据保留）需评估。**现在**：§5-E 的公开认证页。**以后**：先与一两家企业试"认证作为简历附件"。

### 6.9 AI 视频生成流水线

数字人、文生视频、课件转视频、错题解析微视频。**不在平台内做**：平台不存视频，生成的视频也要放到 YouTube 等处；成本与版权由内容方承担。
**可以做的**：`tools/quizbuks/` 下的脚本把 Quiz 的资料生成讲解稿（Claude）供商户去外部工具制作，不接入任何视频服务；以及商户后台"从资料生成讲解稿"的按钮（Q8 的作业类型再加一种）。
放在以后：等商户确有需求。

### 6.10 计价与资金：CPK、平台使用费、创作者质押 Kudos

按"有效认知"收费的 CPK、平台使用费（Q70 第 13 条"以后统一规划"）、任何用户为自己的视频出 Kudos（创作者成为发布者）。
**不做的理由**：平台使用费要一次规划（含 Q47c 的规则费、Q48 的分成）；创作者出资即普通人充值与付奖励，資金決済法的判断（01 §4.6）须先有结论。

### 6.11 "认知度提升比例"

没有对照组算不出来。以后若做，用同一发布的"看前自评 / 看后测验"或 A/B 两版发布。

### 6.12 规模与全球化的战略判断

对标"彭博终端式的高净值生态""Duolingo + LinkedIn + Google Ads"，只是叙事；不改变当前的计划顺序。

## 7. 客观评估（不讨好）

### 7.1 助手的夸张之处

- "毛利率趋近 100%""服务器成本趋近于零"：不保存视频省的是带宽与存储，审核、客服、风控、支付手续费、法务、运营商分成都在；Stripe 的手续费与转账成本已在 Q6 的账里。
- "万亿级""抖音不配""降维打击"：没有依据。对话第 8、21 项助手自己的客观回答更可信：**补充与微创新，不是全面颠覆；用户面比娱乐产品小，单位价值可以更高**。
- "CPK""认知型营销网络""注意力投资银行"：是叙事词，对外使用前由需求方判断是否与品牌调性相符。

### 7.2 规模

需要动脑的产品覆盖的人群小于不需要动脑的；场景驱动（等上菜、要资格、要优惠）而不是无缝填充。QuizBuks 的量级取决于商户数与场景数，不取决于日活。这与 Q48（运营商）、Q31（招商）的方向一致。

### 7.3 学分本位的边界

Kudos = 1 JPY、可提现，使它更像预付式价值而不是游戏积分；01 §4.6 已把資金決済法列为开发前的法务问题。"完播即得"（§5-B）、"创作者出资"（§6.10）、"消耗 Kudos 解锁"（§6.3）都会放大这个问题，每一项都先问法务。

### 7.4 防作弊

需求方的立场成立：有奖励就有刷量，是常态成本。现有手段（02 §9）加 §5-A、§5-G 的时间与频率检查足够应对脚本；有组织的多账号靠运营商审核与保留期（Q10b）兜底；再强的手段（§6.7）以隐私为代价，由需求方决定。

### 7.5 隐私

"对用户的了解远超抖音"在数据上成立（答题记录是结构化的），但它正因此更敏感。现行立场是商户只见汇总、本人可清空资料、账号可删除（Q71）；对外开放画像不在计划内（§6.6）。

### 7.6 对 YouTube 的依赖

广告与竞品推荐（Unlisted 与 `rel=0` 只能减轻）、自动播放限制、iOS 全屏、在中国大陆不可用（§5-F）；视频被删或设为不可嵌入时答题照旧（Q19）。多一个来源（Bilibili、Vimeo 已有）即可，不自建托管。

## 8. 对话中产出的文案与图示（原样保留，供 §5-H 选用）

以下是助手的草稿，未经需求方审定，不是对外的定稿。

### 8.1 主标语与一句话定位

- 主标语：**不卖无人问津的"假课程"，只交付确定落盘的"真认知"。**
- 一句话：QuizBuks 不是又一个让用户挂机敷衍的 e-learning 系统，而是基于"科技树 + 确定性凭证"的认知履约与业务检查网络——对商家，它是高价值产品的深度转化引擎；对企业内部，它是防作弊的 SOP 检查与合规履约中枢。

### 8.2 面向品牌商家

标题：告别无效曝光！让潜在客户"主动点亮"您的产品科技树

- 痛点：在传统平台投广告，大部分预算花在划过的 3 秒里；即使看了，也不懂产品好在哪。
- 从"强行打扰"到"主动解锁"：产品知识是科技树上的节点，用户为了点亮节点而自愿看懂您的核心优势。
- 只为有效认知付费：不按展示或误触收费，看懂视频、通过答题，预算才转化为认知。
- 告别老客户骚扰：点亮节点或完成购买后不再重复推送，而是解锁售后延伸与复购节点。

### 8.3 面向企业客户（B2B）

标题：从"假装看过"到"确定履约"——重构企业日常 SOP 培训与业务检查

- 痛点：传统 LMS 是挂机播放器：PDF 没人读、视频后台静音、检查抄答案；出事追责无据。
- 防作弊的确定性验证：短视频、随机抽题、时间窗口校验，确保真懂、真看、真执行。
- 岗位 SOP 科技树：开店流程、特种设备、数据合规，节点逐级解锁，权责清晰。
- 凭证与审计：每次通关都有数字签名的凭证与审计记录。
