## 1. 需求概要

双边平台：商家（赞助方）充值 buk → 编辑 Quiz 模版 → 创建"发布"（冻结某版本 + 地区、时间、奖励档位、预算） → 用户在手机端答题 →
按得分档位一次性发放 buk（商家钱包扣、用户钱包入，同一事务；不足则"待支付"） → 用户提现为外币 → 平台对账、向外部财务系统推送汇总凭证。

| 角色 | 入口 | 需求条目 |
|---|---|---|
| 用户（答题人） | 手机尺寸 App（≤ 430px，底部 5 个导航） | U-01 … U-74（34 条，P0 21 条） |
| 商家（赞助方） | Web 后台（中 / 英、深色模式，左侧 7 项导航） | M-01 … M-73（29 条，P0 15 条） |
| 平台管理员 | Web 后台（超级管理员 / 内容编辑 / 财务支持） | P-01 … P-09（9 条，P0 5 条） |
| 财务对接 | 平台设置与定时任务 | F-01 … F-09（9 条，P0 1 条） |

业务规则 14 条（需求 5.3）、实体 9 个（5.4）、非功能 6 条（6.1）、已确认决策 9 条（6.2）、会计分录 7 种（7.2）。

## 4. 需要在设计中解决的要点

### 4.1 钱包与并发

- **钱包即账本**：建议不建独立的余额表，而是用平台账本，科目"商家预收款""应付用户奖励"按维度（商家 / 用户）记账；余额 = 维度余额。
  这样需求第 7 节的会计分录与钱包是同一份数据，余额校验（F-06）自动成立。
- **热点**：一个热门发布在短时间内有大量提交，都扣同一个商家的钱包。每次结算取 `HoldLock.exclusive("wallet:<商家>")` 会串行化；
  需要估算峰值（问题 Q11）。若不够，可把"扣商家"改为按发布预留预算（发布时从钱包转入"发布预算"维度），结算只扣发布自己的预算维度，锁的粒度降到发布。
- **待支付**：余额不足的奖励不入账（需求 7.1），只记"待支付"记录；充值流程在同一事务中按提交顺序补发，直到余额不足为止。

### 4.2 模版版本与发布快照

时态实体的历史是"字段级的修改记录"，不是可发布的整体版本。需求要求"选择模版及版本""v1.0、v1.1"与"发布即冻结"，
所以设计为：模版（可变、时态）+ **模版版本**（每次"保存版本"生成一个只写一次的整体快照：题目、选项、资料、文件引用）+ 发布引用模版版本。
答题与结算只读快照。

### 4.3 与外部财务系统

需求第 7 节假设"平台只有明细，总账在外部"。jabiz 平台本身就有复式总账，建议：所有分录在平台账本中记；
F-01 – F-03 变成"按科目映射把一段期间的账本汇总导出 / 推送给外部会计系统"，对账（F-05）用平台导入。外部系统的选择见 Q13。

### 4.4 三个前端

| 前端 | 方案 A（推荐） | 方案 B |
|---|---|---|
| 用户 App | 应用前端 `quizbuks-web/app`（Radix，移动优先，需登录） | 同 A |
| 商家后台 | 应用前端 `quizbuks-web/sponsor`（Radix，7 项导航，面向付费客户的体验） | 平台通用后台 + 扩展页（按权限只显示商家菜单） |
| 平台管理员 | 平台通用后台 + 扩展页 | 同 A |

方案 B 少写代码，但商家看到的是"数据视图 / 流程目录"风格的通用后台，且受阶段 15 进度约束。方案 A 需要平台把认证与 API 客户端做成应用前端可复用的库（第 3 节末）。

### 4.5 反作弊与公平

- 题目的正确答案在提交前绝不下发；选项顺序可按会话打乱（需求未提，问题 Q8）。
- "一人一次"挡不住多账号刷奖：至少需要邮箱验证（G1）、提现前银行账户唯一性检查；更强的手段（设备指纹、手机号）需求未提。
- 时限以服务器时间为准，开始时间在开始流程中记录。

### 4.6 合规风险（需业务方确认，不是本分析能判断的）

- 用户可把 buk 提现为现金、商家预付资金由平台持有并转付给用户：在日本可能涉及资金決済法（资金移动业 / 前払式支払手段）与景品表示法；
  覆盖欧洲 / 中国 / 美国等地区时各自另有要求。**建议在开发 P0 闭环之前咨询法务。** 这可能改变充值、提现、余额有效期的设计。
- 个人信息：覆盖欧洲时适用 GDPR（删除权等）；平台目前不做个人信息的物理删除 / 匿名化（已设计未开放），可能需要另立平台需求。
- 税务：需求 7.6 已列为会计师确认，平台只保证明细可导出。

### 4.7 Stripe：充值与自动转账

- **充值**：商家在商家后台发起充值 → 应用创建 Stripe Checkout Session（日元）→ 商家在 Stripe 页面付款 → Stripe 发送
  `checkout.session.completed`（或 `payment_intent.succeeded`）到入站 Webhook（G9）→ 充值流程按事件去重、记账（借：应收通道款，贷：商家预收款）、
  按提交顺序补发待支付奖励。到账以 Webhook 为准，浏览器跳回只用于显示。
- **用户收款**：用户在 App 中开通 Stripe 收款账户（Stripe Connect 的 Express 账户，身份与银行信息由 Stripe 收集，平台不保存银行账号）。
  奖励累计达到门槛（平台设置）后，定时任务调用转账流程：先记账（借：应付用户奖励，贷：应付转账款），提交后经 Stripe 转账；
  Stripe 的结果通知（成功 / 失败）再记账（失败则冲回用户余额）。需求中的"提现审批"变为可选的大额人工审核。
- **需确认（Q18）**：Stripe Connect 的跨境转账只对设在美国、英国、欧洲经济区、加拿大、瑞士的平台开放；平台的 Stripe 账户设在哪个国家、
  用户分布在哪些国家，决定能否用 Connect 转账，还是要用 Stripe 的 Global Payouts（直接打到银行账户）。设计中把"转给用户"做成一个接口，两种都能接。
