# QuizBuks × Shopify：总体方案（2026-10-26 讨论结论，开发在 1.3 线）

本文是 Shopify 集成的**交接文档**：记录需求方与助手在 1.2 线收尾时讨论定下的结构、收费、顺序与未决问题。
开发在 `1.3/quizbuks`（应用）与 `1.3/platform`（平台）上进行；`1.2/quizbuks` 已冻结，只修 bug，继续测试与部署到真实环境。
每个阶段仍按根目录 `CLAUDE.md` §7 的方式交付：先出实施计划并等待需求方确认，再写代码；PR 由需求方合并。

## 1. 需求方的原始设想（摘要）

把"视频答题 + 领券 + 极速下单"做成 Shopify App，卖给全球的 D2C 独立站商户：

- 店面：Theme App Extension（Liquid + Web Component，不改商户主题），视频静音自动播放，点击进入答题。
- 奖励：答对即由后端经 Admin GraphQL 生成唯一折扣码（或直接作用于购物车），弹窗内选规格、带折扣码跳到 Shopify 原生结账。
- 商户后台：内嵌应用（App Bridge + Polaris）：AI 由视频自动出题、奖励规则（答对 N 题几折、限时有效）、看板（播放 → 完成 → 领券 → 订单 GMV）。
- 收费：Freemium + 阶梯月费（原设想 Free 50 次 / $29 500 次 / $99 3,000 次 / $299 + 1% GMV），经 Shopify Billing。
- 推广：应用商店 ASO、冷启动外联、CRO 机构分佣。
- 市场定位：与"选型 Quiz"（Octane AI 等，按答案匹配商品）不同，也与纯 Shoppable Video（Firework 等）不同；
  QuizBuks 是**看视频答题得奖励**的游戏化转化工具。经网上检索，应用商店里没有相同组合的应用，只有相邻的。

## 2. 定下的结构：两个商户系统，一个答题引擎

| | 普通商户（现有） | Shopify 商户（新） |
|---|---|---|
| 身份 | 邮箱注册、密码、二次验证 | **店铺**（shop 域名）即身份，店主经 Shopify OAuth / 会话令牌登录，无密码 |
| 钱 | Kudos 钱包充值、手续费 | **Shopify Billing 代收**订阅费，QuizBuks 不碰钱 |
| 奖励 | 现金、到店、数字奖品、商户发送 | 只有**折扣码** |
| 答题人 | QuizBuks 用户 | 店铺的顾客，匿名（访客键） |
| 入口 | 商户后台（`quizbuks-web/sponsor`） | Shopify Admin 内嵌页 |
| 生命周期 | 注册 → 审核 → 活跃 | 安装 → 试用 → 付费 → **卸载**（随时、无通知） |

分界线：

- **各自独有**：商户账户、登录、套餐与账单、后台界面、商户生命周期。
- **共用（答题引擎）**：发布（视频 + 题目）、AI 出题、答题会话、判分、"可领取凭证"抽象、看板统计。

实现上：Shopify 侧全部放在独立模块 **`backend/quizbuks-shopify/`**（自己的 `jabizApp`、登录入口、实体表 `qbs_*`、SPA `quizbuks-web/shopify`），
只调用引擎的流程，不碰钱包、不碰普通商户表；可以作为**独立的部署单元**运行，店面流量不影响普通商户后台。
**不要**在 `QbSponsor` 上加 `channel` 字段去兼容两边。路径须加入 `.jabiz-app-paths`。

引擎唯一要改的地方（S0）：发布从直接挂 `sponsorId` 改为挂"**发布方**"（编号 + 类型，`SPONSOR` / `SHOPIFY_SHOP`）。
这是不兼容改动，也是开 1.3 线的理由。S0 的验收：现有全部场景回放、集成测试、端到端原样通过，快照除字段改名外不变。

Shopify 侧**零可选项**：一种奖励（折扣码）、一种身份（访客）、一种收费（Billing 月套餐）、一种页面。功能请求先记清单，不进代码。

品牌：对外叫 "QuizBuks for Shopify"（待需求方最终确认）；有自己的落地页、隐私政策页与支持邮箱；
普通商户的商业网站（`quizbuks-web/site`）**不提 Shopify**。

## 3. 收费：照 Shopify 应用商店的通行做法

Shopify 强制应用费用经 Billing API 收取，QuizBuks 不接触卡号。

1. 免费试用 7 或 14 天，装上就能用完整功能。
2. 按月阶梯套餐，差别只在**每月完成答题次数上限**和一两个功能开关（数字待定，先以真实店铺试运行后再定；Free 带 "Powered by QuizBuks" 标）。
3. 超额：第一版只做"拦住 + 提示升级"，不做用量计费。
4. 年付打折以后再加。

计量只有一个数：**本结算周期内完成的答题次数**，周期由 Shopify 订阅周期给出。
普通商户的计量收费（原拟 Q35）与 Q33b（商户发送）**暂停**，不在这条线上。

## 4. 顺序（每步可单独上线、单独回滚）

| 步骤 | 线 | 内容 | 估计 |
|---|---|---|---|
| S0 | 1.3/quizbuks | 引擎"发布方"抽象 + 全部场景回放（计划 `S0-publisher.md`，2026-10-26 确认方案 B；已实现，分支 `1.3/quizbuks-S0-publisher`，迁移 V29，待评审） | 2–3 天 |
| 17a | 1.3/platform → 同步 PR | 入站 webhook 验签（已有 `/api/inbound/**`，补 Shopify 的 HMAC 形式与去重）、公开接口的限流 | 2 天 |
| S1 | 1.3/quizbuks | 安装 / OAuth、会话令牌登录入口、内嵌后台骨架、GDPR 三个 webhook、卸载 webhook（平台 17b 先行；实施说明 `S1-install.md`，已实现，待评审） | 3–4 天 |
| S2 | 1.3/quizbuks | 店面组件（Theme App Extension）：视频 + 答题 + 领折扣码（**预生成池**，Admin GraphQL `discountCode`，`usageLimit 1`、有效期）、刷码限制 | 3–4 天 |
| S3 | 1.3/quizbuks | Billing：试用、套餐、周期计数、超限拦截 | 2–3 天 |
| S4 | 1.3/quizbuks | 上架收尾：隐私政策页、性能预算、Polaris 风格、支持邮箱 | 2–3 天 |

合计约 15–20 个开发日；之后应用商店审核 1–3 周（期间可用自定义应用装到自己的店铺试运行）。
S0 期间不需要 Shopify 的任何东西；S1 开始前需求方须准备：Shopify Partner 账号、开发店铺、应用的 API 密钥、公网可达的测试地址；S2 需要有商品的测试店铺；S3 需要套餐名字与价格。

普通商户的生产环境继续跑 1.2，直到 S0 与 S1 做完并回归通过后再升到 1.3；升级只执行引擎的迁移，Shopify 模块的表是空表。

## 5. 已识别、尚未设计的问题（各阶段计划中必须逐条回答）

**Shopify 平台强制要求**
- GDPR webhook：`customers/data_request`、`customers/redact`、`shop/redact`，30 天内响应。
- 卸载 webhook：订阅终止、令牌作废；数据保留多久（拟 30 天供重装）、重装怎么接续。
- 内嵌页用 App Bridge 会话令牌，不用 Cookie；Polaris 风格减少审核阻力。
- 店面脚本有性能预算（Lighthouse），视频不能拖慢首屏。
- 审核需要测试店铺、隐私政策页、支持邮箱。

**业务**
- 刷码：按访客键、IP 的频率限制；每店每日最多发码的硬顶；AI 出题按套餐限次。
- 折扣码失效（商户删掉、过期）：第一版只在领取时查一次有效性。
- 多店：各店独立安装、独立套餐。
- 视频带宽与存储成本进定价模型。
- 退款由 Shopify 处理；给商户一个"本周期用量"页。
- 语言：店面按顾客、后台按店主，相互独立。
- 卸载后数据与法规保留期。

**安全**
- 店面组件是第一次大面积暴露的**匿名写接口**（开始答题、提交答案、领码）：限流、轻量防机器人（不先接验证码服务）。
- Shopify webhook 必须 HMAC 验签并去重（17a）。
- 答题人三层身份（访客 → 影子账号 → 完整 QuizBuks 用户）：S1–S3 只做访客；后两层推到有用户数据再说。

## 6. 不做

- 按需（领取时）生成折扣码——先只用预生成池；GMV 抽成；用量计费；A/B 测试；自定义 CSS；Storefront API 一键结账（先用 `/discount/{code}?redirect=/cart`）。
