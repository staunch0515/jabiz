# 性能摸底（F1c）

设计 Q1 的依据：FIN-NF-001 的量（每年 250 万总账行、3 年在线、600 个科目）下，FIN-NF-002 的目标能否达到，试算表是否需要期间余额快照。
这是摸底，不是 FIN-NF-002 的验收：验收是 F11 带 50 用户的压测。

## 1. 方法

- 生成器 `tools/finance/perf/`：`probe.sh` 经 API 建账（`FIN_SETUP`、财年、600 个科目），`generate.sql` 直接写库生成一年的过账：
  100 万笔平衡的交易（2 或 3 行，平均 2.5 行），共 250 万行，每笔带 `FinPosting`，记录时间为过账日（芝加哥零点）、主键按时间排序（同 UUIDv7）。
  直接写库绕过了 `LEDGER_POST`、审计与编号，只用于专门的库（名称须含 `perf`，脚本检查）。
- 计时：经 API（服务端时间加本机网络），每项预热 1 次后 20 次，取 p50 / p95；SQL 的分析用 `EXPLAIN ANALYZE`。
- 环境：容器内 4 vCPU、15 GB 内存；PostgreSQL 16.13 缺省配置（`shared_buffers` 128 MB、`work_mem` 4 MB），库 2.3 GB；应用为打包的 jar。
  正式环境的配置会更好，但下面的差距是数量级的，不是配置能弥补的。

数据：2025 年 2,500,000 行、1,000,000 笔交易（另有 0.2 万笔探测用的分录）。

## 2. 结果

| 项目（FIN-NF-002 目标） | 经 API | 说明 |
|---|---|---|
| 试算表，截至 2025-11-30（≤ 5 s） | 20 次全部超时（数据视图的查询时限 5 s，HTTP 500） | 同一 SQL 在库中 28 s |
| 账户查询，一个科目一个月（≤ 2 s） | 20 次全部超时（5 s） | 同一 SQL 的主要部分在库中 3.9 s |
| 提交并过账一笔 50 行的分录（≤ 1 s） | p50 2.6 s，p95 3.1 s，最大 4.0 s | 其中两次唯一性检查各约 1 s |

## 3. 原因

平台读时态实体的方式是"先取每个实例的当前版本，再过滤"：模板中的 `{{LedgerEntry}}` 展开为
`(SELECT DISTINCT ON (主键) * FROM 表 WHERE effect_start_time <= :asOf ORDER BY 主键, effect_start_time DESC, version_no DESC)`。
无论查询要多少行，都要先把整张表按主键排序去重：250 万行的分录表、100 万行的交易与过账表各一次。

| 实验（库内，同一数据） | 时间 |
|---|---|
| 试算表，平台的读法 | 28 s |
| 试算表，直接读版本表（过账后的行只有一个版本，结果相同） | 5.0 s |
| 账户查询，平台的读法 | 3,857 ms |
| 账户查询，直接读版本表（按科目索引） | 49 ms |
| 试算表，从按"科目 × 期间"预先汇总的余额读（7,200 行） | 3.7 ms |
| 唯一性检查（`gl_no`），平台的读法（`DISTINCT ON` 全表后比较） | 约 1,000 ms |
| 唯一性检查，经该列的索引找候选再确认其为当前版本 | 0.1 ms |

- **试算表**：即使去掉 `DISTINCT ON`，一年的量已在 5 s 的边上，3 年在线（750 万行）时约 15 s。逐行汇总无法达标，**需要期间余额**。
- **账户查询与唯一性检查**：慢在平台的读法，不在数据量：只要能按索引先缩小范围，就是毫秒级。
- 过账的其他部分（检查、取号、写入 50 行与审计）合计约 0.6 s，以后再细看。

## 4. 结论与建议

**设计 Q1 的结论：需要。** 试算表、资产负债表与利润表（FIN-RP-001…003）都从期间余额读，不逐行汇总。做法（在 F8 结账前的阶段设计，写入设计 §14 与 §7）：

1. 财务的期间余额 `FinPeriodBalance`（科目 × 期间 × 维度：借方、贷方发生额），与 `FinPosting` 在同一过账事务内追加：每次过账追加该笔对各科目的增量行，
   定期（结账时）合并为该期间的汇总行，报表读"汇总行 + 汇总后的增量"。只追加，可按 `knownAt` 重现。
2. 截至某日（期中）的试算表 = 之前各期的余额 + 本期截至该日的行（一个月约 21 万行，配合下面的平台改进可在秒级内）。

**平台的改进（需要新的平台阶段，建议 14i "时态数据的规模"）**：
1. 时态实体的唯一性检查改为"经唯一键的索引找候选，再确认其为当前版本"（0.1 ms 对 1 s）。不改变语义。
2. 只写一次的时态实体（每个实例只有一个版本：账本交易与分录、`FinPosting`）可以声明，模板读它们时不做 `DISTINCT ON`，直接读版本表加时间条件。
   结果与现在完全相同（只有一个版本），账户查询由 3.9 s 降到 50 ms。
3. 或者更一般地：对不可变字段的过滤可以放进 `DISTINCT ON` 子查询内部（不可变字段在各版本中相同，结果不变）。

在这些改进之前，F1 的模板在小数据量（样例公司、测试）下正确，大数据量下会触发查询时限（报错而不是给出错误结果）。

## 6. 平台 14i 之后（F1d，2026-10-01）

平台阶段 14i（决策 D29）：唯一性检查经索引找候选；不可变字段的条件下推到当前版本子查询；账本交易、分录与 `FinPosting` 只写一次，读取不做 `DISTINCT ON`。
同一库、同一数据（迁移 V26 与财务 V3 在 250 万行上共约 30 s），`ANALYZE` 后 `GENERATE=false` 重新计时：

| 项目（FIN-NF-002 目标） | F1c | 14i 之后 |
|---|---|---|
| 试算表，截至 2025-11-30（≤ 5 s） | 全部超时（5 s） | 仍全部超时（5 s） |
| 账户查询，一个科目一个月（≤ 2 s） | 全部超时（5 s） | p50 0.246 s，p95 0.261 s，最大 2.5 s |
| 提交并过账一笔 50 行的分录（≤ 1 s） | p50 2.6 s，p95 3.1 s | p50 0.417 s，p95 0.648 s，最大 3.0 s |

- 最大值是第一次运行（预热后连接与计划缓存仍在建立），不影响 p95。
- 账户查询与过账达到目标；试算表仍逐行汇总一年的行，如 §4 所述由期间余额解决（F8 之前设计），不再等平台。


## 7. 并发与崩溃（FIN-NF-003，F11b，2026-10-03）

验收：20 人同时过账与收款核销 30 分钟、期间两次杀掉服务，事后借贷相等、编号无缺、每笔已确认的过账恰好一次。

- 工具 `tools/finance/concurrency/run.sh`：10 人记日记账（保存并提交，一笔两行，在审批限额之下即过账），10 人各有自己的客户、开发票（一行、免税）并立即记收款全额核销；
  每个请求带新的幂等键，没有得到回答（服务不在、409、5xx）时以同一个键重发，得到 200 即为"已确认"。在第 10、20 分钟 `kill -9` 并重启。
- 检查：经接口的试算表借贷相等；库中（`invariants.sql`）每笔已确认的单据恰好有一笔过账、本次运行没有已确认之外的单据（重发没有造出第二张）、
  所有编号序列无缺号无重复、每笔账本交易借贷平衡、本次运行在应收控制科目上相抵。检查本身以构造的反例验证过。
- 环境：容器内 4 vCPU，PostgreSQL 16 缺省配置，打包的 jar，工具与服务在同一台机器上。

| 项目 | 结果 |
|---|---|
| 两次 `kill -9` 后恢复（到健康检查通过） | 16.8 s、18.5 s |
| 已确认：日记账 / 发票 / 收款 | 16,836 / 11,509 / 11,509（账本交易 39,854 笔、分录 79,708 行，约 22 笔/秒） |
| 编号（JE、GJ-MAN、INV、RCPT、GJ-AR） | 各与已确认的数相等，无缺号、无重复 |
| 已确认的过账在账中的次数 | 全部恰好一次；本次运行没有多出的单据 |
| 试算表借贷、每笔交易、应收控制科目 | 相等、平衡、相抵 |
| 服务端 409 / 5xx | 0 / 0（杀掉期间的请求在客户端连接失败后重发） |

- 第一次 30 分钟的运行（同一工具的早先版本）在最后调用子账调节模板时超过 5 秒的查询时限（约 2.3 万张应收单据），平台报为 500；
  子账与账龄在大数据量下的性能随 F11c，NF-003 的应收检查改为直接在库中核对本次运行的单据。
- 正式环境（硬件、库的配置）由使用方用同一工具复跑：`NF003_START` 为重启服务的命令，`PG*` 指向应用的库。

## 8. 50 用户压测（FIN-NF-001、NF-002，F11c，2026-10-04）

工具（都对运行中的应用，经接口；见各脚本头部）：
- 数据 `tools/finance/perf/build.sh`：主数据经接口建（600 个科目、5,000 个客户、2,000 个供应商、500 项资产）；每月经接口做四组真实单据
  （发票并收款核销、未收的发票、账单并经付款批付清、未付的账单），`clone.sql` 把每组流程写下的行按份数复制到当月（新标识、编号、日期，客户与供应商轮换），
  每月复制后 `ANALYZE`；然后逐月折旧并关账 1–11 月。`PERF_SCALE` 按比例缩小。
- 压测 `tools/finance/load/run.sh`：50 人按角色操作（会计记 50 行日记账并跑报表，应收员开 50 行发票、打开发票、看应收账龄，财务主管打开发票并跑报表），
  每人两次操作之间停 `LOAD_THINK_MIN_MS`–`LOAD_THINK_MAX_MS`（缺省 5–15 秒，人的节奏；过账仍为 NF-001 年平均速率的许多倍）；按客户端计时（与服务同机）。
- 批处理 `tools/finance/load/run.sh batch`：12 月 500 项资产折旧、一个新银行账户 5,000 笔存入的对账单导入与匹配（建议并接受）、12 月关账与年结。它关掉年度，最后运行。
- 环境：容器内 4 vCPU、15 GB，PostgreSQL 16 缺省配置（只开 `pg_stat_statements`），应用与数据库、压测工具在同一台机器上。

**结果（1/10 数据量：30,000 张发票、20,004 张账单、21.5 万行总账，库 0.9 GB；50 人、人的节奏、10 分钟）** — 全部达标、无失败：

| 项目（p95 目标） | 次数 | p50 | p95 |
|---|---:|---:|---:|
| 过账 50 行的发票（1 s） | 506 | 0.31 s | 0.60 s |
| 过账 50 行的日记账（1 s） | 474 | 0.32 s | 0.80 s |
| 打开单据（1 s） | 606 | 0.03 s | 0.07 s |
| 一个科目一个月的查询（2 s） | 343 | 0.47 s | 0.76 s |
| 月试算表（5 s） | 145 | 0.13 s | 0.33 s |
| 资产负债表（5 s） | 142 | 0.14 s | 0.29 s |
| 利润表（5 s） | 167 | 0.67 s | 1.70 s |
| 账龄（10 s） | 469 | 0.12 s | 0.27 s |

1/1000 数据量的批处理（只是工具的验证，不是 NF-002 的验收）：500 项资产折旧 3.4 s（目标 1 分钟）；200 行对账单导入 0.9 s、建议并接受 2.5 s
（目标是 5,000 行，没有测量；`BankMatchIT` 覆盖 150 行一次导入与接受）；12 月关账 1.3 s、年结 0.5 s（1/1000 数据量）。
计时说明：报表取第一页（500 行；600 个科目的试算表不止一页）；"账龄"一行混合应收与应付；"过账日记账"计 `FIN_JOURNAL_SUBMIT`，50 行的分录在审批限额之下直接过账。

**全量（NF-001：30 万张发票、20 万张账单、约 215 万行总账，库 7.7 GB）**：数据造成（12 个月的复制共 31 分钟），资产与 1 月折旧完成；
按用户要求在全量上的压测与批处理计时没有做完，1–11 月关账没有完成（见下方第 3 条的修正之后未再运行）。单项测量：
1 月 31 日的应收账龄 1.3 s；关账检查的例外查询 3.0 s（关闭 JIT 后，之前 8 s）。

**压测中发现并已改正**
1. 平台 14p：流程中的模板与实体查询被浏览分页截断（600 个科目的试算表只读到 500 行，关账检查对不上）。
2. 平台 14q：查询超时只在应用一侧生效，超时的查询在数据库中继续运行并占着连接，过载时雪崩（3,363 次 `request queue limit is exceeded`）；
   超时返回 500；每页都另跑一遍计数。改后：数据库在时限中止、503 `QUERY_TIMEOUT`、页未满不计数——同样的压力下吞吐约为原来的 4 倍、不再有 500。
3. 账龄、子账调节、外币重估项目、坏账建议逐张单据求已核销额（随单据数平方增长，1/10 数据量时关账超时）：改为汇总一次再关联；
   账龄只读那天可能未结的单据（现在未结、之后作废、或有之后日期的核销），按单据以索引判断。1/10 数据量下 50 人时账龄 p95 3.8 s → 0.27 s。
4. 对账单超过 100 行导入不了、一次接受超过 100 条匹配建议失败（数据视图的写入批量）：改为一次写入（`BankMatchIT`）。
5. 每个审批事件都送到所有审批订阅者，发票的订阅者对不是发票的审批返回空输出而无限重试（`PayablesMasterIT`）。
6. 造数中批量复制后统计信息过时，计划器按小表选计划：每月复制后 `ANALYZE`。

**部署建议**
- 关闭 JIT（`jit = off`）：报表与关账模板大，JIT 每次重新编译，例外查询 8 s → 3 s。`deploy/finance/docker-compose.yml` 的数据库已如此配置；
  内存等其他参数按主机设定，本次没有测量其影响（所有结果都在缺省配置下）。
- 4 vCPU 上压力节奏（每人 1–3 秒一次操作，约 10 次/秒）时 CPU 饱和：报表与过账 p95 都超过目标，过账在无缺号的编号计数器上排队（每笔过账取单据号与总账号，锁到提交）。

**未完成与已知限制**
- 全量下的 50 人压测、批处理计时（折旧、5,000 行匹配、年结）与 1–11 月关账没有完成；正式环境由使用方以同一工具复跑（`PERF_SCALE=1`）。
- 流程事务中的读取在数据库中没有时限（平台 14q 的已知限制）：关账中的慢查询会在客户端超时后继续运行到结束。
- 关账检查与年结读取全年数据，全量下单个查询接近平台 5 秒的视图时限（账本的数据视图属于平台，不能单独放宽）；需要时由平台为流程中的读取另设时限。
- 一次接受 500 条建议、每条又有很多账面项时，匹配项可能超过一次写入 10,000 行而在提交时失败（不是明确的 422）。
- 总账行约 215 万（目标 250 万，未另补）；利润表在 1/10 数据量下 p95 1.7 s，按数据量推算全量下可能接近 5 s。
