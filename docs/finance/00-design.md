# finance 设计（F0，待确认）

应用 finance 的设计：一个美国单一公司的基础财务系统（US GAAP），建在 jabiz 平台上。
需求是 `docs/finance-requirements/`（fin-req-v1.0，冻结，**只读**）；需求编号 `FIN-*`、场景编号 `FIN-SCN-*`、期望结果编号 `FIN-EXP-*` 都出自那里。
阶段计划见 `ROADMAP.md`，总体计划与已确认的决定见 `docs/finance-work/00-development-plan.md`。

本文件是**约定**：实现与本文件冲突时，先改本文件再改代码（与平台的 `docs/design/` 相同）。每个财务阶段的实施计划会细化相应章节。

## 4. 通用约定

### 4.1 金额与舍入

- 金额 `BigDecimal`；USD 2 位小数；币种的小数位来自币种表（FIN-FX-001）。汇率 `numeric(19,10)`，至少 6 位有效小数。
- 舍入**远离零**到币种最小单位：`RoundingMode.HALF_UP`（Java 的 HALF_UP 对负数同样远离零）。只在需求规定的层级舍入：
  税按"单据 × 辖区"（FIN-TX-003）；折旧按"资产 × 月"（FIN-FA-004）；外币换算按行；分摊按最大余数法，尾差放最后一行。
- 所有舍入经一个工具类 `calc.Money`（单元测试 + 属性测试），别处不直接调用 `setScale`。

### 4.2 日期与时间

- 过账日期（posting date）、单据日期（document date）是无时区的 `LocalDate`，实体字段用平台的日期类型 `f.asDate()`（14h，列 `date`）。
- 账本的 `bookingTime` = 过账日期在公司时区（`America/Chicago`，配置 `finance.company.zone`）的 00:00 对应的时刻；按日期查余额时用"次日 00:00 之前"。
- 记录时间（recorded-on）= 平台的操作时间 `op_time` / `created_time`，来自注入的 `Clock`。场景中"2026-02-20 录入"用模拟时钟（`advanceClock`）。
- 审计时间戳 UTC 毫秒，界面按公司时区显示（FIN 00 §4.3）。

### 4.3 两个时间轴与报表

- "as of" = 过账日期；"as known on" = 记录时间。每个报表与查询都带 `asOf`（或区间）与 `knownAt`（缺省为现在）两个参数（FIN-RP-020）。
- 实现：账本余额与明细模板按 `booking_time` 与 `created_time` 过滤（14c）；主数据、单据等时态实体经 14d 按 `knownAt` 渲染。
- 已发出的报表、结账产物、银行调节表都存档（14d 的报表运行存档：参数、定义版本、内容哈希），"重现"= 用存档的参数（含 `knownAt`）重跑并比对哈希。

### 4.4 实体的时态选择

- **时态**（只追加，保留历史、支持 `knownAt`）：全部主数据（科目、客户、供应商、银行账户、税码与税率、资产类别与资产、币种、汇率、付款条件、报表格式、结账清单模板）、全部单据头与行、期间、核销、匹配。
- **普通表**：只有明确可删除的工作数据（例如尚未提交的导入暂存），并在设计中逐一说明。
- 单据过账后不可改：状态字段 `processOnly`，过账后的数据视图范围只读；更正只能是贷项通知单、作废（冲正）或调整分录（FIN-GL-012、AR-004）。
- 删除草稿 = 墓碑版本（草稿不消耗编号，FIN-GL-013）。

### 4.5 编号（14b）

| 序列 | 范围 | 样式 | 需求 |
|---|---|---|---|
| 总账分录号 | 财年 × 来源（MAN、AR、AP、BK、FA、FX、IMP、CLS） | `GJ-<来源>-<年>-<6 位>` | FIN-GL-013 |
| 日记账单据号 | 财年 | `JE-<4 位>` | GL-010 |
| 发票 / 贷项通知单 | 全局（起始值可配置，样例 1004 / 2001） | `INV-<n>`、`CM-<n>` | AR-004 |
| 收款、付款批、账单内部号等 | 财年 | `RCPT-<4 位>`、`PAY-RUN-<2 位>`、`BILL-<n>` | — |

号码只在过账（或提交，视单据）事务内分配，回滚不消耗号（14b 保证）。样例公司的单据号（如 `BILL-V300-2601`、`DEP-2601`）在验收测试中作为**外部引用**录入，不强加给编号规则。

### 4.6 权限与角色

权限码 `fin.<模块>.<动作>`（例如 `fin.journal.prepare`、`fin.journal.approve`、`fin.period.close`、`fin.vendor.bank.maintain`、`fin.payment.release`、`fin.tax.data.read`）。
角色（FIN-DOC-01 §2）由初始化流程 `FIN_SETUP` 创建：

| 角色 | 主要权限 |
|---|---|
| Controller | 科目表、期间与结账、审批（无上限）、报表、审批规则、重开批准 |
| Accountant | 日记账准备、对账、计提、折旧与重估运行、结账任务 |
| ReceivablesClerk | 客户、发票、贷项通知单、收款与核销 |
| PayablesClerk | 供应商（不含银行信息批准）、账单、付款建议、1099 数据 |
| Approver | 限额内的账单、付款、分录审批 |
| Treasurer | 付款释放、银行账户、正向支付文件、银行账号明文 |
| Executive | 报表与仪表盘只读 |
| ExternalAuditor | 只读（账簿、审计记录、证据），数据期限为审计期（14g） |
| SystemAdministrator | 用户、角色、配置、集成；**无任何过账权限** |

- 平台账本的 `ledger.post` / `ledger.reverse` 不授予任何角色：总账只经财务流程以子流程写入（平台 D11：子流程不再检查权限）。因此**控制科目只能由子账过账**（FIN-GL-005），手工日记账对控制科目的检查在日记账流程中（例外须 Controller 逐笔授权并记录）。
- `FIN_SETUP`（`fin.setup`，平台管理级二次验证）幂等：建立缺少的角色与权限、本位币 USD；不删除管理员另外授予的权限。
  各阶段把自己的权限加入 `setup.FinanceRoles`，再运行一次即可。角色也不授予 `ledger.account.write`（科目只经财务流程维护）；
  读取账本余额与模板需要平台的 `ledger.read`、`ledger.account.read`，授予需要看账的角色。
- 职责分离（14b）的财务规则（FIN-CT-001）：准备人 ≠ 审批人（分录、账单、付款批、核销、重开）；维护供应商银行信息 × 释放付款；维护用户角色 × 过账。

## 5. 过账模式

每个会影响总账的单据都有一个过账流程，结构相同：

1. `LoadEntity` / `QueryEntities` 读取单据、主数据、期间；`LoadParams` 按业务日期读取参数（审批阈值等）。
2. 计算步骤（纯函数）：校验（全部违规累积）、计算（税、换算、折旧、损益）、生成总账行。
3. **期间检查**（§7.2）：过账日期所在期间对该子账与总账都允许过账，且操作人有相应权限。
4. **审批检查**（14b）：按当前生效的规则版本判定；需要审批而未批准 → 单据停在"待批准"，不过账。
5. 分配单据号与总账分录号（14b）。
6. `CallProcess.of("LEDGER_POST", …)`：同一事务写入账本，行上带来源引用（单据实体类型 + 主键 + 行号，14c）→ 钻取（FIN-RP-006、GL-021）。
7. 更新子账（状态、未结金额、核销、资产、匹配候选）并登记事件（`PublishEvent`，FIN-DI-007）。

作废 / 冲回：流程调用 `LEDGER_REVERSE`（过账日期为作废日期，落在开放期间），子账同时恢复（FIN-AP-014、AR-004）。

**不变量**（属性测试与集成测试）：每笔借贷相等（本位币；外币分录另按交易币种）；任意时点控制科目余额 = 子账合计（FIN-GL-005、RP-007）；已过账的行从不改变。

## 6. 总账（F1）

### 6.1 科目

| 实体 | 要点 |
|---|---|
| 平台 `LedgerAccount`（14c 扩展：上级科目、汇总科目不可过账、启用） | 代码唯一不可变；名称可改（历史） |
| `FinAccount`（时态，按科目代码一对一） | 财务类型（asset、liability、equity、revenue、expense、other income/expense、income tax）、正常余额方向、报表行（资产负债表/利润表格式行，§14.3）、现金流分类、控制科目类别（AR、AP、FA_COST、FA_ACCUM、BANK）、清算/可疑标记、是否需要维度 |

- 财务类型映射到账本的五类（other income/expense、income tax → REVENUE/EXPENSE），报表按 `FinAccount` 的类型与报表行分类。
- 有发生额的科目不能删除，只能停用；停用后拒绝过账但仍出现在报表（FIN-GL-004）。
- 标准科目模板（GL-002）：资源文件 `finance/coa/us-small-business.csv`（美国小型商业公司，含汇总科目、控制与清算标记）；
  `FIN_COA_TEMPLATE_PREVIEW` 只显示，`FIN_COA_TEMPLATE_APPLY` 在尚无科目的账簿中复制（可排除某些代码及其下级），之后逐个调整。
- 流程（F1a）：`FIN_ACCOUNT_CREATE` / `_UPDATE` / `_DEACTIVATE` / `_REACTIVATE` / `_DELETE`，同时写两个实体（`fin.account.maintain`）；
  `FinAccount` 的数据视图只经流程写入。财务类型不可改；其他收支的正常余额方向决定账本类型，因此也不可改（改则另开科目）。
  删除前先查发生额给出明确的原因；即使操作人受数据期限限制看不到发生额，平台删除时的引用检查（不受范围限制）仍会拒绝（`STILL_REFERENCED`）。
  已知限制：删除科目与同时对该科目过账之间没有互斥锁（平台的引用检查是通用的"先查后写"）；删除只用于尚未使用的科目，影响有限，记入平台待改进项。

### 6.2 维度（FIN-GL-006）

两个分析维度：`department`、`location`，值分别来自 `FinDepartment`、`FinLocation`（时态，代码、名称、启用；平台 `LedgerDimension` 以实体为值来源）。
科目可声明必填维度（`FinAccount.requiredDimension`，由日记账校验，F1b）。
平台以实体为维度值来源时接受当前所有值，不看 `active`；停用的值由日记账等单据的校验拒绝（F1b 起），账本本身仍接受（例如冲回旧分录）。维度在账本行上（14c），日记账、发票、账单行可填；报表可按维度列示。CR-C 只需加维度值与报表列，不改代码。

### 6.3 日记账

| 实体 | 要点 |
|---|---|
| `FinJournal` | 单据号、过账日期、单据日期、描述、来源（manual、import、recurring、reversing 等）、状态（draft → submitted → approved → posted；rejected）、准备人、自动冲回日期、控制科目例外授权、附件（文件字段，过账后不可变，显示内容哈希） |
| `FinJournalLine` | 行号、科目、借/贷金额、备注、维度、（外币）币种与汇率 |

| `FinJournalAttachment` | 文件（`fin.journal.support`：PDF、图片）或表格（`fin.journal.sheets`：CSV、XLSX）二者之一、内容哈希、说明；两个策略是因为导入类型不能与其他类型同属一个策略（14e） |
| `FinPosting` | 每笔总账交易一行：过账日（`date`）、财年、期间号与期间键、来源（MAN/AR/AP/BK/FA/FX/IMP/CLS）、总账号、来源单据号与实体；报表按它的过账日取数 |

- 草稿由准备人编辑或删除；提交后锁定；任何修改退回草稿并使审批与控制科目例外失效（14b 的内容哈希，FIN-GL-014、CT-003）。
  取得单据号后的草稿不能删除（否则缺号，FIN-GL-013），只能修改后再提交。
- 编号：单据号 `JE-nnnn` 按财年连续（序列 `fin.journal`，范围为财年；唯一键（财年，单据号）），提交通过检查时取得；总账号 `GJ-<来源>-<财年>-nnnnnn`（序列 `fin.gl`）过账时取得。
- 审批的业务时间是提交时刻（规则按此时生效的版本评估）；批准经事件 `jabiz.approval.approved` 回到 `FIN_JOURNAL_APPROVAL_RESULT`，内容哈希与状态都相符才过账（Q3）。
- 控制科目例外（Q1）：Controller（不是准备人）在提交前以 `FIN_JOURNAL_GRANT_CONTROL_EXCEPTION` 对当前内容授权，记下内容哈希；内容变了即失效。
- 批准事件只对当前的审批请求生效（比较请求号与内容哈希）；迟到的旧请求的决定被忽略。过账时再查一次科目与维度：提交后被停用的科目不过账，
  分录停在已批准状态并说明原因，由准备人修改后重新提交（不让事件反复失败）。
- 附件只由准备人在草稿或被驳回时增删，且只能附自己上传的文件：审批人看到的就是过账时的附件。
- 冲回分录的行固定为原分录的相反方向（日期、描述可改）；原分录记下 `reversedById`，自动冲回只看尚未冲回的分录，且不提前于冲回日（`FIN_AUTO_REVERSE_FUTURE_DATE`）。
- 周期分录：不能过账的模板（科目、维度、借贷）跳过并在输出中说明，其余照常生成。周期模板由会计维护，Controller 不持有 `fin.recurring.maintain`：
  模板生成的分录准备人是运行者（定时任务为 system），若审批人能维护模板就能批准自己写的分录（职责分离）。
- 提交：试算平衡（差额显示，FIN-GL-011）、科目可过账、控制科目检查、期间检查；按规则判定审批（阈值 10,000.00，参数带生效日；CR-A 的第二审批人 = 规则数据）。不需审批时直接过账，并记录"已评估的规则版本、无规则要求审批"（FIN-GL-015 第 2 条）。
- 周期分录（GL-017）：模板（时态）+ 计划；定时任务调用生成流程，幂等键 = 模板 × 期间（第二次运行不生成）；生成的分录照常审批。
- 自动冲回（GL-018）：标记冲回日期（缺省下期首日）；定时任务在该日生成冲回分录（`<原号>-R`，引用原分录），幂等。
- 录入网格（GL-020、UI-002/003）：`finance-web` 页面，保存草稿走同一流程与校验。

### 6.4 查询

都按 `FinPosting` 的过账日取数，`knownAt` 重现当时记录的账（报表头 `timeSlice`）：

- 试算表 `finance.gl.trial_balance`（参数 `through`、`adjustments`）：每个科目的借或贷余额、财务类型、正常余额、报表行；汇总科目为下级合计（GL-003）。
- 账户查询 `finance.gl.account_inquiry`（GL-022，参数 `account`、`from`、`to`）：期初余额、区间内每行（总账号、来源单据与实体、备注、维度）与滚动余额、期末余额。
- 日记账登记簿 `finance.gl.journal_register`（参数 `from`、`to`、`status`）。

## 7. 期间与结账（F1 期间部分、F8）

### 7.1 日历

`FinFiscalYear`（年份、起止日、是否启用第 13 期）与 `FinPeriod`（年、期号 1–12/13、键 `2026-01`、起止日期、状态、各子账状态）。
财年以结束所在的日历年命名（7 月起的财年 FY2027 = 2026-07-01 至 2027-06-30），第 1 期是财年的第一个月；财年不重叠。
`FIN_FISCAL_YEAR_CREATE`（`fin.period.maintain`）一次建立财年与全部期间，初始都为开放。
过账日期决定期间；第 13 期与 12 月同日期范围，只能由显式选择"调整期"的分录进入，出现在年度报表、不出现在 12 月月报（FIN-PC-001）。
首年另有期初期间 0（`2026-00`，首年第一天的前一天），只容纳期初分录（§13.1）。

### 7.2 状态与检查

- 状态：`OPEN`、`SOFT_CLOSED`（只有 `fin.period.close` 且只允许调整分录）、`CLOSED`（拒绝，原因"period closed"）；子账（AR、AP、BANK、FA）可先于总账关闭（FIN-PC-003）。
- 状态只经流程改变（`processOnly`）：`FIN_PERIOD_SET_STATE`（总账：三种状态）、`FIN_PERIOD_SET_SUBLEDGER_STATE`（子账：开放、关闭），都需要 `fin.period.close`；
  F8 之前在各状态间自由切换，每次改变都在期间的历史中。总账关闭时子账自动视为关闭（`PeriodPolicy` 先看总账）。
- 每个过账流程的期间检查是同一个纯函数 `PeriodPolicy.check(期间, 来源, 是否调整分录, 是否持有 fin.period.close)`。
- 以前期间项目（PC-007）：单据日期在已结期间、过账日期在开放期间；保留两个日期；报表 `finance.gl.prior_period_items`。

### 7.3 结账（F8）

- 清单模板（时态）+ 每期清单：任务、负责人、到期日、状态、证据文件；自动检查（未过账/未批准、银行已调节、子账 = 控制科目、周期/折旧/重估已运行、清算科目为零）各记录结果、时间、证据链接（FIN-PC-004、CT-005）。
- 关账 `FIN_PERIOD_CLOSE`：全部必需项通过 → 写结账产物 `FinCloseArtifact`（只追加：期间、试算表、子账合计、清单结果、操作人、时间、`knownAt` = 关账时刻、内容哈希）。之后按"as known on 关账时刻"重跑试算表必须与产物一致（PC-005）。
- 重开 `FIN_PERIOD_REOPEN_REQUEST` / `…_APPROVE` / `…_REJECT`：他人批准；再次关账生成新产物并引用旧产物，旧产物标记被取代（PC-006）。
- 年结（PC-008）：结账分录把当年损益类科目结转到留存收益（来源 CLS，过账到 12 月或第 13 期末），新年度从余额结转开始；调整后重新年结则冲回旧结账分录再生成新的，旧产物被取代。

- 报表（FX-007）：账龄与未结项同时显示交易币种与本位币；按单据的已实现 / 未实现损益报告。
- 外币银行账户（FX-006，Should）。

## 13. 导入与迁移（F2）

基于平台 14e。每种导入是一个导入定义（`com.jabiz.finance.io.FinanceImports`）：每行或每组交给手工录入用的同一个流程；整个文件先全部校验，
任何行有错即整体拒收、逐行报告原因、不写入任何数据（只留被拒的导入记录）；预览是试运行；同一文件、同一外部引用只导入一次；
导入报告即平台的导入记录（FIN-DI-001）。文件策略 `fin.import`（CSV，权限 `fin.import`；需要表格文件的导入另给 XLSX 版式的定义）；每种导入另需自己的权限。

| 导入 | 交给的流程 | 权限 | 需求 | 阶段 |
|---|---|---|---|---|
| `finance.chart` 科目表（样例公司的列或科目模板的列，父科目在前） | `FIN_ACCOUNT_CREATE` | `fin.account.maintain` | DI-001 | F2a |
| `finance.fx_rates` 汇率（长表；每对货币一列的宽表经映射给出列与币种常量） | `FIN_EXCHANGE_RATE_SET` | `fin.fx.maintain` | DI-001、FX-002 | F2a |
| `finance.opening_balances` 期初试算表（整文件一笔） | `FIN_OPENING_POST` | `fin.migration` | PC-002、DI-002 | F2a |
| `finance.journals` 日记账（按单据号分组，导入后照常提交与审批） | `FIN_JOURNAL_SAVE` / 提交 | `fin.journal.prepare` | GL-019 | F2b |
| `finance.payroll` 工资汇总（提供商代码经映射 → 科目、借贷、部门） | `FIN_PAYROLL_IMPORT` | `fin.payroll.import` | DI-004 | F2b |

### 13.1 期初（F2a）

- **期初期间**：财年的期间 0（键 `2026-00`，日期为首年第一天的前一天，`opening = true`），由 `FIN_OPENING_POST` 建立，只容纳期初分录：
  其他分录按日期查期间时不会找到它（同一天也不会）；`FIN_PERIOD_SET_STATE` 不能改变它；期初完成后 `FIN_OPENING_CLOSE` 关闭，以后不再打开。
  期初之后不能再建更早的财年（它会含有期初分录已经汇总的期间）。
- **期初分录**：一笔平衡的日记账（来源 `OPENING`，单据号 `OPENING-2026`，总账号 `GJ-OPN-2026-000001`，过账来源 `OPN`），由 `FIN_OPENING_POST`
  直接以已批准状态写入并经 `FIN_JOURNAL_POST` 过账（过账失败则整笔拒收，不留下期初期间）；不平则拒收并给出差额（PC-002 验收 2）。
  每套账一次；账套已有更早的财年时拒绝；**账套已在使用**（已有任何过账，或有期间不再开放）时拒绝——期初只属于迁移，不能在之后改动已报告的余额。
  期初分录不能冲回：期初的错误以首年中的调整分录更正。
  期初分录不受审批规则约束：它是迁移自己的记录，由迁移对账报告与来源核对；权限 `fin.migration` 只给 Controller。
- **控制科目**：期初分录是所有科目期初余额的唯一来源，控制科目（1200、2000、1500、1510、1590 等）也由它记入。各子账在自己的阶段导入期初未结项目时
  **不再过账**，只登记为"期初迁移、总账已由期初分录记入"，导入时校验其合计等于对应控制科目在期初分录中的余额；"子账 = 控制科目"随 F3（应收）、
  F4（应付）、F5（银行）、F6（资产）逐项验收，FIN-SCN-01 在 F6 完整通过。

### 13.2 迁移的决定与对账（F2a）

- `FinMigrationDecision`（时态）：种类、旧值、决定的值、理由、决定人、决定时间；每种类、每个旧值一条，只经 `FIN_MIGRATION_DECIDE`（`fin.migration`）记录与更改，
  旧的决定留在历史中（FIN-DI-003）。F2 的种类为 `ACCOUNT`：期初（以及以后的日记账）导入中的旧科目代码按决定读作科目表中的科目；
  科目表中已有的代码不能再映射；决定之后才建立的同名科目优先（读作其自身）。重复客户合并（`CUSTOMER`）随 F3。不平的批次没有"强制接受"的决定：只能改文件后重新导入，被拒的导入本身留有记录。
- 迁移对账报告 `finance.migration.reconciliation`（报表，可 `REPORT_ISSUE` 签发）：每个科目的期初分录（来源）与总账在期初日的余额及差额、借方与贷方合计、
  全部决定及决定人与时间（FIN-DI-002：每个控制总数差额为 0.00）。子账的期初项目对账随各阶段加入。

### 13.3 日记账与工资导入（F2b）

- `FIN_JOURNAL_IMPORT`：一张导入的分录存为草稿（来源 `IMPORT`，来源单据号记入 `externalRef`，唯一），缺省随即以 `FIN_JOURNAL_SUBMIT` 提交，
  检查、编号、审批与控制科目规则与手工录入完全相同（GL-019）。
- `FinPayrollMapping` 与 `FIN_PAYROLL_IMPORT`：提供商文件 `code,department,amount` 按映射合并为摘要分录（单据号即发放号，来源 `PAYROLL`），照常提交与审批（DI-004）。
  映射只由 Controller 维护；映射到银行科目即 Controller 对工资分录付款科目的长期例外（GL-005），记在每张工资分录上，其他控制科目一律拒收。
  例外只覆盖按映射方向付款：映射到银行科目的代码金额为负即拒收。发放号必须以 `PAYROLL-` 开头，不会占用日记账编号序列给出的号码（`JE-…`）；
  保存为草稿（不提交）的工资分录也必须平衡、至少两行（有编号的草稿不能删除）。
- `externalRef` 存为"来源:单据号"（`IMPORT:LEG-1`、`PAYROLL:PAYROLL-2601`），各来源各自唯一，互不占用。
- 已知限制：工资映射的修改由一位 Controller 完成（不经四眼控制变更），低于审批额度的工资分录不逐张审核即过账到银行科目；如需更严，可在审批规则中对来源 `PAYROLL` 另设条件（经 `CONTROL_CHANGE_PROPOSE` / `PUBLISH`）。

外部引用与幂等键：每个导入行与 API 请求都可带外部引用，重复不会产生第二张单据（DI-006，平台幂等键 + 外部引用唯一约束）。

## 14. 报表（F9）

### 14.1 口径

全部报表是 SQL 模板（`queries/finance/report/*.sql`）+ 财务后台页面；参数至少有 `asOf`（或期间 / 区间）与 `knownAt`；可导出 PDF / XLSX / CSV（14d，FIN-RP-010）；发出时存档（14d，RP-009）。

### 14.2 显示（FIN-UI-005）

金额右对齐、千分位、固定小数；报表中负数用括号 `(2,000.00)`；有多种币种时显示币种代码；显示的合计 = 显示行之和 = 存储合计（报表先按存储精度汇总，不对已舍入的值再汇总）。

### 14.3 报表格式（RP-002 第 2 条、RP-011）

`FinStatementLayout`（时态、版本化）：行（标题、科目或科目范围、小计、符号）、列（期间、比较、差异）。发出报表前校验：每个有余额的科目都映射到某行，否则报告"未映射"并拒绝发出。报表存档记录使用的格式版本，用旧版本发出的报表按旧版本重现。
